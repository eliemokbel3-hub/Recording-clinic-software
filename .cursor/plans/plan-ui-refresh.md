## Goal
### Why this plan
The app was built function-first over PLAN.md Phases 1–7; its nine tabs are stock Qt widgets with no theme, no spacing system and no visual hierarchy, and the everyday flow (Session → Transcript → Note) is mixed in with four setup tabs. The practitioner (2026-10-09): it "looks pretty messy and old", "a lot of stuff can get moved to a settings button", it "looks very confusing and in your face when you first open the app", and "when finishing a note through the app I have to complete it in a separate tab".

### What the practitioner decided (2026-10-09, this planning session)
- Scope: the look, the layout and the wording; a FULL redesign is acceptable mid-pilot ("I only have 4 patients left for today and then it's the weekend").
- Theme: light AND dark, following the Windows app-mode setting.
- Direction: mockup **A — "Clinic"** (light canvas, blue accent, Segoe UI Variable, a left icon rail, cards; a dark variant of the same tokens). Mockups B ("Paper") and C ("Console") were shown and not chosen.
- The everyday flow: **Record → Review**. One Review screen — transcript left, note right, one button row (Save note → Write draft to Cliniko → Copy note; Complete → Discard on the right), "Edit the note" as a strip under the note that opens the existing line tools; before a note exists the right pane holds today's "Generate note" group.
- Settings: all four setup tabs (Microphone, Practitioner, Clinics, Status) behind a Settings gear, as a view inside the main window; the main window shows Record, Review, Past sessions and Recovery.
- First open: a one-time **setup checklist** page (microphone ✓, clinic key ✓, voice profile ✓, Chrome link ✓) that goes away once done; recording keeps working without the voice profile.
- The Chrome side panel: **matched later** — a final optional phase, same tokens, no behaviour change, after the desktop build is installed and settled.

### What the practitioner decided at `/review-plan` (2026-10-09, the same session)
- 0.4.0 ships Phases 1 → 2 → 3 → 4 → 5 in THIS plan's numbering: theme, Review screen, shell, the wording for renamed screens, docs/version — the checklist, the full Review composition (the one shadow-exit pin change) and the Chrome panel go to 0.4.1 (Phase 6), because the checklist never shows on a set-up machine and the weekend install is the target.

## Design Decisions
- **D1 — One theme module owns every visual value.** New `ui/theme.py`: a frozen `Tokens` dataclass (colour roles: `canvas`, `surface`, `surface_alt`, `border`, `text`, `text_muted`, `accent`, `on_accent`, `danger`, `warning`, `success`, `focus`, `link`, `rec`, `paused`; type: `family`, `size_body`, `size_caption`, `size_title`, `size_heading`; spacing: `space_1..5`; `radius_control`, `radius_card`), `LIGHT` and `DARK` instances, `render_qss(tokens) -> str` producing ONE stylesheet whose selectors are widget classes plus dynamic properties (`QLabel[role="danger"]`, `QLabel[role="muted"]`, `QLabel[role="title"]`, `QPushButton[variant="primary"|"danger"|"link"]`, `QFrame[card="true"]`, and the shell's object ids `#rail #railButton #railCue #header #appTitle #settingsStrip #settingsTabs`), and `set_role(widget, role)` / `set_variant(button, variant)` / `mark_card(frame)`, which set a dynamic property and unpolish/polish the widget (Qt does not restyle on `setProperty` alone — probed). The 16 ad-hoc style sites (15 `setStyleSheet` calls and one `StyledPanel`) become those calls; `#b00020`, `#0645ad` and `font-weight: bold` disappear from every other module (a test greps for them — D13). Values live in code; `docs/design-system.md` gets a "Tokens" section naming the roles and pointing at `ui/theme.py` for the values. Rationale: the only way a stylesheet can be tested, packaged (strings, no new `APP_DATAS`) and kept from drifting.
