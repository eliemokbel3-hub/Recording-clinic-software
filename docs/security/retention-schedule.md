# Retention Schedule (Phases 1–3A, practitioner profile, note learning Phases 0–4, Cliniko workflow safeguards, Cliniko draft write, privacy and professional controls, installation, pilot, kept recordings)

What the software keeps, where, for how long, and how it is destroyed.
Since Phase 2 the desktop app stores clinical data (audio, transcripts, and —
since Phase 3A — the composed note) — always encrypted at rest under
per-session keys (and, since the privacy-professional-controls plan, the kept
transcript and notes under per-entry Past-sessions keys); UNPROTECTED recovery
stores are bounded by the 24-hour rule
below, while a live or under-review session is sweep-exempt from it (see the
rule). Phase 3A also adds
clinician-authored config files (plaintext, INTENDED to hold non-patient
boilerplate, deliberately outside the 24-hour rule).
The note-learning-and-styles plan's Phase 0 added the learned-style store and
the practitioner settings file, its Phase 1 the in-memory live-transcription
buffers, its Phase 2 the learned rules, its Phase 3 fills the store from the
practitioner's own past notes (read into memory, never stored — the row below)
and its Phase 4 the in-memory prose-rendering state; every row is BUILT — the
Phase 0 stubs were finalised at that plan's Phase H (task H3, 2026-09-25).
The Cliniko workflow safeguards plan's Task 1.1 adds the in-memory Cliniko API
rows, its Phase 2 the clinic-key and registry rows, and its Phase 3 the encounter-record row and note verification's part of the API-response row (all 2026-09-27); its Phases 4–7 the in-memory Chrome-link, reminder-index and Chrome-side rows and the crash-dump row, and its Task 8.2 the clipboard formats on the copied-note row (2026-09-28); all are BUILT.
The cliniko-draft-write plan (PLAN.md Phase 4, built 2026-09-29) adds the draft-write record row (`write.enc`) and the own template-defaults row, the draft write's part of the API-response and key-in-use rows, the `default_source` field on the registry row, the Complete-after-a-confirmed-write ordering on the key row, and turns the pre-committed write-back rule below into a built one. Its Phase 7 (D15, 2026-09-30) makes `write.enc` schema v2 (the expected final and the as-read digests), drops the template from the draft write's part of the API-response row, retires the registry row's `default_source` (tolerated on load, never written) and retires the own template-defaults row (the file is no longer read).
The privacy-professional-controls plan (PLAN.md Phase 6, built 2026-10-01) REVERSES "Complete destroys everything": at every non-mock Complete the session's transcript, saved note (unless the path deletes it) and generated note (when readable) are copied, encrypted under a fresh per-entry key, into a **Past sessions** entry kept for a retention the practitioner chooses (default: until they delete it), before the session's key is deleted — audio is never kept (except, since the development-recordings plan, below, a recording kept under the patient's written consent). It also adds a durable, content-free **audit record** (one encrypted row per session, kept 7 years), the session files `generated.enc` and `saved-provenance.enc`, the Past-sessions settings file, the exported audit CSV (outside the app's custody), and the exclusions (per-user Windows Error Reporting values, the not-content-indexed folder attribute, a start-up location check); and every Complete now removes the session directory. The rows marked "(privacy-professional-controls)" below, and the "Past sessions" and "Audit record" rules after the 24-hour rule, are BUILT.
The installation plan (PLAN.md Phase 7, built 2026-10-02 → 2026-10-03; installed on this computer 2026-10-03, 0.1.2 since 2026-10-04) adds the installed program, its read-only models, the installer's machine-wide registry values, the model pack, the release download and the build working files, and splits a source checkout off as the developer build with its own data folder `%LOCALAPPDATA%\ClinikoScribe-dev` (the "Installation" rows after this table). Every `%LOCALAPPDATA%\ClinikoScribe` location in this table is the installed (production) app's; a source checkout keeps the same stores under `ClinikoScribe-dev`.
The pilot plan (PLAN.md Phase 7's pilot half, built 2026-10-04, version 0.2.0) adds the recording's mode (`normal` / `shadow`) to the encounter record, the mode and the app version to the audit row and a shadow flag to the Past-sessions label (each schema v2, reading v1 as normal — the rows below say so), the pilot setting file, and the developer-build validation harness's files, the role-play recordings and the pilot's own records (the "Pilot" rows after the Installation table). A shadow recording's note is never placed on the clipboard (the copied-note row).
The development-recordings plan (built 2026-10-07 → 2026-10-08, version 0.3.0) lets ONE kind of recording keep its audio: one the patient consented IN WRITING to keep for developing the program (`docs/practice/development-recording-consent.md`, `development-consent-v1`), started with the Status tab's "Keep recordings for development (written consent only)" on and the Session tab's second tick given. Its audio is re-encrypted at Complete into the Past-sessions entry beside the transcript and notes, under an audio key wrapped by the entry key, kept until the practitioner deletes it and reviewed at 12 months (the tab's reminder comes 365 days after Complete, and never for an entry whose label cannot be read — that one is reviewed by hand); the encounter record and the audit row become schema v3 (the consent's version; the audit row's `recording` facts), and the setting file, the export ledger and the exported WAV are new (the "Kept recordings" rows after the Pilot table). Every other recording's audio still dies with its session key.

## The 24-hour rule (Phase 2, enforced by code)

- Every session store becomes EXPIRY-ELIGIBLE at **24 h** from creation and is
  then destroyed (key custody first) by the next SUCCESSFUL scheduled sweep —
  UNLESS it is PROTECTED from the sweep. The protected set
  (`app.sweep_protected_ids` → `SessionController.custody_protected_ids`) is:
  a session live in `recording`/`paused`/`processing`; the controller's OWN
  session in ANY non-terminal state, INCLUDING a `queued` transcript/note held
  open for review (round 42 MED-001 — so review is never cut off by custody
  loss at the 24 h boundary); and a recovered session checked out for
  resume / Complete / Discard (PR round 18). A protected store SKIPS age
  evaluation entirely, so while a session is active or under review its
  retention is bounded by the review/session lifetime, NOT by 24 h — the 24 h
  cap governs UNPROTECTED recovery stores (a crashed or abandoned session no
  longer held by the controller or a recovery checkout). This is deliberate:
  the alternative — deleting a note's key mid-review at the 24 h mark — would
  destroy work in progress. An Unreviewed session opened for review (Cliniko
  workflow safeguards Task 5.4) becomes the controller's own queued session
  again and is protected the same way; retired again, it is unprotected and
  its window counts from its creation as before. The listing's age filter
  means a session whose age is ESTABLISHED past its window is not offered for
  opening; one with no readable timestamp at all is listed regardless of age
  (the sweep owns that case, round 47 PR-LOW-001), and its shown expiry is
  provisional (codex round 34 PR-LOW-192). The
  app warns 2 hours before an Unreviewed session's window closes and lists
  each one's expiry on close — both from the sweep's own
  `session_expires_at`.
- Enforcement: a sweep at every app start (before the recovery screen lists
  anything) + a 15-minute periodic sweep while the app runs + an age filter
  on the recovery listing itself. All three consult the protected set above.
- Accepted residual — expiry at the next SUCCESSFUL sweep, not a hard deadline
  (UNPROTECTED stores only): an unprotected recovery store expires at the first
  scheduled sweep that RUNS SUCCESSFULLY after its 24 h mark — normally within
  about the 15-minute QTimer CADENCE while the app runs, and at next launch
  while it is closed (nothing can decrypt the store in the meantime without the
  user's DPAPI context). The 15 minutes is the intended INTERVAL, not a
  guaranteed bound: GUI-thread blocking, OS process suspension (sleep/hibernate),
  or a sweep that retains the store after a transient I/O error (it fails closed
  toward RETENTION and retries next cycle — below) can push actual expiry past
  one interval. A PROTECTED store is exempt from the cap for as long as it stays
  protected — potentially unbounded while a session stays active or under review.
- Timestamp handling is fail-safe: untrusted candidates (non-finite, or
  more than the clock-skew tolerance in the future) are discarded and can
  never extend retention — age is computed from the earliest TRUSTED
  candidate. If candidates exist but none is trusted, the sweep fails
  CLOSED and expires the store; if no candidate is readable at all
  (transient I/O trouble), the store is kept for that sweep and retried
  next cycle — transient filesystem errors must never trigger
  cryptographic deletion. The rule lives in exactly one place
  (`session_store.earliest_trusted_timestamp`), shared by the sweep and the
  recovery listing so the two can never disagree.
- Clock-skew tolerance (`CLOCK_SKEW_TOLERANCE`, 5 s): filesystem mtimes can
  read marginally AHEAD of a later `time.time()` — Windows' wall clock is
  coarse (~15.6 ms on Python ≤ 3.12) while NTFS records mtimes at 100 ns,
  and FAT-family volumes round mtimes up to a 2 s boundary. Treating that
  as "future = untrusted" made the sweep destroy sessions it had just
  created, so stamps within the tolerance are accepted and clamped to the
  present. A stamp beyond it is a genuine clock problem and still fails
  closed. Cost: at most 5 s of extra retention beyond the 24 h mark, on top of
  the cadence delay described above.

## Past sessions (privacy-professional-controls plan, built 2026-10-01)

- **What Complete keeps.** Every Complete of a non-mock session copies the
  source-derived set (the Past-sessions entry row) into a new entry, verifies
  it through the entry's own key read back from disk, and publishes it BEFORE
  the session key is deleted; then the session key is deleted and the session
  directory removed. The session's audio, its encounter record, its write
  record and its provenance file die with the session key (a recording kept
  under written development consent survives as a RE-encrypted copy in the
  entry — "Kept recordings" above). Discard, the 24 h
  expiry of the session and a failed session keep nothing (a failed session
  later recovered and Completed IS kept — Complete decides).
- **How long — 7 YEARS MINIMUM** (practitioner decision 2026-10-02: a kept
  transcript is part of the health record, VIC/NSW/ACT). The practitioner's
  setting on the Past sessions tab: "7 years" (2557 days) or "Until I delete
  them" (the default, following Heidi Health's compliance-FAQ default,
  checked 2026-10-01). The shorter settings an earlier build offered (1, 7,
  30 or 90 days, 1 year) are gone: a settings file holding one LOADS as 7
  years (never a fail-closed reset), the tab says so until the next save
  writes 7 years, and any other value still fails closed. The sweep itself
  refuses a window under 7 years before any read (nothing deleted; the tab
  says so). Choosing 7 years from "Until I delete them" asks first and then
  deletes every entry older than 7 years at once; choosing "Until I delete
  them" deletes nothing. **Delete now** is kept, worded for a recording made
  in error only (the wrong patient, a test, or one recorded without
  consent); its behaviour is unchanged. A transcript of a patient who was a
  child must be kept until they turn 25; the app does not know ages, so the
  warning tells the practitioner to choose "Until I delete them" then. The
  tab shows the warning that
  a kept transcript becomes part of the practitioner's health record (VIC
  Health Records Act 2001, NSW HRIP Act 2002, ACT Health Records (Privacy and
  Access) Act 1997, elsewhere APP 11.2), can be reached by an APP 12 access
  request or a subpoena, is kept encrypted, only in this Windows login's data
  folder, with no backup of the app's own — though backup or sync software,
  or a folder location the app has warned about, can still copy the encrypted
  files — that Cliniko stays the system of record, that a kept transcript
  is kept for at least 7 years, and the child rule (`docs/practice/` carries
  the same research and the practitioner's 2026-10-02 answer).
- **Enforcement.** The retention sweep runs at start-up and then at most
  hourly on the 15-minute timer, ONLY WHILE THE APP RUNS (accepted, as for
  the 24-hour rule): an entry can outlive its setting while the app is
  closed, and is deleted at the next start. Under "Until I delete them" it
  does nothing and decrypts nothing. Each entry's completion date is read
  from its label once per process.
- **Fail toward keeping.** An entry whose label this account cannot read
  (no date), and one dated in the future, is KEPT whatever the setting (the
  tab counts the unreadable ones, says they are still kept, and that Delete
  now is only for a recording made in error — round 40 PR-LOW-034); an unreadable
  label is tried again a day after it failed, not on every hourly check; an
  unreadable
  settings file deletes nothing by age; a deletion that fails is reported on
  the tab and retried at a later hourly check while the app runs.
- **Wall-clock trust.** The sweep trusts the system clock: a clock jumped
  forward can expire entries early (as it can the 24-hour sweep), and one
  jumped back keeps them longer.
- **"Until I delete them" with no backup.** Kept transcripts accumulate on
  this PC indefinitely. A dead disk, a lost Windows profile or an
  administrator's reset of the Windows password (which breaks DPAPI) loses
  every entry — the entries are then listed as unreadable: kept, never
  deleted by age, and never readable again (Delete now still works on them,
  but the tab limits it to a recording made in error; whether an unreadable
  transcript must still be kept is a reviewer question in
  `docs/practice/downtime-procedure.md`). Passphrase-protected backup/restore is deferred (plan, Deferred —
  Actionable Later). Cliniko holds the clinical record.

## Audit record (privacy-professional-controls plan, built 2026-10-01)

- **Written at Start, before anything of the session exists.** If the row
  cannot be written, Start is refused ("Start failed: AuditWriteError: the
  audit record could not be saved (…). Nothing was recorded.") and nothing is
  recorded. Every later update — the write's transitions, Complete's models
  and outcomes, Discard, expiry, `orphan_gc`, Past-sessions events — is
  best-effort: it never blocks a write, a Complete, a Discard or a sweep, and a
  failure is counted, logged by its stage code and shown on the Past sessions
  tab.
- **Kept 7 years** from the session's local calendar month (the month's end
  + 7 years + one day, because the folder is the LOCAL month, which can end up
  to 12 h after the UTC one), pruned at start-up and every 24 h while the app
  runs. A system clock wrong AT Start dates the row by that clock (a date
  more than seven years back would be pruned at the next start-up); the
  prune trusts the wall clock, so a clock jumped forward by seven years or
  more removes every month it has passed, irreversibly (threat model, residue
  (p)); a pre-audit session's creation time before 2026-01-01 (or missing, or
  in the future) is untrusted and the row is dated by the clock of the update
  that creates it instead.
- **`pre_audit` rows.** A session started before this build gets a row at its
  first audit update of any kind — a draft-write transition or refusal, a
  Complete, a Discard or a sweep — dated by its own creation time read
  before the directory goes. A Past-sessions event on a row the audit no
  longer holds (pruned, or set aside by "Start a new audit record") creates a
  `pre_audit` row too for a DELIBERATE action — Delete now, and since 0.3.0
  Delete recording and Export — dated by the entry's start ("now" when its
  label cannot be read). The UNATTENDED writers (a reconciled commit's
  `archived`, the kept-fact and deletion repairs, the retention sweep's kept
  fact and `expired`) date a re-made row by the session's start, never re-make
  one in a month the prune has passed, and with no readable label write only
  to an existing row (threat model, "Kept recordings", THE AUDIT FACTS).
- **Named residues.** A process killed between Start's row and the session
  directory's creation leaves that row `pending` for ever (nothing on disk for
  the sweep to end). A Complete killed after its key deletion but before
  its own audit update is never recorded as completed (its outcome is not guessed): the next sweep ends the
  row `orphan_gc` if the keyless directory is still there, else its deletion
  state stays `pending`; the next reconciliation records `archived` if the
  entry's marker was still there, but if the Complete had removed the marker
  and not yet written its own update, the entry is listed while the row's
  Past-sessions state stays `none`. A Discard or a 24 h expiry killed between
  its key deletion and its audit update is never recorded as such either
  (`orphan_gc` or `pending`; a kill during a sweep tick can leave every
  session that expired in that tick `pending`) (threat model, residue (o)).
  An unreadable
  audit key (an administrator's password reset) refuses every Start until the
  practitioner presses "Start a new audit record", which sets the old store
  aside unread and deletes nothing.
