# Validation harness (pilot plan Phase 2)

An offline batch run of the shipped pipeline over synthetic encounters (it can also measure a recorded one — below — but the run of record is synthetic only since the clinic-smoke plan, 2026-10-09). It reports text-free quality numbers and a pass or fail against a pass rule decided BEFORE any run (pilot plan decision 3.5). It is a developer-build tool. It is separate from the shipping-gate run (`shipping-gate.md`): that run scores notes by hand inside the app; this one measures automatically against scripts.

Code: `desktop/src/scribe_desktop/validation.py` (script format, metrics, runner, report, command line) and `desktop/src/scribe_desktop/validation_set.py` (the synthetic set builder). Launchers: `scripts/run-validation.py` and `scripts/build-validation-set.py`. Tests: `desktop/tests/test_validation_metrics.py`, `test_validation_harness.py`, `test_validation_set.py` and `test_validation_scripts.py`.

## What goes in

A **set folder** holds three files per encounter, sharing one name:

- `<id>.json` — the encounter script (below). The name must equal its `encounter_id`.
- `<id>.wav` — 16 kHz mono 16-bit PCM (the `speaker_eval.read_wav_pcm` contract; nothing is resampled).
- `<id>.txt` — the timed Audacity label track `speaker-measurement.md` defines: one span per turn, labelled with its role, exactly one role `clinician`.

A name with only some of the three is reported and counted as a set-level error, and any set-level error fails the run. Every name must be an encounter id (lower-case letters, digits and hyphens): a `.json`, `.wav` or `.txt` named otherwise is counted as one set-level error and never printed by name (it could be anyone's). A name that IS shaped like an encounter id is printed wherever the encounter is named (an incomplete triple, the report), so a recorded encounter's files take a neutral id, never a person's name. **"Role-play" in the harness's code and messages means a RECORDED script** — one without `conditions`, whose WAV and label track were made by hand rather than built — the name of the mock role-play set the pilot first planned. That set was retired on 2026-10-09 (clinic-smoke plan D1): no recorded encounter is part of the run of record, and a real consultation is never placed in a set folder (pilot plan Constraint 8) — a kept consultation reaches measurement only through `measure-speakers.py` (`speaker-measurement.md`). The behaviour is unchanged; the vocabulary stays. The harness reads only a folder's top level: a lone WAV there would be a set-level error and fail the run.

**The script** (`EncounterScript`, schema version 1): an id, an appointment type, the axis tags it exercises (PLAN.md's AI-quality list: negation, laterality, numbers, small talk, uncertain, contradictory, scribe instruction, end of consultation and new patient, noise, overlap, rate), the reference lines in start-time order (`role`, `text`), the expected facts, the checker warnings it is written to provoke (`expected_warnings`), and — for a synthetic script only — the conditions the builder applies (one voice slot per role, the speaking rate, the signal-to-noise ratio, the overlapped lines). Each fact names its kind (`laterality`, `dose`, `negation`, `absent`, `present`), its tokens (normalised words that occur together in its line), the line that states it, whether it is `material`, and whether its uncertainty is expected to be surfaced (`expect_uncertain`; refused on an `absent` fact, whose uncertainty could be surfaced only by its wrongly reaching the note). A script is refused by file name and field, never with its text.

The repository holds 50 invented scripts in `validation/scripts/` and the note config they are written against in `validation/config/`: the shipped defaults plus three autofill rules whose trigger phrases are spoken only in `syn-07`, `syn-08` and `syn-09`, so a confirmed config line contradicts what the patient said and the checker's warning is the expected result; before the run of record the practitioner adds their own cue file there (rule v1's call 1, below). Consent is spoken and routed to the consent section in `syn-10`, `syn-19`, `syn-26` and `syn-42`, each as a material fact (linted). A synthetic script picks its voices by slot, the voice's index in SAPI order on the computer that builds the set. The current voice baseline (clinic-smoke plan Task 0.3, 2026-10-09) is 0 = Microsoft David Desktop (US English), 1 = Microsoft Hazel Desktop (UK English), 2 = Microsoft Zira Desktop (US English): `syn-01` to `syn-40` use slots 0 and 2, and the patient of `syn-41` to `syn-50` is slot 1, the third installed voice — the synthetic set's accent coverage (clinic-smoke plan D4; linted: slot 1 is the patient of exactly those ten). `validation/rules/option-a-proposed.json` is decision 3.5's option (a) as data — ratified unchanged as rule v1 on 2026-10-07 (below). Invented content only: no real patient, consultation or recording is ever placed in a set folder (pilot plan Constraint 8).

## How to run it

From a normal terminal (never an agent shell — `docs/lessons.md`), on the developer build, with the installed app closed and the models downloaded by `scripts\setup-models.py`:

1. Build the synthetic set (three Windows voices installed, in the current voice baseline's order — above). First list the voices with their slots, in PowerShell, keeping the single quotes (a backtick-n inside double quotes would break the Python string):
   `.venv\Scripts\python.exe -c 'from scribe_desktop.validation_set import sapi_voices; [print(i, v) for i, v in enumerate(sapi_voices())]'`
   and build only if the name at slots 0, 1 and 2 equals the baseline. Adding or removing a voice can renumber the slots (adding UK English with text-to-speech under Settings, Time & language, Language & region moved Zira from 1 to 2 on 2026-10-09), and the builder checks only that a slot exists, so a renumbered inventory would build without any error in other voices; restore the inventory, or remap the scripts in a new commit, first. Then:
   `.venv\Scripts\python.exe scripts\build-validation-set.py validation\scripts <set-folder>`
   `<set-folder>` must be outside the repository (the builder refuses one inside it). `--only syn-01 syn-02` builds a subset; a name that matches no script exactly is an error (one that is not an encounter id is reported without its name, peer round 27). Recorded ("role-play") scripts — no conditions; none is in `validation/scripts` — are skipped and said so. A script file whose name is not an encounter id is counted as an error and reported without its name ("(a file not named as an encounter id)"), and nothing is written for it. Each file is written whole and then moved into place, the script copy last (the bytes that were rendered, read once) after the earlier copy is removed first, so an interrupted build leaves an incomplete triple the harness reports, never a mixed one. A role-play whose `<id>.json` is in the set folder, or a script there that does not load, is never overwritten: that script is refused by name. The builder also leaves an ownership mark, `<id>.built`, beside each encounter it writes (the harness ignores it): a WAV or label track without its `<id>.json` is rebuilt only when that mark is beside it (an interrupted build); without the mark it is someone's recording and is refused by name, untouched. A failed build removes a mark left with nothing beside it, but an interrupted one (Ctrl+C) can leave `<id>.built` alone, and a by-hand deletion can miss it: delete any leftover `<id>.built` before a recording uses that id, or the builder will treat the recording as its own. If a recorded script is ever added to a set folder (none is in the run of record, step 2), add its script before building into that folder, and never give it a `syn-` id. A write that fails (a file open in another program) is refused by name, saying which files to close or delete. A script that fails removes its earlier synthetic build from the set folder (never a role-play's files), so a stale build is never measured; a file that cannot be removed (open in another program) is named on the error line for you to delete.
2. Keep the set synthetic. Since the clinic-smoke plan (2026-10-09; D1, D5) the run of record adds no recording to the set folder: build into an empty folder, never into the smoke's measurement folder, and never put a kept consultation or an exported copy of one there (pilot plan Constraint 8). After the run delete the set folder — it is rebuilt from the repository at any time. (Until 2026-10-09 this step added the mock role-play recordings to the set under decision 3.6, now superseded.)
3. Run: `.venv\Scripts\python.exe scripts\run-validation.py <set-folder> --config validation\config --rule <rule-file>`
   Options: `--template-profile <id>` (default: the config's only profile), `--allow-small` (measure with Whisper `small` when `medium` is not installed; the report says so), `--prose` (also run the narrative prose stage and report its section counts; a stage that could not run — the model failing to load — is reported as `unavailable` and fails the run).

Exit status: 0 only when the run passed; 2 for a refusal before any encounter runs (models that cannot be loaded included, reported by error type only); 1 otherwise. The report is Markdown on standard output; redirect it to a file to keep it. A run stopped with Ctrl+C prints no report and no traceback, only one line naming the temporary folder to look in for a `scribe-speaker-eval-*` folder an interrupted teardown may have left — it may still hold its key — and asking you to delete it (exit status 1); stopped while the models load, it says so and nothing was run.

**Refusals, in order, each by name:** a packaged build; a set or config path that is not a folder; the app's own config folder (either channel — use `validation\config` or a folder of files you wrote, never a copy of the app's own); an unusable rule; an unreadable or malformed config file (its error TYPE only — the loader's detail can quote the file); a config folder carrying the app's learned phrases or rules (a learned-phrase or learned-rule sidecar, or a `learned-` rule — the sign of a copy); a template profile that cannot be bound (an unknown `--template-profile`, or several profiles and none chosen); a models folder that cannot be located; no Whisper model installed (naming the models folder and the remedy); a fallback to `small` without `--allow-small`; the silero VAD model missing; `--prose` without the language model; a set folder that cannot be listed; models that cannot be loaded (their error type only). A rule file over 64 KiB is refused, and a label track over 4 MiB fails its encounter (as the 256 KiB script cap does). The builder refuses a packaged build, a missing scripts folder, PyAV missing (it resamples every spoken turn), an output folder that is the scripts folder or lies inside the repository or inside either app data folder (`%LOCALAPPDATA%\ClinikoScribe` or `ClinikoScribe-dev`), Windows voices that cannot be listed, fewer than two installed voices, a set folder that cannot be created and a scripts folder that cannot be listed, in that order — before any voice speaks. The builder needs no model, so the models-folder refusal is the harness's alone (Task 2.7's reading).

## The declared policies (pilot plan D9)

- **Proposals:** every proposal is confirmed through the review surface's own `ui/note_review.build_resolutions`, and every pre-filled line the config decided stands — as if the practitioner confirmed every row and removed nothing. Because that confirms what a clinician might decline, the checker's warnings on the finalised note count against the encounter (the checker tally).
- **Body region:** the earliest detected prefill region.
- **Clinician speaker:** from the label track — each diarised segment takes its duration-weighted majority true label (`speaker_eval.align_segments`); the cluster whose majority is `clinician` is the clinician. No such cluster, or two holding the clinician's seconds equally, is "role unresolved": a failed encounter, never a guess.
- **Config:** the explicit `--config` folder only; files absent from it fall back to the shipped defaults. Learned phrases and learned rules live inside the app's own files (phrases merged into its `section_cues.json`, rules as `learned-` entries in its `autofill_rules.json`), so the harness refuses the app's folder and any folder that carries their marks; a learned rule would otherwise be confirmed like any other. Phrases already merged into a copied `section_cues.json` carry no mark and cannot be told apart, so never copy the app's files.
- **Model:** Whisper `medium`; `small` only with `--allow-small`, named in the report either way.
- **Build:** the report names the commit (read from the `.git` files; it cannot tell whether the working tree differs) and the SHA-256 of `packaging/models-manifest.json`. Both are found from where the harness module sits, so they need the editable install of AGENTS.md step 2 in a plain checkout: from a linked worktree (where `.git` is a file) the commit reads `unknown`, and from a non-editable install both read `unknown` / `absent` and the set builder's in-repository refusal guards the virtual environment's folder instead of the checkout.

## What each number means (pilot plan D8, Task 2.3)

Everything is decided against the SCRIPT, through one word-level alignment: the script's reference tokens (its lines in order) against the transcript's words, by the edit distance that also gives the word error rate (`note.content_tokens` on both sides). Where several alignments cost the same, every one of them is considered and the worse outcome is reported.

- **Word error rate:** edit distance over reference tokens, per encounter and in total.
- **Unsupported clinical line:** a note line quoted from the transcript in which a side, number, dose, strength unit or negation word (`note_check`'s own token classes) is substituted or inserted on any equal-cost alignment. Every one fails the run. Other substituted or inserted words in note lines are counted only. Lines that came from the config are counted separately and judged by the checker tally.
- **Checker tally:** the count of each warning code on the finalised note. Any error-severity warning, and any `contradiction`, `contradiction_low_confidence`, `laterality_mismatch` or `dose_mismatch` the script does not list, fails the encounter. A listed code exempts every instance of it in that encounter, not only the one the script was written to provoke. A listed warning that did not appear is reported as "expected but absent", not failed — which is why `syn-08` and `syn-09` list `contradiction_low_confidence` beside `contradiction`: which of the two Check 2 raises depends on the recogniser's confidence in the evidence words.
- **Per fact:** `correct` (every token matched and carried in a note line), `wrong` (some of its aligned words are in a note line, but not every token was matched and carried — a substituted side, dose or negation, or a fact carried only in part), `omitted` (no aligned word in a note line); for an `absent` fact, `correctly_absent` or `wrongly_present`. A fact stated twice in its line takes the worse of its occurrences. `warned`: one of the fact's own aligned words is outside every note line, high-risk by `note_check`'s predicate, and its segment carries a `high_risk_omission` warning — a warning elsewhere in the segment never counts. `uncertainty_surfaced` (for `expect_uncertain` facts only): a `low_confidence_source` warning sits on one of the fact's aligned words — judged on its own, and surfaced only when EVERY equal-cost alignment, and every repeated statement of the fact in its line, surfaces it (so the alternative or statement that decides the verdict cannot hide a miss). "Not transcribed": every token was deleted by transcription.
- **Silent omission:** an omitted, material fact that was not warned — on ANY equal-cost alignment or repeated statement, so the worse outcome reported for the fact cannot hide one. A fact can therefore count both as material `wrong` and as a silent omission.
- **Ambiguous** (the report's column): a fact whose judged outcomes differed across equal-cost alignments or across its repeated statements in its line; the worse outcome is the one reported.

**Fixed failures (not part of the rule):** a harness error, a role-unresolved encounter, any unsupported clinical line, any checker failure and a requested prose stage that could not run. A rule file cannot relax them; changing one is a code change. **The rule file** (`PassRule`, schema version 1) sets the rest: the most material `wrong`/`wrongly_present` facts allowed (default 0), the most silent omissions allowed (default 0), whether every `expect_uncertain` fact must be surfaced (default yes) and an optional word-error-rate ceiling (default none). The rule is ratified as decision 3.5, recorded here as rule v1, and never adjusted after a run.

## Rule v1 (decision 3.5, ratified by the practitioner on 2026-10-07)

**The rule is option (a), unchanged**, and its file is `validation/rules/option-a-proposed.json` (pass it as `--rule validation\rules\option-a-proposed.json`). A run PASSES only when, over the whole set:

- at least one encounter ran and no set-level error occurred (an incomplete triple or a badly named file, above);
- no encounter has a fixed failure (above): no harness error, no role-unresolved encounter, no unsupported clinical line, no checker failure — no error-severity warning other than a contradiction-class code the script lists in `expected_warnings`, and no unlisted `contradiction`, `contradiction_low_confidence`, `laterality_mismatch` or `dose_mismatch` — and no requested prose stage that could not run;
- no material fact is `wrong` or `wrongly_present` (`max_material_wrong` 0);
- no material fact is a silent omission (`max_silent_omissions` 0);
- every `expect_uncertain` fact has its uncertainty surfaced (`require_uncertainty_surfaced` yes);
- there is NO word-error-rate ceiling: the word error rate, the other unsupported words and the warned omissions are recorded, not thresholded.

Three calls ratified with it, all settled before any run:

1. **The practitioner's own cue file.** Before any run of record (pilot plan Task P.3), the practitioner writes their own `section_cues.json` into `validation\config` — written fresh, never copied from the app's config folder (the harness refuses a folder carrying the app's learned content, and phrases already merged into a copied file could not be told apart). A cue file there replaces the shipped cues as a whole, as the app's own does. It is committed with the repository, which is public: cue phrases only, never patient content. The scripts' routing lints (`test_validation_scripts.py`: every `expect_uncertain` fact in a routed clause; consent routed in at least three scripts) then read it; a lint that fails is resolved by a script revision before any run, recorded on Task P.3 — never by a change to the rule.
   - Written 2026-10-09 (clinic-smoke plan Task 0.2): 26 phrases in 16 sections, outcome measures empty. Its routing lints were met by revising 13 lines in 10 scripts (a practitioner cue in the fact's own clause; the consent clauses of `syn-10`, `syn-19`, `syn-26` and `syn-42`), fact tokens unchanged. A text-level count before the commit found 114 of the 133 non-absent material facts in a clause these cues do not route (51 under the shipped cues), so the run of record is expected to fail on silent omissions — a finding about the cue file's coverage, recorded on the plan's Task 0.2.
2. **Fenced-off content is material.** The content a spoken instruction fences off is a material `absent` fact: `syn-05` ("surgeon rushed it"), `syn-18` ("call the plumber"), `syn-19` ("boss doesn't know"), `syn-31` ("racing my brother-in-law", after "Scribe, don't record the following") and `syn-40` ("pay by card", after "Scribe, pause the note") — every script on the `scribe_instruction` axis. The instruction lines themselves and small talk stay `material: false` where a script gives them a fact (counted, never failed; `syn-31`'s instruction line has no fact, so a leak of it is not counted). This is the rule-v1 script revision of 2026-10-07 (`syn-31` added at review round 17 the same day). (`syn-47`, added 2026-10-09 by the clinic-smoke plan, follows the same rule: "row with my manager", after "Scribe, please leave out what comes next", is a material `absent` fact, and its instruction line is `material: false`.)
3. **Accent coverage comes from the role-plays.** At least one role-play speaker's accent differs from the practitioner's, and each role-play speaker's accent is recorded in broad terms (no name) with Task P.2's records, so the run's accent coverage can be read beside its result.
   - **Amended 2026-10-09 (clinic-smoke plan D4; cite the rule as "rule v1 as amended 2026-10-09").** The role-plays are retired (D1), so call 3 is met in two halves; the thresholds, call 1, call 2 and the rule file are untouched. (i) Synthetic: the patient of `syn-41` to `syn-50` is a non-Australian English voice — Microsoft Hazel Desktop (UK English), slot 1 of the current voice baseline (above) — and the run's record names every voice used, in SAPI order, beside the commit and the rule file's blob hash (`git rev-parse HEAD:validation/rules/option-a-proposed.json`). (ii) Real speech: an AGGREGATE COUNT only — how many of the clinic 1 smoke's measured recordings had a speaker whose accent differed from the practitioner's, out of how many — written in the practitioner's off-repository pilot log and never in the repository, because a per-recording accent is sensitive information.

## Custody and privacy

Each encounter is transcribed in a temporary encrypted session store under a fresh DPAPI-wrapped key — the same helpers `measure-speakers.py` uses (`speaker_eval.transcribe_in_temporary_store` and `destroy_temporary_store`). The store is torn down key-first and probed; one that cannot be shown gone stops the whole run and names its path. The harness writes no audit row and no Past-sessions entry and reads none. The offline environment is applied and asserted before any model loads. The report holds ids, numbers, flags and closed vocabularies only — never a transcript, note or script line; an unexpected failure is reported by its exception type name.

## Known limits (residues)

- **Number and unit spelling.** A number or unit the recogniser spells differently from the script ("500 mg" against "500 milligrams" or "500mg") is a substitution of a structured-claim word, so its note line counts as unsupported. The scripts write doses as digits with the unit in full, as recognisers usually do, but a formatting difference still fails. Rule v1 keeps this strictness (decision 3.5): such a failure is a finding.
- **Medication names** are not structured-claim words in `note_check`'s classes, so a substituted medication name in a note line is counted, not failed, and shows in its fact's verdict.
- **Overlapped speech** is judged against one start-time order. Speech the recogniser drops, merges OR correctly transcribes in another order reads as not transcribed or substituted, and a displaced side, number or negation inserted into a note line makes it an unsupported clinical line — so a faithfully transcribed overlap can still fail. The seven overlap scripts (`syn-13`, `syn-14`, `syn-15`, `syn-27`, `syn-29`, `syn-36`, `syn-45`) are candidates for an expected fail; overlap is measured, not excused.
- **Repeated words beside a fact.** Where the reference repeats a fact's first or last word right beside it ("no, no numbness"), a transcript that drops or doubles the repeat has equal-cost alignments that disagree about the fact, and the worse is reported — a false `wrong` or an unsupported line on a faithful note. The scripts avoid it, and `test_validation_scripts.py` lints for it; a recorded script (none is in the set) could still contain it.
- **A dropped word inside a note line is not "unsupported".** Only substituted or inserted words make a line unsupported, so "there is swelling" carried for a spoken "there is no swelling" passes that test; only a script fact on the negation catches it.
- **Many material facts are omitted by construction.** The extractive provider quotes only an utterance that carries a section cue, and Check 4 warns only on clinician speech and only for numbers, names and medications (never a side or a negation). A material fact said in an uncued sentence — a patient's, or a clinician's side or negation (`syn-27` "Six weeks since the left hip replacement.", `syn-25` "So the right ankle.") — is therefore a silent omission whatever the transcription quality: under the shipped cues about 31 of the 50 encounters carry at least one (six of `syn-41` to `syn-50`) (for example "No locking" in `syn-07` and "No numbness" in `syn-09`, which were written for the contradiction axis). "N out of 10" never matches the cue "out of ten", and a cue in another sentence of the same line is lost if the recogniser splits the line at a pause. This is a fair measurement of the shipped pipeline and config. Decision 3.5 settled it with rule v1's call 1: the run of record uses the practitioner's own cue file in `validation\config`, so it measures routing as the clinic uses it; a material fact still unrouted under those cues fails the run and is a finding.
- **Expected uncertainty is the script author's prediction**, and reaches only words in the note: `low_confidence_source` sits on included words, so an `expect_uncertain` fact outside the note is reported missed. Every `expect_uncertain` fact sits in a clause the provider routes for its speaker (linted). A clean, confident and correct transcription of such a fact still counts as "uncertainty missed" under a rule that requires it.
- **A fact stated twice in its line** takes the worse occurrence: a note that carries the first statement but not the repeat reports the fact omitted.
- **Spoken contradictions** between two transcript lines raise no checker warning (the checker compares config and typed lines against the transcript); they are measured through the facts. Only `syn-07` to `syn-09` provoke contradiction-class warnings, through the validation config; encounters may also carry ordinary review warnings such as `high_risk_omission` and `low_confidence_source`.
- **Script length.** The alignment keeps two integer tables of (reference + 1) by (transcript + 1) cells: tens of kilobytes for a synthetic script, and roughly 130 MB for a 30-minute recorded encounter of about 4,000 words each side.
- **End of consultation and new patient.** Although three voices are installed, each script uses two, so the next patient speaks with the first patient's voice. The pipeline has no new-patient detection, and in five of the six such scripts (`syn-06`, `syn-20`, `syn-21`, `syn-38`, `syn-46`) the next patient's line carries a shipped cue in a section anyone's speech may fill, so that material `absent` fact is `wrongly_present` whatever the transcription quality (unless the practitioner's own cues leave that line unrouted): expected fails under rule v1, measuring the shipped behaviour — and only new-patient detection, which the pilot plan does not contain, could resolve them. In the sixth, `syn-43`, the next patient's line carries no shipped cue (the clinician's greeting before it does), so it fails only if the recogniser joins the two lines or the practitioner's cues route it.
- **Small talk and spoken instructions to the scribe.** The app has no spoken instruction to the scribe, so those lines and the content an instruction fences off ("Scribe, do not include the next comment") are `absent` facts. Small talk and the instruction lines themselves are `material: false` where a script gives them a fact (`syn-31`'s instruction line has none), so a leak of them into the note is counted, never failed, and a faithfully carried line is not "unsupported" either. The FENCED-OFF content is `material: true` since rule v1's call 2 (2026-10-07; `syn-05`, `syn-18`, `syn-19`, `syn-31`, `syn-40`, and `syn-47` since 2026-10-09): it is what the instruction protects, so its reaching the note is `wrongly_present` and fails the run — and since the app honours no spoken instruction, it will whenever that line carries a cue. A carried line can still fail as an unsupported clinical line when its transcription substitutes a structured-claim word ("twelve" written "12" in `syn-22`'s small talk).
- **The own-config refusal** compares paths as strings; a link to the app's folder under another name, an 8.3 short name, a `subst` drive letter or a `\\?\` or `\\localhost\c$\` form of the same path is not recognised.
- **Synthetic speech** is cleaner and more regular than a consultation room, and the set is synthetic only. Real voices are measured separately, by the clinic 1 smoke's kept consultations through `measure-speakers.py` (speaker labelling only — `speaker-measurement.md`); the harness never takes a real consultation (pilot plan Constraint 8), so its material-fact numbers have no real-speech counterpart.
- **Accent is a property of the voice, not of a script.** PLAN.md's validation list includes accents, but a script picks only a voice slot among the installed Windows voices, so an accent cannot be scripted. The set's accent coverage is the installed voices' own: all three are US or UK English (none Australian), and the patient of `syn-41` to `syn-50` is the UK voice (clinic-smoke plan D4). Rule v1's call 3, as amended 2026-10-09 (above), adds the real-speech half as one aggregate count kept off the repository.
