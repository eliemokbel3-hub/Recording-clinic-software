# Validation harness (pilot plan Phase 2)

An offline batch run of the shipped pipeline over synthetic encounters (it can also measure a recorded one — below — but the run of record is synthetic only since the clinic-smoke plan, 2026-10-09). It reports text-free quality numbers and a pass or fail against a pass rule decided BEFORE any run (pilot plan decision 3.5). It is a developer-build tool. It is separate from the shipping-gate run (`shipping-gate.md`): that run scores notes by hand inside the app; this one measures automatically against scripts.

Code: `desktop/src/scribe_desktop/validation.py` (script format, metrics, runner, report, command line) and `desktop/src/scribe_desktop/validation_set.py` (the synthetic set builder). Launchers: `scripts/run-validation.py` and `scripts/build-validation-set.py`. Tests: `desktop/tests/test_validation_metrics.py`, `test_validation_harness.py`, `test_validation_set.py` and `test_validation_scripts.py`.

## What goes in

A **set folder** holds three files per encounter, sharing one name:

- `<id>.json` — the encounter script (below). The name must equal its `encounter_id`.
- `<id>.wav` — 16 kHz mono 16-bit PCM (the `speaker_eval.read_wav_pcm` contract; nothing is resampled).
- `<id>.txt` — the timed Audacity label track `speaker-measurement.md` defines: one span per turn, labelled with its role, exactly one role `clinician`.

Since the metric amendment of 2026-10-23 (below) a synthetic set folder also holds the builder's `enrolment/` subfolder, one `slot-<n>.wav` per clinician voice slot its scripts use: the fixed passage the harness enrols each clinician voice from. The encounter listing skips it (a folder, never a set file).

A name with only some of the three is reported and counted as a set-level error, and any set-level error fails the run. Every name must be an encounter id (lower-case letters, digits and hyphens): a `.json`, `.wav` or `.txt` named otherwise is counted as one set-level error and never printed by name (it could be anyone's). A name that IS shaped like an encounter id is printed wherever the encounter is named (an incomplete triple, the report), so a recorded encounter's files take a neutral id, never a person's name. **"Role-play" in the harness's code and messages means a RECORDED script** — one without `conditions`, whose WAV and label track were made by hand rather than built — the name of the mock role-play set the pilot first planned. That set was retired on 2026-10-09 (clinic-smoke plan D1): no recorded encounter is part of the run of record, and a real consultation is never placed in a set folder (pilot plan Constraint 8) — a kept consultation reaches measurement only through `measure-speakers.py` (`speaker-measurement.md`). The behaviour is unchanged; the vocabulary stays. The harness reads only a folder's top level: a lone WAV there would be a set-level error and fail the run.

**The script** (`EncounterScript`, schema version 1): an id, an appointment type, the axis tags it exercises (PLAN.md's AI-quality list: negation, laterality, numbers, small talk, uncertain, contradictory, scribe instruction, end of consultation and new patient, noise, overlap, rate), the reference lines in start-time order (`role`, `text`), the expected facts, the checker warnings it is written to provoke (`expected_warnings`), and — for a synthetic script only — the conditions the builder applies (one voice slot per role, the speaking rate, the signal-to-noise ratio, the overlapped lines). Each fact names its kind (`laterality`, `dose`, `negation`, `absent`, `present`), its tokens (normalised words that occur together in its line), the line that states it, whether it is `material`, and whether its uncertainty is expected to be surfaced (`expect_uncertain`; refused on an `absent` fact, whose uncertainty could be surfaced only by its wrongly reaching the note). A script is refused by file name and field, never with its text.

The repository holds 50 invented scripts in `validation/scripts/` and the note config they are written against in `validation/config/`: the shipped defaults plus three autofill rules whose trigger phrases are spoken only in `syn-07`, `syn-08` and `syn-09`, so a confirmed config line contradicts what the patient said and the checker's warning is the expected result; before the run of record the practitioner adds their own cue file there (rule v1's call 1, below). Consent is spoken and routed to the consent section in `syn-10`, `syn-19`, `syn-26` and `syn-42`, each as a material fact (linted). A synthetic script picks its voices by slot, the voice's index in SAPI order on the computer that builds the set. The current voice baseline (clinic-smoke plan Task 0.3, 2026-10-09) is 0 = Microsoft David Desktop (US English), 1 = Microsoft Hazel Desktop (UK English), 2 = Microsoft Zira Desktop (US English): `syn-01` to `syn-40` use slots 0 and 2, and the patient of `syn-41` to `syn-50` is slot 1, the third installed voice — the synthetic set's accent coverage (clinic-smoke plan D4; linted: slot 1 is the patient of exactly those ten). `validation/rules/option-a-proposed.json` is decision 3.5's option (a) as data — ratified unchanged as rule v1 on 2026-10-07 (below). Invented content only: no real patient, consultation or recording is ever placed in a set folder (pilot plan Constraint 8).

## How to run it

From a normal terminal (never an agent shell — `docs/lessons.md`), on the developer build, with the installed app closed and the models downloaded by `scripts\setup-models.py`:

1. Build the synthetic set (three Windows voices installed, in the current voice baseline's order — above). First list the voices with their slots, in PowerShell, keeping the single quotes (a backtick-n inside double quotes would break the Python string):
   `.venv\Scripts\python.exe -c 'from scribe_desktop.validation_set import sapi_voices; [print(i, v) for i, v in enumerate(sapi_voices())]'`
   and build only if the name at slots 0, 1 and 2 equals the baseline. Adding or removing a voice can renumber the slots (adding UK English with text-to-speech under Settings, Time & language, Language & region moved Zira from 1 to 2 on 2026-10-09), and the builder checks only that a slot exists, so a renumbered inventory would build without any error in other voices; restore the inventory, or remap the scripts in a new commit, first. Then:
   `.venv\Scripts\python.exe scripts\build-validation-set.py validation\scripts <set-folder>`
   `<set-folder>` must be outside the repository (the builder refuses one inside it). `--only syn-01 syn-02` builds a subset; a name that matches no script exactly is an error (one that is not an encounter id is reported without its name, peer round 27). Recorded ("role-play") scripts — no conditions; none is in `validation/scripts` — are skipped and said so. A script file whose name is not an encounter id is counted as an error and reported without its name ("(a file not named as an encounter id)"), and nothing is written for it. Each file is written whole and then moved into place, the script copy last (the bytes that were rendered, read once) after the earlier copy is removed first, so an interrupted build leaves an incomplete triple the harness reports, never a mixed one. A role-play whose `<id>.json` is in the set folder, or a script there that does not load, is never overwritten: that script is refused by name. The builder also leaves an ownership mark, `<id>.built`, beside each encounter it writes (the harness ignores it): a WAV or label track without its `<id>.json` is rebuilt only when that mark is beside it (an interrupted build); without the mark it is someone's recording and is refused by name, untouched. A failed build removes a mark left with nothing beside it, but an interrupted one (Ctrl+C) can leave `<id>.built` alone, and a by-hand deletion can miss it: delete any leftover `<id>.built` before a recording uses that id, or the builder will treat the recording as its own. If a recorded script is ever added to a set folder (none is in the run of record, step 2), add its script before building into that folder, and never give it a `syn-` id. A write that fails (a file open in another program) is refused by name, saying which files to close or delete. A script that fails removes its earlier synthetic build from the set folder (never a role-play's files), so a stale build is never measured; a file that cannot be removed (open in another program) is named on the error line for you to delete. Last, the builder writes `enrolment/slot-<n>.wav` for every clinician voice slot the encounters it built use (`--only` writes only theirs; the metric amendment of 2026-10-23): the fixed passage `validation_set.ENROLMENT_PASSAGE`, spoken by that voice at the standard rate with a spoken turn's synthesis and level, written whole and moved into place. A slot that cannot be spoken or written is an error by name (`[error] enrolment/slot-<n>.wav: …`, its refusal text or an exception type), and its earlier file is removed so a stale one is never enrolled from; a file that cannot be removed is named for you to delete. The builder refreshes only the slots of the encounters it built this time: a slot no built encounter uses — after an `--only` build, or when an encounter's rebuild failed — keeps its earlier WAV, which other encounters in the folder may still use (the run of record is built whole into an empty folder).
2. Keep the set synthetic. Since the clinic-smoke plan (2026-10-09; D1, D5) the run of record adds no recording to the set folder: build into an empty folder, never into the smoke's measurement folder, and never put a kept consultation or an exported copy of one there (pilot plan Constraint 8). After the run delete the set folder — it is rebuilt from the repository at any time. (Until 2026-10-09 this step added the mock role-play recordings to the set under decision 3.6, now superseded.)
3. Run: `.venv\Scripts\python.exe scripts\run-validation.py <set-folder> --config validation\config --rule <rule-file>`
   Under rule v2 (a schema-2 rule file, below) add `--set <name>`, the set the folder was built from — one of the rule's set names (`scripts`, `heldout`, `heldout-2`, `heldout-3` in `validation\rules\rule-v2.json`): the set folder can be anywhere, so its path cannot name the set, and the rule's ceilings are per set. It is required with a schema-2 rule and refused with a schema-1 rule (validation-run6 plan D17). Run 6 is FOUR runs, one per set, each built into its own empty folder and run with its own `--set`. Under rule v3 (a schema-3 rule file, below) `--set` is required the same way, with five names (`scripts`, `heldout`, `heldout-2`, `heldout-3`, `heldout-4` in `validation\rules\rule-v3.json`); `--set heldout-4` with rule v2's file is refused, since rule v2 has no row for it. Run 7 is FIVE runs, each with `--rule validation\rules\rule-v3.json` and its own `--set` (the validation-run7 plan's P.1). Under rule v5 (a schema-4 rule file, below) `--set` is required the same way, with six names (`scripts`, `heldout`, `heldout-2`, `heldout-3`, `heldout-4`, `heldout-5` in `validation\rules\rule-v5.json`). Run 8 is SIX runs, each with `--rule validation\rules\rule-v5.json` and its own `--set` (the validation-run8 plan's P.1).
   Options: `--attribution enrolment|clustering` (default `enrolment`, the metric amendment of 2026-10-23; `clustering` is runs 1–5's reading, needs no speaker model and no enrolment WAV, and measures a recorded script), `--template-profile <id>` (default: the config's only profile), `--allow-small` (measure with Whisper `small` when `medium` is not installed; the report says so), `--model <name>` (the larger-model plan's D8: measure with that installed Whisper model, named as its folder in the models folder; never a fallback, named in the report; a measurement, never the run of record's model), `--prose` (also run the narrative prose stage and report its section counts; a stage that could not run — the model failing to load — is reported as `unavailable` and fails the run), `--suggestions off|confirm-all` (default `off`, the run unchanged; `confirm-all` asks the local model for a section for every left-out line before the next-patient boundary and adds every suggestion the chooser accepts before the note is finalised, with six more report columns — the metric amendment of 2026-11-09, below; a stage that could not run is reported as `unavailable` in each and fails its encounter).

Exit status: 0 only when the run passed — under a schema-2 rule, rule v2's verdict for the named `--set` (rule v1's verdict is printed beside it, never the exit status; the main table's Rule column and its TOTAL verdict are rule v2's too); under a schema-3 rule, likewise rule v3's verdict, with the R1 exemption as the file sets it (the verdict without the exemption and rule v1's are printed beside it, never the exit status; the Rule column and the TOTAL verdict are rule v3's); under a schema-4 rule, likewise rule v5's verdict (the verdict with marked R1 counted, the verdict without the exemption and rule v1's are printed beside it, never the exit status; the Rule column and the TOTAL verdict are rule v5's); 2 for a refusal before any encounter runs (models that cannot be loaded included, reported by error type only); 1 otherwise. The report is Markdown on standard output; redirect it to a file to keep it. A run stopped with Ctrl+C prints no report and no traceback, only one line naming the temporary folder to look in for a `scribe-speaker-eval-*` folder an interrupted teardown may have left — it may still hold its key — and asking you to delete it (exit status 1); stopped while the models load, it says so and nothing was run.

**Refusals, in order, each by name:** a packaged build; a set or config path that is not a folder; the app's own config folder (either channel — use `validation\config` or a folder of files you wrote, never a copy of the app's own); an unusable rule; a `--set` that does not fit the rule (given with a schema-1 rule; missing, or not one of its set names, with a schema-2 or later rule — the refusal lists the rule's set names and never prints the name typed); an unreadable or malformed config file (its error TYPE only — the loader's detail can quote the file); a config folder carrying the app's learned phrases or rules (a learned-phrase or learned-rule sidecar, or a `learned-` rule — the sign of a copy); a template profile that cannot be bound (an unknown `--template-profile`, or several profiles and none chosen); a models folder that cannot be located; no Whisper model installed (naming the models folder and the remedy); a fallback to `small` without `--allow-small`; the silero VAD model missing; `--prose` without the language model; `--suggestions confirm-all` without the language model; under the default attribution, the speaker-embedding model not installed (naming the models folder and the remedy); a set folder that cannot be listed; under the default attribution, an `enrolment/slot-<n>.wav` the set's scripts need missing ("rebuild the set"); models that cannot be loaded (their error type only); under the default attribution, the speaker model that cannot be loaded, or an enrolment WAV that cannot be enrolled — by error type, with the WAV format's help for a malformed file (never its path) and the enrolment's own fixed text for too little speech. A rule file over 64 KiB is refused, and a label track over 4 MiB fails its encounter (as the 256 KiB script cap does). The builder refuses a packaged build, a missing scripts folder, PyAV missing (it resamples every spoken turn), an output folder that is the scripts folder or lies inside the repository or inside either app data folder (`%LOCALAPPDATA%\ClinikoScribe` or `ClinikoScribe-dev`), Windows voices that cannot be listed, fewer than two installed voices, a set folder that cannot be created and a scripts folder that cannot be listed, in that order — before any voice speaks. The builder needs no model, so the models-folder refusal is the harness's alone (Task 2.7's reading).

## The declared policies (pilot plan D9)

- **Proposals:** every proposal is confirmed through the review surface's own `ui/note_review.build_resolutions`, and every pre-filled line the config decided stands — as if the practitioner confirmed every row and removed nothing. Because that confirms what a clinician might decline, the checker's warnings on the finalised note count against the encounter (the checker tally).
- **Body region:** the earliest detected prefill region.
- **Clinician speaker** (since the metric amendment of 2026-10-23, below): the enrolled pass's `enrolled_speaker` — the cluster the app's own speaker step gives the enrolled clinician voice — CONFIRMED by the label track. Two things must hold: `clinician_speaker` on the enrolled document returns that same label (each diarised segment takes its duration-weighted majority true label, `speaker_eval.align_segments`; the cluster whose majority is `clinician`); and the cluster's ACTUAL overlap seconds with the track (`validation.overlap_by_label`, summed per segment, never a segment's whole duration under its winning label) give `clinician` more than every other label together, by more than `ROLE_TIE_SECONDS`. Anything else — no enrolled speaker, a different cluster, a tie, or an overlap majority that is not the clinician — is "role unresolved": a failed encounter, never a guess. A missing enrolment is not this either: a synthetic script whose clinician slot has no `enrolment/slot-<n>.wav` refuses the whole run before anything is transcribed (exit 2, the refusal list above); a recorded script, which has no voice slot, is refused before it is transcribed and reported as an error (`EnrolmentMissingError`, below). Under `--attribution clustering` (runs 1–5): from the label track alone — the cluster whose duration-weighted majority is `clinician` (`validation.clinician_speaker`); no such cluster, or two holding the clinician's seconds equally, is "role unresolved".
- **Config:** the explicit `--config` folder only; files absent from it fall back to the shipped defaults. Learned phrases and learned rules live inside the app's own files (phrases merged into its `section_cues.json`, rules as `learned-` entries in its `autofill_rules.json`), so the harness refuses the app's folder and any folder that carries their marks; a learned rule would otherwise be confirmed like any other. Phrases already merged into a copied `section_cues.json` carry no mark and cannot be told apart, so never copy the app's files.
- **Model:** Whisper `medium`; `small` only with `--allow-small`, and another installed model only when `--model` names it (a measurement, never the run of record), named in the report either way. Since the gpu-decoding plan (Task A.2) `--device cuda` decodes on the NVIDIA graphics card (default `cpu`), named in the report as `<model>@cuda`; a card that cannot decode is refused, never replaced by the processor (a measurement, never the run of record).
- **Section suggestions** (since the metric amendment of 2026-11-09, below): `off` by default — no suggestion is asked for and the report is unchanged; under `--suggestions confirm-all`, every suggestion the chooser's ownership rule accepts is added before the one finalisation, as if the practitioner added every suggested line. Because that adds what a clinician might leave out, its cost counts against the encounter like the proposals' (the fact verdicts read the finalised note).
- **Writing style** (since 0.3.6, the note-content-design plan's D5): under `--prose` the stage is the Note tab's narrative stage, built by `ui.models.build_prose_stage` with the shipped clinical lexicon (`note_config.CLINICAL_EQUIVALENTS`), so it writes in the clinical register under prompt `narrative-v7`. The register is measured ONLY through the existing "Prose p/f/e" counts (`ProseCounts`, Check 5's own verdicts): no second fold, no new column and no report-format change. On the 50 under rule v5 they read 159 passed / 4 failed / 0 errored, equal to the pre-register baseline (prompt `narrative-v2`, the plan's Task 0.2) — the plan's Task R.6, run 3. What the prose SAYS is read by the practitioner over the fixture notes on `docs/testing/prose-register-scoring.md` (rubric `register-v1`), never by the harness; the fact verdicts never read prose.
- **Build:** the report names the commit (read from the `.git` files; it cannot tell whether the working tree differs) and the SHA-256 of `packaging/models-manifest.json`. Both are found from where the harness module sits, so they need the editable install of AGENTS.md step 2 in a plain checkout: from a linked worktree (where `.git` is a file) the commit reads `unknown`, and from a non-editable install both read `unknown` / `absent` and the set builder's in-repository refusal guards the virtual environment's folder instead of the checkout.

## What each number means (pilot plan D8, Task 2.3)

Everything is decided against the SCRIPT, through one word-level alignment: the script's reference tokens (its lines in order) against the transcript's words, by the edit distance that also gives the word error rate (`note.content_tokens`, then — since the metric amendment of 2026-10-11, below — canonical spelling, the same on both sides). Where several alignments cost the same, every one of them is considered and the worse outcome is reported.

- **Word error rate:** edit distance over the script's canonical tokens (its "Ref words"), per encounter and in total. From run 3 these are canonical-token figures: recorded beside runs 1–2, never compared with them (those runs compared the words before canonical spelling).
- **Spelling-normalised words** (the report's column right after WER, since the metric amendment of 2026-10-11): how many of the transcript's words canonical spelling rewrote — "500mg" counts 1, "five hundred" 2, "milligrams" 1, "500" and "mg" 0. The script's own rewrites are not counted. Recorded, never failing: it shows how much of a run's agreement rests on the amendment.
- **Unsupported clinical line:** a note line quoted from the transcript in which a side, number, dose, strength unit or negation word (`note_check`'s own token classes) is substituted or inserted on any equal-cost alignment after canonical spelling — so "500mg" against the script's "500 milligrams" is not a substitution, and a different value ("50" against "500") still is. Every one fails the run — except, under rule v3, a line the R1 exemption excuses (Rule v3, below); rule v1's verdict still fails every one. Other substituted or inserted words in note lines are counted only. Lines that came from the config are counted separately and judged by the checker tally.
- **Checker tally:** the count of each warning code on the finalised note. Any error-severity warning, and any `contradiction`, `contradiction_low_confidence`, `laterality_mismatch` or `dose_mismatch` the script does not list, fails the encounter. A listed code exempts every instance of it in that encounter, not only the one the script was written to provoke. A listed warning that did not appear is reported as "expected but absent", not failed — which is why `syn-08` and `syn-09` list `contradiction_low_confidence` beside `contradiction`: which of the two Check 2 raises depends on the recogniser's confidence in the evidence words.
- **Per fact:** `correct` (every token matched and carried in a note line — over canonical tokens since the metric amendment of 2026-10-11, so a fact the script writes "2 out of 10" is matched by a spoken "two out of ten"), `wrong` (some of its aligned words are in a note line, but not every token was matched and carried — a substituted side, dose or negation, or a fact carried only in part), `omitted` (no aligned word in a note line); for an `absent` fact, `correctly_absent` or `wrongly_present`. A canonical token made from two transcript words ("five hundred" read as "500") is carried in part when a note line holds only one of them. A fact stated twice in its line takes the worse of its occurrences. `warned`: one of the fact's own aligned words is outside every note line, flagged by the omission check's predicate for its speaker (`note_check._omission_flag_token` since the metric amendment of 2026-10-09, below), and its segment carries a `high_risk_omission` warning — a warning elsewhere in the segment never counts — or, since the metric amendments of 2026-10-22 and 2026-10-24 (below), the aligned word, never a suspect one, lies on a segment that an omission warning of either code (`high_risk_omission`, `clinician_line_omitted`) anchors, that the confirmed clinician spoke, that no note line touches and that lies before the next-patient boundary (Check 6's warning). `uncertainty_surfaced` (for `expect_uncertain` facts only): a `low_confidence_source` warning sits on one of the fact's aligned words, or — since the metric amendment of 2026-10-13, below — the fact is `correct`, its script line holds a spoken hedge and one of its aligned words sits under a `hedged_source` mark whose segment holds one too — since the metric amendments of 2026-10-22 each within the hedge scope: its own words, or a same-speaker neighbour joined mid-sentence (`validation.script_line_hedged` over the script, `note.segment_hedged` over the transcript); judged on its own, and surfaced only when EVERY equal-cost alignment, and every repeated statement of the fact in its line, surfaces it (so the alternative or statement that decides the verdict cannot hide a miss). "Not transcribed": every token was deleted by transcription.
- **Silent omission:** an omitted, material fact that was not warned — on ANY equal-cost alignment or repeated statement, so the worse outcome reported for the fact cannot hide one. A fact can therefore count both as material `wrong` and as a silent omission.
- **Silent (run-1 predicate)** (the report's column beside "Silent omissions", since the metric amendment of 2026-10-09): the same count with run 1's reading of `warned` — `note_check._is_high_risk_token` (numbers, names and medications) on the clinician's segments only. Recorded so a run can be read in run 1's terms; no rule reads it. Every silent omission is a run-1 one too, so it is never smaller. From run 3 it is evaluated on the canonical alignment (the metric amendment of 2026-10-11), so it does not reproduce run 1's own counts: it reads run 1's predicate, not run 1's spelling.
- **Silent (0.3.3 predicate)** (the report's column right after "Silent (run-1 predicate)", since the metric amendments of 2026-10-22 and 2026-10-24): the same count with 0.3.3's reading of `warned` — the widened predicate on the fact's own word under the segment's `high_risk_omission`, with no whole-line credit — kept across every equal-cost alternative as run 1's is. Recorded so run 6 can be read in run 5's terms; no rule reads it. Every silent omission is a 0.3.3 one too, so it is never smaller.
- **Residue class** (the Facts table's last column, rule v2): the residue classes the fact meets — `R1`, `R2`, `R3`, joined by `+` — or `-`; computed on every run, read only by a schema-2 or later rule (Rule v2, Rule v3 and Rule v5, below). The column prints `R1` for both kinds of R1 fact; a schema-4 report splits them in its residue section (Rule v5, below).
- **Surfaced (acoustic only)** (the report's column right after "Uncertainty missed", since the metric amendment of 2026-10-13): how many `expect_uncertain` facts the recogniser's low-confidence words alone surface — runs 1–4's reading, with no hedge credit. Recorded so a run can be read in those runs' terms, and so a fall in the recogniser's own surfacing stays visible; no rule reads it.

## Custody and privacy

Each encounter is transcribed in a temporary encrypted session store under a fresh DPAPI-wrapped key — the same helpers `measure-speakers.py` uses (`speaker_eval.transcribe_in_temporary_store` and `destroy_temporary_store`). The store is torn down key-first and probed; one that cannot be shown gone stops the whole run and names its path. The harness writes no audit row and no Past-sessions entry and reads none. The offline environment is applied and asserted before any model loads. The report holds ids, numbers, flags and closed vocabularies only — never a transcript, note or script line; an unexpected failure is reported by its exception type name.

## Known limits (residues)

- **Number and unit spelling.** Until the metric amendment of 2026-10-11 a number or unit the recogniser spelled differently from the script ("500mg" or "two out of ten" against "500 milligrams" or "2 out of 10") was a substitution of a structured-claim word, so its fact read `wrong` and its note line unsupported — most of run 2's wrong facts and unsupported lines. Since the amendment both sides are compared after canonical spelling (above), and what it leaves AS IT IS — still a substitution, so still a finding under rule v1 — is the residue: "hundred" or "thousand" with no spelled number before it ("a hundred"); ordinals ("second"), fractions ("one-third", "half") and spelled decimals ("two point five"); years ("twenty twenty-five"); "N hundred M" without "and" and "hundred and N" (only the "N hundred" part joins, so "two hundred and fifty" never matches "250"), and "twenty five hundred" (only "twenty five" joins); a unit outside the checker's strength-unit table ("units", "tablets", "µg"); a decimal written differently ("2.50" against "2.5"); a thousands separator ("1,000" against `syn-50`'s "1000", and "1,000mg" is not split — the split reads plain digits only); and a join cut by a segment boundary ("five | hundred" against "500" is a substitution plus an insertion) or by punctuation.
- **Medication names** are not structured-claim words in `note_check`'s classes, so a substituted medication name in a note line is counted, not failed, and shows in its fact's verdict.
- **Overlapped speech** is judged against one start-time order. Speech the recogniser drops, merges OR correctly transcribes in another order reads as not transcribed or substituted, and a displaced side, number or negation inserted into a note line makes it an unsupported clinical line — so a faithfully transcribed overlap can still fail. The seven overlap scripts (`syn-13`, `syn-14`, `syn-15`, `syn-27`, `syn-29`, `syn-36`, `syn-45`) are candidates for an expected fail; overlap is measured, not excused.
- **Repeated words beside a fact.** Where the reference repeats a fact's first or last word right beside it ("no, no numbness"), a transcript that drops or doubles the repeat has equal-cost alignments that disagree about the fact, and the worse is reported — a false `wrong` or an unsupported line on a faithful note. The scripts avoid it, and `test_validation_scripts.py` lints for it; a recorded script (none is in the set) could still contain it.
- **A dropped word inside a note line is not "unsupported".** Only substituted or inserted words make a line unsupported, so "there is swelling" carried for a spoken "there is no swelling" passes that test; only a script fact on the negation catches it.
- **Material facts in an uncued sentence.** The extractive provider quotes an utterance that carries a section cue and, since the note-routing-omissions plan's D11 (after run 2), one more: an uncued utterance that continues the same speaker's cue-routed utterance ending in a comma, semicolon, colon or dash — one hop, never into a clinician-owned section. Until 0.3.1 it read only the config's own cue file, and Check 4 warned only on clinician speech and only for numbers, names and medications (never a side or a negation), so a material fact said in an uncued sentence — a patient's, or a clinician's side or negation (`syn-27` "Six weeks since the left hip replacement.", `syn-25` "So the right ankle.") — was a silent omission whatever the transcription quality: under the shipped cues about 31 of the 50 encounters carried at least one (six of `syn-41` to `syn-50`) (for example "No locking" in `syn-07` and "No numbness" in `syn-09`, which were written for the contradiction axis), and run 1, under the practitioner's 26-phrase cue file, found 99 (above). Since 0.3.1 (note-routing-omissions plan D1–D2) the provider routes by the practitioner's cues first and then by the shipped cues, and a line still unrouted draws Check 4's warning when it carries a side, number, dose, strength unit, negation or medication from either speaker, or a name on the clinician's line — so such a fact is placed (possibly in the wrong section, below) or warned. What stays silent is a material fact in an uncued sentence with none of those words (`syn-48`'s "it is better" is the one the note-routing-omissions plan's text-level count found in the set) — since 0.3.4 only on another speaker's line, on a clinician's line the note quotes in part, on one whose every content word the guard marked suspect (that line draws no warning), or past a next-patient boundary: any other wholly unquoted line of the confirmed clinician's before any boundary draws Check 4's second code, `clinician_line_omitted` — one content word not marked suspect is enough for the LINE — and a fact on it is warned unless every one of the fact's OWN words was marked suspect, since the harness never credits a suspect word (Suspect segments, above; the metric amendments of 2026-10-22 and 2026-10-24, above). Since 0.3.3 (validation-pass plan D4) an uncued line that STARTS with a correction marker from the frozen list ("actually", "i mean", "i meant", "correction", optionally after "well") is carried too, under the same conditions as the comma carry (the same speaker, the previous line cue-routed and clean of suspect words, one hop, never into a clinician-owned section), so `syn-48`'s correction — its own segment after a full stop, opening with "Actually" — is predicted carried (the plan's Task 0.10); a self-correction opened any other way (the held-out `hld-16` and `hld-18`) stays silent unless Check 4 flags a word in it. Layering also quotes more: a next patient's line that carries a shipped cue now reaches the note whatever the practitioner's cues say (End of consultation and new patient, below), so those six encounters are run 2's expected routing residue, beside run 1's non-routing failures. "N out of 10" never matched the cue "out of ten" (the metric amendment of 2026-10-11 is the harness's comparison only — cue matching never canonicalises); since 0.3.2 (the invented-text guard plan's Phase 6, 2026-10-12, after run 4's diagnosis above) the shipped cues carry both forms, "out of ten" and "out of 10", in Outcome measures, so a pain score written either way is routed by the shipped layer wherever the practitioner's own cues route it nowhere — but a form the recogniser writes otherwise ("2/10", one token) still matches neither and the router still never reads "10" as "ten" (`test_note.py` `TestTheDigitScoreCue`). A cue in another sentence of the same line is lost if the recogniser splits the line at a pause; since 0.3.1 an unmatched score or such a split is caught only where the shipped cues route the line or it carries a word Check 4 flags (the score's numbers always are). Since D11 a split at a comma (or a semicolon, colon or dash) is carried when the first half was cue-routed for the same speaker (run 2's `syn-14`); a split with no mark at all (a bare cut), a split whose first half routed nowhere, and a clinician's split diagnosis, assessment, advice or plan line (an owned section, never a carry target) stay silent unless Check 4 flags a word. This is a fair measurement of the shipped pipeline and config. Decision 3.5 settled it with rule v1's call 1: the run of record uses the practitioner's own cue file in `validation\config`, so it measures routing as the clinic uses it; a material fact still silent under that routing fails the run and is a finding — from run 6, on a gate set (`scripts`, `heldout-3`) unless rule v2's R1 clears it within its ceiling, while on a reported set (`heldout`, `heldout-2`) it is reported and entered as a finding without deciding the gate (Rule v2, above).
- **Section placement is not measured.** A fact is judged by whether its words are carried in a note line, not by WHICH section carries them, and rule v1 has no section-placement line. A line in the wrong section also clears Check 4's omission warning, which counts coverage across every section. The limit predates 0.3.1, but the built-in fallback cues make a misplaced line likelier (an exercise-advice line that only a built-in cue routes can land in Presenting complaint, `test_note.py` `TestLayeredRouting`), and the bounded carry (D11) is a second cause: a carried line follows the section of the line before it, right or wrong (`test_note.py` `TestBoundedCarry`). Since 0.3.3 the self-correction carry (validation-pass plan D4) is a third: a line opening with a correction marker follows the line before it whatever its content, so an "Actually, …" that starts an unrelated point is placed with the previous point — misplaced, never lost, and not measured here. So run 2's and run 3's omission figures do not show that facts are in the right section; the clinician's own section review stays the control (note-routing-omissions plan, H4 round 20, PR-MED-019).
- **Expected uncertainty is the script author's prediction**, and reaches only words in the note: `low_confidence_source` and `hedged_source` both sit on included words, so an `expect_uncertain` fact outside the note is reported missed. Every `expect_uncertain` fact sits in a clause the provider routes for its speaker (linted). A clean, confident and correct transcription of such a fact still counts as "uncertainty missed" under a rule that requires it — unless, since the metric amendment of 2026-10-13, its script line and its quoted line both hold a hedge from the frozen list (since the amendments of 2026-10-22, within the hedge scope: their own words, or a same-speaker neighbour joined mid-sentence) and someone other than the confirmed clinician said it. What stays missed is acoustic only: a fact whose line holds no listed hedge (a hedge outside the list, or a listed hedge with other words inside it, is a known gap — the held-out set's `hld-19` and `hld-21` show the first and `hld-20` the second, as the plan's Task 0.10 predicted; the list widened from 16 to 33 on 2026-10-23), a hedge the recogniser dropped or moved into another segment not joined to the fact's mid-sentence (after a full stop, a bare cut or a segment between), the clinician's own hedged line (never marked), and any single-speaker transcript (its only speaker is the clinician). The mark is per line, so a hedge about a neighbouring clause of the same line still credits a fact on that line (the amendment's stated coarseness).
- **A fact stated twice in its line** takes the worse occurrence: a note that carries the first statement but not the repeat reports the fact omitted.
- **Spoken contradictions** between two transcript lines raise no checker warning (the checker compares config and typed lines against the transcript); they are measured through the facts. Only `syn-07` to `syn-09` provoke contradiction-class warnings, through the validation config; encounters may also carry ordinary review warnings such as `high_risk_omission` (and, since 0.3.4, Check 4's second code `clinician_line_omitted`, one per wholly unquoted line of the confirmed clinician holding a content word not marked suspect, before any next-patient boundary, and from 0.3.5 one per joined run of the pieces the recogniser split such a line into — both read by `warned`, the metric amendments above) and `low_confidence_source`, and — since the invented-text guard (0.3.2) — `number_source` (a quoted line holding a number) and `suspect_source` (a quoted line holding a word the guard marked as possibly not speech), one per line, and — since the validation-pass plan (0.3.3) — `hedged_source` (a quoted line someone other than the confirmed clinician said with a hedge from the frozen list — or, since 0.3.4, joined mid-sentence to a same-speaker line holding one), one per line, and Check 6's `possible_next_patient` (the note stops at a possible next patient), once per note. Those four are counted in the checker tally and never fail an encounter; a set with numbers in its scripts carries many `number_source` warnings by design. Metrics read them in three places, none failing an encounter on the warning itself: `hedged_source` feeds the uncertainty credit (the metric amendment of 2026-10-13, above); and under rule v2 the R1 class (recogniser residue) reads all four review marks — `number_source`, `low_confidence_source`, `suspect_source` and `hedged_source` (`REVIEW_MARK_CODES`) — requiring one on a word aligned to the wrong fact in every end state judged `wrong`, so a confidently misheard word on an unmarked line still fails (peer round 46 PR-LOW-002). Check 6's `possible_next_patient` is read for its segment only — the measured boundary, before which the flagged-line credit stops and whose absence R3 requires.
- **Script length.** The alignment keeps two integer tables of (reference + 1) by (transcript + 1) cells: tens of kilobytes for a synthetic script, and roughly 130 MB for a 30-minute recorded encounter of about 4,000 words each side.
- **End of consultation and new patient.** Although three voices are installed, each script uses two, so the next patient speaks with the first patient's voice. Until 0.3.3 the pipeline had no new-patient detection, and in five of the six such scripts (`syn-06`, `syn-20`, `syn-21`, `syn-38`, `syn-46`) the next patient's line carries a shipped cue in a section anyone's speech may fill, so that material `absent` fact was `wrongly_present` whatever the transcription quality (until 0.3.1, only when the practitioner's own cues routed that line too — in run 1 none did; from 0.3.1 the shipped cues routed it whatever those cues did): expected fails under rule v1 in runs 1–4. In the sixth, `syn-43`, the next patient's line carries no shipped cue (the clinician's greeting before it does), so it fails only if the recogniser joins the two lines or the practitioner's cues route it. **Since 0.3.3** (validation-pass plan D2–D6) the note stops at a possible next patient: at the first segment holding a greeting from the frozen list with a closing from the frozen list in one of the three segments before it, or at the segment after one that holds a closing and then a greeting, after earlier cued content (the threat model's Phase 3A surface 2, NEXT PATIENT, states the rule). Its lines are withheld from the provider, so their `absent` facts read `correctly_absent`; Check 4 still warns on their flagged words and Check 6 adds `possible_next_patient` — both review warnings in the checker tally, never failing. Predicted before run 5 (the plan's Task 0.10, ids only): the boundary on `syn-06`, `syn-20`, `syn-21` and `syn-43` and nowhere else; `syn-38` and `syn-46` hold no greeting from the frozen list (decision 0.2 (a) froze the lists unchanged), so they stay expected fails under rule v1 until a dated vocabulary amendment — under rule v2 (validation-run6 plan D14) each is one R3 encounter, within the 50's R3 ceiling of 2; `syn-43` already passed and gains Check 6. The boundary is a phrase heuristic, so a script whose closing or greeting uses other words is not cut, and a goodbye then a greeting inside one consultation would cut it falsely (a withheld line still flagged by Check 4 shows in "warned"). **Since the dated vocabulary commit of 2026-10-26** (validation-run7 plan D2, Task 0.4 (c); shipping in 0.3.5) the lists hold 30 closings and 26 greetings (14 and 12 before): 16 and 14 phrases proposed by an isolated session that saw no failing script, each attributed — from memory, unchecked — to a named published source family, and kept by mechanical rules written before it ran — the record of every phrase class accepted and rejected, with each rule's counts, is on that task (44 proposed; 13 already listed, 1 greeting rejected for a false cut on a seen `heldout` negative; none rejected on the two kept recordings, each assumed one patient). On the reference documents of every script of the four seen sets and the `heldout` edge cases (127 items: 92 negatives, 35 next-patient positives) the widening cuts no negative and no positive earlier than its expected boundary, loses no match, and changes nine held-out boundaries: eight now match (`hld-11`, two `heldout` edge cases, `h2-05`, `h2-09`, `h3-02`, `h3-12`, `h3-18`) and `h2-14` still diverges, one segment later; none of the 50's changes, so at text level `syn-38` and `syn-46` are still uncut (their run-7 class is predictions v3's, Task 0.6) — pinned in `test_consultation_boundary.py`, `TestVocabularyRule4` and the dated record `_BOUNDARY_PREDICTIONS_BEFORE_RUN7_0_4`. 16 positives still miss their expected boundary, 24 before the widening. Most of the gain rests on the two everyday closings "see you" and "thank you", which are also said mid-visit, and three accepted greetings hold "see you", so one greeting line can make the pair — a false cut is residue (b) of the threat model's NEXT PATIENT.
- **Small talk and spoken instructions to the scribe.** The app has no spoken instruction to the scribe, so those lines and the content an instruction fences off ("Scribe, do not include the next comment") are `absent` facts. Small talk and the instruction lines themselves are `material: false` where a script gives them a fact (`syn-31`'s instruction line has none), so a leak of them into the note is counted, never failed, and a faithfully carried line is not "unsupported" either. The FENCED-OFF content is `material: true` since rule v1's call 2 (2026-10-07; `syn-05`, `syn-18`, `syn-19`, `syn-31`, `syn-40`, and `syn-47` since 2026-10-09): it is what the instruction protects, so its reaching the note is `wrongly_present` and fails the run — and since the app honours no spoken instruction, it will whenever that line carries a cue — or, since the note-routing-omissions plan's D11, whenever it continues the same speaker's cue-routed line that ended at a comma, semicolon, colon or dash (the carry's named residue, pinned by the fixture matrix's `ex-comma-then-instruction`) — or, since 0.3.3's self-correction carry (validation-pass plan D4), whenever it opens with a frozen correction marker after such a line, however that line ended. A carried line can still fail as an unsupported clinical line when its transcription substitutes a structured-claim word with a different value ("twelve" heard as "twenty"); since the metric amendment of 2026-10-11 a spelling difference alone ("twelve" written "12", as in `syn-22`'s small talk in run 2) no longer does.
- **The own-config refusal** compares paths as strings; a link to the app's folder under another name, an 8.3 short name, a `subst` drive letter or a `\\?\` or `\\localhost\c$\` form of the same path is not recognised.
- **Synthetic speech** is cleaner and more regular than a consultation room, and the set is synthetic only. Real voices are measured separately, by the clinic 1 smoke's kept consultations through `measure-speakers.py` (speaker labelling only — `speaker-measurement.md`); the harness never takes a real consultation (pilot plan Constraint 8), so its material-fact numbers have no real-speech counterpart.
- **Accent is a property of the voice, not of a script.** PLAN.md's validation list includes accents, but a script picks only a voice slot among the installed Windows voices, so an accent cannot be scripted. The set's accent coverage is the installed voices' own: all three are US or UK English (none Australian), and the patient of `syn-41` to `syn-50` is the UK voice (clinic-smoke plan D4). Rule v1's call 3, as amended 2026-10-09 (above), adds the real-speech half as one aggregate count kept off the repository.
