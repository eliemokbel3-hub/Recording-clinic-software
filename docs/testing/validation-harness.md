# Validation harness (pilot plan Phase 2)

An offline batch run of the shipped pipeline over synthetic and mock encounters. It reports text-free quality numbers and a pass or fail against a pass rule decided BEFORE any run (pilot plan decision 3.5). It is a developer-build tool. It is separate from the shipping-gate run (`shipping-gate.md`): that run scores notes by hand inside the app; this one measures automatically against scripts.

Code: `desktop/src/scribe_desktop/validation.py` (script format, metrics, runner, report, command line) and `desktop/src/scribe_desktop/validation_set.py` (the synthetic set builder). Launchers: `scripts/run-validation.py` and `scripts/build-validation-set.py`. Tests: `desktop/tests/test_validation_metrics.py`, `test_validation_harness.py`, `test_validation_set.py` and `test_validation_scripts.py`.

## What goes in

A **set folder** holds three files per encounter, sharing one name:

- `<id>.json` — the encounter script (below). The name must equal its `encounter_id`.
- `<id>.wav` — 16 kHz mono 16-bit PCM (the `speaker_eval.read_wav_pcm` contract; nothing is resampled).
- `<id>.txt` — the timed Audacity label track `speaker-measurement.md` defines: one span per turn, labelled with its role, exactly one role `clinician`.

A name with only some of the three is reported and counted as a set-level error, and any set-level error fails the run. Every name must be an encounter id (lower-case letters, digits and hyphens): a `.json`, `.wav` or `.txt` named otherwise is counted as one set-level error and never printed by name (it could be anyone's). A name that IS shaped like an encounter id is printed wherever the encounter is named (an incomplete triple, the report), so name role-play files with neutral ids such as `rp-01`, never a person's name. A role-play folder made for `measure-speakers.py` loads once each recording has its `<id>.json` and its files are named by encounter id; keep the voice-enrolment WAV in another folder.

**The script** (`EncounterScript`, schema version 1): an id, an appointment type, the axis tags it exercises (PLAN.md's AI-quality list: negation, laterality, numbers, small talk, uncertain, contradictory, scribe instruction, end of consultation and new patient, noise, overlap, rate), the reference lines in start-time order (`role`, `text`), the expected facts, the checker warnings it is written to provoke (`expected_warnings`), and — for a synthetic script only — the conditions the builder applies (one voice slot per role, the speaking rate, the signal-to-noise ratio, the overlapped lines). Each fact names its kind (`laterality`, `dose`, `negation`, `absent`, `present`), its tokens (normalised words that occur together in its line), the line that states it, whether it is `material`, and whether its uncertainty is expected to be surfaced (`expect_uncertain`; refused on an `absent` fact, whose uncertainty could be surfaced only by its wrongly reaching the note). A script is refused by file name and field, never with its text.

The repository holds 40 invented scripts in `validation/scripts/` and the note config they are written against in `validation/config/`: the shipped defaults plus three autofill rules whose trigger phrases are spoken only in `syn-07`, `syn-08` and `syn-09`, so a confirmed config line contradicts what the patient said and the checker's warning is the expected result. Consent is spoken and routed to the consent section in `syn-10`, `syn-19` and `syn-26`, each as a material fact (linted). `validation/rules/option-a-proposed.json` is decision 3.5's option (a) as data. Invented content only: no real patient, consultation or recording is ever placed in a set folder (pilot plan Constraint 8).

## How to run it

From a normal terminal (never an agent shell — `docs/lessons.md`), on the developer build, with the installed app closed and the models downloaded by `scripts\setup-models.py`:

1. Build the synthetic set (at least two Windows voices installed — Settings, Time & language, Speech):
   `.venv\Scripts\python.exe scripts\build-validation-set.py validation\scripts <set-folder>`
   `<set-folder>` must be outside the repository (the builder refuses one inside it). `--only syn-01 syn-02` builds a subset; a name that matches no script exactly is an error. Role-play scripts (no conditions) are skipped and said so. Each file is written whole and then moved into place, the script copy last (the bytes that were rendered, read once) after the earlier copy is removed first, so an interrupted build leaves an incomplete triple the harness reports, never a mixed one. A role-play whose `<id>.json` is in the set folder, or a script there that does not load, is never overwritten: that script is refused by name. The builder also leaves an ownership mark, `<id>.built`, beside each encounter it writes (the harness ignores it): a WAV or label track without its `<id>.json` is rebuilt only when that mark is beside it (an interrupted build); without the mark it is someone's recording and is refused by name, untouched. A failed build removes a mark left with nothing beside it, but an interrupted one (Ctrl+C) can leave `<id>.built` alone, and a by-hand deletion can miss it: delete any leftover `<id>.built` before a recording uses that id, or the builder will treat the recording as its own. Still, add each role-play's script before building into the same folder, and never give a role-play a `syn-` id. A write that fails (a file open in another program) is refused by name, saying which files to close or delete. A script that fails removes its earlier synthetic build from the set folder (never a role-play's files), so a stale build is never measured; a file that cannot be removed (open in another program) is named on the error line for you to delete.
2. Add any role-play recordings with their scripts and label tracks to the same folder.
3. Run: `.venv\Scripts\python.exe scripts\run-validation.py <set-folder> --config validation\config --rule <rule-file>`
   Options: `--template-profile <id>` (default: the config's only profile), `--allow-small` (measure with Whisper `small` when `medium` is not installed; the report says so), `--prose` (also run the narrative prose stage and report its section counts; a stage that could not run — the model failing to load — is reported as `unavailable` and fails the run).

Exit status: 0 only when the run passed; 2 for a refusal before any model is built; 1 otherwise. The report is Markdown on standard output; redirect it to a file to keep it.

**Refusals, in order, each by name:** a packaged build; a set or config path that is not a folder; the app's own config folder (either channel — use `validation\config` or a folder of files you wrote, never a copy of the app's own); an unusable rule; an unreadable or malformed config file (its error TYPE only — the loader's detail can quote the file); a config folder carrying the app's learned phrases or rules (a learned-phrase or learned-rule sidecar, or a `learned-` rule — the sign of a copy); a template profile that cannot be bound (an unknown `--template-profile`, or several profiles and none chosen); a models folder that cannot be located; no Whisper model installed (naming the models folder and the remedy); a fallback to `small` without `--allow-small`; the silero VAD model missing; `--prose` without the language model; a set folder that cannot be listed. The builder refuses a packaged build, a missing scripts folder, PyAV missing (it resamples every spoken turn), an output folder that is the scripts folder or lies inside the repository, Windows voices that cannot be listed, fewer than two installed voices, a set folder that cannot be created and a scripts folder that cannot be listed, in that order — before any voice speaks. The builder needs no model, so the models-folder refusal is the harness's alone (Task 2.7's reading).

## The declared policies (pilot plan D9)

- **Proposals:** every proposal is confirmed through the review surface's own `ui/note_review.build_resolutions`, and every pre-filled line the config decided stands — as if the practitioner confirmed every row and removed nothing. Because that confirms what a clinician might decline, the checker's warnings on the finalised note count against the encounter (the checker tally).
- **Body region:** the earliest detected prefill region.
- **Clinician speaker:** from the label track — each diarised segment takes its duration-weighted majority true label (`speaker_eval.align_segments`); the cluster whose majority is `clinician` is the clinician. No such cluster, or two holding the clinician's seconds equally, is "role unresolved": a failed encounter, never a guess.
- **Config:** the explicit `--config` folder only; files absent from it fall back to the shipped defaults. Learned phrases and learned rules live inside the app's own files (phrases merged into its `section_cues.json`, rules as `learned-` entries in its `autofill_rules.json`), so the harness refuses the app's folder and any folder that carries their marks; a learned rule would otherwise be confirmed like any other. Phrases already merged into a copied `section_cues.json` carry no mark and cannot be told apart, so never copy the app's files.
- **Model:** Whisper `medium`; `small` only with `--allow-small`, named in the report either way.
- **Build:** the report names the commit (read from the `.git` files; it cannot tell whether the working tree differs) and the SHA-256 of `packaging/models-manifest.json`.

## What each number means (pilot plan D8, Task 2.3)

Everything is decided against the SCRIPT, through one word-level alignment: the script's reference tokens (its lines in order) against the transcript's words, by the edit distance that also gives the word error rate (`note.content_tokens` on both sides). Where several alignments cost the same, every one of them is considered and the worse outcome is reported.

- **Word error rate:** edit distance over reference tokens, per encounter and in total.
- **Unsupported clinical line:** a note line quoted from the transcript in which a side, number, dose, strength unit or negation word (`note_check`'s own token classes) is substituted or inserted on any equal-cost alignment. Every one fails the run. Other substituted or inserted words in note lines are counted only. Lines that came from the config are counted separately and judged by the checker tally.
- **Checker tally:** the count of each warning code on the finalised note. Any error-severity warning, and any `contradiction`, `contradiction_low_confidence`, `laterality_mismatch` or `dose_mismatch` the script does not list, fails the encounter. A listed code exempts every instance of it in that encounter, not only the one the script was written to provoke. A listed warning that did not appear is reported as "expected but absent", not failed — which is why `syn-08` and `syn-09` list `contradiction_low_confidence` beside `contradiction`: which of the two Check 2 raises depends on the recogniser's confidence in the evidence words.
- **Per fact:** `correct` (every token matched and carried in a note line), `wrong` (some of its aligned words are in a note line, but not every token was matched and carried — a substituted side, dose or negation, or a fact carried only in part), `omitted` (no aligned word in a note line); for an `absent` fact, `correctly_absent` or `wrongly_present`. A fact stated twice in its line takes the worse of its occurrences. `warned`: one of the fact's own aligned words is outside every note line, high-risk by `note_check`'s predicate, and its segment carries a `high_risk_omission` warning — a warning elsewhere in the segment never counts. `uncertainty_surfaced` (for `expect_uncertain` facts only): a `low_confidence_source` warning sits on one of the fact's aligned words — judged on its own, and surfaced only when EVERY equal-cost alignment, and every repeated statement of the fact in its line, surfaces it (so the alternative or statement that decides the verdict cannot hide a miss). "Not transcribed": every token was deleted by transcription.
- **Silent omission:** an omitted, material fact that was not warned — on ANY equal-cost alignment or repeated statement, so the worse outcome reported for the fact cannot hide one. A fact can therefore count both as material `wrong` and as a silent omission.
- **Ambiguous** (the report's column): a fact whose judged outcomes differed across equal-cost alignments or across its repeated statements in its line; the worse outcome is the one reported.

**Fixed failures (not part of the rule):** a harness error, a role-unresolved encounter, any unsupported clinical line, any checker failure and a requested prose stage that could not run. A rule file cannot relax them; changing one is a code change. **The rule file** (`PassRule`, schema version 1) sets the rest: the most material `wrong`/`wrongly_present` facts allowed (default 0), the most silent omissions allowed (default 0), whether every `expect_uncertain` fact must be surfaced (default yes) and an optional word-error-rate ceiling (default none). The rule is ratified as decision 3.5, recorded here as rule v1, and never adjusted after a run.

## Custody and privacy

Each encounter is transcribed in a temporary encrypted session store under a fresh DPAPI-wrapped key — the same helpers `measure-speakers.py` uses (`speaker_eval.transcribe_in_temporary_store` and `destroy_temporary_store`). The store is torn down key-first and probed; one that cannot be shown gone stops the whole run and names its path. The harness writes no audit row and no Past-sessions entry and reads none. The offline environment is applied and asserted before any model loads. The report holds ids, numbers, flags and closed vocabularies only — never a transcript, note or script line; an unexpected failure is reported by its exception type name.

## Known limits (residues)

- **Number and unit spelling.** A number or unit the recogniser spells differently from the script ("500 mg" against "500 milligrams" or "500mg") is a substitution of a structured-claim word, so its note line counts as unsupported. The scripts write doses as digits with the unit in full, as recognisers usually do, but a formatting difference still fails. Weigh this in decision 3.5.
- **Medication names** are not structured-claim words in `note_check`'s classes, so a substituted medication name in a note line is counted, not failed, and shows in its fact's verdict.
- **Overlapped speech** is judged against one start-time order. Speech the recogniser drops, merges OR correctly transcribes in another order reads as not transcribed or substituted, and a displaced side, number or negation inserted into a note line makes it an unsupported clinical line — so a faithfully transcribed overlap can still fail. The six overlap scripts (`syn-13`, `syn-14`, `syn-15`, `syn-27`, `syn-29`, `syn-36`) are candidates for an expected fail; overlap is measured, not excused.
- **Repeated words beside a fact.** Where the reference repeats a fact's first or last word right beside it ("no, no numbness"), a transcript that drops or doubles the repeat has equal-cost alignments that disagree about the fact, and the worse is reported — a false `wrong` or an unsupported line on a faithful note. The scripts avoid it, and `test_validation_scripts.py` lints for it; a role-play script can still contain it.
- **A dropped word inside a note line is not "unsupported".** Only substituted or inserted words make a line unsupported, so "there is swelling" carried for a spoken "there is no swelling" passes that test; only a script fact on the negation catches it.
- **Many material facts are omitted by construction.** The extractive provider quotes only an utterance that carries a section cue, and Check 4 warns only on clinician speech and only for numbers, names and medications (never a side or a negation). A material fact said in an uncued sentence — a patient's, or a clinician's side or negation (`syn-27` "Six weeks since the left hip replacement.", `syn-25` "So the right ankle.") — is therefore a silent omission whatever the transcription quality: under the shipped cues about 25 of the 40 encounters carry at least one (for example "No locking" in `syn-07` and "No numbness" in `syn-09`, which were written for the contradiction axis). "N out of 10" never matches the cue "out of ten", and a cue in another sentence of the same line is lost if the recogniser splits the line at a pause. This is a fair measurement of the shipped pipeline and config; weigh it in decision 3.5, and decide whether `validation\config` should carry the practitioner's own cue file.
- **Expected uncertainty is the script author's prediction**, and reaches only words in the note: `low_confidence_source` sits on included words, so an `expect_uncertain` fact outside the note is reported missed. Every `expect_uncertain` fact sits in a clause the provider routes for its speaker (linted). A clean, confident and correct transcription of such a fact still counts as "uncertainty missed" under a rule that requires it.
- **A fact stated twice in its line** takes the worse occurrence: a note that carries the first statement but not the repeat reports the fact omitted.
- **Spoken contradictions** between two transcript lines raise no checker warning (the checker compares config and typed lines against the transcript); they are measured through the facts. Only `syn-07` to `syn-09` provoke contradiction-class warnings, through the validation config; encounters may also carry ordinary review warnings such as `high_risk_omission` and `low_confidence_source`.
- **Script length.** The alignment keeps two integer tables of (reference + 1) by (transcript + 1) cells: tens of kilobytes for a synthetic script, and roughly 130 MB for a 30-minute role-play of about 4,000 words each side.
- **End of consultation and new patient.** With two voices the next patient speaks with the first patient's voice. The pipeline has no new-patient detection, and the next patient's line carries a shipped cue in a section anyone's speech may fill, so in all four such scripts (`syn-06`, `syn-20`, `syn-21`, `syn-38`) that material `absent` fact is `wrongly_present` whatever the transcription quality: expected fails under option (a), measuring the shipped behaviour.
- **Small talk and spoken instructions to the scribe: their facts never fail the run.** The app has no spoken instruction to the scribe, so those lines, and the content an instruction fences off ("Scribe, do not include the next comment"), are `absent` facts — marked `material: false` by the script author, so a leak into the note is counted, never failed, and a faithfully carried line is not "unsupported" either. A carried line can still fail as an unsupported clinical line when its transcription substitutes a structured-claim word ("twelve" written "12" in `syn-22`'s small talk). Whether fenced-off content should be material is decision 3.5's call.
- **The own-config refusal** compares paths as strings; a link to the app's folder under another name, an 8.3 short name, a `subst` drive letter or a `\\?\` or `\\localhost\c$\` form of the same path is not recognised.
- **Synthetic speech** is cleaner and more regular than a consultation room; the role-plays (pilot plan Task P.2) carry the real-voice part of the set.
- **Accents are not in the synthetic set.** PLAN.md's validation list includes accents, but a script picks only a voice slot among the installed Windows voices, so an accent cannot be scripted; only the role-plays (Task P.2) can carry one. Weigh this in decision 3.5.
