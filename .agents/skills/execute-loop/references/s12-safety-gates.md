## Safety gates — the loop PAUSES, it never bypasses

Every gate of the composed workflows is inherited and honoured. Under a headless/loop invocation the composed children pause on every MUST-PAUSE case and never auto-resolve it; only AUTO-DISPOSABLE candidates are auto-applied and logged, per the three-way contract below. What the COMPOSER then does with a surfaced item is governed by the composer-seat policy bullet below (`gates=`/`cap-raise=`): an auto-route there is ACT-AND-INFORM — journaled and notified, with CRIT and every operator-owned class still pausing (under a bound away grant, the stops and waits **Away mode** names) — so the loop still never BYPASSES a gate: it pauses or it acts-and-informs, never silently.

- **MUST-PAUSE (headless auto-disposition contract).** Under a headless/loop invocation, only AUTO-DISPOSABLE gate candidates flow automatically: direction is do-the-work (`Fix-now` / `Include in plan`) AND severity is LOW/MED AND not production-impacting — the executor applies its own recommendation and **logs** it. Everything else is MUST-PAUSE and surfaces to the user, never auto-decided: `Defer` / `Accept`; CRIT / HIGH; production-impacting (new dependency / env var / migration / deploy-config / parity drift); a `/fix` stop-on-failure; or genuine uncertainty. (This is the same three-way classification the composed gate skills carry — the CHILD-side contract, identical in every gate mode; in-executor `Fix-now` APPLICATION at any severity is likewise pre-existing child behavior identical in every gate mode, because headless `/fix`'s LOW/MED ceiling gates only skip-fixing dispositions. How the composer disposes of what SURFACES is the composer-seat policy bullet below.)
- **Composer-seat gate policy (`gates=` / `cap-raise=` / `high-auto=` — Loop-config-scoped, additive key-groups).** Three run-settings keys govern how the COMPOSER disposes of what REACHES it, and nothing else: `gates=strict|fix-biased|executor` (wizard DEFAULT `executor`, operator-set — an absent or malformed key still fails closed to `strict`; v33.0 D1) here, `cap-raise=ask|auto-plus-one|follow|executor` (wizard DEFAULT `executor`, operator-set — absent/malformed → `ask`; v33.0 D2), owned by **Termination**'s cap row, and `high-auto=on|off` (wizard DEFAULT `on`, operator-set — an absent key still fails closed to `off`; v32 D1) here — the run-level HIGH auto-route authorization that REPLACES the retired per-phase `[gates: high-auto-ok]` label grammar. **`gates=executor` (the executor-verified recommendation is FOLLOWED act-and-inform).** Under `gates=executor` the composer follows the executor-verified recommendation — read from the round's LEG-1 verified-tuple block or the record-and-end gate record, never from peer labels (the executor-verified triage bullet below) — act-and-inform, with the DISPOSITION-TIME pair (`OWNERSHIP: auto-disposition` + paired `NOTIFY:`; on loop step 4's verify-then-fix leg, v47.0, the pair is written after the leg's fix — the one such place) for: MED-and-below `Fix-now` / `Accept` / `Defer` / `Include-in-plan` (the `[pending-hardening]` append; `Accept`/`Defer` land as the recorded Accepted-Assumption / Deferred item with the executor's rationale), `docs-only` / `invalid` resolutions at any severity below CRIT, and HIGH `Fix-now` (carrying the existing `authority_check=`/`authority_epoch=` pair bound to the `high-auto` snapshot — the v32 TA.1 proof stays; `gates=executor` REQUIRES `high-auto=on`: the wizard writes both, and an explicit `gates=executor` beside `high-auto=off` is a `config-conflict` MUST-PAUSE at Preflight step 13). **Residual MUST-PAUSE under executor mode — this list is exhaustive and stated ONCE (Critical Constraint 1; the companion STICKY card and every other site point here, never restate):** a VERIFIED CRIT; production-impacting (new dependency / env var / migration / deploy-config / parity drift); scope expansion at ANY severity (doctrine unchanged: scope is the operator's dimension); a verified `regression` recommended `Accept`/`Defer` (auto-fix stays legal when in-scope and non-production); HIGH `Accept` / `Defer` / `Include-in-plan` (first field cycle — widening is retro-triggered); a `[decision]` task without `Chosen:`; the live-user-smoke pause; usage/auth exhaustion that neither the router's re-pick (under `router=on`, v41.0) nor `profile-fallback=` resolves (Usage-exhaustion recovery); `/fix` stop-on-failure; a missing, ambiguous, or conflicting executor recommendation; the executor-mode per-pass raise budget / `peer-max` ceiling (Termination's cap row, once per pass); `escape-check result=dirty` WITHOUT a fresh attribution (the Filesystem-escape check bullet); a preflight `config-conflict`; genuine uncertainty declared by the executor. Under a bound away grant the composer disposes most of this list itself — see **Away mode**, which states the four stops and the always-the-operator's items that still pause; the list itself is unchanged — and a scope expansion BELOW stop 2's line there (not CRIT, and `impact=none` on the executor's route record — **Away mode** → The four stops, item 2) is disposed under the grant while the use-time check passes, on the executor's recommendation (the disposition table's row); with no grant, an ended grant, or a failed use-time check this list's rule stands as written. ATTESTATION for executor mode: a SECOND run-start `OWNERSHIP: config-snapshot` record `key=gates value=executor` in the same policy log (Preflight step 13 — per-key hash `iso|plan|epoch|gates=<value>`, FIRST-wins PER KEY, its own `config-revoke key=gates` stream; the existing `high-auto` hashes are byte-identical) is REQUIRED ONLY for `gates=executor`: an executor-mode run whose `attest-check --key gates` (D12 — the ONLY attestation read; never a probe-log eyeball) is not `bound` + `value=executor` + unrevoked behaves as `strict`, while `strict` and `fix-biased` runs write NO gates snapshot and keep their contracts unchanged (a v33.0 composer resuming a v32.5-started `fix-biased` run stays `fix-biased`; `attest-check`'s `absent` for `key=gates` on a legacy-mode run is informational, never a downgrade). HIGH-route binding is UNCHANGED: `authority_check=`/`authority_epoch=` bind to the `high-auto` key ONLY — a gates snapshot never replaces the high-auto authority and a gates revoke never invalidates a HIGH route. **Mid-run toggle — "autonomy on|off" (D1; BOUNDED by run-start authority).** The operator message "autonomy off" (or an explicit key rewrite) is a MID-RUN-CHANGE (the `Loop config:` bullet, Visibility + run-state): one `config-change` record per changed key + the `Loop config:` rewrite; composer-seat keys bind immediately, a live executor keeps its spawn-time carry. "off" selects `gates=fix-biased; cap-raise=follow` (the operator may name `strict`/`ask` instead), ends an open away grant first (`away end … reason=autonomy-off` — **Away mode**), and RETAINS the run's authority records — a mode selection, never a `config-revoke`. "autonomy on" re-selects `gates=executor; cap-raise=executor` ONLY while the run's FIRST `key=gates` snapshot is `value=executor`, unrevoked, and its `high-auto` attestation is usable (`attest-check` on both keys) — i.e. a run that STARTED in executor mode and was toggled off; a run started `strict`/`fix-biased` (no gates snapshot exists — legacy modes write none), a poisoned first snapshot, or a revoked run CANNOT be enabled mid-run: the composer reports "executor mode needs a run started with it" and never appends a replacement or repair snapshot (authority is run-start and one-way). A `config-revoke key=gates` remains the explicit one-way disable no later toggle undoes. Scope is exact: the policy exists ONLY where `/execute-loop` resolves a `Loop config:` line; the composed child workflows keep their own contracts — v32.3 makes exactly TWO gate-relevant, precisely-scoped child edits (`/peer-loop`'s orchestrated-CODE early tail accept-close branch and `/fix`'s advisory fix-delta self-check line); `/review-loop` was byte-untouched by v32.3 (v47.0 adds one pointer sentence at its cap bullet — no gate change), and `/review`'s own v32.3 edits (the fan-out predicate + the exhaustive-siblings rule) change how findings are produced, never a gate seam — and standalone runs of those loops keep today's strict/ask behavior (standalone GATE behavior is unchanged by both edits: the early-close branch is inert standalone — it resolves no keys outside the orchestrated composer seat — and the fix-delta self-check, which binds every `/fix` leg, is advisory-only and gate-neutral). The composer seat is the three places findings/stops reach the composer for disposition: (a) peer-round findings verified and routed by the composer — every round of the default composer-seat `/peer-loop` topology and a dead opt-in executor's takeover round alike (loop step 4; the modal case live); (b) MUST-PAUSE gate records that record-and-end to the composer (the surfacing bullet below); (c) child cap-stops (Termination). Key ownership is EXACT and INDEPENDENT — every key combination is legal, which is why the restore is the PAIR: `gates=` governs seats (a) and (b) — findings, gate records, and the disposition of verified triage results; `cap-raise=` ALONE governs seat (c) (Termination's cap row, decided independently of `gates=` — exact for actual AT-CAP stops; the pre-cap early tail accept-close in Termination is the one gates-sensitive exception, requiring both validated keys); `high-auto=` MODIFIES the `gates=fix-biased` disposition table ONLY and is INERT under `gates=strict` (strict surfaces everything regardless of `high-auto`). `gates=strict` surfaces every seat-(a)/(b) finding and verified result to the operator — the surface-everything ceiling (the pre-v31 shape); strict auto-resolves NOTHING. `gates=fix-biased` auto-routes a seat finding to `/fix` (via loop step 4's TWO-LEG resume-first path: the verification-only leg returns the executor-verified tuple to the composer as durable round state BEFORE any `/fix` entry, and the fix leg fires ONCE) as ACT-AND-INFORM — journal `OWNERSHIP: auto-disposition gates=fix-biased` with the rationale AND fire the notify-at-gate notification (the operator can veto on wake) — ONLY when ALL of: verified severity ≤ HIGH, CRIT never — and a HIGH additionally requires the run-start-attested `high-auto=on` (Preflight step 13's `config-snapshot` record: FIRST-wins, identity-bound `config_hash=`, fail-closed on an absent/malformed/mismatched/revoked attestation — a HIGH under `high-auto=off`, an unattested `on`, or any prior `config-revoke` pauses exactly as strict, so every pre-v32 run and every unattested run is fail-closed by construction) — and a PASSING attestation is PROVEN on the record: the authorizing HIGH auto-route's `OWNERSHIP: auto-disposition` record REQUIRES the pair `authority_check=<config_hash>` + `authority_epoch=<prior valid revocation count>` (the record-side proof the authority check ran; grammar in the Journal line family, Visibility + run-state; elsewhere on `auto-disposition` the pair stays additive-optional); recommendation = Fix-now; inside the phase's DECLARED task list in the plan (in-scope keys on the declared tasks, never on the mere absence of a scope-expansion flag); and not production-impacting per the enumeration above (new dependency / env var / migration / deploy-config / parity drift). ALSO under `high-auto=on` (and only there; PR-HIGH-001): an **Include-in-plan recommendation — any severity below CRIT — auto-APPENDS the recorded task to the plan** act-and-inform, marked `[pending-hardening]`, and is NEVER built until a scoped `/review-plan` hardens it and removes the marker: RECORDING is automated; EXECUTION AUTHORITY is not — task selection in `/execute` and this loop's phase advance both REFUSE a marked task, the ONLY remover is a successful scoped `/review-plan` over the marked task(s) (the composer may run it at the next phase boundary; a failed or aborted hardening leaves the marker in place), duplicate appends are idempotent (one task, one marker), and the append is journaled + notified like every auto route (`OWNERSHIP: auto-disposition` + paired `NOTIFY:`). Everything else MUST-PAUSEs exactly as strict: every CRIT, `Defer`/`Accept` recommendations, scope expansion, production impact, `/fix` stop-on-failure, `[decision]` tasks without a `Chosen:` line, the live-user-smoke pause (the UX autonomy ceiling in every mode), usage-exhaustion recovery, genuine uncertainty. Stated plainly so the diff is never misread: under `gates=fix-biased` ALONE the auto-disposable set at the COMPOSER SEAT stays MED-and-below (plus docs-only/invalid triage) — HIGH joins ONLY when the run-start attestation `high-auto=on` is additionally in force, and `gates=strict` does NOT add an in-executor HIGH pause (that would need child edits, and is no part of this policy). Absent or malformed keys FAIL CLOSED to `strict`/`ask`/`off`; the restore pair `gates=strict; cap-raise=ask` reproduces the surface-everything ceiling per run (the pre-v31 shape; `high-auto` inert under strict; an absent key fails closed to `off`), and `gates=fix-biased; cap-raise=follow` reproduces the v32.5 shape. **The seat boundary, stated plainly (NEVER delegated):** composer-seat dispositions — the seat-(a)/(b) disposition of findings and gate records and the seat-(c) cap decision — are executed at the COMPOSER SEAT ONLY and are never delegated to an executor, a delegate, a peer, or any other spawned role: no spawned role applies a composer-seat disposition, records a MUST-PAUSE gate disposition on the composer's behalf, or raises a cap — a delegated in-session loop is BOUND to this same gate machinery (its findings, gate records, and cap-stops still reach the composer for disposition; delegation moves work, never the seat). ONE bounded exception from v47.0 — loop step 4's verify-then-fix leg: there the executor continues from its own verified tuples into `/fix` for MED and LOW plain `Fix-now` findings, on the composer's own brief line and its fresh `gates=executor` attestation read; the disposition RECORDS stay the composer's, written after that fix, and a finding outside the leg's conditions still reaches the composer before any edit. The in-executor `/review-loop`→`/fix` chain is a DIFFERENT seam with its documented pre-existing behavior — in-scope `Fix-now` application at any severity, identical in every gate mode (the child-side contract above) — and run scoring must never conflate the two seams. **Blind window (one line):** a RUNNING executor keeps its spawn-time carry until its activation ends — composer-side policy currency comes from the every-wake `Loop config:` re-read and the Resume contract's byte-verbatim revalidation, so a mid-phase `gates=`/`cap-raise=`/`high-auto=` change binds the composer immediately but reaches a live executor only at its next spawn/resume (a `high-auto` DISABLE additionally takes effect at the composer seat the moment its `config-revoke` lands — step 13's transaction); a policy change that must bind the CURRENT executor mid-phase requires hard-pause + respawn.
- **Executor-verified triage is the gate-routing authority (composer seat).** A peer's severity/recommendation labels are INPUTS, never routing truth — peer labels are demonstrably noisy (docs-wording findings arriving MED/HIGH; severity jitter across rounds, both run-evidenced). The verifying executor — resumed per loop step 4's VERIFICATION-ONLY leg (its record-and-end returns the verified tuple to the composer before any `/fix` entry — or, on step 4's verify-then-fix leg, v47.0, the same verified block is written before that leg's own first edit), holding the premium build context — re-classifies each finding WITH EVIDENCE: materiality = `docs-only | behavioral | regression | invalid` plus a verified severity, plus the `surface=` qualifier `production | test-harness | docs` — `test-harness` = EVERY target is a test/fixture/census/parity/guard-harness file and the materiality is non-production, EXCLUDING this repo's own validators by name (`scripts/loop-*-selftest.py`, `scripts/loop-grammar-oracle.py`, `scripts/loop-history-check.py`, `scripts/loop-observer/*-selftest.py` — a finding on those keeps `production` routing); every downgrade/upgrade carries a one-line evidence note journaled on the round, and the ORIGINAL labels stay recorded beside the verified ones (so `/retro` can measure label inflation). Two D9 disposition rules at the verify leg: (1) HARNESS TAIL — after the 2nd consecutive same-family round whose survivors are ALL `surface=test-harness` at MED-and-below, the executor's recommendation DEFAULTS to `Accept-with-record` (recorded on the tuple with the harness class named); the composer follows it under `gates=executor`, while a HIGH harness finding keeps its normal route (HIGH Accept pauses — the residual list); (2) RECORD-CURRENCY — a peer finding whose SOLE target is the currency of records the fix leg just refreshed (the handoff note, `Overall Progress`, `Last plan sync`, operator-order prose) is `invalid` at LEG 1 regardless of peer model — auto-resolved, no fix leg (`/peer-loop`'s prompt invariant (d) stays the prevention; this is the disposition when it leaks). Routing keys on the VERIFIED classification, under the `gates=` mode (the key that owns finding disposition): `docs-only` / `invalid` → under `gates=fix-biased`, auto-resolve (apply or refute), LOGGED AND NOTIFIED — every auto path fires the notify-at-gate notification as its paired same-ts/key emission, zero silent auto-actions — while under `gates=strict` they SURFACE with the verified classification attached (strict auto-resolves nothing); `behavioral` → the composer-seat policy above (under `gates=executor`, the executor's recommendation is followed for everything outside that bullet's ONE residual MUST-PAUSE list); any `regression` → never silently Accepted or Deferred (auto-fix under `fix-biased`/`executor` when in-scope and non-production, otherwise pause — a verified `regression` recommended `Accept`/`Defer` is on the executor-mode residual list); a VERIFIED CRIT always pauses in every mode; and scope-expansion routing is unaffected by materiality — scope is the operator's dimension.
- **Notify-at-gate (durable, deduped, PAIRED, tiered).** Every MUST-PAUSE surfacing — usage-exhaustion and `result=limit-death` classifications included — fires ONE desktop notification immediately: the operator must never need the host's work indicator to learn they're needed. TIER MAP (helper-computed from the record's `class=` — no new class, no new state): **critical** = `class=must-pause` (EVERY `reason=` — live-smoke, usage/auth, limit-death, `[decision]`, escape, and a SURFACED cap, which is a must-pause owner: the cap identity rides `key=`/`reason=`, never a cap class) and `class=config-conflict` — Linux `notify-send -u critical "execute-loop: operator needed" "<runkey>: <gate summary>"` (persistent by design); **informational** = every other class (`auto-disposition`, `docs-only`, `invalid`, `cap-raise`, `cap-accept`) — Linux `notify-send -u normal -t 20000 "execute-loop: <runkey> — done" "<what was done>"` (a 20-second expiry; the title says no input is needed); macOS `osascript -e 'display notification ...'` and the Windows PowerShell toast carry no urgency/expiry, so the tier degrades to the TITLE split there. URGENCY is orthogonal to MODE: `docs-only`/`invalid` resolutions are recorded `mode=queued` (the existing state — v33.0 moved them out of the immediate set) and delivered as the phase-boundary batch at the informational tier; auto `cap-raise`/`cap-accept` and HIGH auto-routes STAY `mode=immediate` but fire at `normal` with the done title. `notify=action-only` (the `Loop config:` key, exported at Preflight step 14 as `LOOP_NOTIFY`; absent → `all`) suppresses ONLY the batch desktop notice: the queue still SETTLES truthfully — each member's `batch-flushed` record carries `detail="policy-suppressed notify=action-only"` (no new state), a suppressed settlement is never a delivery or a successful retry, and under `all` a failed delivery leaves members `queued` exactly as today. RE-FIRE DEDUPE (a must-pause on a new idle-reentry epoch): `emit OWNERSHIP:must-pause … --log <probe-log> [--liveness <min>|off]` reads the log FIRST — the same qualified `key=` with an owner younger than the interval (default 10 min; `--liveness` needs `--log`, `off` disables) and no later `gate-disposition` REFUSES the whole pair with a named message (nothing written; the open gate keeps its existing owner + notice; narrate in chat only); past the interval on a new epoch the full pair fires exactly as today. The `LOOP_JOURNAL_NOTICE_CMD` override receives the same tiered argv (`-u <urgency> -t <ms> <title> <body>`); the observer applies the same tiers. Pre-existing contract (unchanged): Every MUST-PAUSE surfacing is also RECORDED: the composer writes `OWNERSHIP: must-pause ts=<iso> run=<runkey> key=<gate key> reason=<the actual routing leg>` PAIRED same-`ts=`/same-`key=` with that immediate `NOTIFY:` emission — every gate pair is ONE helper invocation (`python3 scripts/loop-journal.py emit OWNERSHIP:<must-pause|auto-disposition> --run <runkey> --role composer --log <probe-log> --epoch "<id>" [--round <n> --id <ID>] …` — `--log` PERSISTS both lines atomically to the probe log (without it the tool prints to stdout, unpersisted); the tool builds the qualified key, computes `mode=`/`class=`, fires the immediate desktop notice itself, and writes both lines atomically; the composer supplies only the judgment values) — the fail-closed route leaves a disposition record exactly as the auto routes do, `reason=` names the ACTUAL routing leg (never a blanket rule), and a considered-and-declined auto route writes THIS record, never a bare `skipped` token on `auto-disposition`. Every composer-seat auto route (a fix-biased route, a docs-only/invalid auto-resolution, an auto cap-raise) is act-and-inform with its `OWNERSHIP: auto-disposition` record and its `NOTIFY:` record written as ONE PAIRED EMISSION — together, with the SAME `ts=` and the SAME `key=`, at EVERY severity, at disposition time; a disposition without its same-ts/key pair is a violation, and bare counts or summary claims never substitute for the pair (the auto route's notification text states what was done, not that input is needed). The pair's human delivery is TIERED and TRUTHFUL, carried as two fields on the `NOTIFY:` record: a delivery MODE — `mode=immediate` for HIGH routes AND for auto cap-raises/cap-accepts (a run-topology event with no finding severity; immediate preserves the pre-v31 one-notification behavior — the desktop notification fires NOW) or `mode=queued` for LOW/MED routes and — from v33.0 (D5) — for the `docs-only`/`invalid` triage resolutions (no desktop notice yet; the phase-boundary batch delivers them) — and an outcome STATE in the verb slot recording what actually happened: `sent` (delivered now), `queued` (queued truthfully), `failed` (the delivery command errored; at most ONE `retried` per epoch may follow), `retried` (the single same-epoch retry that delivered), `batch-flushed` (delivered via a batch). At the PHASE BOUNDARY — BEFORE the phase's commit record, and on EVERY Termination stop path, which flushes before ending (round-4 S-C, DR4-2: an `OWNERSHIP: commit` with a queued-not-flushed member as of its APPEND position is the oracle's `queued-at-commit` whole-file violation, evaluated on the append-order log prefix, never by timestamp; the terminal queued-never-flushed assertion stays the backstop for commit-less stop paths) — the composer flushes all pending `queued` items as ONE batch via the helper — `python3 scripts/loop-journal.py flush --run <runkey> --role composer --log <probe-log> --epoch "<activation id>"` derives the queued-not-flushed member set from the RECORDS by qualified `key=` (the read-only `flush --dry-run` form exposes the same derivation for RESUME reconstruction) and emits the items named in the phase-boundary status line, ONE desktop notice, and one `NOTIFY: batch-flushed … key=<item-key> batch=<batch-key>` record per member, all members sharing that flush's single `batch=` key; on a failed flush the members STAY `queued` (one `failed` on the batch key, at most one `retried` per epoch), and a SUCCESSFUL queued-mode `retried` is followed IMMEDIATELY by the per-member `batch-flushed` records — only those member records clear the durable queue (a batch-key retry alone leaves every member reconstructible as pending) — a record never claims a delivery that did not happen. Gate identity is DURABLE, never remembered, and EPOCH-EXPLICIT: a FINDING-route gate's stable `key=` is the DR-3 qualified form `<runkey>/r<round>/<finding-ID>`, BUILT by the helper from `--round`/`--id` (never hand-composed — colliding bare keys were F-19; the runkey is phase-scoped, so the round segment alone disambiguates); topology gates (cap-raise, live-user-smoke, config-conflict …) keep the unqualified runkey + gate-class key — the gate's identity ACROSS epochs — and every non-`skipped` emission ALSO carries `epoch="<activation id>"` (the policy-record epoch-key precedent — `OWNERSHIP: config-snapshot`, and historically `label-snapshot`), so the append-only stream alone decides delivery legality — **the activation id, defined once, here:** it is the composer's own name for its current activation — one unbroken stretch of orchestration, a new one beginning at run start, at each Resume, and after an operator's gate decision (that decision record's `ts=` is the fresh one's anchor) — chosen by the composer when the stretch begins (a session with nothing to carry on from, a `/close-run` started by itself included, takes the clock read that begins it, as `date -Iseconds` prints it; any other token this run's logs have not yet used as an epoch — a leg id, a counter — serves as well) and passed unchanged as `--epoch` on every pair, notice and flush of that stretch, while the helper only requires it wherever the shape carries `epoch=` and tests it as it tests every value and for nonblank, never for what it names; each fire writes its `NOTIFY:` record — `NOTIFY: <state> ts=<iso> run=<runkey> key=<key> epoch="<activation id>" mode=<immediate|queued> [batch=<batch-key>]` (value sets pinned in the Journal line family, Visibility + run-state; the oracle asserts every admitted mode × state × key row and every legal transition) — and the every-wake sticky rehydrate consults those records: RESUME derives pending/queued notices from RECORDS, never memory; the same key + epoch dedupes (`NOTIFY: skipped` records the suppression), at most ONE `retried` per key per epoch, and a NEW resume/activation epoch permits exactly one re-fire/retry. The composer and any external observer (a harness watchdog) are SEPARATE emitters — two notifications during an observed run is expected, not a dedupe failure. **Record first, then ask:** the pause pair is written before the question is put, and the chat ask is composed from the block the helper prints once the pair is written — the rule, its no-output branch, and the `options=` key are stated once, on the companion STICKY card §7 (DISPOSITION-TIME item 1). **A live decision with no open pause:** an operator decision given live — in chat, while present — on a gate the run has not surfaced (no `must-pause` is open for that key) is recorded as its `must-pause` pair FIRST, the record of the question, and only then as its `gate-disposition`, the record of the answer; never a `gate-disposition` alone, which reads as a gate closed with no pause before it (the v35.0 rehearsal's `stage-1-hold`), and never a notice-free pause: the pair's notice still fires, and the ask it prints is answered in the same breath by the decision already given.
- **Live-user-smoke pause (mandatory).** On any UI-bearing or runnable phase, hard-pause for a live user smoke test before document + commit. This is the autonomy ceiling for UX — except under a bound away grant — see **Away mode**, whose away live smoke takes its place when `scope` has `smoke`. Feedback from this pause is never applied ad hoc and never composer-implemented — it routes through the smoke-feedback triage contract, its routing default, and the composer prohibition in loop step 6.
- **Premium boundary.** A `[executor: premium-only]` task inside a phase hard-stops per `/execute`; confirm the executor backend is on the intended tier before continuing.
- **Never auto-push.** Pushing is always the user's explicit call — the ONE carve-out, `/close-run` run by the operator or by an agent acting on the operator's request, is stated in **Run isolation (worktree-per-run)**, except under a bound away grant — see **Away mode**, under which the composer runs that same `/close-run` itself.
- **Filesystem-escape check.** Record the main checkout `git status` before and after every headless spawn; a peer should touch only the plan file, an executor only the phase's files. The check's destination is the probe log: the SPAWNING session writes ONE `OWNERSHIP: escape-check ts=<iso> run=<runkey> role=<spawned role> result=<clean|dirty> before=<digest> after=<digest> roots="base=<realpath>|<before>|<after>[; worktree=…][; external=…]" leg=<leg> [edit_surface=<root>:<changed|unchanged>] [attributed=<foreign iso> attributed_age=<min>]` record per HEADLESS ACTIVATION — COMPUTED, never hand-typed (F-04); v33.0 (D4) keeps `result=` in `{clean, dirty}` and adds two ADVISORY keys the helper derives: `edit_surface=` REPORTS the spawned role's declared edit-surface root (`worktree` for executor/architect/delegate under isolation — `--edit-surface`, wrapper env `LOOP_EDIT_SURFACE`; a peer declares none) as `changed`/`unchanged` while the `result=` verdict is computed over the OTHER roots ONLY — an executor's own worktree product is never an escape (102 of 345 field checks read `dirty` on exactly that) — and, on a `dirty` whose every changed root is base/external, `attributed=`/`attributed_age=` name a LIVE concurrent run when `--iso <this run>` (wrapper `LOOP_ISO`) is given and a foreign `-active` marker claims the changed checkout (different `iso=`, no `.complete-*` sibling, `checkout=` realpath-equal to EVERY changed root, its newest genuine `stage-*-probe.log` — `*harness-probe*` excluded — younger than 2× the liveness interval; `--liveness <min>|off`, wrapper `LOOP_LIVENESS`, the composer-resolved value passed to BOTH twins and the composer-run peer twin; liveness OFF ⇒ no freshness basis ⇒ never attributed; absent ⇒ the helper default 10) — attribution is KNOWN-WEAK (a live concurrent run, never proof of authorship). A peer's permitted writes ride `--allow-path <root>:<repo-relative path>` (wrapper `LOOP_ALLOW_PATH`, `;`-separated — quote the value in a shell, `;` is a command separator — the authoritative plan file + its `findings-*.md` sidecar): those exact paths are filtered out of that root's digest on BOTH captures, so a round append stays `clean` while any other worktree change stays `dirty`. Pre-existing contract, unchanged: wrapper-spawned roles get it from the WRAPPER (an unskippable spawn-window moment); `codex exec` peers and inline fallbacks get it from the helper twin (on a launcher leg BOTH captures are the launcher's: it runs the twin itself around its spawn, and the composer runs neither — the clean close's POST aside, Visibility + run-state → **`ROLE:` log lines** → Launcher legs) — PRE before the spawn: `python3 scripts/loop-journal.py escape-check --run <runkey> --role <spawned role> --capture pre --leg <leg> --log-root <dir> --root base=/abs [--root <name>=/abs …]`; POST after its exit (the SAME run/role/leg/root tuple, adding only the output log): `python3 scripts/loop-journal.py escape-check --run <runkey> --role <spawned role> --capture post --leg <leg> --log-root <dir> --log <probe-log> --root base=/abs [--root <name>=/abs …]` (a failed post is two exits — a git-status capture failure (exit 3) emits the `refused=capture-failure` record naming the root, while a `refuse()` on missing/malformed pre-state or a shrunk root set (exit 2) writes NO probe-log record, only a stderr diagnostic — the spawning session folds either to non-success and never claims a record that was not written) — with the two-sided evidence in DISTINCT machine-checkable fields: `before=`/`after=` are digests of the normalized main-checkout `git status --short` output, the `roots=` manifest binds EVERY root in this bullet's baseline (the main checkout always as `base`, the worktree under the isolation two-role split, every confirmed external read root), and `result=` must AGREE with digest equality across every manifest root EXCEPT the one named by `edit_surface=` (the oracle's amended agreement rule; an `edit_surface=` naming a root absent from `roots=` is a violation) — an unattributed `dirty` result routes to MUST-PAUSE (the composer rule above), and a run's manifest root set never shrinks mid-run. When the run carries confirmed cross-repo read roots (Preflight step 2), the baseline extends to each external git root — record its `git status --short` before/after the same spawns: an added root is an accessible filesystem surface for the spawned role, so a read-only-intent root is verified unchanged, never assumed. The check follows the **spawning session** — on the default composer seat the composer runs `/peer-loop`'s per-round checks; when an opt-in executor spawns peers in-session (loop step 4), the executor runs them itself. Under `isolation=worktree` the check runs the two-role split from preflight step 8: the WORKTREE's status is the edit-surface check (an executor's edits appear there — reported on the record as `edit_surface=worktree:changed|unchanged`, excluded from the verdict), and the BASE checkout's status is verified separately as the non-interference proof — an unexpected BASE change stops the loop just the same unless a fresh attribution under `gates=executor` auto-proceeds it (see **Run isolation (worktree-per-run)**); INVARIANT: under `isolation=worktree` EVERY spawned role — peers included — runs with cwd = the worktree (the one field run that spawned peers with cwd=base produced every base-side `dirty` in the corpus). An unexpected change stops the loop.
- **MUST-PAUSE surfacing from a spawned executor.** A spawned executor cannot block waiting for a human: when a MUST-PAUSE gate fires inside its run (including inside an in-executor peer pass), it records the open gate in the plan's `Current State / Handoff Note` and its final message — WITH its recommendation and evidence (a recorded gate without a recommendation line is an incomplete brief) — then ENDS its run; the composer relays the gate to the user and resumes per the disposition. This is the canonical definition — `/peer-loop`'s orchestrated mode points here. **Recommendation-first asks (D6).** Every surfaced gate's chat ask begins with `Executor recommendation: <disposition — evidence>` (read from the round's verified-tuple block or the handoff artifact; `none recorded` when absent) and `Composer recommendation: <…>`; option 1 = the executor's, marked "(recommended)". The gate's `OWNERSHIP: must-pause` record and the operator's `gate-disposition` record carry the optional `rec=<executor|composer>:<disposition>` key (helper value-safety-checked; the NOTIFY body carries it as `[rec=…]`), so the recommendation is durable on the record, never only in chat.
- **Inconclusive over unsafe.** If the cross-family peer cannot run, the peer pass is inconclusive — never fall back to a same-family peer.
- **Composer-shell failure — probe the degraded surface before pausing.** When the COMPOSER's own shell stops executing commands (distinct from an executor failure — e.g. repeated no-exit-status failures on trivial commands), probe whether subagent shells still work before pausing the run: a working subagent shell is a legitimate degraded surface for composer-owned duties (commits, smokes, spawn wrappers). Guardrails on the degraded surface: the subagent runs EXACT composer-specified commands only — no autonomous edits, planning, or scope discretion — and every existing gate is preserved unchanged (commit authorization, confirmed-grants-only — a permission the composer added under a bound away grant, recorded as `grant-add`, counts as confirmed (**Away mode**) — a SCOPED-tier gate: under `perms=bypass` there is no grant list and the close-table confirm was the entire injection gate, while every OTHER gate named here stands on both tiers — user confirmations, filesystem-escape checks — the composer still verifies the escape baseline from the subagent's reported `git status`). Record the degradation in the run-state note (Visibility + run-state) and continue; pause only when both surfaces are dead (observed live: the composer session's shell died post-handoff; a shell subagent performed the authorized phase commit and the run continued).
- **Composer duties are never asks.** Three duties are the composer's unconditionally and are never offered to the user as options: (a) monitoring/polling a spawned role — the wake layers named by the preflight-resolved `Wake:` line (Preflight step 10: the Layer-1 output watch, the Layer-2 monitor subagent, or the sleep-sentinel fallback — see the wake contract in Visibility + run-state) are armed at spawn, always, with the `WATCH: armed` artifact printed as proof ("Want me to start polling?" is the anti-pattern; observed live); (b) `/document` — performed per loop step 7 and at phases-done (see Termination), never offered as a menu item; (c) phase-boundary closeout + auto-advance — under `scope=all`, closing out a done phase (Run isolation → **Release groups** — task markers alone) and spawning the next phase's executor — and, at a finished release group, the group close and then the next group's executor (Termination → **Group end**: under a bound grant its merge is the composer's; attended, it waits for the operator's merge click and then proceeds) — is performed, never offered ("Say continue for composer closeout + the next spawn" is the anti-pattern; observed live). This clause removes duty-shirking asks ONLY: MUST-PAUSE gates, the live-user-smoke pause, user-only environment verification legs (e.g. a toolchain the agent's host lacks), usage-exhaustion recovery, and every Termination stop remain legitimate waits — except under a bound away grant — see **Away mode**, which says which of them the composer disposes.
- **The composer's own questions (stated once, here).** A question the composer puts of its own accord — one no gate, skill step, or wizard item owns — recommends, as option 1, the option that keeps the run moving (the autonomous defaults: away mode yes, `scope=all`, the next release group); under a bound away grant it is not asked at all — the composer decides it by **Away mode**'s disposition table (its "The composer decides" rows point here). A gate's own menu keeps its own recommendation (Recommendation-first asks, above).
