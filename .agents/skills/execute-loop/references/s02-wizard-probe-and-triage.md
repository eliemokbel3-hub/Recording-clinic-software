## Setup wizard (interactive, before preflight)

The wizard is a fixed script. Execute it with zero interpretive freedom:

- Ask the numbered questions in the exact scripted order below. Never skip an applicable question; never invent extra questions — in-script fallbacks (free-text entry, downgraded menus) and the `Q1R — keep or switch` interstitial are part of the script, not deviations. EVERY applicable wizard question AND the wizard's close confirm (the single confirm of **Close** below — not `/close-run`'s Step 5) follow **the structured-question contract**.
- **The structured-question contract** (the one statement; the wizard here, the pre-departure batch (**Away mode** → **The batch and the departure file**), and `/close-run`'s Step 5 confirm point to it by name and never restate it). The host tools: Cursor's `AskQuestion` and Claude Code's `AskUserQuestion`. Detection is ATTEMPT-based: ask the surface's first question through the host's tool and degrade only on a real call failure (retry once) — never on tool-inventory introspection (a composer false-negatived its own inventory live; the same acceptance-not-introspection rule as `--advisor` detection). On a successful attempt EVERY question of that surface rides the tool — one question per step, single-select unless a step genuinely needs multiple selection: `AskQuestion` takes one `questions[]` entry per step with a stable `id`, a human-readable `prompt`, and `options[]` of `{ id, label }`, and its answer is read from the returned `Question <id>: Selected option(s) …` block; `AskUserQuestion` takes the question and its option labels, and its answer is read from the tool's reply (a typed menu after a successful call is a contract violation, not a fallback — a step with more options than the tool accepts included: **Overflow**, below). **Chunking:** at most 4 questions per call and 2–4 options per question (`AskUserQuestion`'s limits; a batch is built to them on both hosts); a surface with more questions asks them over several calls in that surface's fixed order — still ONE batch, the calls back to back with nothing else between them. **Overflow:** a step with more options than the host's tool accepts STILL rides the tool — it is never asked as a typed menu. Its buttons are the 3–4 likeliest options, the step's recommended option first and the others in the step's own order; every option left off the buttons is named in the question's text, by the number or label the step gives it, so it can be typed; and the tool's own free-text answer ("Other") carries the typed choice. A typed answer that names exactly ONE of the step's options — a button's or one named in the text — selects it; one that names none, or more than one, is no answer, and the step is asked again through the tool. Where the host's tool offers no free-text answer, the last button reads `Other — I will type it`, at most three options ride the buttons before it, and choosing it is followed by ONE typed line, read the same way. No option is dropped on either path: each is on a button or named in the question's text. Degrade is LOUD, never silent: on the real call failure print the visible line `<tool> unavailable — using typed menus for <surface>` (for the wizard: `AskQuestion unavailable — using typed menus for this wizard`) naming the failure, then ask that question and every later one of that surface as typed numbered menus; a call failing mid-surface retries once, then degrades from that question onward under the same loud line; a host with neither tool (a Codex composer) prints the same line, with `structured-question tool` as `<tool>`, before the surface's first question. Free text stays free text on every path: an input a surface takes as free text (a model name, a path, a custom number, a correction) is a typed line, never a picker question — the tool's own free-text option ("Other", where it offers one) may carry a correction or an overflow option's name (**Overflow**, above), never replace the typed line.
- The **Profile** question is REQUIRED for every `claude -p` role: it downgrades (warning + default account + free-text entry) ONLY when no claude candidate passes the isolation probe and the run continues degraded — a failed candidate alongside a passing pinned one is a warning only, leaving the normal profile menu intact (Step 0's candidate rule) — and it never disappears. **Effort** default = **inherit**: offer it explicitly every time, never silently assume it, and pass NO effort flag unless the user picks a level (an explicit flag would silently override the user's own CLI config).
- Use the fixed terminology everywhere — **Role, Backend, Model, Effort, Profile** — mirroring the `ROLE:` log keys.
- Three artifacts are output obligations, not suggestions: the Step 0 probe report line, the numbered question headers (`Q1`, `Q1R` — when its interstitial fires — `Q1P-1`… on a preset path, `Q2`, `Q3a`…), and the close table + completeness line.
- The wizard configures the RUN'S ROLES; the composer is the live session running it — no wizard question ever asks which model the COMPOSER runs (the only live-session model question is Preflight step 4's, and only when the live session IS the executor).

**Step 0 — probe available models (mandatory, first; canonical definition).** Build each backend's model list from what is actually available right now — never hardcode a model list in this prose. **Script-first:** run `python3 .cursor/bootstrap/probe-models.py` from the repo root and consume its JSON by the module docstring's exact field names — FIRST asserting integer `probe_schema == 1` on every emission this wizard consumes (the lazy `--usage` / `--probe-advisor` runs included): a missing or different value is skill↔script version skew — stop loudly and point at re-running the bootstrap UPDATE ONLY, then re-probe; never consume the payload as schema-1 and never widen the manual fallback (its only trigger stays no-python) — then top-level `codex` / `claude` / `cursor` / `plans` / `report_line`, per-probe `status` values from its pinned vocabulary — rendering the menus and degradations below mechanically from the statuses: `absent` → omit that backend, `degraded` → that backend's menus fall back to free-text entry, `no-candidate-passed` → the environment-readiness pause, `skipped` → that optional probe was not requested (the usage and advisor probes stay behind their explicit flags). **Host and `python3`.** The same emission's `host` object names the host — `host.platform` is `win32` with `host.is_wsl` false on a WINDOWS-NATIVE host (Claude Code + Git Bash + Windows Python), `linux` with `host.is_wsl` true under WSL — and nothing else decides it (no shell detection recipe). The loops run on a Windows-native host from v45.0 with three differences, each stated at its owner: the Router is unavailable there (the router bullet below); every `LOOP_*` path is spelled `C:/…` and `LOOP_ADD_DIRS` is `;`-separated (Backends → the Spawn wrapper paragraph); and architect mode's `fold-delegation` containment carries a documented residual (Optional delegating executor → Log every delegation). `python3` on PATH is REQUIRED on every host — the helper, the spawn wrapper's shim, and the peer launcher run under it, and the shim refuses a spawn without it: Step 0 checks `command -v python3` before the probe, and an absent `python3` is a user-fixable stop with the exact remedy (Setup-remediation classification) — install Python 3 and open a fresh shell; on a Windows-native host the Microsoft Store `python3` alias, or a `python3.exe` on PATH (a copy of the installed `python.exe` under that name is enough; a host answering only to `python` or `py` does not satisfy it, and neither does a `python3.cmd` wrapper — Git Bash resolves no `.cmd` by a bare name; Git for Windows supplies the `bash` the grant shapes name) — the manual probes below can still build the report, but no run starts until `python3` resolves (every run's records are written by the helper under it). **Store-packaged Python (T4.5, Windows-native host only).** Once `python3` resolves there, read the interpreter the loop tooling will actually run — not `command -v` / `Get-Command` alone: `python3 -c "import sys; print(sys.executable); print(sys.base_prefix)"` (an App Execution Alias stub under `%LOCALAPPDATA%\Microsoft\WindowsApps` can point at a real install elsewhere, or at nothing). The installation is STORE-PACKAGED when `sys.base_prefix` lies under a `\WindowsApps\` directory (observed: `C:\Program Files\WindowsApps\PythonSoftwareFoundation.Python.3.13_…`). When it is, print ONE warning line — `Python: Store-packaged (<base_prefix>) — processes a Store-packaged Python starts have outlived the loop's Job kill on the test host: a timed-out or killed leg can leave survivors and held files` — then ask ONE question under the structured-question contract (above), three options: `1. Fix it now (recommended) — install the python.org build and point python3 at it`; `2. Continue as is — the residual is accepted for this run`; `3. Stop — I will fix it myself`. Never block on it: a headless or away run prints the warning and continues as option 2; off Windows, or with a non-Store Python, nothing prints. **The fix path (option 1 — the user's answer is the consent for the one install and its package agreements; interactive-only; verified on the test host in v45.1):** (a) `winget install --id Python.Python.3.13 --exact --scope user --silent --accept-package-agreements --accept-source-agreements --disable-interactivity` — the agent's shell answers no prompt, so the agreement flags belong to the command; the package prepends its directories (`…\Programs\Python\Python313\`, its `Scripts\`, and the launcher's) to the USER PATH, ahead of the `WindowsApps` alias directory (observed); (b) the python.org build installs `python.exe` and `py.exe` and NO `python3.exe`, so in a fresh shell `python` resolves to the new install while `python3` still falls through to the Store alias — provide the name the tooling invokes: copy the installed `python.exe` to `python3.exe` beside it (the shim runs `python3 -I`, the `.py` files `sys.executable`); then (c) RE-CHECK from a fresh Git Bash — `python3 -c "import sys; print(sys.base_prefix)"` — and report the outcome: a base prefix outside `\WindowsApps\` is the fix made true (observed: `…\Programs\Python\Python313`, and the forced Job kill that Store-Python processes had outlived then took every process of the leg), anything else is reported as still Store-packaged (never claimed fixed); the probe is then re-run. (d) Only when that re-check still names `\WindowsApps\` — a host whose SYSTEM PATH lists the alias directory, or whose user PATH was not prepended — tell the user to turn OFF the `python.exe` and `python3.exe` App Execution Aliases themself (Settings → Apps → Advanced app settings → App execution aliases — a Windows setting this skill never changes), or to move the install's directories ahead on PATH, and re-check again. Fallback (one line): when the host has no python 3, run the per-backend probes manually per the bullets below — they remain the canonical probe definitions on both paths; the script is their deterministic executor, not their replacement:

- **`codex`** (if installed): `codex debug models` returns a JSON catalog; offer the models with `visibility == "list"`, showing each slug, display name, and supported reasoning levels with the catalog default marked. (It is a debug subcommand — treat the JSON shape as version-dependent.)
- **Cursor subagents** (on a Cursor host): enumerate the composer's in-context allowed subagent slugs — no shell probe exists, and effort is encoded in the slug variants.
- **`claude`** (if installed): no catalog command exists — derive the current model aliases from `claude --help` (the `--model` description's examples name the latest aliases), offered alongside free-text full-name entry, with effort choices read from the same help output (`--effort`).
- **`claude` account profiles:** first **pin the binary** (v2 — enumerate, prefer native, probe-arbitrated): enumerate the candidate binaries (`which -a claude` plus the known nvm bin paths, e.g. `~/.nvm/versions/node/*/bin/claude`) and prefer the **environment-native** candidate — the preference keys on the composer's execution environment, not the project's location: under WSL a Linux binary beats a `/mnt/c/...` Windows npm shim even for a project on `/mnt/c/...`, while on native Windows the npm shim IS the native binary. The **bogus-dir isolation probe** below arbitrates: pin the preferred PASSING candidate and use that absolute path in every probe, login command, and spawn of the run (see Backends); warn about candidates that fail the probe — never silently pin a failing one. After pinning, **re-show the pinned binary's default-account identity** — the default account differs per binary (observed live: the shim's default ≠ the Linux binary's default), so never assume it carried over from a prior `Loop config:` line or an earlier pin. The **bogus-dir isolation probe** (the canonical isolation probe, run per candidate): `CLAUDE_CONFIG_DIR=/nonexistent-dir <candidate claude> auth status` MUST report logged-out — a still-logged-in answer means the env var is not reaching the binary (a read-side "does the env var change the answer" check is defeated once a login has written to the wrong store, so bogus-dir-must-be-logged-out is the only reliable shape). The probe script implements this same canonical probe per candidate — `claude.candidates[].isolation_probe` status `ok` = logged-out PASS (the only state that pins) / `failed` = still-logged-in / `degraded` = indeterminate / `timeout`, with `CLAUDE_CONFIG_DIR` auto-merged into `WSLENV` for a `/mnt/` shim candidate under WSL — so an indeterminate or timed-out candidate never pins on either path. On probe pass: always offer the **default account** first (no `CLAUDE_CONFIG_DIR` prefix; identity via the pinned `claude auth status` — its config root may live outside `~/.claude*`, e.g. Windows-side under WSL interop), then enumerate additional profile config dirs matching `~/.claude*` — applying the script predicate's semantics by hand: skip `*.lock`/control dirs, any dir carrying the `.quarantined-` marker, and malformed/non-directory entries (a credential-less stub is NOT excluded — the script surfaces it as a degraded row, and the manual path lists it identity-degraded the same way), then realpath-dedup the list against itself and the pinned binary's default root so ONE physical store lists once (the alias-dedup renderer duty holds on the manual path too) — and show each profile's bound identity via `CLAUDE_CONFIG_DIR=<dir> <pinned claude> auth status` — list identities (email / org), not directory names, for identity-bound rows. **Identity-DEGRADED pools stay listed:** a profile whose `auth status` binds NO identity — a credential-less stub, an indeterminate probe, or a token-seated pool reporting `Login: Expired — log in again` with a null email while inference still works (the setup-token status shape; that status line alone is never an auth failure — a setup-token credential carries no refresh token and no `user:profile` scope, so the CLI reports expired while inference works; when the distinction from a genuinely dead pool matters, verify with ONE cheap `-p` call — the v32 TD.2 rule; recipe in `docs/integrations/cross-agent-orchestration.md` → Cloud VM token pools) — surfaces as a degraded row, never dropped from any menu. Its display label comes from the profile dir's `profile-email.txt` marker when a VALID marker exists, read under the probe's bounded safe-read contract (a no-follow open of a REGULAR file inside the already-approved profile dir, bounded to one short UTF-8 line under the pinned email/display-label grammar; invalid, oversized, multi-line/control-character, symlinked, special-file, or unreadable markers degrade identity fail-silent — raw marker content never renders anywhere), shown marker-sourced (e.g. `ops@example.com [marker]`); with no valid marker the row falls back to the config-dir name explicitly marked `identity degraded` — the one case where a directory name is the legal display. Also probe each enumerated profile's usage — the script's `--usage` probe is LAYERED: ONE stream-json `-p "/usage"` call FIRST, reading exact print evidence from its result text or `rate_limit_event` threshold evidence → a tmux interactive-panel probe (unbilled, exact, seated-store-only) ONLY when that call yielded no exact evidence, a parsed panel outranking the threshold result → degraded; the accounts are probed in parallel (a bounded worker pool; the additive `--workers N` flag, never required); the manual no-python recipe stays `"<pinned claude>" -p "/usage" --output-format text </dev/null` with the profile's `CLAUDE_CONFIG_DIR` prefix (~2–7s per profile), knowing print-mode `/usage` returns exact quota lines on CLI 2.1.278 (verified live) and returned none at 2.1.226 on Cursor Cloud VMs — the probe tries the one-call print path first and falls back to the tmux panel only where print-mode is dark (on the manual path a dark row degrades; the panel/rate-limit recipes live in the orchestration doc's Cloud VM token pools subsection) — with LAZY timing: the default script run reports every usage entry `skipped`, and the wizard runs `python3 .cursor/bootstrap/probe-models.py --usage` (or manually probes just the profiles it needs; Q1R's capability-gated `--profile-dir` fast path is this same lazy probe in filtered form) only when a usage-displaying profile surface is actually about to display profile headlines — a Q3/Q4 profile menu or Q1R's keep-or-switch alike, per the Q3/Q4 menu-semantics paragraph's usage-surface rule (mid-run, the usage-exhaustion switch menu keys the same on-demand timing) — so the per-profile cost is never paid before a `claude -p` role is in play; keep the headline (session + week percentages AND their reset times) for those surfaces' profile rows; a failed usage probe degrades that profile's display to identity-only, never blocking the wizard. When NO candidate passes the probe, fire the **environment-readiness pause** — a MUST-PAUSE that is Step 0 probe-failure behaviour, not a new wizard question — with three options: **(1) user installs** the environment-native binary (`npm install -g @anthropic-ai/claude-code` under WSL node), then re-probe; **(2) agent installs** — ONLY after explicit user confirmation, and only after checking that WSL node/npm exist (absent → degrade to the user-install instruction), then re-probe; **(3) continue degraded** — default account only, with the consequences named up front: composer-run verification and no in-executor peer pass. A candidate that fails the probe while a passing candidate is pinned is a WARNING only — the pinned binary's normal profile flow (default account + enumerated profiles) proceeds untouched. Only on the continue-degraded path (NO candidate passed): warn and name the fixes (see the multi-account subsection in `docs/integrations/cross-agent-orchestration.md`) — the Profile question is still asked, downgraded to default account + free-text entry, with the warning that a free-text profile cannot bind on a binary that failed the isolation probe (the env var is not reaching it): a readiness-degraded run effectively uses the default account only, per the pause's stated consequences.
- **The account router — `claude-switch-route` (v41.0 router mode; detection in wizard prose on BOTH paths — the probe script never runs it, so the manual path and the script path do exactly this):** FIRST the host: on a Windows-native host (Step 0's `host.platform` / `host.is_wsl` read) the wizard makes NO router call at all — the router line below reads `Router: UNAVAILABLE — Windows-native host`, the Q5 Router item is not offered, and a stored `router=on` is written `off` (the router's own process census and private-cache checks have no Windows leg, and the scripts' collector needs `os.waitid`; every role runs on its Profile answer, as every run did before v41.0). On every other host each router call this skill makes runs under the composer's bounded runner — `scripts/loop-run-bounded.py` (Preflight step 15 publishes the runner, its recipe, and its per-call disposition table ONCE, and nothing here restates it; v45.0 retired the coreutils runner detection and the `UNAVAILABLE` reason it printed — the runner is a committed script, so no host lacks one). Then `command -v claude-switch-route` → its realpath (the value every `LOOP_ROUTE_BIN` export of the run carries — re-resolved at preflight and on every resume, Preflight step 15; never a PATH lookup inside the wrapper or the launcher) → the runner's permission read (Preflight step 15 — before each `--version` this wizard runs) → `--version`, which must print exactly `route_schema 1` (a missing command, a non-zero exit, a timeout, or any other text is NOT DETECTED: the item is not offered, nothing else changes) → `status --json`, read whole (the status read carries many records on a healthy store — never the pick's 4096-byte budget), for the report. Print ONE router line right after the probe report line: `Router: <on|off> · snapshot <fresh|stale> · dashboard <running|stopped> · picks: <model pick> / <other pick> / <codex pick> · records <n> (<ok|unreadable>)` from the object's `enabled`, `stale`, `server`, `picks`, `records`, and `records_ok` fields, plus — when the object carries a top-level `skipped` map (additive on `route_schema 1`: `{<class>: [{dir, reason}]}`, the candidates the router set aside) — one more segment at the line's end, ` · skipped: <dir> <reason>, …` (each folder once, in the object's order, as read, never interpreted; no map, or an empty one, prints no segment); `Router: not detected` when the command did not answer `--version`; `Router: status did not answer` when `status` timed out or did not parse (still DETECTED — the item is offered; the picks read as unknown); `records_ok` false prints `records unreadable` (Preflight step 15 turns that into `Router: UNAVAILABLE` and names the hand reset). A read with no Claude pick is a transient, not a failure, ONLY when ONE read is empty (the dashboard sweeps on its own cadence, and a read can fall between sweeps): the line prints what it read, and a wizard whose Step 0 read had no Claude pick reads `status --json` ONCE more just before the close table (the same bounded call). Two reads in which every Claude candidate sits under `skipped` as `no-reading` are SURFACED there, never called transient, on one line above the table: "the dashboard reports no weekly reading — check `claude-switch-route status --json`'s `skipped`" (detection is unchanged — the item stays offered and its answer stands, and a routed role runs on its fallback until the dashboard reads again; a router that prints no `skipped` map gives no reason to surface). Detection decides ONLY whether the Q5 Router item is SHOWN; the spawn-time rule — the call, the six refusals and the topology rule, the answer rule, the no-answer words — is the scripts' (the Spawn wrapper paragraph in Backends points at the wrapper's usage header, the one list).
- Omit backends whose CLI is absent (state the omission in the probe report). On ANY probe failure of a present backend, degrade that backend's menus to free-text entry — a failed probe never blocks the wizard, never removes a question, and never silently narrows a menu. Two `claude`-specific refinements: a failed claude CANDIDATE is not a backend probe failure while another candidate passes and is pinned — it is a warning only, and the pinned binary's menus stay full; and the environment-readiness pause above DOES pause the wizard when no claude candidate passes the isolation probe — every probe, login, and spawn of the run depends on that binary, so degrading silently is worse than pausing.

Print the REQUIRED one-line probe report, failed/absent probes included, with a REQUIRED fourth plan-scan segment on BOTH paths, e.g. `Probes: codex OK (4 models) | claude OK (aliases + 2 profiles) | cursor OK (in-context slugs) | plans: 1 Active candidate (offer: same as last run -- <plan>)`. Script path: print the script's preassembled `report_line` after replacing its single `{CURSOR_SLUGS}` placeholder — the one segment no shell probe can fill — with the composer's in-context slug summary; manual path: run pre-check (a) below FIRST (its result IS the fourth segment), then assemble all four segments from the bullets above. Then run the two silent pre-checks that shape Q1 — on the script path (a) is already computed as `plans.q1_offer` and is consumed, never re-run; on the manual path (a) has just run for the report line, so only (b) remains:

- **(a) Reuse lookup:** script path — render the offer MECHANICALLY from the script's `plans.q1_offer`, never re-deriving what the scan already decided: `offer=active` ⇒ offer "same as last run" naming its `plan`; `offer=archived` ⇒ offer it labelled "(from archived plan <name>)"; `offer=none` ⇒ omit the option (the `reason` is what the report segment states) — except when that `reason` reads `multiple Active candidates`: then Q1's option 1 reads `Same as last run — choose the plan`, and choosing it asks ONE question of the candidates under **the structured-question contract** (above; its Overflow rule when they are more than the tool accepts), rendered MECHANICALLY from `plans.active_candidates[]` — one option per entry, in the list's order: its `file` and its `loop_config` — before that plan's stored config is revalidated exactly as option 1 revalidates any reuse; every other `none` reason still omits the option. No script change and no new argument. The script applies exactly the rule below, heading-scoped and fence-skipping, with the `## Lifecycle State`-leads-`Active` filter load-bearing (a Completed plan still carrying a config line must never count). Rule (canonical; the manual path runs it by hand): if exactly ONE Active plan in `.cursor/plans/` has a parseable `Loop config:` line in its `Current State / Handoff Note` (grammar in **Visibility + run-state**), Q1 offers "same as last run" naming that plan; multiple Active candidates → the candidate menu above (on the manual path, its rows are the Active plans with a parseable `Loop config:` line). If NO Active plan qualifies, fall back to the single most recently modified plan in `.cursor/plans/completed/` with a parseable `Loop config:` line, offered labelled "(from archived plan <name>)" — the config is reused, not the plan; zero candidates in both locations → omit the option.
- **(b) Defaults feasibility:** Q1 offers "recommended defaults" only when this fixed selection rule resolves BOTH roles from the probes (defaults never pick live-session): executor Backend = Cursor subagent on a Cursor host, else the composer's own family CLI; peer Backend = the probed backend whose family differs from the executor's; Model per role = that backend's probe-marked flagship/default (codex: the newest `visibility == "list"` flagship at its catalog-default reasoning; claude: the first alias named in the `--model` help examples; Cursor: the executor family's newest premium slug at its highest thinking variant); Effort = inherit; Profile = default account. If the rule cannot pick uniquely, omit the option and say why in one line. The Profile leg carries a health gate: default account resolves for a `claude -p` role ONLY when Step 0's probe shows that account healthy (a resolved configuration with no `claude -p` role has no Profile leg to gate) — the pinned binary's `auth status` reports a bound logged-in identity; a logged-out or identity-degraded default makes "recommended defaults" infeasible, omitted via the same one-line-reason mechanism (a logged-out default offered on a defaults path died at the harness probe; observed live).
