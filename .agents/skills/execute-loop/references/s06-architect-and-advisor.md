## Optional delegating executor ("architect")

Default **OFF**. When enabled, the executor acts as an architect: it **designs, specifies, and reviews; the delegate implements against the approved spec**. The architect holds all design and judgment work, writes a short spec for each implementation unit, offloads the implementation to a designated same-family delegate, and verifies each delegate diff before proceeding. This is still billing-pool arbitrage + context hygiene (run the metered top model less; let the delegate absorb verbose implementation output), not capability tiering — the delegate is itself premium-capable — but the offload target is **most implementation**, not just bulk-mechanical work.

**Delegation posture (the run-settings key `delegation=conservative|broad`, the wizard's Q3d answer, carried to a spawned architect on its spawn prompt (a live-session architect reads it from the plan's `Loop config:` line); the rails per posture are stated ONCE here — the wizard, the close table, loop step 1, STICKY, and `/retro` point).** The posture governs WHAT the architect hands over; it changes nothing about how a delegate is spawned, verified, or logged, and no per-unit override exists. Under **`delegation=conservative`** (the default — today's rails) the heuristic is: delegate a unit only if you can specify it in a few sentences and verify it by reading the diff; keep it if verifying would cost as much as writing it. Under **`delegation=broad`** the test is specifiability alone: default-delegate EVERY unit the architect can write a spec for — security / auth and API-contract IMPLEMENTATION included (the contract itself is written into the spec), and "ambiguous logic" once the architect has resolved the ambiguity into the spec — and a diff whose verification approaches re-derivation is still delegated, the cost logged on the unit's `roi` record rather than used to withhold it (the heavier verification is the posture's price — "Expected outcome, honestly", below). Under BOTH postures the architect holds the triad — design decisions, the plan's `Critical Constraints`, and the diff verification — and delegation NEVER bypasses `/review-loop` or `/peer-loop`: these are the work a delegate cannot be specified into, because the spec IS the design decision.

Guardrails:
- **Delegable under `conservative`:** any unit with an architect-approved spec that is verifiable by reading the diff — including UI implementation from the architect's design spec (layout, component structure, visual language, states, interactions) — plus bulk/repetitive edits, mechanical refactors, test scaffolding, formatting, wide find-replace.
- **NOT delegable under `conservative` (architect-held beyond the triad):** UI design; security/auth; API contracts; ambiguous logic; subtle invariants where verifying ≈ re-deriving. Under `broad` every item on this list except UI design (a design decision — the triad) becomes delegable as IMPLEMENTATION once its decision is in the spec: the auth unit against the checks and threat model the architect states, the API contract as the spec writes it, the ambiguous logic as the spec resolves it, the subtle invariant with the invariant itself stated — the architect still verifies each diff (the triad). The downstream record is why the list exists in two forms: zero-delegation architect legs cite exactly these classes (`reason=none-eligible` — the constraint-implementing, API-contract, and auth tasks named as the whole remainder, no spec-backed unit outside them), while no logged miss across 226 downstream outcomes was attributed to delegate capability.
- The architect **verifies every delegate diff against its spec** before proceeding, and **logs misses rather than silently patching** them — under either posture (the triad above). The phase-smoke half of verification is backend-capability-split: a spawn-capable architect runs the smoke itself; for a headless architect the composer runs it and feeds the result into the delegation outcome log.
- **Log every delegation — per-shape channel.** Each decision (unit, spec one-liner, delegate backend/model) and outcome (diff verified / misses / smoke result) is a `DELEGATION:`-prefixed record in the CLOSED variant grammar (`decision|outcome|roi|smoke-addendum` — normative owner: the `DELEGATION_VARIANTS` constant in `scripts/loop-journal.py`, generated/verified from the checked-in `scripts/fixtures/delegation-variants.json`), reflected in the per-phase status line — and the record CHANNEL is per-shape. A LIVE-SESSION architect appends directly to the base-side role log `.cursor/loops/stage-<N>-executor.log`, creating the file if absent — the pre-existing contract, unchanged: its records live in the role log, never the new canonical file. A SPAWNED architect uses NEITHER stdout NOR the canonical file: stdout is not a record transport — the mandatory stream-json spawn shape JSON-escapes the tee, so the text survives but the line-start record shape `/retro` parses does not — and the canonical delegation file has ONE writer, the tool. The spawned architect appends its plain-text records to its ACTIVATION's staging file — the leg-keyed identity `stage-<N>-delegation.<leg>.log`, worktree runs under `<worktree>/.cursor/loops/`, `branch`/`none` runs at the flat base log root — whose ABSOLUTE path rides its spawn prompt. The COMPOSER pre-creates that staging file EMPTY, no-clobber, at the spawn boundary (channel-open — the pre-spawn intent-artifact pattern: later absence can never masquerade as "no delegations"), and at that activation's exit consume — BEFORE any teardown and BEFORE any generic worktree-record copy (Run isolation's staging exclusion) — runs `python3 scripts/loop-journal.py fold-delegation` to PROMOTE the staging bytes to the canonical `<log-root>/stage-<N>-delegation.log`: the tool is the canonical file's ONLY writer — validated (the closed variant grammar, bounded, snapshot-read), ACTIVATION-KEYED append-once under durable receipts (a retry verifies its receipt and no-ops; canonical bytes are never rewritten or truncated), COMPOSER-ONLY at the grant layer (spawned-role grants carry only the narrowed emission shapes — the wizard Close's Grants rule; under `perms=bypass` no grant boundary exists and the close-table confirm covers it) — and after a VERIFIED publication it RETIRES that activation's staging file to a non-corpus name, so `/retro` sees each admitted record exactly once. A MISSING staging file at exit consume REFUSES — retain + surface, never read as zero work (the fail-open loss class this transport closes); the explicit zero case is the still-empty pre-created file, which folds clean; a FAILED fold retains staging untouched and blocks a clean close. **On a Windows-native host** the fold's containment is NOT the POSIX guarantee and is never claimed equivalent: with no `O_NOFOLLOW` and no directory-descriptor walk there, the tool refuses a symlink or a junction at each component by a status check BEFORE the open and binds the opened file's identity AFTER it — the same refusal classes — which leaves a check-to-open window that a process able to create links inside the walked folders could race; architect mode runs there on that documented residual. **The delegate's gates (the gate rule, stated ONCE here; the wizard Close's Grants rule, Preflight step 6's failure print, and the body contract's gate clause point):** the architect writes each unit's EXACT executable gate COMMANDS, with their working directory, into the unit spec, taken from the repo's documented gates (`AGENTS.md` Local Run Steps; the governing plan's `Validation / Verification` section) — the Grants line's permission patterns are never copied into a spec as commands (they are not executable); on a scoped run those patterns must cover the quoted commands (the Grants rule); under `perms=bypass` the same command source applies with no coverage check; under `verify=composer` (Preflight step 6 failed) the architect quotes NO gate commands in the spec — the body contract's gate clause then yields no gate run — the unit's `DELEGATION: outcome` carries the free `smoke=` value `smoke=composer-run`, and the `smoke-addendum` carries the composer's result.
- Delegating mode **raises the cross-family peer pass's importance**: everything is one-family until the peer runs — when delegating, prefer the after-every-phase cadence, and skip `/peer-loop` only as the wizard-resolved cadence or an explicit user call licenses (the per-phase loop's cadence-is-config rule; delegating adds no composer discretion either way). The peer pass is the second reader the `broad` posture relies on: a `broad` run hands the cross-family reader more delegated units and more logged misses, so its cadence matters most there.
- Keep the delegate the **same model family** as the architect, so the cross-family peer coverage (keyed to the architect) stays clean.
- Under `conservative`, delegate **bulk, not trivial one-liners** (coordination cost outweighs the gain); under `broad` that cost is packaging advice, never an eligibility test — bundle small specifiable units into one delegation rather than keeping them on the metered seat (the architect-held triad is unchanged).
- Needs a **spawn-capable architect**. Verified spawn paths: a live session; a top-level Cursor subagent (subagents carry the full toolset including Task — nested spawn verified); or a `claude -p` session via Claude Code's **native subagent tool** — with the delegate model pinned via an AGENT DEFINITION, never the tool's `model` parameter. **Delegate-pin contract (`claude -p` architect).** The native subagent tool's `model` parameter is a closed ALIAS enum (`sonnet | opus | haiku | fable`): it cannot express a model ID, and aliases are ACCOUNT-RESOLVED, so an alias pin is a silent-tier-substitution hazard by construction (observed live downstream: `model="opus"` resolved to a 4.x tier — ~$9.30 of delegate spend on the wrong model, caught only by a post-hoc `modelUsage` read while the `Loop config:` line sat "satisfied"; correcting to the full ID hard-failed parameter validation, and the architect — rightly, under its no-silent-substitution instruction — performed ZERO delegations and self-implemented the leg on the metered model). The pin that works: a wizard-resolved agent definition whose frontmatter carries the FULL model ID, selected per spawn as `subagent_type: "<name>"` with NO `model` parameter passed — the enum never applies and the frontmatter model binds (verified downstream: the first verified spawn plus eight more across three later legs — 9/9 — resolved to the pinned tier). **Precedence — stated ONCE here (Claude Code's documented subagent resolution orders, current since v2.1.251; the pre-2.1.251 order put the environment variable FIRST, and the v31.1 sentence that recorded it is superseded by this one):** MODEL — a per-invocation `model` parameter, then frontmatter `model:`, then the `CLAUDE_CODE_SUBAGENT_MODEL` environment variable, then the session's model; EFFORT — the `CLAUDE_CODE_EFFORT_LEVEL` environment variable, then a per-invocation `effort` parameter, then frontmatter `effort:`, then the session's effort. The pins hold only while the sources ahead of frontmatter stay absent: the spawn passes NO `model` parameter (above) and NO `effort` parameter (named here only as what the architect must NOT pass — it would override the pin, and it stays in effect across a resume), and the architect's spawn environment must NOT set `CLAUDE_CODE_EFFORT_LEVEL` (it beats the effort pin), `CLAUDE_CODE_SUBAGENT_MODEL` (BEHIND the frontmatter since 2.1.251 — asserted unset so a pre-2.1.251 CLI's order cannot bite), or `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` (while on, the `model` field of every definition is IGNORED and no model can be passed at all — the model pin is void) — the three variables asserted unset at Preflight step 5 — and same-name definitions SHADOW the intended one (in-directory duplicates resolve by filesystem read order, nested project scopes by closest-to-cwd, managed definitions win outright) — prefer a run-distinctive name; the first-delegation `modelUsage` read below stays the AUTHORITATIVE check precisely because precedence can defeat any file inspection. The composer writes/updates the definition at preflight, before the phase-1 spawn, from the wizard-resolved delegate model. Location (wizard-surfaced choice, close-table-visible): default is PROFILE-LEVEL — `<architect profile_dir>/agents/<name>.md` under the architect's resolved `CLAUDE_CONFIG_DIR` (a native-subagent delegate runs inside the architect's session, so THAT profile's agents dir is the one consulted; a default-account architect has no profile dir — its agents dir is `agents/` under the binary's default config dir, the leg's EFFECTIVE config root: `$CLAUDE_CONFIG_DIR` from the composer's own environment when set, else `~/.claude` — the wrapper preserves an inherited `CLAUDE_CONFIG_DIR`, so the launched CLI consults that dir; the writer (Preflight step 5), the CLI's discovery, and Preflight step 6's transcript reader share this ONE root) — isolation-immune and outside the product changeset; the project-level `.claude/agents/` alternative is version-controlled but enters the product diff and must exist INSIDE the worktree under `isolation=worktree`. Under `router=on` the project-level location is FORCED: a routed architect's `CLAUDE_CONFIG_DIR` is whichever folder the router answers at spawn time, so a profile-level definition would have to exist in every candidate store — the wizard writes `agent_loc=project` without asking (Q5's Router item) and preflight step 5 writes the definition there. Frontmatter: `name`, `description`, `model: <full model ID>`, `effort: <level>` (the Q3c Effort answer; OMITTED for `inherit`, a value the field does not take), `tools` (WITHOUT `Agent` — the one hard narrowing: no nested delegation; the delegate otherwise runs under the architect's permission context, so the close table's Grants proposal is its grant set too — the Grants rule at the wizard Close); body = the **delegate body contract**, stated ONCE here (Preflight step 5 writes the body from it and restates none of it): implement the architect's spec literally, report ambiguity rather than resolving it, touch nothing the spec doesn't name, never commit or advance a ref; run ONLY the gate commands the spec quotes, as single lines, verbatim — never a variant, never a widened scope to make them pass; report each result; never run the loop's record-emission or spawn shapes — records are the architect's. **Resolved-model-as-artifact:** after the FIRST delegation of each leg, read the delegate's resolved model from the result `modelUsage` and REPORT it — a mismatch against the `Loop config:` `delegate=` group is a CONFIG ERROR (fix the definition, re-verify before the next delegation), never a tolerated degradation: the config line records intent; only `modelUsage` records the resolved tier — and it records the SESSION's aggregate, CUMULATIVE across resumes (the result event `/retro`'s last-per-session cost rule reads), so the entry is attributed to the delegate only when no other participant could have produced it: not the architect's own resolved model, not a Mechanism-N advisor's (Optional advisor — excluded only on a comparable identity: a distinct full ID, or an alias of another family; an alias in the pin's family leaves the entry unattributed), and on a `--resume`d architect not an earlier activation's delegate — attributed on a fresh session, or when the pin was ABSENT from the previous activation's last `result` record; otherwise the read is "present, unattributed" — reported, never a confirmation (Preflight step 6's probe takes the `unverifiable` verdict there, reason `model ambiguous`; this first-delegation read reports the same limit). **`[1m]` caveat:** a full-ID pin may resolve to the account's 1M-context variant, whose above-200k-input requests can bill at long-context rates — keep delegate packages bounded (an observed package hit 164k tokens; treat ~200k input as a ceiling to stay under, not headroom). **Delegate effort:** the effort pin is the frontmatter `effort:` above, selected per spawn WITH the definition — the delegate runs at the pinned level, or at `inherit` = the architect session's EFFECTIVE effort (its own `--effort` flag; under `router=on` with the architect itself at inherit, the routed profile's own settings — the Q5 Router item's advisory); the delegate's account profile is the architect's (the location rule above). The configured value records intent; Preflight step 6's probe reads the delegate's RESOLVED effort from its transcript on every run, the same way the `modelUsage` read above records the resolved tier. The architect never resumes a delegate — each unit is a fresh spawn: the pin is creation-time evidence (the docs state only that a PASSED `effort` parameter persists across a resume; what a resumed delegate's later requests carry is unobserved — step 6's reader refuses a MIXED-effort transcript and detects no resume as such, so the rule is the architect's duty, not the reader's proof). A shell-capable architect may alternatively delegate by invoking `claude -p` directly — there `--model <full ID>` pins exactly (the CLI flag, unlike the tool parameter, accepts IDs), and the flag is REQUIRED on every such invocation: an unflagged `claude -p` runs the account default; add `--effort <level>` when a level is pinned (the ONE place delegate effort rides a flag), and for `inherit` pass no `--effort` — the account default applies there, NOT the architect's effort (a shell-invoked `claude -p` is a separate session, not a subagent of the architect's). `codex exec` is NOT a verified architect spawn path in v32.3 — a scope boundary, not a capability claim: current codex (`multi_agent` stable; probed at 0.147.0) can spawn subagents in-run, but the end-to-end `/execute-loop` codex architect/delegate route is not implemented or field-validated in v32.3 (see `docs/integrations/cross-agent-orchestration.md` → the codex orchestration matrix).

Expected outcome, honestly — per posture. `conservative`: big wins on UI-implementation-from-spec, boilerplate, scaffolding, and wide edits; marginal or negative on ambiguous logic; UI design/taste stays metered. `broad`: more delegated units (the classes that stopped a conservative run — auth, API contracts, resolved ambiguity — leave the metered seat), more logged misses (the architect's spec errors surface in more diffs — the miss class the downstream record already shows), a heavier peer pass (more one-family output for the cross-family reader), and a lighter metered seat (the architect spends on specs and diff reads, not authoring). Nothing has yet run `broad`: a `broad` run's `DELEGATION: roi` records and miss counts are the measurement, and the operator picks the posture per run.

Independently of delegation, encourage the executor to **right-size effort inline** — lower reasoning effort for mechanical subtasks — as the zero-machinery cousin of delegation; on an architect run the delegate's level is its own wizard answer (the Q3c Effort item — the pin contract above), so a `medium` architect may pair with a `high` delegate or the reverse.

## Optional advisor (any backend)

Default **none**. One wizard concept — attach a higher-tier **advisor** to the executor (or to the architect, when delegating): the "plan big, execute small" upgrade where a stronger model advises the advised role at its decision points while that role keeps the implementation context. The advised role is always the executor/architect — never the peer (excluded by design: peers are already one-shot cross-family reviewers). Attached at wizard Q3b, displayed on the close table's `Advisor:` line (mechanism + row + budget), persisted as the `Loop config:` `advisor=` role group. TWO mechanisms, auto-selected from the advised backend + the advisor row — the user picks WHO advises; the workflow picks HOW:

- **Mechanism N — native `--advisor` (auto-preferred when eligible).** Eligible iff the advised role is `claude -p` AND the advisor is an Anthropic model with a matrix-valid pairing AND native support is detected (acceptance-based — the Q3b lazy probe consumption and the step-6 harness assert; never help-grep); loop step 1 then renders `--advisor <model>` on the advised spawn (syntax + caveats in the Backends `claude -p` bullet). N has no separate advisor effort/profile surface — the advisor runs inside the advised session, so the stored group carries backend + model only (Q3b's mechanism-shaped item). Full-conversation quality: the advisor sees the advised session's context, not a bounded package. Capability is version-attributed: `--advisor` is accepted at 2.1.201 (observed live) though HIDDEN from `--help` — detection is acceptance-based, never help-grep (the probe script's explicit `--probe-advisor` leg). **Engagement is OPPORTUNISTIC** (observed live): the main model consults its advisor at its own judgment — engagement evidence (the advisor model present in the result `modelUsage`; mid-stream `server_tool_use name="advisor"` + `advisor_tool_result` blocks) proves capability, but its ABSENCE on an arbitrary prompt proves nothing, so any check that claims to verify engagement MUST use an engagement-forcing prompt (the probe script's advisor leg does; the preflight harness probe asserts acceptance only). **Pairing is enforced by the workflow, not the CLI:** the pairing matrix (the advisor must be at least as capable as the main model; haiku never advises; a fable main pairs only with fable; docs: v2.1.98+, Fable pairing v2.1.170+) is applied at the Q3b menu (matrix-filtered), asserted at Preflight step 5, and carried on the step-6 harness probe — because the CLI's two observed rejection shapes (2.1.201) make spawn-time detection unreliable: an opus←haiku pairing hard-fails (exit 1, spawn dies), but a fable←sonnet pairing is SILENTLY SOFT-STRIPPED — exit 0, a stderr-only warning, and the run continues UNADVISED, indistinguishable on stdout from a healthy unadvised run. Advised spawns therefore tee stderr (`2>&1`) so a strip warning lands in the role log (a monitor anomaly trigger string). **Failure transition (config error):** a spawn rejected — or strippable — on advisor pairing is a CONFIG ERROR, never a degradation: the workflow NEVER silently strips a close-table-confirmed advisor (the CLI would; the workflow must not) — re-ask the advisor item or user-confirm the drop, then respawn. **Billing:** N runs inside the advised session and bills ITS pool — a quality lift, not pool arbitrage (the Agent-SDK billing caveat in Preflight step 5 covers the pool; an advisored run costs materially more — observed ~2.3× an unadvised control on a trivial prompt). **N is UNCAPPED by design** — the native tool exposes no cap surface; its burn is the usage checkpoint's job (Visibility + run-state).
- **Mechanism C — the workflow consult role (every other combination).** Any advised backend × any spawnable advisor backend. A consult is ONE bounded, one-shot, foregrounded, non-interactive advisor spawn — `role=advisor`, an enum add on the existing `ROLE:` grammar (no new example shape; the spawning session writes the `start`/`end` pair per the writer rule) — that returns bounded advice TEXT to the advised role. **Transport inheritance boundary (pointer-first):** a consult inherits from loop step 4 ONLY the transport mechanics — foreground-and-wait (never background-and-end-turn), the writer + filesystem-escape checks (run by the spawning session), the truthful arming artifact on a CLI consult spawn (`WATCH: armed … role=advisor layer1=fg-wait layer2=none reason="foregrounded synchronous wait"` — the peer-spawn shape, printed by the spawning session), and the composer-driven fallback for advised backends without an in-executor spawn route — and EXCLUDES the peer semantics: NO cross-family requirement (an advisor MAY be same-family; HIGHER TIER is the guidance — only the peer pass requires family diversity), no `PEER_LOOP_NONINTERACTIVE` sentinel or peer-review payload, no Findings-Log writes (a consult returns advice text, never plan writes), no peer grant-list semantics (a consult spawn rides the same fixed spawn-grant shapes where the advised backend needs grants — scoped tier; moot under `perms=bypass`), no convergence/round state. **Billing:** C bills the advisor backend's OWN account/profile — the cross-pool "plan big, execute small" claim attaches to Mechanism C only. **Failure transition:** a failed or unavailable advisor WARNS-AND-CONTINUES unadvised for THAT consult — except a `[decision]` task that cannot proceed unadvised (at cap or on failure), which is MUST-PAUSE (record-and-end for a spawned executor, per Safety gates), never a silent skip.

**Consult triggers + the per-phase budget (Mechanism C).** Three trigger classes, contract-defined: a **`[decision]` task** — consult BEFORE surfacing/recording the decision, so the recommendation reaches the user advised (a task with a pre-recorded `Chosen:` line needs no consult — the decision is already made); **stuck-after-2-failed-attempts** — at `/execute`'s verification-failure boundary, consult before the hard-stop; and **ad hoc** — the advised role's judgment. ONE unambiguous per-phase budget — default **3** — counts EVERY Mechanism-C consult regardless of trigger class, failed advisor spawns included; the budget rides the spawn-prompt carry (loop step 1). The protocol is **RESERVE-THEN-INVOKE**, an append-only ledger correlated by attempt id — the ledger is the phase's `CONSULT:` lines in the phase executor's loop log (the same file as the phase's `ROLE:` lines), written by the invoking session:

  ```text
  CONSULT: reserve ts=<iso> run=<runkey> phase="<n>" id=<N> trigger=<decision|stuck|adhoc> advisor="<backend/model>"
  CONSULT: outcome id=<N> result=<ok|failed>
  CONSULT: refused ts=<iso> run=<runkey> phase="<n>" trigger=<decision|stuck|adhoc> reason=cap
  ```

  Cap-check algorithm (pinned): count THIS phase's prior `reserve` lines BEFORE reserving. Under cap → append the `reserve` line, invoke, then append the correlated `outcome` (the reserve line is NEVER mutated). At cap → append the NON-reserving `refused` line instead: no id is consumed, reservations stay ≤ cap, and refusals are counted separately — never a fourth reserve, never an uncorrelated outcome. The budget counts RESERVATIONS, so a crash between reserve and outcome stays reconstructible — a dangling reserve is a consumed attempt, classified on recovery (the Resume contract, Visibility + run-state). The advised executor's `ROLE: handoff` reports `consults=<reserved>/<cap> refusals=<n> dangling=<n>`; the composer reconciles the counters against the ledger at the phase boundary. A `[decision]` task blocked at cap is MUST-PAUSE, never a silent skip. Each phase starts at zero (fresh executor, fresh ledger). (Golden four-attempt fixture — a real consult, a failed spawn, a dangling reserve, a pre-billing refusal, and the next-phase reset: observed live, run lr291-0.)

**The consult package (bounded by construction).** The advised role authors a self-contained package — the advisor has NO session context: the decision/problem statement, the minimal plan slice (the goal line + the specific task + the constraints that bind it), the options considered with their evidence, and ONE question. Bounded input — never full transcripts, whole plans, or log dumps — and bounded output: the advisor returns one advice text (a paragraph or a short list); it implements nothing, reviews nothing, and writes nothing.
