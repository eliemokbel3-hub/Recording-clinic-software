## The per-phase loop

Each phase is: spawn a fresh executor → build → converge → cross-check → smoke → pause-if-needed → document → commit (default ON) → discard. Start at phase 1.

1. **Spawn a fresh executor** for this phase on the chosen backend (a subagent prompt points at `.agents/skills/execute/SKILL.md`), using the wizard's resolved configuration: the chosen model, the effort level only if one was explicitly picked (inherit = no effort flag), and — for a `claude -p` backend — the `CLAUDE_CONFIG_DIR=<profile dir>` prefix (the invocable path — the `Loop config:` line's `profile_dir`, not the display identity). Under `router=on` that folder is the role's FALLBACK: the composer sets `LOOP_ROUTE_BIN=<the realpath resolved at Preflight step 15>` beside `LOOP_IDENTITY_FILE` and `LOOP_PROFILE_DIR=<the role's profile_dir>` on EVERY wrapper spawn of the run — fresh spawns, respawns, and resumes, peers included — EXCEPT a pinned leg: a spawn made WITHOUT `LOOP_ROUTE_BIN` by a manual Switch account or by a last-resort leg (Usage-exhaustion recovery) PINS that role to its folder for the rest of the phase — its identity record carries no `route_run=` (the pin's signal: the composer never guesses the missing keys), every later spawn of that role in the phase keeps `LOOP_ROUTE_BIN` off and `LOOP_PROFILE_DIR` the pinned folder, and the next phase's first spawn routes again. On a `LOOP_RESUME_SESSION` spawn `LOOP_PROFILE_DIR` is the folder that holds the transcript — never the `Loop config:` line's value — (the composer still passes the holder it knows; the wrapper's resume pin then FINDS the holder among that folder, the router's answer, and the ambient folder, starts the role on the newest copy, warns when that is not the folder passed, and refuses the spawn when no candidate holds the transcript — Backends → the spawn wrapper) and WHICH value names that folder is the resume-root rule (stated ONCE here; STICKY §4 step 9 and Preflight step 6's provenance list point): on an architect-mode run governed by Preflight step 6's reader, the composer's RETAINED verified root for the role — the previous leg's root as step 6 verified it, or a recovery transfer's validated target — with the identity record's `profile_dir=` read back as DATA that must EQUAL it: a disagreeing record is never launched on and never promoted to a trusted root — the role takes the three-option pause (Usage-exhaustion recovery) with the value quoted back, the disposition the ambiguity rule below gives an ambiguous value (the wrapper wrote the record from its own launch folder, so a disagreement is drift or tampering, never routine); on every other run the record's `profile_dir=` is the folder — for a role that has a profile in `Loop config:`; a role with none passes NO `LOOP_PROFILE_DIR` on its resume, as on its first spawn (the record now names the launch folder on every spawn, the ambient one included, and copying that into `LOOP_PROFILE_DIR` would export a `CLAUDE_CONFIG_DIR` the role never had — with none passed the pin finds the ambient folder) — (the wrapper's resume pin then honours the router's answer exactly when it IS the transcript's holder, whatever its `sticky` flag, else `resume-mismatch` and the role runs on the holder — its usage header) — and, on a ROUTED identity, `LOOP_PHASE` is the record's `route_phase=` byte for byte (the routed-resume phase rule, stated once at the Resume contract, Visibility + run-state: a pinned identity keeps today's phase label; the read-back of the record's lines before every resume). **Identity-record values are data, never shell text (the one statement; the re-pick, the manual switch, the codex branch, and the usage checkpoint point here):** a recorded `profile_dir=`, `codex_home=`, `route_run=`, or `route_phase=` that holds a quote, a backslash, a `$`, a backtick, or a newline is AMBIGUOUS wherever the composer binds it into a command — this resume's `LOOP_PROFILE_DIR`, the usage checkpoint's `CLAUDE_CONFIG_DIR` prefix, the re-pick's and the manual switch's `--failed=` and identity flags (the wrapper's answer rule refuses only control bytes, `"`, and non-space Unicode whitespace; the launcher records an inherited home verbatim) — and is treated as the journal bullet treats an ambiguous journal value (Run isolation): nothing is resumed, probed, or picked from it, and the role takes the three-option pause (Usage-exhaustion recovery) with the value quoted back as data. The composer journals EVERY router line of every spawn — the wrapper's `SPAWN_ROUTE` or `SPAWN_WARN check=router` stdout line AND, when it prints, the `SPAWN_WARN check=route-skipped` line right after it — as `ADOPT:`, both (the Spawn wrapper paragraph in Backends). Every `claude -p` spawn — and every respawn/resume of it — runs through the SHIPPED spawn wrapper by its exact granted path, `bash scripts/loop-spawn-wrapper.sh` (the `LOOP_*` parameter contract — see the Spawn wrapper paragraph in Backends): the wrapper holds invariant (ii)'s spawn lock across the spawn when passed `LOOP_SPAWN_LOCK`, appends ONLY the DR-1 enumerated emission set to the probe log — its native START/`EXIT:` pair plus the helper-emitted `ROLE: start` / escape-check / exit-census records and, from v48.0, the leg's own `ROLE: end` (lock outcomes surface on its stdout for composer-voice `ADOPT:` journaling) — and re-renders the resolved tier's flags per invocation; the inline heredoc shape is the documented fallback for wrapper-unavailable hosts only. Two spawn invariants on every CLI spawn: (i) the working directory is PINNED EXPLICITLY — the invocation sets its cwd to the intended checkout (the repo root; the journal-recorded worktree under isolation), never inheriting the composer's ambient shell cwd (an inherited cwd points the role at the wrong tree the moment composer shell state drifts — observed live downstream); toolchain-path pinning for version-managed node on WSL hosts rides the same spawn-shape discipline (canonical guidance: `docs/integrations/cross-agent-orchestration.md` → Host setup); (ii) ONE live executor per phase — before spawning, confirm no prior spawn for this phase is still live (its shell/PID confirmed dead per the stall watchdog's check, never assumed from silence; from v48.0, for a wrapper leg, neither a shell that ended nor a gone `wrapper_pid` nor a `<leg>.exit` file is that confirmation by itself — the tail's shell can end with the role running, a wrapper killed outright leaves its role behind, and `.exit` says only that the wrapper returned: the role-liveness reader decides, by the read-only `python3 scripts/loop-watchdog.py tick --base "<abs base>"` and its `legs=live:<n>,unknown:<n>,over:<n>` count on this run's line: `live:0` is required — any `live` leg is a role to watch, never to spawn beside — and an `unknown` leg is a pause for the operator unless it is one already closed on their attestation, its `ROLE: end` on the log naming `owner-dead`; that count reads the run's log folder, `<base>/.cursor/loops/<iso-id>` or the journal's `log_root=`, so on a run with NO run worktree — `isolation=branch|none`, whose leg files sit in the flat `.cursor/loops/` root — it is always zero and proves nothing: there the composer cannot ask the reader and takes the CONSERVATIVE reading of the leg's own files beside the probe log — EVERY `<leg>.live`, `<leg>.exit` and `<leg>.<n>.*` file whose `leg=` line names the leg, the role over only when each one says so. A file says "over" when it is an `.exit` reading `launched=no`; or, on a POSIX host, when `kill -0 <role_pid>` and `kill -0 -- -<role_pgid>` BOTH answer "No such process" and, for a `.live` with no `.exit`, `kill -0 <wrapper_pid>` answers the same; or, on a Windows-native host, when it is an `.exit` reading `launched=yes` (the wrapper writes it after the role's Job is closed). Everything else is NOT over — any other answer from `kill` ("Operation not permitted" is a process that is there), a `.live` that records no `role_pid`, `launched=unknown`, and on a Windows-native host every `.live` with no `.exit`, where no probe can be trusted: a role that may be running is watched, and what cannot be told is a pause for the operator, never a spawn): a double-spawned phase has two roles editing and logging over each other; and a RETRY fires only on CONFIRMED-ABSENT, under a lock — hold a per-run spawn lock across the spawn: `<log root>/<runkey>-spawn.lock` under a worktree run's iso-scoped log root, and `<iso-id>-<runkey>-spawn.lock` in a non-isolated run's flat `.cursor/loops/` root (`<runkey>` recurs across runs — Run isolation — so the flat name must carry the iso-ID, or two confirmed concurrent runs at the same phase contend on one lock): a spawn attempt that LOOKS failed (a tool-bubble timeout, a missing confirmation) may still have succeeded, so before ANY retry probe for its effects (recorded identity live, role log created/growing, lock held); a HELD lock means ADOPT the lock-holder as the sole spawn ONLY when its recorded identity belongs to THIS run's iso-ID/ownership claim (verify + record its identity) — a foreign run's holder is a COLLISION to surface (the ownership-marker contract), never an adoption candidate — and never spawn beside a held lock; on duplicate suspicion, sole-count against THIS run's recorded identities only — bare process patterns false-positive against concurrent runs on the same machine — and kill only the untracked extra (bubble-timeout retries double-spawned twice, observed live; the lock + ADOPT prevented occurrence three). Under `isolation=worktree`, every executor/architect (and delegate) spawn is cwd-pinned to the journal-recorded WORKTREE path, and the spawn prompt carries the run's ABSOLUTE base-side log paths — tee, probe, and prompt files live under the base checkout's per-run log root, never the worktree; tee redirection stays composer-owned base-side (see **Run isolation (worktree-per-run)**). The per-run log root (tee, probe, and prompt files) is the ONE base-side exception: every OTHER absolute path the spawn prompt points the role at — skill files, the plan, docs — resolves against the WORKTREE, never the base checkout (a worktree-pinned scoped role cannot read base-side copies: three permission denials observed live downstream before the role found the worktree copies on its own), and the prompt states up front that base-side probe-log APPENDS may be denied to scoped roles — worktree-local landing is the documented census path (Run isolation's LOW-E folding rule), not an error worth burning probes on. A `claude -p` spawn invocation also passes the run's grants as `--allowedTools` flags — the fixed peer-spawn grant list (loop step 4; on a `peer-seat=executor` opt-in run only — a composer-seat spawn passes none) PLUS the verification-command grants confirmed on the wizard close table (the always-proposed narrowed journal-emission shapes ride among them), and never more: a grant the user has not seen and confirmed on the close table is never passed (the wizard's injection gate) — and adding ANY grant after the close-table confirm (at a later phase's spawn, a respawn, or mid-run) requires a fresh user confirm of the amended grant list before it is passed (observed live: a `Bash(cp *)` grant slipped into a phase-2 spawn unconfirmed) — except under a bound away grant — see **Away mode**: there the composer may add ONE named command permission a role needs, quoted in its `grant-add` record — never the close-table confirm itself, a permission-tier change, or a read-root change. The grant machinery is the SCOPED tier (`perms=scoped`, the default). Under `perms=bypass` the spawn renders the resolved tier's flag INSTEAD of any `--allowedTools` list — `claude -p`: `--dangerously-skip-permissions`; `codex`: `--dangerously-bypass-approvals-and-sandbox` (see Backends) — and **permission rendering is a PER-INVOCATION invariant**: every fresh spawn, respawn, AND resume of the executor/architect renders the resolved tier's flags — resume sites included: composer-run verification resumes (step 3), smoke-feedback relays (step 6), Mechanism-C advice returns (Optional advisor), and usage-recovery resumes/account transfers — because the tier never survives implicitly from the prior process (observed live: a resumed `claude -p` session without the re-passed flag came up `permissionMode: auto`, and codex's resume command carries its own bypass flag) — all WITHOUT re-asking the already-confirmed tier; genuinely NEW grants keep the fresh-confirm rule above, with its away exception. When preflight confirmed cross-repo read roots (Preflight step 2), the spawn invocation also carries them as `--add-dir <path>` flags, and the spawn prompt states they are read-only reference roots (Preflight step 2's guardrail). For wrapper spawns the WRAPPER emits the executor's `ROLE: start` line (single-emitter ownership — the composer supplies `LOOP_PHASE`/`LOOP_LEG`/`LOOP_MODEL`, mints the leg FRESH per activation, and writes neither line — from v48.0 the wrapper writes the matching `ROLE: end` as well, and the composer's leg-bound `CONSUME:` reuses that leg verbatim: Visibility + run-state → **`ROLE:` log lines** → Wrapper legs); on non-wrapper backends the composer emits the pair via the helper, per Visibility + run-state — except on a launcher leg (a composer-seat codex peer round through the peer launcher), where the launcher writes both lines (**`ROLE:` log lines** → Launcher legs). At each executor/architect activation the composer also snapshots the repository's commit/ref/reflog state — the commit-authority boundary evidence compared at every ownership transition (**Auto-commit (git-safety)**) — and the spawn prompt states the commit prohibition: the executor NEVER runs `git commit` or advances any ref; commits are composer-seat-only. When architect mode is ON, the spawn prompt must additionally carry the delegate backend + model — for a `claude -p` architect, also the delegate agent-definition name (the `Loop config:` `subagent_type=` value) with the no-`model`-/no-`effort`-parameter rule and the never-resume-a-delegate rule stated (the pin contract in `Optional delegating executor` owns both; the delegate's effort is the group's `effort=`, pinned in the definition — never carried as a parameter) — and point at this skill's `Optional delegating executor` section for the delegation rails + logging contract — subagents do not auto-load slash skills (see Backends), so without this a spawned architect never sees the rails. The spawn prompt also carries the run's delegation posture as one line — `delegation=<conservative|broad>`, the `Loop config:` value, an absent or malformed key carried as `conservative` (the fail-closed reading at the `Loop config:` bullet) — and points at that section's posture paragraph for what each posture delegates: a spawned architect reads its posture from the prompt, never infers it. A live-session executor skips the spawn (and a live-session architect reads the section directly — no prompt carry needed). When an advisor is configured (`Loop config:` `advisor=`): a Mechanism-N spawn renders `--advisor <model>` on the advised invocation; a Mechanism-C spawn prompt carries the advisor row (backend / model / effort / profile_dir), the consult triggers, the bounded package spec, and the per-phase budget with the RESERVE-THEN-INVOKE `CONSULT:` ledger obligation, plus the exact section pointer (**Optional advisor (any backend)**) — subagents do not auto-load skills, so without this carry the wizard's advisor selection never reaches the executor; a live-session advised role reads the section directly. An advised backend without a wired in-executor consult-spawn route (`codex exec` in v32.3 — the advisor-table scope boundary, not a capability claim) or a failed in-executor consult gets the composer-driven fallback, with the advice returned over the pinned per-backend route (the transport matrix). On a `peer-seat=executor` OPT-IN run ONLY (the composer seat is the default — loop step 4 — and a default-seat spawn carries NO peer-spawn machinery: no peer row, no peer-loop skill pointer, no peer-spawn grants), the spawn prompt also carries what the in-executor step-4 peer pass needs, so it can run without asking a user: the `/peer-loop` skill path (`.agents/skills/peer-loop/SKILL.md`), the executor's own model family (known by construction from the wizard), the resolved peer row (backend / model / effort / profile_dir), the peer round cap, the run key, the wake-artifact obligation for its own peer spawns — an exact pointer to **Wake arming artifacts** (Visibility + run-state) plus the instruction that each in-executor foregrounded peer spawn prints its OWN truthful armed line, `WATCH: armed … role=peer layer1=fg-wait layer2=none reason="foregrounded synchronous wait"` (fg-wait by construction per loop step 4; never a copy of the composer's outer `Wake:` state) — and, for a `claude -p` executor, the fixed peer-spawn grant list (see loop step 4). For a SCOPED `claude -p` executor the spawn prompt additionally carries the close-table-confirmed verification-command grant shapes VERBATIM, with the instruction to run verification ONLY in those exact shapes (or via the committed wrapper-script path when one exists): a variant of a granted command — an added env-var prefix, a re-ordered flag — is denied on every attempt (observed live: a `TMPDIR=/tmp`-prefixed variant of a granted test command was denied on every re-verify in a downstream run, with the grants sitting unused). Under `perms=bypass` that carry is replaced by one line — run verification directly; no grant-shape restriction applies. It also states the two exit rules a headless executor cannot infer: EVERY child it spawns — opt-in peer rounds first among them — runs foregrounded-and-waited (never background-and-end-turn — see loop step 4), and the exit is an ATOMIC final step: immediately before the final message the executor lists its live child tasks and makes ONE validated declaration call — `python3 scripts/loop-journal.py emit VERIFY_OK --run <runkey> --role <role> --log <probe-log> children=<n>`, the count of its still-live child tasks at that moment (format tool-owned, count role-declared — r2-B2; the wrapper's `OWNERSHIP: exit-census` is the independent observed cross-check — Journal line family, Visibility + run-state) — ANY live child (`n` > 0) means keep waiting, never exit — and the LITERAL last output line is the `ROLE: handoff` exit sentinel (see Visibility + run-state; loop step 4's authenticated child-kind routing is the mechanical guard when this prompt rule fails — it failed 3× live). From v46.4 the spawn prompt also carries the turn-end rule and the plain-shape rule (STICKY §5 — the one statement of both; this step restates neither), and the probe log's ABSOLUTE path as literal text on EVERY spawn, with the line "wherever the footer says `$LOOP_PROBE_LOG`, type this path" (the override the Spawn wrapper paragraph in Backends documents; the wrapper and its footer are unchanged). And before the spawn the composer reads its prompt's own "do not" lines against the phase's tasks: a line a task contradicts is removed, or scoped for that task, in the prompt — the role is never left to weigh a prohibition against a task. The spawn prompt also states the operator-brief artifact rule: the executor's final operator-facing assessment/handoff brief is written INTO the plan's handoff note (or `<log root>/<runkey>-handoff.md` when it outgrows the note) — an artifact the composer relays verbatim (loop step 6's relay-fidelity rule); a brief living only in the session's final message risks lossy relay. The spawn prompt also carries the run-relevant lessons distilled at Preflight step 12 — one line per lesson, only the roles each touches — so a recorded gotcha reaches the role that could repeat it. The spawn prompt also carries the current wall-clock time at spawn — a headless session does not know wall clock reliably, so this is the role's timestamp anchor (spawn time + elapsed) for its self-written `ROLE: handoff` `ts=`, which stays advisory per the timestamp-authority rule in Visibility + run-state. **Attached spawn (a host-conditional mandate keyed to the preflight-resolved `Wake:` line — Preflight step 10; the host predicate is resolved THERE, never re-assessed per spawn).** Under `layer1=bg-shell` (e.g. a Cursor composer session), a CLI executor/architect MUST run as a composer-owned background shell — teed to its role log, and never backgrounded by the composer's own `&`, `nohup` or disown (what that shell holds is the wrapper's TAIL — on a POSIX host the shipped wrapper itself puts the leg under a supervisor it means to place outside the composer's process tree, **Backends** → the Spawn wrapper paragraph's v48.0 item; so the shell is the leg's watch surface and no longer what keeps the role alive) — with the output watch configured AT SPAWN on the full Tier-1 anchor set, and the resolved Layer-2 mechanism armed at the same moment, per the two-layer wake contract in Visibility + run-state: the shell's completion notification is the exit wake (in a repo whose content documents the anchor vocabulary, anchor matches are advisory — key exit on shell completion + the role's own final line, per the wake contract's meta-repo caveat), and **a spawn wrapper exiting 0 is not a watched executor** (observed live: a wrapper detached the PID, the composer owned no watchable shell, and the executor's `ROLE: handoff` sat unread for hours). A headless or non-persistent composer has no such surface (`layer1=fg-wait`) — it foreground-waits the spawn, with the sleep-sentinel wake timer covering quiet windows where resolved (`layer2=sentinel`). ("headless" is not by itself "no such surface": a `claude -p` composer on Claude Code was read to stay alive while a background task is pending, each notification starting a turn. Whichever its `Wake:` line resolved, such a composer waits by the waiting rules below and never ends its turn over a live leg — rule 4.) **Harness-spawn variant (degraded composer shell — `layer1=subagent-harness`):** when the composer's own shell surface is degraded but subagent shells work (the Safety-gates degraded mode), spawning the CLI role inside a FOREGROUND shell subagent that waits on it preserves Layer 1 — the subagent's completion notification becomes the exit wake — with the Layer-2 monitor unchanged and the same exact-commands-only harness contract (verified live: a pool-reset resume and a full phase both ran end-to-end through foreground subagent harnesses after the composer shell died). **A leg that outlives the composer's shell (this replaces "the one legitimate detached exception").** Surviving a composer restart is no longer something a composer arranges for one spawn: on a POSIX host every wrapper spawn takes the wrapper's own split unless `LOOP_SURVIVE=off` (**Backends**), and no composer ever detaches a role itself. What the monitor rule becomes: the Layer-2 mechanism the `Wake:` line resolved is armed at every spawn as before; and for a leg that is running with NO composer shell around it — found after a Resume, after a `SPAWN_DETACHED` line, or after a background task that ended while the leg's `<leg>.live` file stands — a watch on the leg's recorded `wrapper_pid` and its role log is the leg's ONLY wake path and is REQUIRED: the resolved Layer-2 mechanism where there is one, else bounded foreground polls of that pid and log in the same turn (`fg-wait`'s contract) — such a leg is never left unwatched and never spawned again. **The waiting rules (stated ONCE, here; the companion card's §3 and §4 compress them, and the watcher's takeover prompt repeats the headless one).** What was read is said with each (a `claude -p` composer on Claude Code 2.1.325, Linux, with legs through the v47.0 wrapper and an emulation of the split); an interactive composer's limits were not read, and the rules are written for every composer because none costs anything where the limit is absent. (1) **A background spawn call carries an explicit `timeout` above the leg's expected length.** With none, the host ended the background task at 10 minutes — and the role with it wherever the leg does not outlive that task: `EXIT:143`, an `incomplete` end. Which legs do is the leg's own `survive=` word (**Backends**): `on` — built to run on (the emulation did; the built wrapper under a real host's task end is not yet read); `off` — one process, the role its child: the task's end is a signal to the wrapper, which forwards it to the role (`EXIT:143` — what was read); that is the layout, not a guarantee of the role's end — a wrapper killed outright, or a role that ignores the signal, leaves the role running, and the role-liveness reader says which; `in-tree` — still split, the supervisor adopted by the composer or a process under it: it will not outlive the composer's process tree, and whether a task's end reaches it is not established (the launched process is the tail there too, and ends alone, exit 5); `unverified` — not established either way. The largest value read as accepted was 1800000 ms; the host's tool description names its own ceiling — read it there, never assume a larger one. A leg longer than the largest `timeout` the host takes cannot be covered by one call: where `survive=on` the call's expiry ends the tail and not the role, and rule (3) is its cover; where it says `off` the expiry is expected to end the role as well; where it says `in-tree` or `unverified` nothing is established either way. In NO case is a role's end inferred from its task's: a leg is resumed, as any incomplete leg is, only once its own end is on the log and the spawn guard's read (invariant (ii) of this step) finds no live role — until then it is rule (3)'s leg to find and watch. (2) **A watch arm has an end.** A Monitor arm ended at 10 minutes; its expiry notice is a wake like any other — rehydrate, and with the role live re-arm in the same turn. No single arm is assumed to cover a leg. (3) **`SPAWN_DETACHED`, or a task that ended while `<leg>.live` stands, means the leg may still be running: find it, watch it, never spawn again.** The wrapper's tail prints `SPAWN_DETACHED supervisor_pid=<n>` and exits 5 when a TERM, HUP or INT ends the tail — a host that ends the background task does exactly that — and the line can also arrive for a leg that has already ended, and beside a `SPAWN_LOST` line; exit 6 with `SPAWN_LOST supervisor_pid=<n> detail="…"` means the supervisor went without writing `<leg>.exit`. Neither code is the role's, and after either the leg's state is in its files, in the probe log's folder: `<leg>.exit` there → the wrapper returned: its `exit=` is the leg's code, and the leg's `ROLE: end` is read from the log, not from the file — it is there wherever the wrapper wrote the leg's start, unless its end was refused (a `SPAWN_WARN check=role-end` line; then the clean close below) → consume the leg; `<leg>.live` with no `<leg>.exit` → the wrapper has not returned: read `wrapper_pid=` from it and test that pid (`kill -0` — the reader's own test also compares the recorded start token, the `tick` read below) — alive → re-arm the watch on it as the paragraph above says; not alive → the wrapper is gone and left no `.exit` — which says nothing about its end, an earlier write: read the log. An end that is there is consumed; a leg with a start and no end is the clean-close case of **`ROLE:` log lines**, whose helper check decides whether the role is over; where that check refuses the leg as `live` with its wrapper dead, the role outlived its wrapper — the pid to watch is then `role_pid=` from the same file, and its role log no longer grows (the pump ended with the wrapper). `python3 scripts/loop-watchdog.py tick --base <abs base>` (no `--act` — read-only, it writes nothing and runs in any composer shell) prints the role-liveness reader's count for each live run, `legs=live:<n>,unknown:<n>,over:<n>` — read from the run's log folder, `<base>/.cursor/loops/<iso-id>` or the journal's `log_root=`: a run with no run worktree keeps its leg files in the flat `.cursor/loops/` root, which neither this read, nor the watcher, nor the stop command looks in, so its count is always zero and says nothing. **Finding a surviving role** — at a Resume, and whenever a spawn's shell is gone — is this same read: every `<stem>.live` in the run's log folders with no `<stem>.exit` beside it is a leg whose wrapper has not returned (the leg is named by the `leg=` line inside, never by the file name); a live `wrapper_pid` there is a role to watch, not a phase to respawn. (4) **A headless composer does not end its turn while a leg of the run reads `live`.** A `-p` composer with nothing pending ends, and its leg is then nobody's until the next composer: it waits by rule (1)'s call or rule (2)'s re-armed watch, and it ends its turn only when every leg it started is consumed or the run is parked. **Arming artifact (REQUIRED on every CLI-role spawn).** The composer MUST print one `WATCH: armed` line at the moment the spawn's watch is armed — e.g. `WATCH: armed ts=<iso> run=<runkey> role=executor layer1=bg-shell layer2=monitor delivery=bg` (grammar in **Wake arming artifacts**, Visibility + run-state; the `delivery=` key rides wherever the run resolved a Layer-2 consume — the v32.2 delivery epoch) — carrying the MANDATORY `layer1=`/`layer2=` state fields — the ACTUALLY-armed state, which normally matches the resolved `Wake:` line; the phase's FIRST armed line also writes the `Wake:` header as line 1 of that phase's `<runkey>-probe.log` (Preflight step 10). When the resolved Layer-2 mechanism fails to arm (e.g. a monitor spawn error), fall back to the sentinel and print the armed line as `layer2=sentinel reason="..."` naming the failed monitor arm — the actual mechanism, never the resolved-but-dead one; when the sentinel fails too, the line still prints — as `layer2=none reason="..."` naming the failure and stating that quiet-hang detection is OFF — so degradation is loud by construction: there is no separate degraded verb, a spawn with no printed arming artifact is an unwatched spawn (a contract violation, never a silent fallback), and the `layer2=none` continuation is legal only under an actual Layer-1 surface per the return-handling duty in **Wake arming artifacts**. Spawn+arm is ONE act: the SAME message that spawns the role states its spawn-guard result (invariant (ii)'s prior-spawn-confirmed-dead check) and arms the resolved wake layers with the armed line printed — never spawn-now-arm-later. The armed line is pinned to a REAL watch: `WATCH: armed` may only describe a mechanism that actually exists at print time (e.g. a shell whose output watch is actually configured, an in-turn foreground wait or harness subagent, a live monitor subagent, a scheduled sentinel timer) — never a raw unwatched background job and never an intention — and an expected-fast phase is not an exemption (both failure shapes observed live: one run printed no wake artifacts at all; another printed declarative armed lines over raw background jobs and received zero wakes). After spawning a CLI executor (or architect), **surface its live streaming terminal once** so the user can watch the build breathe — on a Cursor host, via the `cursor-app-control` `open_resource` tool as a **fallback chain, never failing silently**: target the role's tee TERMINAL resource first; if that fails, try the tee-log file URI; if both fail, print the tee-log path in chat as the last resort (observed live: the file URI was rejected with "file URI must be inside the current workspace" even for an in-workspace path, and the run went dark). An orchestrator without such a surface prints the tee-log path instead. Surface at spawn only — never re-focus mid-run (repeated focus-stealing is worse than silence). The Cursor-subagent backend needs nothing here: its running-agent card is the native working indicator. Composer-seat peer spawns (loop step 4's default) follow the preflight-resolved wake shape (D5 — a preference, never a mandate; the resolved `Wake:` line stays the mode authority): where the run resolved `layer1=bg-shell` and delivery is not `fg`, the round runs as a composer-owned background shell with the preflight-resolved Layer-2 mechanism armed (loop step 4's preferred shape; the `Wake:` tuple owns BOTH layers — a monitor only where `layer2=monitor` resolved, the resolved sentinel or the legal Layer-1-only `layer2=none` continuation otherwise) and surfaces like any other watched background shell; where a foreground wait applies (resolved `delivery=fg`, surface-less hosts), the round surfaces as a running foregrounded shell call — and a peer round is NOT a short call (xhigh rounds run tens of minutes): the chunked-poll heartbeat rule (Visibility + run-state) covers that foreground wait — bounded polls of up to min(the liveness interval, ~10 min) each (~10 min flat under liveness OFF — the COMPOSER-SEAT bound, v32.5; spawned headless roles keep the ≤2-minute ceiling) and a `[<runkey>]` heartbeat line at least once per liveness interval (liveness OFF: at least every ~10 minutes of waiting) — because a single long silent wait over a live round is a violation (an observed multi-tens-of-minutes silent window), not patience.
2. **Build the phase** — the executor runs `/execute` on this phase's tasks only, honouring every `/execute` hard-stop (decision-point tasks, premium boundary, verification failure, safety boundary). If the architect mode is on, the executor may delegate spec-backed, diff-verifiable units per the guardrails above.
3. **Converge** — the **executor** runs `/review-loop` in-session to convergence on the phase's changes (its own gates and cap apply): it holds the phase's execution context, and the composer only orchestrates — it never runs the review itself. Independence comes from the step-4 cross-family `/peer-loop`, not from moving the review to the composer. Cadence is CONFIGURATION, never composer discretion: "throwaway content" or a small-looking phase never licenses skipping this step's `/review-loop` (which has no skip setting at all) or step 4's `/peer-loop` — a peer-pass skip is licensed only by the wizard-resolved cadence (non-trivial-phases-only or plan-end-only) or an explicit user call (a composer unilaterally skipped a configured every-phase cadence live). **Verification runs before review convergence:** when the phase's verification suites are composer-owned (an ungranted backend or a `verify=composer` run — see step 5), the executor ends its run with `ROLE: handoff reason=composer-run suites="..."` BEFORE starting `/review-loop`; the composer runs the named suites and resumes the executor (backend-correct resume syntax — claude `--resume <session-id>`, codex `codex exec resume <session-id>`) with the results — review convergence over tests that were written but never executed is not convergence (observed live: a review + peer round converged on never-run DB suites). Granting the pure non-DB/non-network suites via scoped `--allowedTools` (see Backends) shrinks these round-trips to the composer-owned suites only. Carve-out: on a genuinely docs-only phase the composer MAY run the review directly — with caution: in the v27 Stage 8 C2 live run, a composer diff-review found 0 findings where the in-executor review caught a real LOW; any phase touching code stays in-executor. At step-3 completion the composer asserts that `/review-loop` reported its per-round `Review History` integrity check (see `/review-loop` loop step 1) AND runs the mechanical FULL-history check itself — `python3 scripts/loop-history-check.py <plan path>` (the shipped checker, invoked by its exact installed path; it parses the plan's complete `## Review History`, rejecting duplicate round numbers, non-monotonic ordering, and contradictory duplicate statuses) — on this executor-complete path and again on every composer-takeover path (loop step 4); a missing report OR a failing check stops the loop and surfaces it (Termination's review-integrity row). **Phase-close mode:** at the PHASE BOUNDARY — before the phase's commit record, alongside the boundary flush — the composer runs the SAME checker in close mode, `python3 scripts/loop-history-check.py --phase-close <plan path>`: it adds the no-Open-rounds gate (any Findings-Log round still carrying a recognized in-flight `Round status:` — Open/in-progress/… — FAILS; no open round crosses a phase boundary — the run-7 escape: a phase closed to commit over an Open round) and the NUL-byte corruption scan (which runs in BOTH modes); a failure stops the close exactly like the step-3 assert. Mid-phase, an Open round remains fully legal — the gate is close-scoped. At a run-END close the composer re-runs this same gate itself as part of the close sequence (§PHASE-CLOSE ordering: the close-mode history gate precedes the mechanical close); the Phase E mechanical close helper does NOT invoke the checker — the gate is a composer duty on every close path.
