## Backends (capability-conditional)

Choose per role from what the host actually supports; degrade gracefully, never silently:

- **Cursor subagent (Task tool)** — *recommended executor/peer on Cursor hosts.* Fresh context per spawn, a model selectable from the available set (Claude / GPT / xAI families in-app), background execution, and resume-by-id. Effort is encoded in the slug variant (e.g. `-thinking-xhigh`, `-thinking-max`) — picking the model slug IS the effort choice; there is no separate effort flag. No `cursor-agent` auth block and no `claude -p` billing exposure. A subagent prompt MUST point at the exact `.agents/skills/<name>/SKILL.md` path — subagents do not auto-load slash skills.
- **`codex exec`** — GPT-family CLI. `codex exec -s workspace-write "PROMPT" </dev/null` — **stdin MUST be redirected** or it hangs. Model + effort per run: `codex exec -m <slug> -c model_reasoning_effort=<level>` (levels from the model's catalog entry; omit `-c model_reasoning_effort=...` when effort is inherit, so the user's own `~/.codex/config.toml` default applies). Resumable multi-turn; dogfooded from a Cursor composer. Permission tier (Q5 `perms=`): a bypass executor renders `--dangerously-bypass-approvals-and-sandbox` in place of the `-s` sandbox flag (verbatim from `codex exec --help`, codex 0.144.1; throwaway run observed live with run-header `approval: never` + `sandbox: danger-full-access` — the header is the codex-side tier-verification surface); the resume command carries its OWN bypass flag (`codex exec resume --dangerously-bypass-approvals-and-sandbox` exists; resume exposes NO `-s/--sandbox` option — a scoped sandbox mode on a resume rides `-c` config overrides instead), so the tier is re-rendered per invocation, never inherited from the prior process. **Composer-seat peer rounds:** on a run with a run worktree the composer does not hand-run `codex exec` for a peer round — the shipped peer launcher (`scripts/loop-peer-launcher.py`) runs the round and writes its records (the Spawn wrapper paragraph below names its grant and the topology it serves; Visibility + run-state → **`ROLE:` log lines** → Launcher legs says who writes what; the recipe is published once, on the companion STICKY card §4 step 8).
- **`claude -p`** — Claude-family CLI. **Pin the binary first (v2):** at wizard time, enumerate the candidate binaries (`which -a claude` + the known nvm bin paths), prefer the environment-native one, and let the bogus-dir isolation probe arbitrate — the canonical pin definition lives in **Setup wizard Step 0**. Use the pinned absolute path for every probe, login command, and spawn of the run — never let bare `claude` re-resolve mid-run (two installs on one host caused the 2026-07-03 profile incident; see `docs/integrations/cross-agent-orchestration.md`). Invocation for loop-spawned roles: `claude -p "PROMPT" --output-format stream-json --verbose --permission-mode acceptEdits --setting-sources user,project </dev/null` teed to the role's log — stream-json is REQUIRED for orchestrated roles so the heartbeat has a live surface (text mode buffers its narrative to exit; see Visibility + run-state). Plain `--output-format text` remains right for one-shot synchronously-waited calls (e.g. the `/usage` probe). Long-prompt shape: write a long spawn prompt to a gitignored file (e.g. `.cursor/loops/<runkey>-<role>-prompt.txt`) and deliver it via stdin redirect — `claude -p < promptfile`, the other flags unchanged (the prompt file replaces both the argv prompt and the `</dev/null` redirect) — quoting-proof through any host interop layer that flattens or re-expands argv (e.g. a Windows-side composer crossing `wsl.exe`; observed live: 7/7 incident-free long-prompt spawns in run lr291). Permission tier (Q5 `perms=`): a bypass executor renders `--dangerously-skip-permissions` in place of `--permission-mode acceptEdits` AND of any `--allowedTools` grant list (observed live, 2.1.201: init `permissionMode: bypassPermissions`; ungated Write + unprompted shell confirmed); the tier is INVOCATION-SCOPED — a `--resume` invocation must re-pass the flag (a resume without it came up `permissionMode: auto`; the init event's `permissionMode` field is the deterministic per-invocation tier detector). Model + effort per run: `--model <alias or full name>` and `--effort <low|medium|high|xhigh|max>` (omit `--effort` when effort is inherit). Account profile per run: prefix the invocation with `CLAUDE_CONFIG_DIR=<profile dir>` to run under a specific account (see the multi-account subsection in `docs/integrations/cross-agent-orchestration.md`). **Cloud VM token pools:** where accounts are seated from numbered secrets (`CLAUDE_CODE_OAUTH_TOKEN_1..N` boot-seated into `~/.claude-acctN` stores — the verified Cursor Cloud pattern), headless spawns prefix BOTH `CLAUDE_CODE_OAUTH_TOKEN="$CLAUDE_CODE_OAUTH_TOKEN_N"` AND `CLAUDE_CONFIG_DIR=~/.claude-acctN` (per-dir credentials outrank env auth in 2.1.x; the interactive `/usage` panel probe is the one seated-store-only exception — a token in the env suppresses its quota bars); the wrapper renders this from `LOOP_OAUTH_TOKEN_ENV` by NAME-indirection under the least-credential contract (the Spawn wrapper paragraph below); a setup-token pool's `auth status` reads `Login: Expired — log in again` with a null email while inference WORKS — never read that status line alone as auth failure, and verify with one cheap `-p` call when it matters (the orchestration doc's Cloud VM token pools subsection). Cross-repo read roots: `--add-dir <path>` grants access to a directory outside the working repo, per spawn — account profiles (`CLAUDE_CONFIG_DIR`) control auth/billing only, never file roots, so the flag must ride every spawn that needs the root (Preflight step 2 + loop step 1); `.claude/settings.local.json` `permissions.additionalDirectories` is the persistent per-project alternative for interactive sessions only (gitignored) — a spawned role does not read that file (Preflight step 16); its read roots ride `--add-dir`. Backend limits: a Cursor subagent is workspace-bound; codex is confined to its sandbox roots (see the read-roots subsection in `docs/integrations/cross-agent-orchestration.md`). Resumable via `--resume`/`--continue`. Surface the Agent-SDK billing caveat only when this backend is chosen (see Preflight). Capability notes (observed live, v27 Stage 8 C2; re-probed; approval behavior re-qualified at 2.1.201): headless `claude -p` can EDIT files (`acceptEdits`); UNGRANTED approval-gated shell is HEURISTIC — host-, version-, and config-dependent, with NO established allowed/denied command-class boundary (the earlier blanket "denied by default" observation no longer holds universally: at 2.1.201 on one host, several ungranted safe commands were auto-approved under `auto`/`acceptEdits`, while the one observed denial was an out-of-workspace write) — so routing never keys on assumed denials: scoped `--allowedTools` grants remain the DETERMINISTIC always-allow layer (e.g. `--allowedTools "Bash(npm run typecheck)"`; verified live), the preflight harness probe (step 6) decides executor-vs-composer verification for the run, and the composer runs the phase smoke/verification when the probe or the grant set says so — and, with the fixed peer-spawn grant list (loop step 4; nested `claude -p` → `codex exec` verified live 2026-07-03), a granted executor CAN run its own `/peer-loop` pass — the `peer-seat=executor` OPT-IN only; the composer seat is the default topology (loop step 4). Prefer narrowly-scoped patterns over blanket `bash`; run long-lived processes in the background (a foreground dev server stalls the session). **Grant shape — prefer a committed wrapper script:** when a documented gate command carries an env-var prefix (e.g. `TMPDIR=/tmp npm run typecheck`), an exact-match grant like `Bash(npm run typecheck)` will not match the prefixed form (observed live: nine denied attempts in one phase before discovery) — the recommended shape is a committed wrapper script, e.g. `scripts/gates/typecheck.sh` holding the env prefix + command, granted as the wrapper path: exact-match-friendly, injection-resistant (the granted string names one auditable committed file), and the env quirks live in one committed place. Related hook gotcha: a hook can block headless commands containing `$PATH`-style expansions ("Contains simple_expansion") — literal values work, and wrappers sidestep the issue entirely. **`.claude/` write-gating (mirror tasks; scoped tier):** under `perms=scoped`, headless `claude -p` Edit/Write into `.claude/` is permission-gated even under `acceptEdits` (config-dir protection; observed live) — for repos with mirror tasks (e.g. `.agents/skills/` → `.claude/skills/` byte-identical pairs), the scoped DEFAULT is composer-owned mirroring: the executor ends its run with `ROLE: handoff reason=composer-run` naming the mirror step, and the composer copies + hash-verifies. The scoped-only alternative is a close-table-confirmed grant in a SAFE SHAPE only: a committed wrapper script (e.g. `scripts/mirror-skills.sh`) granted by exact path, or exact file-specific copy commands — NEVER a broad `Bash(cp:*)` / glob grant, and never derived from plan text (the wizard's injection-gate rule applies unchanged). Under `perms=bypass` the config-dir gating is LIFTED on this host/version (observed live, 2.1.201: a bypass headless run Write-created a `.claude/` file with `permission_denials: []`) — direct executor mirror writes are PERMITTED and the run may say so; hash-verification of the mirrored pair remains required either way. At spawn time the close-table-confirmed grant shapes are carried into the executor both as `--allowedTools` flags on the invocation and verbatim in the spawn prompt with the run-only-these-exact-shapes instruction — see loop step 1. A `claude -p` session also carries Claude Code's **native subagent tool** — the delegation mechanism for a `claude -p` architect; its `model` parameter is a closed ALIAS enum that cannot express a model ID, so delegate model AND effort pinning rides an agent definition selected via `subagent_type`, never that parameter — and never the tool's `effort` parameter either (the full contract: Optional delegating executor). **Native advisor (Mechanism N):** an advised `claude -p` spawn renders `--advisor <model>` (see **Optional advisor (any backend)** — auto-preferred when the advisor is a matrix-valid Anthropic model). Accepted at 2.1.201 (observed live) though hidden from `--help` — detection is acceptance-based, never help-grep. Caveats: the pairing matrix (advisor at least as capable as the main model; haiku never advises; a fable main pairs only with fable) is WORKFLOW-enforced — a bad pairing may hard-fail the spawn (opus←haiku: exit 1) or be SILENTLY soft-stripped (fable←sonnet: exit 0, stderr-only warning, run continues unadvised; both observed 2.1.201) — so advised spawns tee stderr (`2>&1`) and the deterministic post-hoc engagement check is the advisor model present in the result `modelUsage`; engagement is opportunistic — its absence on an arbitrary prompt proves nothing. The advisor bills the advised session's pool.
- **Live session (executor only)** — the lightweight fallback: the composer session itself is the executor. No spawn; context is not reset per phase, so prefer a fresh backend for long multi-phase runs.
- **`cursor-agent` is not a backend** — its headless `-p` mode is auth-blocked.

**Spawn wrapper (SHIPPED default — `scripts/loop-spawn-wrapper.sh`).** Every loop-spawned `claude -p` role — fresh spawns, respawns, AND resumes alike — runs through the COMMITTED wrapper script, invoked by its EXACT granted path: `bash scripts/loop-spawn-wrapper.sh`, a grant naming the one committed file, never a glob — and because an env-var-prefixed command does not match an exact grant (the grant-shape rule above), ALL parameters ride the wrapper's `LOOP_*` ENVIRONMENT contract, set by the invoking composer shell. **One implementation behind a shim.** `scripts/loop-spawn-wrapper.sh` is a thin exec shim from v45.0: it keeps the usage header (the parameter contract's documentation of record), resolves `python3` — REQUIRED on PATH on every host; absent ⇒ the shim refuses the spawn (`SPAWN_REFUSED check=params`, v44.0's gate text), and Step 0 checks it first and names the remedy — blob-verifies `scripts/loop-spawn-wrapper.py` against `HEAD:` and `exec`s `python3 -I` on it with the same arguments and environment; `scripts/loop-spawn-wrapper.py` is the ONE implementation on Linux, macOS, WSL, and a Windows-native host. Nothing a composer or a grant names changes — the grant shape, the `LOOP_*` contract, every stdout token, every probe-log record, the refusal classes and their order, and the exit codes are v44.0's — plus v47.0's additions, all the resume pin's (below): ONE more `SPAWN_REFUSED` class, `check=resume-pin` (the frozen class list changed), two more warning words, and `profile_dir=` on every identity record ("the wrapper" below is that pair; where the text below names a shell mechanism — the trap, `>>`, `$$` — the Python implementation keeps the stated outcome). **Paths on a Windows-native host:** every `LOOP_*` path is spelled absolute with forward slashes and a drive letter — `C:/Users/…` — the one spelling the wrapper records (it converts a Git Bash `/c/…` spelling and backslash separators itself and refuses any other `/`-rooted spelling by name; the shim converts nothing), and `LOOP_ADD_DIRS` is `;`-separated there (`:`-separated everywhere else — a drive letter's colon would split a member). **The param-file transport is CLOSED (the exact grant delegates NO write-reach or activation control to a role-writable data file):** every selector — the binary (`LOOP_CLAUDE_BIN`), tier (`LOOP_PERMS`), grants (`LOOP_ALLOWED_TOOLS`), cwd (`LOOP_CWD`), roots (`LOOP_ADD_DIRS`), profile (`LOOP_PROFILE_DIR`), token pool (`LOOP_OAUTH_TOKEN_ENV` — a NAME, never a value), AND the paths/identity/behavior (`LOOP_PROBE_LOG` / `LOOP_ROLE_LOG` / `LOOP_IDENTITY_FILE` / `LOOP_PROMPT[_FILE]` / `LOOP_MODEL` / `LOOP_RESUME_SESSION` / `LOOP_RUNKEY` / `LOOP_ROLE` / `LOOP_SPAWN_LOCK`), plus the v33.0 OPTIONAL keys (`LOOP_EDIT_SURFACE` / `LOOP_ALLOW_PATH` / `LOOP_ISO` / `LOOP_LIVENESS` → the escape-check twins; `LOOP_PASS` / `LOOP_PEER_ROUND` / `LOOP_CAP` → the keyed peer `ROLE: start`; `LOOP_ROLE_LOG_ROTATE` → per-leg rotation; the wrapper's usage header + STICKY §8 carry their grammar), and the v41.0 OPTIONAL key `LOOP_ROUTE_BIN` (router mode — the ABSOLUTE realpath of claude-switch-gui's `claude-switch-route`, set by the composer under `router=on` only, never resolved from PATH by the wrapper: the wrapper then asks the router which logged-in folder THIS spawn runs under — `pick`, bound per run, role, and phase, through its own bounded collector — and exports the answer as `CLAUDE_CONFIG_DIR`, `LOOP_PROFILE_DIR` becoming the role's FALLBACK — or, on a python3 without `os.waitid` (CPython on macOS), skips the pick before any router starts and runs the role on that fallback with the warning line; the wrapper's usage header is the ONE statement of the call shape, of the answer rule, of the no-answer words, and of its six refusals — not an absolute executable regular file; set without `LOOP_IDENTITY_FILE`, without `LOOP_ISO`, or without `LOOP_PROFILE_DIR`; beside `LOOP_OAUTH_TOKEN_ENV`; a `LOOP_PROFILE_DIR` that fails the answer rule's folder checks — and its topology rule — a realpath inside `LOOP_CWD` or a `LOOP_ADD_DIRS` root, or a root or the command itself that does not resolve to a clean physical path — each a pre-lock `SPAWN_REFUSED`-class refusal, exit 2, no spawn; the launcher mirrors the rule in its own docstring, and the skills never restate or re-validate it. Its outcome lines ride the wrapper's OWN stdout — the composer's channel — and the composer journals them in COMPOSER voice exactly as it journals lock outcomes (`ADOPT:`): `SPAWN_ROUTE dir="<dir>" via=pick|binding` on an honoured answer, `SPAWN_WARN check=router detail="<word>"` on no answer, where the role runs on `LOOP_PROFILE_DIR` (on a resume: on the folder the resume pin finds — below) — the router's word is never a refusal, never a stop — and a SECOND line right after that one, `SPAWN_WARN check=route-skipped detail="<text>"`, printed ONLY when the router printed anything after its reason word (a diagnosing router's per-candidate `<dir> <reason>` lines) or the wrapper's own folder, shape, or resume check gave a reason (`<dir> <check>` — the check words, `unicode-space` included, and `resume-mismatch`), the text sanitized and capped by the wrapper itself (the usage header is the ONE statement of the token, of the sanitizer rule, and of the cap; the launcher's second `note()` mirrors it): the composer journals EVERY router line of every spawn — BOTH lines when two print — as `ADOPT:`; no line is a probe-log record, the `ROLE: start` keys are unchanged, and the EFFECTIVE folder rides the identity record as `profile_dir=` beside `route_run=` and `route_phase=` — the carrier every resume and the re-pick COPY from, never retype (loop step 1; Usage-exhaustion recovery); the variable is unset before the child starts, so the child never sees it) — is environment-only; the wrapper NEVER reads a value from a file, and if the default file (`.cursor/loops/spawn-wrapper.env`; override path via `LOOP_SPAWN_ENV`) exists and names ANY `LOOP_*` key it REFUSES LOUDLY (`SPAWN_REFUSED check=param-file`, exit 2, no spawn) — that file is stale or an attempted confused-deputy, never a transport. So a prior scoped role editing that file cannot make the later trusted composer invocation read, append, replace, or spawn outside the exact activation the composer resolved (nor escalate to a bypass-tier or attacker-`argv[0]` child — the F10 escape class closed mechanically); a no-env surface cannot select the binary either and fail-closes, so the file was vestigial. **The injection-resistance is scoped to the PARAMETER TRANSPORT (this authority-key separation), NOT to the executable bytes of a mutable worktree path** — the exact grant authenticates a pathname, and Bash runs whatever bytes live there. Two duties keep that from being a boundary hole (like every exact-path script grant, this one assumes the committed file is trusted, not role-rewritten-then-run): **(1) the wrapper grant is COMPOSER-ONLY** — a spawned role never holds repo-edit permission AND the `bash scripts/loop-spawn-wrapper.sh` grant together unless it is already trusted-equivalent to the composer (in the default topology executors never invoke the wrapper — peers spawn via `codex exec`, composer-seat rounds on a run with a run worktree through the peer launcher named below, not the wrapper — so only the trusted composer carries it); and **(2) composer-side committed-blob verification, run OUTSIDE the wrapper** — BEFORE relying on the wrapper for any spawn/respawn/resume the composer verifies its working-tree bytes match its committed git blob using git builtins it runs directly (`git hash-object -- scripts/loop-spawn-wrapper.sh` equals `git rev-parse HEAD:scripts/loop-spawn-wrapper.sh`, and `git hash-object -- scripts/loop-spawn-wrapper.py` equals `git rev-parse HEAD:scripts/loop-spawn-wrapper.py` — or the appropriate tracked ref; BOTH wrapper files from v45.0, the shim the grant names and the implementation it runs; the git object store is the trust anchor a tampered worktree cannot forge). An untracked, dirty, or mismatched wrapper file — either one — means the composer does NOT invoke the exact-grant path — it spawns composer-owned (the inline fallback below) or MUST-PAUSEs; a hash check written INSIDE the mutable script is worthless (the tamperer edits the check too), which is exactly why the verification lives outside it. **The peer launcher (`scripts/loop-peer-launcher.py`) joins the composer-held scripts under the same two duties.** It runs ONE composer-seat codex peer round and writes that round's records itself (Visibility + run-state → **`ROLE:` log lines** → Launcher legs; the recipe is published once, on the companion STICKY card §4 step 8). Its exact grant shape is `python3 -I scripts/loop-peer-launcher.py` — Python's isolated mode, no argument, every parameter a `LOOP_*` environment variable (an env-prefixed command does not match an exact grant) — and the grant is COMPOSER-ONLY: it is never added to a spawned role's grant list (an opt-in executor-seat peer keeps its `codex exec` and `emit` grants). BEFORE relying on it the composer checks its bytes itself, the same way: `git hash-object -- scripts/loop-peer-launcher.py` equals `git rev-parse HEAD:scripts/loop-peer-launcher.py`; an untracked, dirty, or mismatched launcher is not invoked. The topology it serves is a run with a run worktree (`isolation=worktree`): it runs from the base checkout, with the tools and the logs on the base side and the peer in the worktree, and it refuses when it, the two tools it calls, the logs, the interpreter, or `git` lie inside what the peer's sandbox can write (the worktree, `/tmp`, `TMPDIR`) — a run with no worktree keeps the hand route. The wrapper is evidence-forced, not a convenience: the footer-quoting prose alone demonstrably failed twice (ledger-4e ×2, then stage-10 ×2 with the rule present in the running skill), so the trap/footer is written ONCE here and reviewed once — never re-authored per phase. It implements the full spawn parameter contract in one place: `--output-format stream-json --verbose` always (orchestrated roles need the live heartbeat surface); stdin routing in BOTH shapes via the round-4 S-D PRIVATE COMBINED SNAPSHOT (`LOOP_PROMPT_FILE` and inline `LOOP_PROMPT` alike materialize one snapshot in the child-unreachable pump workspace — the original prompt content + one deterministic separator + the exit-contract footer with the VALIDATED run/role values rendered in — the probe-log path (validated absolute and opened pre-spawn) is deliberately NOT rendered: the footer carries only the fixed quoted `LOOP_PROBE_LOG` environment reference the child expands from its inherited environment, so no raw `LOOP_*` path enters prompt bytes (R9 PR-LOW-001, documenting the PR-HIGH-003 data-carriage form; **expansion-blocked-host override, composer-side:** a host hook that rejects Bash commands containing shell expansions — the `Contains simple_expansion` refusal class, the same hook family as the recorded `PATH=`-prefix gotcha — makes the footer's environment reference unrunnable for the child; the SUPPORTED path is the composer injecting the literal absolute probe-log path into the spawn prompt with an explicit wherever-the-footer-says-`$LOOP_PROBE_LOG`-substitute-this-literal override, observed live downstream 12/12 spawns clean; the wrapper and its footer are unchanged — from v46.4 EVERY spawn prompt carries the override (loop step 1), on every host: PR-LOW-001's no-raw-path preference is given up for this one path, which the wrapper refuses unless it is absolute) — carrying the `emit VERIFY_OK` atomic-final-step declaration and the `ROLE: handoff` exit-sentinel rule; the child consumes ONLY the snapshot on stdin, no argv prompt in either shape, a captured caller prompt with NO non-whitespace content refuses pre-START (R9 PR-HIGH-004, refined at R11 PR-HIGH-006 — a child never receives a footer-only snapshot; accepted bytes are never trimmed), and the caller's prompt file is NEVER modified — resumes carry the footer too); the round-4 S-A leg-2 rehydrate trigger (a fixed `STICKY_REREAD run=<runkey> role=<role> …` line on the wrapper's OWN stdout — printed PRE-CHILD after param validation and again on the post-exit result surface; a wake-visible re-read signal for the composer's STICKY card, never a probe-log record — the scored artifact stays the composer's `OWNERSHIP: sticky-ack` receipt); the v33.4 mirror rewrite (the role-log pump — the ONE process that appends the child's stream to the role log and mirrors it to the wrapper's stdout; a `python3 -I` filter where a `tee` stood before v33.4 — passes that stream to stdout verbatim, beside the two `STICKY_REREAD` copies, EXCEPT `allowed`/`allowed_warning` `rate_limit_event` lines, each rewritten to ONE `USAGE_TICK status=<s> window=<w> util=<u>` line — whitelisted values, no anchor token; stdout ONLY: never a probe-log record, and the role log keeps the event byte-verbatim; any other status passes through unrewritten and still fires the anchor); PER-INVOCATION tier rendering, nothing inherited (`LOOP_PERMS=scoped` → `--permission-mode acceptEdits` plus the close-table-confirmed `LOOP_ALLOWED_TOOLS` grant list passed verbatim; `LOOP_PERMS=bypass` → `--dangerously-skip-permissions`; a `LOOP_RESUME_SESSION` resume re-renders the tier flags exactly as a fresh spawn; beside the tier flags, `--setting-sources user,project` on every spawn and every resume, on both tiers, with no input — a constant in the wrapper, v46.3; what it means for a role is Preflight step 16's statement); **the resume pin** — on a `LOOP_RESUME_SESSION` spawn (the id must be a UUID; any other value is a `params` refusal) the wrapper itself finds the profile folder that HOLDS the session's transcript: it searches `LOOP_PROFILE_DIR`, the router's answer when one was picked and passed its folder checks, and the ambient folder (`CLAUDE_CONFIG_DIR`, else `~/.claude`) for `projects/*/<session>.jsonl` — under any project folder; it does not compute which one `LOOP_CWD` maps to — and starts the role on the folder holding the NEWEST copy (a tie goes to the earlier candidate in that order). A candidate holds the transcript, does not (the folder or its `projects/` is not found), or is INDETERMINATE (it could not be listed, the file of that name is not a regular file, its time could not be read, or — on a Windows host — the folder cannot be established): ONE indeterminate candidate refuses the spawn, naming the folder — an older readable copy is never chosen over a folder that could not be searched. No candidate holding it is `SPAWN_REFUSED check=resume-pin` (exit 2, no child) — before START when no router is configured; after the pick and before `ROLE: start` under router mode (START and `EXIT:2` in the log, no `ROLE: start`). The holder is read once more immediately before the role's environment is built, which is after `ROLE: start`: a transcript gone by then refuses too, leaving START, `ROLE: start`, the wrapper's own `ROLE: end` (`incomplete: exit 2; no handoff`, written as for every leg whose start it wrote), `EXIT:2`, and no child — the composer writes no end for it: it consumes the wrapper's, as after any refusal that follows the start, and writes one itself only where that end is missing, by the clean close (Visibility + run-state → **`ROLE:` log lines** → Wrapper legs). The same refusal covers a token-pool spawn (`LOOP_OAUTH_TOKEN_ENV`) whose holder is not `LOOP_PROFILE_DIR` — the pool's token is never started on another folder — and, under router mode, a holder that is not the router's answer and fails the answer rule's folder checks. Its stdout lines, journaled as `ADOPT:` like the router's: `SPAWN_WARN check=resume-pin detail="<holder>"` when the holder is not the folder the spawn was GIVEN (`LOOP_PROFILE_DIR`, or the ambient folder when none was passed), and `SPAWN_WARN check=resume-pin-stale detail="<folder>[; <folder>]"` naming every strictly OLDER copy elsewhere. Under router mode the answer is honoured exactly when it IS the holder, whatever its `sticky` flag (`SPAWN_ROUTE … via=pick|binding`); an answer that is not the holder is `resume-mismatch`, with its second line, and the role runs on the holder. When the pin refuses beside an answer that PASSED its checks, no router line is printed for that answer — the role is not started, so no line about its folder would be true; a router that gave no answer, or whose answer failed its checks, still has its `SPAWN_WARN check=router` line — and the `check=route-skipped` line, when there is text to relay — printed BEFORE the refusal, journaled as `ADOPT:` like every router line. An ambient holder leaves the inherited environment as it was — no `CLAUDE_CONFIG_DIR` is exported.
