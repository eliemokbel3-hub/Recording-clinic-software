# Setup wizard, part 2 — the Q1 presets and Q2 to Q5
Previous: s02-wizard-probe-and-triage.md. Next: s04-wizard-close.md. Words such as above and below may point into those files.

Contents, in order: Q1 presets, the two quick-setup flows and their conditional items; Q2 architect mode; Q3 executor or architect menus, with the advisor item; Q4 peer menus; the menu semantics for every Q3 and Q4 menu; Q5 run settings.

**Q1 presets — the two quick-setup flows.** Both presets resolve a `claude -p` executor + `codex exec` peer run at the CURRENT scripted defaults and ask ONLY the role items no default can answer, plus the conditional run-behaviour items (Router, Delegation) — each asked only where it applies: the Router item when Step 0 detected the command, the Delegation item on the Architect ON preset; every unasked item resolves to its scripted default exactly as the recommended-defaults path resolves it (advisor none; architect fixed by the chosen preset). A preset is a question-set shortcut, never a contract shortcut: Step 0 probing, the three output obligations, the close table + single confirm, the Persistence rule, and preflight all run unchanged. Preset questions use the standard Q3/Q4 menu semantics (family-grouped model menus from the Step 0 probes; Effort offered every time, default inherit; Profile REQUIRED for every `claude -p` role, its lazy usage probe run before the menu renders), numbered sequentially as asked (`Q1P-1`, `Q1P-2`, …) — an item that does not apply consumes no number. Question set, in order:

- **Q3b advisor item (both branches — the executor/architect role only).** The Q3b message ends with one more item: `Advisor — attach an optional higher-tier advisor to this role? (default none)` — see **Optional advisor (any backend)**. When the user attaches one, the item is MECHANISM-SHAPED within the same Q3b exchange, its menu filtered to what is actually runnable. **Native-N candidate** (advised role `claude -p` × Anthropic advisor): ask the advisor MODEL only, matrix-filtered (the advisor must be at least as capable as the main model) — effort and account profile are NOT separately selectable: the native tool renders only `--advisor <model>` and runs inside the advised session, inheriting its context and billing ITS pool (the Q3c account-inheritance shape — display the inheritance, do not ask). Native support is part of N's eligibility and is consumed LAZILY at this item (Step 0's lazy-billed-probe timing): the script's advisor entry stays `skipped` by default — when a native-N attach is actually in play, run `python3 .cursor/bootstrap/probe-models.py --probe-advisor` (or the manual equivalent: one engagement-forcing advisored one-shot) and consume its status — `ok` offers N; `failed`/`timeout` means N is NOT offered and the item falls to the executable Mechanism-C rows or a re-ask (a close-confirmed advisor is never silently dropped). **Mechanism-C candidate** (every other combination): ask the advisor's Backend → Model → Effort → Profile with the standard menu semantics (Profile REQUIRED for a `claude -p` advisor); every offered row must be executable per the Mechanism-C transport matrix. The mechanism is auto-selected and displayed, never asked. On the reuse-last path a stored `advisor=` group follows the Degradation + reuse rule in the Optional-advisor section — revalidated, re-asked only when stale, never silently dropped; a stored row resolving to native N re-checks the pairing matrix AND consumes the SAME lazy current-run acceptance probe BEFORE the close table renders (every run observes native support on the pinned binary before close-confirming N — a reused row may predate a binary/version change; one probe per run, exactly when an N attach is in play, never eager and never doubled; `ok` keeps N, `failed`/`timeout` falls to an executable Mechanism-C row or re-asks), with the step-6 harness acceptance assert kept as defense-in-depth.

**Q4 — peer menus.** **Q4a** peer Backend with the family exclusion printed (e.g. "executor is Claude-family — Claude options excluded"): Cursor subagent on a different family / `codex` / `claude -p`; never `cursor-agent` → **Q4b** peer Model + Effort (+ Profile if `claude -p`).

Menu semantics for every Q3/Q4 menu — **Model:** family-grouped, from the Step 0 probe for that backend (free-text fallback). **Effort:** backend-shaped — `codex` = the model's supported reasoning levels with the catalog default shown; `claude` = the `--effort` choices (low–max); a `claude -p` architect's native-subagent DELEGATE (Q3c, v43.0) = the same choices plus `inherit` — the architect's effort — pinned in the definition's frontmatter, never a flag (the pin contract in **Optional delegating executor**); Cursor subagent = the slug variant IS the effort choice, no separate question; live session = confirm what is already loaded. **Profile** (`claude -p` roles only, REQUIRED): a probed identity, the default account, or "new profile" — display each probed profile's current usage AND reset times alongside its identity (e.g. `kount org — session 35% (resets 8:20pm), week 7% (resets Jul 9)`; from the per-profile `/usage` probes, run lazily at this menu per Step 0's lazy-`--usage` timing; display-only, no new question — it lets the user pick the pool with headroom, or knowingly pick one that resets soon). **Usage-evidence rendering (the layered probe emits `usage_quality`/`usage_source` per row; render by class, never assume percentages):** an **`exact`** row (`usage_source=panel|print`) renders the session/week percentages + resets as above. A **`threshold`** row (`usage_source=rate-limit-event` — the billed stream-json call's evidence where print-mode is dark and no panel parsed) is PERCENTAGE-FREE — render its `availability_band` word plus the `limit_status` and, when present, the reset time (e.g. `kount org — rate-limit: allowed (healthy headroom), resets 8:20pm`), and NOTHING numeric: `limit_utilization` (exposed only past the ~75% warning threshold) is a machine-only ranking input, NEVER rendered as a percentage or any `NN%`-shaped figure on any surface — TD.1's pinned rule is "never render threshold evidence as a percentage", so a threshold row shows only the qualitative band/status words. A **`none`** row (degraded) renders label-only. The pinned rank word order is `allowed` (healthy) > `allowed_warning` (near limit) > `rejected` (exhausted — never selectable-as-recommended). **`pool_ranking` (ADVISORY):** when the script ran `--usage`, its `claude.pool_ranking` (`recommended` label + one-line `reason` + per-label `bands`) is the mechanical availability-first pick — surface it as the steer (mark the recommended row), never as a forced selection: it is advisory exactly like the sharing advisory, `recommended: null` means the ranker made no confident pick (an exhausted-only set, or every eligible row incomplete) and the menu simply carries no steer; the human still chooses. **Degraded-identity pools stay listed:** a pool whose auth-status identity is degraded — a credential-less stub, an indeterminate identity probe, or a token-seated pool reporting the expired-login status with a null email while inference still works (Step 0's setup-token status shape — that bullet's literal is canonical; never read that status line alone as an unusable pool) — remains LISTED and SELECTABLE on every profile surface (these menus, Q1R's keep-or-switch, and the usage-exhaustion switch menu alike), never dropped: its identity cell renders the profile dir's `profile-email.txt` marker label when a valid marker exists (marker-sourced display, per Step 0's marker rule), else the config-dir name explicitly marked `identity degraded`; its usage probes and displays under the same lazy rules as any other row (usage needs no bound identity — a failed usage probe degrades that row to label-only exactly like the identity-only degradations below), and the ranking, advisory, and completeness rules apply to it unchanged. A selected degraded-identity pool persists `profile=` as its rendered label — identity is display-only in the `Loop config:` grammar; `profile_dir` stays the invocable key. Lazy timing defers the probe's COST, never the display: the probe runs BEFORE the surface renders, so on EVERY usage-displaying profile surface — these Q3/Q4 menus, Q1R's keep-or-switch, and the usage-exhaustion switch menu alike — a profile row rendered with usage absent because it was not probed this run is a contract violation, never a legal display (skipped twice live despite the lazy-probe mandate); resolved-CONFIGURATION tables (Q1's recommended-defaults preview, the close table) are not usage surfaces — their Profile cells render the resolved value (plus Q1R's kept-profile parenthetical when one applies), never probed usage rows — the defaults path's usage moment is Q1R itself; a preset path's is its own Profile question — and the only legal usage-less rows on a usage surface are Step 0's identity-only degradations: a usage probe that RAN and failed, or a readiness-degraded run with no pinned binary to probe. **Profile-sharing advisory (Q3b/Q4b, display-only):** when a candidate profile's recent-repos enumeration (the script's always-on pre-probe `projects/` snapshot) shows RECENT activity from a DIFFERENT repo, append one warning line to that menu row — pool usage is account-global, so this run would share the pool with that repo's work — and steer toward idle profiles; the advisory never blocks, never reorders the menu, and adds no question. Its completeness rule (canonical for EVERY idle-ranking surface — this advisory, `Q1R`, and the usage-exhaustion switch menu): a profile ranks or is steered-toward as "idle" ONLY when its recent-repos snapshot is complete (`status == ok`) — `absent`/`failed` rows render `unavailable`, and unavailable or incomplete (`degraded`) rows stay UNRANKED in stable order with no idle recommendation; unknown or incomplete activity is never read as inactivity, while known activity on a degraded row still displays as evidence. The new-profile guided flow: create the dir, run `CLAUDE_CONFIG_DIR=<dir> <pinned claude> auth login` (the user completes the browser OAuth with the target account), then verify the binding via `auth status` + echo the org AND require the artifact check — `.credentials.json` must exist inside the target config dir — before declaring the profile ready (a login that wrote to the wrong store passes `auth status` but fails the artifact check). Detail: `docs/integrations/cross-agent-orchestration.md`.

**Q5 — run settings (one compact message, defaults pre-filled).** Peer cadence — default **after every phase**; alternatives: non-trivial phases only / plan-end only. Peer seat — default **composer** (the composer drives every `/peer-loop` pass; loop step 4's evidence-forced default): `executor` is the explicit OPT-IN, offered ONLY when the executor/architect backend has a validated in-executor peer-spawn route (Cursor subagent / live session / a granted or bypass `claude -p`; never `codex exec` — capability-probed at 0.147.0 but its in-executor route is unimplemented/unvalidated in v32.3) and persisted as the optional `peer-seat=executor` key — absence = composer. Caps — `/review-loop` max rounds (default 3), `/peer-loop` max rounds PER PASS (default **5**; operator-set — kount runs already configure peer:5 and converge within it, while runs starting at 3 got raised toward 5 through pure-stall gates; review:3 was never raised in any observed run). The peer cap is a per-PASS budget (mechanized on the `ROLE: start role=peer` record's `pass=`/`peer_round=`/`cap=` keys, loop step 4): the counter restarts at 1 at every `/peer-loop` start — a phase pass, a gate/slice pass, a re-invocation — and a raise applies to that pass only, never rewriting this `caps=` value (three field composers read the cap run-wide and paused 18 times on one counter). Gate policy — the composer-seat key set: `gates=strict|fix-biased|executor` (default **executor**, operator-set — the wizard default only: an absent or malformed key still fails closed to `strict`; `executor` = the composer FOLLOWS the executor-verified recommendation act-and-inform for everything outside the ONE residual MUST-PAUSE list in Safety gates' composer-seat policy bullet; `fix-biased` and `strict` keep their v32.5 contracts byte-untouched) + `cap-raise=ask|auto-plus-one|follow|executor` (default **executor**, operator-set — absent/malformed → `ask`: the LEG-1 `Cap verdict:` decides each cap event within a +3 per-pass raise budget under **Termination**'s pinned total order; `follow` (auto-follow the residue-routing recommendation, +2 budget), `ask`, and `auto-plus-one` retained unchanged) + `high-auto=on|off` (default **on**, operator-set — the wizard default only: an absent or malformed key still fails closed to `off`; run-start-ATTESTED via Preflight step 13's `config-snapshot` record, INERT under `gates=strict`, enable run-start-only with a monotonic mid-run revoke — extends the composer-seat auto-route to verified in-scope non-production Fix-now HIGHs and auto-APPENDS Include-in-plan recommendations as `[pending-hardening]` tasks without building them; Safety gates). COUPLING (D1): `gates=executor` REQUIRES `high-auto=on` — the wizard writes both together, and an explicit `gates=executor` with `high-auto=off` (a hand-edited or stale line) is a `config-conflict` MUST-PAUSE at Preflight step 13, never discovered at the first HIGH. Two conditional companions with DISTINCT applicability — `peer-max=` is cap-MODE-scoped and `profile-fallback=` is BACKEND-scoped, independent of the gate/cap mode: `peer-max=<N>` (asked only when `cap-raise=executor`; never written or displayed under the other modes; default **12** — the per-pass soft ceiling that SURFACES ONCE per pass after the +3 raise budget is spent, the verdict attached; absence = the +3 budget alone) and `profile-fallback="<profile_dir>"` (asked only when the executor/architect backend is `claude -p`, under ANY `gates=`/`cap-raise=` — never written or displayed otherwise — and under `router=on` NOT asked at all but still RESOLVED by its default below, as the Claude roles' last-resort tier (the Router item below); the fallback pool the composer switches to automatically on the run's FIRST usage-exhaustion — Usage-exhaustion recovery; the menu is the standard Profile menu with the executor's own profile excluded, each row carrying its lazily-probed usage per the Q3/Q4 menu semantics; absence = today's usage-exhaustion MUST-PAUSE). Its default (the presets resolve to it unasked) is the probe ranker's OWN rule — `rank_pool_candidates`, the rule that produced `pool_ranking.recommended` — applied by the composer over the probe's per-profile rows with the executor's own row removed: availability band `allowed` before `warning`, `rejected` and band-unknown never; within a band only RECOMMENDABLE rows (a complete recent-repos snapshot AND complete usage evidence for the row's class), and a band with members but no recommendable row ends the rule with no pick, as the ranker's does; then idle-first, most headroom, evidence fidelity + freshness, and the label as the final tie-break. `pool_ranking.bands` alone lists rejected and band-unknown rows too and is never the input; no eligible alternative → **none** (key absent). No script change and no extra question. **Router (`router=on|off`; the canonical item: Q1's interstitial, the presets' `Q1P-n` item, this item, and `same as last run`'s revalidation point here and never restate it).** Asked ONLY when Step 0 detected `claude-switch-route` (its `--version` printed `route_schema 1` on a host that is not Windows-native — Step 0's router line); on every other host the item does not exist — nothing is asked and `router=` is not written (absence = off) — except a stored `on` revalidated `off` there (the CONFLICTS clause below: the downgrade is written and shown).
