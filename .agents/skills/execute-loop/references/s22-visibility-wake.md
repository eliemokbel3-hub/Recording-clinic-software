## Visibility + run-state

- **Per-role visibility.** Tee each spawned role's output to `.cursor/loops/stage-<N>-<role>.log` (gitignored) and keep a concise per-phase status line in the chat (phase, backend, review/peer outcome — including the `Review History` integrity-check report — smoke result, commit state). Do not paste full transcripts into the chat.
- **Progress heartbeat (two-tier).** While a spawned role runs, the composer monitors the plan's task markers plus the role's streaming surface — the tee log for CLI backends; the transcript/progress surface for Cursor subagents. For a `claude -p` role, spawn with `--output-format stream-json --verbose` teed: text mode buffers its narrative to exit (a tee log can sit unchanged for a whole run, leaving nothing to watch), while stream-json emits per-event JSON lines in real time — including a live `rate_limit_event` line (verified). Initialize the baseline read silently BEFORE the first poll (an empty baseline otherwise fires a fake first transition). Then signal on two tiers — prefixing EVERY composer-posted Tier-1, liveness, and status chat line with `[<runkey>]`: the breadcrumb is the RESUME ANCHOR (a recovering composer greps recent chat for the bracketed runkey to re-find its run — see the Resume contract below), and the runkey is the phase's log prefix and already encodes the phase, so no `p<N>` suffix. **Tier 1 — post a one-line chat update:** a task-marker flip, naming the flipped task (diff the task lines, don't just count markers) with its elapsed time in state ("Task 8 🟨 for 42m" — cheap stall detection for free); a new `ROLE:` / `DELEGATION:` line including `ROLE: round` and the `ROLE: handoff` exit sentinel; a peer round completing; a known limit/error-string match (e.g. "You've hit your session limit", a `rate_limit_event` with a blocked status — route to Usage-exhaustion recovery within seconds instead of after a poll-and-sleep cycle). **Tier 2 — log-only, never notify** (the default): file-count ticks, byte-growth liveness, and other "still working" signals — they are information-free as notifications. One Q5-gated exception: when the wizard's Q5 liveness setting is ON (backend-conditional default — ON for CLI executor backends, OFF for Cursor-subagent / live-session; interval default 10 minutes), a window of N minutes with no Tier-1 anchor posts ONE chat liveness line built from the monitor subagent's snapshot — or from the Tier-2 signals on the sleep-sentinel fallback (see the wake contract below) — e.g. `executor alive — log +12KB, last event 3m ago`, then stays quiet until the next window or anchor. The liveness line is informational only — the stall watchdog below keeps sole ownership of hang classification — and transcripts are still never pasted. No new log prefix — the heartbeat keys on these existing anchors only. **Chunked-poll heartbeat (composer-seat child waits — REQUIRED).** Preference first (stated preference, never a mandate; the resolved `Wake:` line stays the mode authority): where the run resolved `layer1=bg-shell` and delivery is not `fg`, a composer-seat peer round runs as a composer-owned background shell with the preflight-resolved Layer-2 mechanism armed (loop step 4's preferred shape — a monitor only where `layer2=monitor` resolved) rather than a foreground wait. While the composer itself foreground-waits a child it spawned (a composer-seat peer round under resolved `delivery=fg` or on a surface-less host — or a composer-driven consult), the wait is CHUNKED: bounded poll commands of up to min(the liveness interval, ~10 min) each (~10 min flat under liveness OFF — the COMPOSER-SEAT bound, v32.5 D4: a persistent host does not die at turn end; spawned headless roles keep the ≤2-minute ceiling everywhere it binds them), re-entered until the child completes, with a `[<runkey>]` heartbeat line posted at least once per liveness interval (liveness OFF: at least every ~10 minutes of waiting — ≈ every poll at full-size chunks, preserving today's effective chat cadence) naming what is waited on and the elapsed time — and carrying `delivery=<resolved>` whenever a delivery resolution exists for the run (chat-line format only; heartbeat lines are chat narration, never probe-log records — no probe-log grammar rides this token) — a multi-tens-of-minutes silent window over a live foreground wait is a contract violation (observed live), and the chunk boundaries are where user messages get consumed instead of queuing behind one long blocking call. **Every bounded wait ends at the first read that settles it (the one generalisation; the verdict wait's own statement is `/close-run` item 6):** a bounded wait — a chunked poll, the CI-verdict wait, a deploy or receipt wait read through the departure file's own readers (**Away mode** → Release work items 4, 5 (c), and 6) — is re-entered only while its last read did not settle it; the read that settles it routes at once to the next step, never to a further confirming read. Under resolved `delivery=fg` (the Q5 Monitor-delivery setting) this SAME contract is also the Layer-2 consume transport, via two foreground wait adapters SCOPED to delivery-fg Layer-2 consumes only (background executor watches and every other wait are untouched): the return-per-event monitor CHILD is foreground-polled — bounded calls of up to min(the liveness interval, ~10 min) each (~10 min flat under liveness OFF), re-entered until its return — and the sentinel SHELL is foreground-awaited the same chunked way; each return or firing is consumed AND the next watch armed in the SAME handling turn (the return-handling duty, unchanged), the liveness-ON interval heartbeat and the liveness-OFF wall-clock cadence (at least every ~10 minutes of waiting — ≈ every poll at full-size chunks) apply exactly as above (chunk boundaries exist under liveness OFF too — the fg × liveness-OFF hole closes by construction), and the chunk boundaries remain where queued user messages get consumed — the wizard caveat's worst case ≈ one liveness interval stays literally true under liveness ON (the bound never exceeds the interval); under liveness OFF the caveat never bound (no interval exists) and the worst case is one chunk (~10 min). **Turn-based orchestrator mechanics — the two-layer wake contract:** an event-driven composer (e.g. a Cursor composer session) never wakes between turns on its own — "monitoring" must be implemented, not assumed. The host's wake modes are resolved ONCE at preflight into the required `Wake:` line (Preflight step 10); every arm below follows THAT resolution, and the artifact grammar + the return-handling duty live in **Wake arming artifacts** below. **Layer 1 — the attached watch (the exit wake).** The CLI role runs as a composer-owned background shell per loop step 1's attached-spawn mandate, with its output watch configured AT SPAWN to fire on the FULL Tier-1 anchor set — any `ROLE:` / `DELEGATION:` line plus the limit/error strings, not just the `ROLE: handoff` exit sentinel (a handoff-only watch leaves entire review/peer passes silent; observed live) — and the shell's completion notification wakes the composer the moment the role exits, so handoff, crash, and limit-death are detected within seconds. Free and instant, but host-conditional (`layer1=bg-shell`, resolved at preflight — it needs a persistent composer with a background-shell watch surface) and regex-blind. **Meta-repo caveat — quoted anchors are advisory:** in a repo whose own content documents the anchor vocabulary (quoted `ROLE:` / `DELEGATION:` prose in skills or docs — e.g. a repo that maintains the workflow skills themselves, or any run whose roles read or edit the workflow files), tee-log anchor matches from tool-result echoes are EXPECTED false positives: a role reading or editing that prose echoes the quoted lines into its stream (observed live: ~80 quoted-prose matches saturated the watch in one run). Treat anchor matches as ADVISORY there — key exit classification on the shell's completion notification plus the role's own final output line (the `ROLE: handoff` sentinel it writes as its last act), and have the monitor's snapshot distinguish a genuinely-new trailing anchor from a mid-stream quoted echo — the concrete stream-json discriminator: a REAL event is an unescaped line-start JSON object (`{"type":"rate_limit_event"`), while a quoted echo inside tool-result content carries escaped quotes (`\"type\":\"...\"`); filter EVENT-shaped anchors (the `rate_limit_event` family) on the unescaped line-start form plus, for limit wakes, a non-`allowed` status, since the healthy stream emits routine `"status":"allowed"` rate-limit events — text anchors (`ROLE:`/`DELEGATION:`) live inside message JSON on both real and echoed paths and stay advisory per this caveat (observed live: two false limit-string wakes, retuned to zero for the rest of the run). **Layer 2 — the monitor subagent (default-on for CLI executor backends on hosts with background subagents).** `layer2=monitor` is the abstraction, not one implementation: it admits the return-per-event monitor SUBAGENT (the canonical shape, fully described here) and a PERSISTENT harness-native watch tool in the same slot — one that emits per-event notifications instead of returning and never ends ON AN EVENT (its arm-proof and writer clauses are in **Wake arming artifacts**; the exit-branch teardown there is mandatory for it; v48.0 — its arm is not unbounded in TIME: where read, a Monitor arm ended at 10 minutes, and that expiry is a wake on which a live role's watch is re-armed — loop step 1, the waiting rules, rule 2). At spawn the composer also arms a background monitor subagent with an explicit prompt contract: the executor PID (on a launcher leg the LAUNCHER's recorded pid, never the child's — **`ROLE:` log lines** → Launcher legs), the tee-log path, the plan path, the pinned Tier-1 anchor strings (matched EXACTLY as pinned — a monitor never loosens them into regexes: a loosened `.*session.*limit` variant matched plan prose live), the liveness window (the Q5 interval), the current watch baseline (the tee-log offset / last-seen anchor plus the plan task-marker snapshot at arm time), the current wall-clock time at arm (the monitor's timestamp anchor for its `MONITOR:` `ts=` values), and the canonical `MONITOR:` snapshot grammar it MUST write (**Wake arming artifacts**). The monitor polls its inputs every ~60–90 seconds and RETURNS on the first NEW Tier-1 anchor (past its baseline), executor exit, liveness-window expiry, or anomaly (`event=anomaly` — exactly three pinned triggers plus a judgment catch-all, defined in **Wake arming artifacts**; informational, never a monitor-side kill) — return-per-event, never one long-lived poller (a long-lived monitor accumulates context and wakes the composer only once) — carrying its one-line `MONITOR:` snapshot in the canonical grammar: current task + time-in-state, log growth, last event age, the return event. The prompt contract also includes a **dead-at-spawn startup check**: within the monitor's first one or two polls, verify the spawn actually started — the tee log exists and is growing with child output past its spawn baseline (the spawner's `ROLE: start` record lives in the probe log — the placement pin on the `ROLE:` bullet below), and the PID is alive; if not, RETURN `dead-at-spawn` immediately instead of waiting out the liveness window (observed live: an `ENOENT`-failed spawn sat undetected for a full 10-minute window; the same check on the respawn confirmed a healthy start in ~75 seconds — a fresh spawn is at its most fragile in its first minute, and the liveness window is tuned for mid-run quiet, not startup failure). The prompt contract's probe-failure rule: when the monitor's OWN probe commands fail — the log read errors, the PID check errors — it RETURNS `event=anomaly` naming its failing probe, never keeps polling silently: a watchdog keyed on a broken probe reports permanent quiet, indistinguishable from a healthy idle run (observed downstream: hours of silent polling on a failing probe command). Each return wakes the composer, which handles it under the ATOMIC, CONDITIONAL return-handling duty in **Wake arming artifacts** — a non-exit return posts the update or liveness line AND re-arms a fresh monitor for the next window with an UPDATED baseline in the same handling turn; an exit return closes the role (verify + the required `CONSUME:` verdict, then `ROLE: end` first among the closure records, then the kind-classification narration, NO re-arm; on a launcher leg, and from v48.0 on a wrapper leg, the end is its spawner's and already exists — verify, then the leg-bound `CONSUME:`, and no second end: **`ROLE:` log lines** → Launcher legs, Wrapper legs) — a monitor reports only anchors new since its baseline, so a re-arm never re-fires on the anchor that triggered the previous return (preflight rotation guards against prior-run anchors; the baseline guards against this run's already-handled ones); the monitor's `MONITOR:` snapshots append to `.cursor/loops/<runkey>-probe.log` (gitignored; line 1 is the phase's `Wake:` header per Preflight step 10; monitor probes are NOT `ROLE:` activations and write no `ROLE:` lines). Q5 liveness OFF disables the liveness-window-expiry returns and the chat liveness line, not the anchor/exit returns. Layer 2 adds what the watch alone cannot: semantic snapshots, the stall watchdog's observation input, and cover when the native watch fails or a leg outlives the composer shell that started it (v48.0 — there a watch on the leg's recorded pid and log is its only wake path and is REQUIRED: loop step 1, the waiting rules). **Sleep-sentinel fallback (`layer2=sentinel` — hosts without background subagents):** schedule a wake timer per quiet window — a backgrounded sleep-N-minutes-then-print-sentinel shell whose output wakes the composer to run the quiet-window check and post the liveness line. Each firing is consumed under the return-handling duty in **Wake arming artifacts**: role live → the next one-shot timer is armed in the SAME handling turn, each arm printing its fresh `WATCH: armed … layer2=sentinel` line; role exited → verify + the required `CONSUME:` verdict, then `ROLE: end` first among the closure records, no re-arm (a launcher leg and, from v48.0, a wrapper leg: the end already exists, and its leg-bound `CONSUME:` completes the exit — **`ROLE:` log lines** → Launcher legs, Wrapper legs); arm failure → the `layer2=none reason=` walk. A continuously-running orchestrator may simply poll; either way every liveness line and watchdog observation must have a concrete wake path — a quiet-window rule with no wake mechanism is a no-op. Cost note (informational, no behaviour change): anchor-driven blocking waits and monitor returns cost nothing while waiting, but each wake is one composer turn over the run's session context — the reason wakes key on Tier-1 anchors, monitor returns, and long quiet windows rather than tight polls, and worth knowing when the composer runs on API billing.
- **Wake arming artifacts (wake grammar, three REQUIRED families — canonical definition; the OPTIONAL journal family on the next bullet is additive and separate).** The wake contract's state is carried by THREE required greppable artifact families — `Wake:` (one authoritative declaration per run, resolved at Preflight step 10; a Resume-contract recovery re-resolves and reprints it, and the NEWEST `Wake:` line supersedes prior ones — consumers read the last, never the first; mechanically backstopped from R8: a forward `WATCH: armed` whose `layer2=` disagrees with the newest `Wake:` line's without a `reason=` naming the transition is the oracle's wake-mode-drift class — DR-5/F-18's silent per-spawn degradation is detectable; the v32.2 optional `delivery=` key rides the SAME drift policing under a MONOTONIC delivery epoch — before a file's first delivery-bearing `Wake:`, absence is legal everywhere and PRESENCE on a `WATCH: armed` is a no-authority violation; after it, every Layer-2-consume `Wake:` carries resolved delivery (a later key-less Layer-2 `Wake:` is itself the violation — omission never resets the epoch), post-epoch `layer2=none` is a NO-ARM state (any later active arm needs a NEW delivery-bearing `Wake:` first), every comparable forward `WATCH: armed` carries an agreeing value, `reason=` explains `layer2=` mechanism transitions only — never delivery absence or mismatch — and a `layer2=none` line never carries the key), `WATCH: armed` (one per CLI-role spawn at arm time, PLUS one fresh line whenever the armed Layer-2 mechanism CHANGES thereafter, PLUS one per one-shot sentinel arm — a sentinel is CONSUMED by firing, so every sentinel re-arm is a fresh arm and prints its own line — PLUS one per overdue-watcher self-heal re-arm (the return-handling duty's heal clause below), always carrying the ACTUALLY-armed state; printed by the arming session — loop step 1's arming artifact), and `MONITOR:` (one snapshot line per monitor EVENT, written by the MONITOR ITSELF — the return-per-event subagent writes it as its last act before returning; a persistent watch tool writes it per event notification, no return existing (the two-shape clause on Layer 2); this is the canonical snapshot prefix — two live runs wrote divergent `MONITOR:`/`PROBE:` prefixes for the same snapshot, so one grammar replaces both) — alongside the existing `ROLE:` family. There is NO `rearmed` and NO `degraded` verb: degradation is the MANDATORY layer-state fields on the `armed` line (`layer2=none` REQUIRES `reason="..."`), and re-arm proof is the PRESENCE of the next `MONITOR:` return — monitor-written evidence beats a composer-written claim, because the party that failed to re-arm is the party that would have written the claim — and a PERSISTENT `layer2=monitor` watch tool (the two-shape clause on Layer 2) needs NO re-arm per event: its single spawn-time `WATCH: armed` line plus its continuing per-event notifications ARE the arm/liveness proof (until its arm's own expiry, which is a wake on which a live role's watch is armed again: loop step 1, the waiting rules, rule 2). Grammar (`layer1` enum: `bg-shell|subagent-harness|fg-wait|native` — there is NO `layer1=none` value: `fg-wait` and `native` have no unwatched-continuation case by construction; `layer2` enum: `monitor|sentinel|none`):

  ```text
  Wake: run=<runkey> layer1=<bg-shell|subagent-harness|fg-wait|native> layer2=<monitor|sentinel|none> [interval=<minutes>m] [delivery=<fg|bg>] [reason="<required when layer2=none>"]
  WATCH: armed ts=<iso> run=<runkey> role=<executor|architect|delegate|peer|advisor|reviewer> layer1=<...> layer2=<...> [delivery=<fg|bg>] [reason="<required for layer2=none and for any mechanism-change line>"]
  MONITOR: ts=<iso> run=<runkey> role=<...> event=<anchor|liveness|anomaly|exit|dead-at-spawn> task="<current task + time-in-state>" log=<growth> last=<age> detail="<one-liner>"
  ```

  ONE end-to-end worked example (a healthy phase, spawn to closure, merged chronologically across the probe and role logs — the second `MONITOR:` line IS the re-arm proof for the first return's handling; the exit return closes the role: the monitor-written `MONITOR:` exit snapshot is the event evidence, the verify read and its `CONSUME:` verdict record precede closure, and the spawner's `ROLE: end` is its FIRST CLOSURE record — the verdict record is REQUIRED on `/execute-loop` runs (the STICKY mandate; only the grammar-admission layer treats the journal family as optional, and that admission rule never changes this operational sequence) — and no `WATCH:` re-arm follows it; the example shows the order of a role whose end the composer writes — a CLI role started without the wrapper, say; a launcher leg and, from v48.0, a wrapper leg — every wrapper-spawned `claude -p` role — have the other order: the end, written by the launcher or the wrapper, precedes the verdict, the leg-bound `CONSUME:` carries the judgment, and an end followed by it is complete: **`ROLE:` log lines** → Launcher legs, Wrapper legs):

  ```text
  Wake: run=lr29-2 layer1=bg-shell layer2=monitor interval=10m delivery=bg
  WATCH: armed ts=2026-07-12T09:02:11+10:00 run=lr29-2 role=executor layer1=bg-shell layer2=monitor delivery=bg
  MONITOR: ts=2026-07-12T09:14:40+10:00 run=lr29-2 role=executor event=anchor task="Task 7 🟨 for 12m" log=+18KB last=40s detail="new ROLE: round reviewer"
  ROLE: handoff ts=2026-07-12T09:25:48+10:00 run=lr29-2 reason=phase-complete
  MONITOR: ts=2026-07-12T09:26:05+10:00 run=lr29-2 role=executor event=exit task="Task 8 🟩" log=+31KB last=5s detail="shell completed; final line ROLE: handoff"
  CONSUME: ts=2026-07-12T09:26:12+10:00 run=lr29-2 source=l2-monitor event=exit result=handoff detail="verified: shell completed, final line ROLE: handoff"
  ROLE: end ts=2026-07-12T09:26:18+10:00 run=lr29-2 role=executor result="phase complete — handoff observed; closed first among the closure records, no re-arm"
  ```

  **Writers:** the `Wake:` line and every `WATCH: armed` line are written by the ARMING session — the composer for every loop-spawned role (chat at preflight; line 1 of each phase's `<runkey>-probe.log` at that phase's first arm — a dry-run writes no file), and an executor arming its own foregrounded peer spawns (loop step 4) — or Mechanism-C consult spawns (Optional advisor) — likewise writes its own, with its own truthful state — `layer1=fg-wait layer2=none reason="foregrounded synchronous wait"` by construction, the obligation riding the loop step 1 spawn-prompt carry (a fresh executor never reads this section unprompted); the monitor writes every `MONITOR:` line — the return-per-event subagent appends it to the probe log as its last act before returning; a persistent watch tool writes the SAME `MONITOR:` snapshot grammar per event notification, no return existing (monitor probes remain non-`ROLE:` activations and still write no `ROLE:` lines). Claude Code wake shape (v33.2 datum, pinned): under a Claude Code composer the persistent watch tool is the observed default — the `MONITOR:` record is COMPOSER-written per event (the check-then-emit fallback writer is the norm there: one record per physical event, never a duplicate) and `WATCH: armed` is emitted by the composer's own arm of that tool. **Anomaly returns (`event=anomaly`) fire on exactly THREE pinned triggers** — two string-shaped: (1) repeated-identical-error lines, ≥3 in one poll window; (2) a permission-denial storm: repeated `was blocked. For security` tool-result lines (verbatim denial shape observed live, single sample: `<action> … was blocked. For security, …`) or a growing structured `permission_denials` array in a stream-json role's result events (the deterministic channel, no string match needed) — and one timing-shaped, applied by the CONSUMING session: (3) the early-return rule — a liveness return arriving less than 0.5× the liveness interval after its arm is RECLASSIFIED as an anomaly at consume time, never accepted as a quiet-window report (the returning watcher's own window claim is not trusted; early returns carrying false "10m window" claims observed live) — plus a judgment catch-all: anything else clearly anomalous (e.g. a visible write to `.env`/secrets) — flag it, the composer classifies. Spawn invocations tee stderr into the role log (`2>&1`) so stderr-only warnings reach the monitor's input (observed live: a CLI capability warning printed to stderr only). Anomaly returns are INFORMATIONAL — composer check-then-classify, never auto-kill; off-plan-surface WRITE detection stays owned by the deterministic git filesystem-escape baseline (Safety gates), never the monitor. **The return-handling duty (ATOMIC and CONDITIONAL — it covers EVERY Layer-2 wake: monitor returns AND sentinel firings).** A Layer-2 wake is not fully processed until, in the SAME handling turn — for a NON-EXIT wake (a monitor's `event=anchor|liveness|anomaly` return, or a sentinel firing that finds the role live): the composer posts the update AND arms the next watch per the resolved `Wake:` mode — for a sentinel that means arming the next one-shot timer AND printing its fresh `WATCH: armed … layer2=sentinel` line (a consumed one-shot's re-arm is a fresh arm, and its armed line IS the proof: no monitor exists to write future `MONITOR:` evidence; unchanged monitor re-arms still print nothing, the next `MONITOR:` return staying their stronger proof); for an EXIT wake (`event=exit|dead-at-spawn`, or a sentinel firing that discovers the role exited): the observing/spawning session (the composer, for loop-spawned roles) VERIFIES the exit against the source log/shell state and records the verification verdict — the `CONSUME:` record, REQUIRED on every `/execute-loop` run (the companion STICKY card mandates the emission for the composers this duty governs; only the GRAMMAR-admission layer treats the journal family as optional, for non-loop corpora — that admission rule never changes this operational sequence) — the reconciled v32.5 order: the verify read and its verdict record precede closure — then writes the role's `ROLE: end` as the FIRST of the closure records — before the update post and the kind-classification narration (the end-first clause on the `ROLE:` bullet below) — posts the update, runs the kind-classification narration (handoff / crash / limit-death per the existing rules) — an ARCHITECT activation's exit consume also owes the delegation staging fold (Optional delegating executor) BEFORE any teardown or generic record copy, and reads the resolved EFFORT of every delegate this activation spawned — the stored-name `agentType` matches newer than the leg's `ROLE: start`, each by its last effort-bearing blob; after a `key=delegate.effort` change, those newer than the record — beside the first-delegation `modelUsage` read (Preflight step 6's reader, stated once there; the probe's delegation is excluded by time) — and explicitly does NOT re-arm — the role is CLOSED; never a watch on a dead PID (on a launcher leg the order and the watched identity differ, by **`ROLE:` log lines** → Launcher legs: both layers watch the LAUNCHER, a child's death is not an exit event, the launcher has already written the end when its shell exits, and the composer verifies, writes the leg-bound `CONSUME:`, and writes no second end; for wrapper-spawned roles the watched identity is unchanged — the recorded `wrapper_pid`, which under the v48.0 split is the supervisor's — and from v48.0 the order is the launcher leg's: the wrapper has written the end before its footer, and the composer verifies, writes the leg-bound `CONSUME:`, and writes no second end — Wrapper legs, same bullet) — and, in the same handling turn, CANCELS/CONSUMES every still-armed wake mechanism for that role that did not self-terminate with the exit return: an armed-but-not-yet-returned monitor (when Layer 1 reported the exit first), a pending sentinel timer, and a persistent harness watch tool (which does not end at the exit event by itself — teardown is mandatory for it, whatever time bound its arm has: loop step 1, the waiting rules, rule 2) alike, because a wake mechanism outliving its closed role emits false events against the frozen log (observed live: two post-exit false stalls) — recording each cancellation with the admitted `WATCH: cancelled` shape (the **Journal line family** bullet below; optional-emit like the rest of that vocabulary — the companion STICKY card mandates it for composers following the card), so a teardown leaves a greppable record, never a bare silence. **Single-call consume.** Within one consume's ordered emissions, genuinely ADJACENT `loop-journal.py emit` invocations — adjacent meaning NO read, verify/classify judgment, cancellation, delegation fold, watcher teardown, or re-arm sits between them under the reconciled order — MAY ride ONE fail-stop (`&&`) chained shell call: a failed emission stops the chain exactly where a failed separate call would, the same-turn atomicity of this duty is unchanged, and the tool-emission mandate stands (hand-authoring a line where an emit exists remains the violation; a chain carries tool emissions only). The `MONITOR` record never joins a chain — event evidence lands solo, first (normally MONITOR-written per the Writers clause; the composer's check-then-emit FALLBACK emission — fired only when a return arrived with no record on disk, one record per physical return — stays solo the same way). Chains are DERIVED from the branch enumeration, never assumed; under the reconciled order the one proven adjacent pair is `CONSUME` + `ROLE:end` on an exit consume (the verify judgment precedes the CONSUME emission, so nothing intervenes between the two emissions; a launcher leg's exit consume, and from v48.0 a wrapper leg's, has no such pair — its spawner wrote the end, and the leg-bound `CONSUME` stands alone) — the architect's delegation fold, every cancellation/teardown record, and every re-arm stay separate calls, and the live branch has no adjacent pair (the re-arm boundary follows its CONSUME). A live-role re-arm failure walks monitor → sentinel → none, and EVERY mechanism change prints a fresh `WATCH: armed` line carrying the actual new state with its transition reason — a successful sentinel fallback prints `WATCH: armed … layer2=sentinel reason="monitor arm failed"`, and only the terminal failure prints the chat-posted `WATCH: armed … layer2=none reason="..."` (quiet-hang detection OFF, stated in the reason); an unchanged, successfully re-armed monitor prints no fresh line — its next `MONITOR:` return is the stronger, monitor-written proof. Two watcher-lifecycle invariants ride this duty: never MORE than one live Layer-2 watcher per role — while Layer 2 is armed that means exactly one, and before arming, confirm the prior watcher returned or was cancelled (double-armed overlapping watchers fired duplicate wakes, observed live in two runs; the legal zero-watcher states — the `layer2=none` continuation, fg-wait children — are untouched), with every Layer-2 watcher armed under a marker identity (the `SENTINEL_<runkey>_<wrap>` pattern — runkey plus arm ordinal) so a stale, replaced, or double-armed watcher stays identifiable at cancel/self-heal time — and the **overdue-watcher self-heal**: on EVERY wake of any kind (a Layer-1 event, a monitor return, a sentinel firing, a user message), under Q5 liveness ON, a live role's current watcher whose newer-of(arm time, last return — a persistent watch tool's last event notification counts as its last return here) is older than ~1.5× the liveness interval is presumed hung — cancel it and re-arm the preflight-resolved mode fresh (the normal monitor → sentinel → none fallback walk applies if that arm fails), printing the armed line naming the heal in `reason=` (unlike a routine unchanged-mode monitor re-arm, a heal replacement DOES print — sentinel arms already print by construction — because the replaced watcher will never write another `MONITOR:` line: the heal's armed line is the immediate evidence, the fresh watcher's first return the stronger proof as always). The self-heal composes with — never replaces — the exit branch and its cancel/consume duty (an exited role still gets its verified closure — `ROLE: end` first among the closure records, or on a launcher leg or a wrapper leg the leg-bound `CONSUME:` after its spawner's own end — and NO re-arm), and liveness OFF has no interval, so no self-heal fires — anchor/exit returns and Layer 1 own detection there (a hung watcher otherwise persists silently: one left a dead executor undetected for 37 minutes, observed live). The `layer2=none` Layer-1-only continuation is legal ONLY while a Layer-1 watch surface actually exists (`layer1=bg-shell|subagent-harness`; Layer 1 is host-conditional, never assumed). A live role with NO Layer-2 mechanism and NO Layer-1 surface has no concrete future wake: the composer foreground-waits it or MUST-PAUSEs — it never continues dark. The handling turn may not end without one of: a fresh armed watch (a persistent watch still armed satisfies this — the two-shape clause), the explicit `layer2=none reason=` line (Layer-1 surface present), or the closed-role / fg-wait / MUST-PAUSE outcome. (Composer death mid-handling is the resume path's case — see the **Resume contract** bullet below — not this rule's.) **Consume-completeness on every wake** (the mechanical detector for exactly that interrupted-handling case, run WITH the sticky rehydrate): before acting on ANY wake, find the MOST RECENT event line in the probe log (a `MONITOR:` exit/anchor return, a Layer-1 completion already known — scoped to THIS run's current activation, never a prior activation's event) and inspect the records AFTER it; the newest line being the event itself is only the commonest incomplete shape. An event whose required completion records have not all landed marks a consume interrupted mid-turn — for an EXIT event the role's `ROLE: end` is NECESSARY but not SUFFICIENT: a trailing `CONSUME:` verdict with NO later `ROLE: end` IS an interrupted exit (under the reconciled v32.5 order the verdict precedes the end — a classification record alone never proves closure), and an end WITHOUT the branch's post-end duties done is STILL an interrupted exit — check the log-checkable artifacts: a spawned-ARCHITECT exit owes its delegation fold (staged-but-unfolded delegation state, no fold record after the end), and every exit owes its watcher teardown (a still-armed wake mechanism for the closed role with no `WATCH: cancelled` after the end) — and the two CHAT-side duties (the update post, the exit-kind narration) are NOT log-detectable, so on re-entry to the most recent exit event whose end is present, REPLAY them FROM the end's recorded `result=` (the kind judgment is already durable there; a repeated chat update is harmless — this replay IS the idempotent completion rule for the chat-side duties, and lifecycle closure never suppresses it); for a non-exit event, the update/re-arm next-action post completes it. Finish THAT consume FIRST, idempotently — skip lines already written, resume at the FIRST missing step (a missing fold or cancellation is finished WITHOUT re-emitting the end; the chat-side duties replay from `result=`; log records are never re-emitted for a fully completed exit — the end PLUS its branch duties) — before any new work (two half-consumed exits observed live: the event line landed, the classify was lost with the host turn). On a launcher leg the first half of this rule is reversed, by **`ROLE:` log lines** → Launcher legs: an end followed by its leg-bound `CONSUME:` is complete; a `ROLE: end` for the leg with no later `CONSUME:` carrying that `leg=` is the interrupted exit, and no second end is written; and the replay source for the chat-side duties is the leg's `CONSUME: … result=`, not the end's `result=`. From v48.0 a wrapper leg is read the same reversed way (**`ROLE:` log lines** → Wrapper legs: the wrapper wrote the end, the leg-bound `CONSUME:` is the completion record and the replay source); only a role whose end the composer itself writes keeps the rule above and the end as its replay source.
