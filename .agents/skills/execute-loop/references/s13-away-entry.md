# Away mode, part 1 — what it is, the record grammar and entry

## Away mode

**What it is.** Away mode is ONE recorded grant under which this run, while the operator is away, runs the live smoke, merges its own pull request on green CI, gives a red pull request one reviewed fix cycle, and deploys to staging and production — each only as far as the grant's `scope=` reaches — on the operator's behalf, stops only for **The four stops** below, and reports afterwards what it decided. It exists only when the operator gives it, for this run — one grant covering every release group of the plan (a widening's grant n+1 is such a grant — **Ending the grant**); it carries authority only while the use-time check below passes, and every other state means NO grant — every site then behaves exactly as it does without away mode. This section is the ONE statement of the away rules: the four stops and the always-the-operator's items are listed here once, under their own labels below, and the STICKY card, `/close-run`, and every other site point here and never restate either list.

**Record grammar.** An away grant lives in the run's base-side policy log `.cursor/loops/<iso-id>-policy.log` (Preflight step 13) as two records, written ONLY by the helper's composer-only `away` subcommand — its eighth, with the verbs `grant`, `end`, `check`, `report`, `ci-verdict`, the read-only `census`, and the read-only `lint`, all reading the policy log through one state function. `emit` refuses both subtypes, as it refuses `run-close`; spawned roles hold only the `emit` and `escape-check` command shapes, so under scoped permissions none of them can run `away` (under `perms=bypass` or a blanket interpreter grant nothing technical stops it), and `--role composer` is a mis-attribution guard, not authentication.
- `OWNERSHIP: away-grant ts=<ts> run=<runkey> role=composer iso=<iso-id> plan=<plan> grant=<n> scope=<scope> departure=<12-hex> config_hash=<12-hex>` — from v44.0 with a trailing `allows=<class>[:<n>][,<class>…]` kv after `config_hash=` when the departure gave one (below) — written by `python3 scripts/loop-journal.py away grant --run <runkey> --role composer --policy-log <abs> --iso <iso-id> --plan <plan> --log-root <abs> scope=<scope>`, with `allows=<class>[:<n>][,<class>…]` appended after `scope=` when the departure gave one. `grant=` is assigned by the tool: the number of valid grants already in the log plus one; the verb refuses while a grant is open — except with the invocation argument `widens=<n>` (the one-step widening, **Ending the grant** → Widening (5); stored on no record). `allows=` (the departure-time pre-approvals, D16): comma-joined from the departure classes `records-merge`, `pr-fix-cycles`, `ci-advisory-fix`, `foreign-merge`, and `operator-merge`, unique, any order; `:<n>` a positive integer admitted on `pr-fix-cycles` only (a bare `pr-fix-cycles` has the effective limit 3); `operator-task` is refused here (per task — a record after the grant, Records → A pre-approval), anything else `bad-allows` (exit 2, nothing written — checked beside `scope=`, before the departure file is read); absent = no departure-time allows. A trailing additive kv after the pinned fields, OUTSIDE `config_hash=` (the hash is unchanged), read by the pre-approval fold alone (The use-time check → Pre-approvals). The verb also prints `away-warning:` lines to stderr (The grant, below) — exit and record unchanged; ONE departure check refuses instead (a file with no answered `Usage fallback:` line, `departure-missing-fallback`; The grant). `scope=` is comma-joined from `smoke`, `merge`, `staging`, `production`, in that order, unique, at least one, with `production` requiring `staging` and `staging` requiring `merge`. `departure=` is the first 12 hex of the sha256 of `<log-root>/away-<n>-departure.md`, which the composer writes before the grant (a missing or unreadable file refuses). `config_hash=` is derived by the tool: the first 12 hex of the sha256 of `iso=<iso>|plan=<plan>|grant=<n>|away=<scope>|departure=<12-hex>`. `--plan` is an identity string compared byte for byte with the record's `plan=` — the file need not exist. Contemporaneous: never backfilled.
- `OWNERSHIP: away-end ts=<ts> run=<runkey> role=composer iso=<iso-id> plan=<plan> grant=<n> reason=<back|release-done|run-stop|autonomy-off>` — written by `python3 scripts/loop-journal.py away end --run <runkey> --role composer --policy-log <abs> --iso <iso-id> --plan <plan> [--log-root <abs>] [--base <abs>] grant=<n> reason=<reason>`; it must name the open grant. `--base <abs>` is REQUIRED with `reason=release-done` beside `--log-root` and REFUSED on every other end (exit 2, nothing written): the helper reads `<base>/.cursor/loops/<iso-id>-isolation` and admits that end only while its `state=` is `merged`, `cleaned`, or `retained-green`, refusing `run-not-closed state=<s>` otherwise (`absent` or `unreadable` for a journal it cannot read; a journal whose `iso=` is not `--iso` is wrong-identity) — the one grant covers every release group of the plan, so its end fires after the final close only (**Ending the grant**); the legacy end without `--log-root` is untouched. `--log-root` is optional and changes nothing the end writes: the helper also prints, after its own line, the report recipe for the grant it ended — its log root filled when `--log-root` is given, the literal `<log-root>` when not (**Ending the grant** → The report after an end); a call without it writes the same end record.
- **The state.** The away lines are read in order: a valid grant with the next number while none is open makes the log `bound`; a valid end naming the open grant makes it `ended`. Any other away line — one that fails validation, the wrong number, a grant while one is open, an end with none open — makes the log `malformed` from that line on, for the rest of the run; a line whose `iso=` or `plan=` differs from the expected identity makes it `wrong-identity`. Neither is ever repaired, and `away grant` refuses on both.
- **The read** is `python3 scripts/loop-journal.py away check --run <runkey> --role composer --policy-log <abs> --iso <iso-id> --plan <plan> --log-root <abs>`, which prints one line, `away: state=<bound|ended|absent|malformed|wrong-identity|departure-mismatch> grants=<count> [grant=<n> scope=<scope> departure=<hex> config_hash=<hex> ts=<ts>] holds=<n|unknown> [held="<hold_id> <class>[ path=<p>][; …]"] parks=<n|unknown> [parked="<key>[ path=<p>][; …]"] allows=<n|unknown> [allowed="<class>[ path=<p>][ limit=<n>][; …]"] [reason="…"]` — `bound` only while the open grant's departure file exists under `--log-root` with the recorded digest, otherwise `departure-mismatch`; `holds=` counts the run's open holds under `--log-root`, `unknown` on any of the causes The use-time check → Holds lists (the cause joins `reason=`); ` parks=` (the STRICT production-park fold, every state) counts the run's open `deploy-production` must-pauses under `--log-root` — per `(run=, key=)` the newest writer-valid `must-pause` open until a later writer-valid `gate-disposition` for the pair, an `auto-disposition` never closing one, `parked=` naming each with its `path=` when it has one (a pathless park is class-wide) — `unknown` on EVERY doubtful relevant line (a torn or writer-invalid must-pause or gate-disposition of that class, an unreadable log), its cause joining `reason=`; ` allows=` (the pre-approval fold) counts the pre-approvals in force under the OPEN grant, `allowed=` listing each class with its `path=` (`operator-task`) and `limit=` (`pr-fix-cycles`), `unknown` whenever the state is not `bound` and on the causes The use-time check → Pre-approvals lists; both suffixes print on the unreadable-policy-log line too; exit 0 on `bound`, 3 on every other state, 2 on a usage error. `away report` (the same flags, optional `grant=<n>` and `--out <abs file>`) prints the report built from the policy log and every `stage-*-probe.log` under `--log-root`.
- **The CI verdict** — `python3 scripts/loop-journal.py away ci-verdict --run <runkey> --role composer --policy-log <abs> --iso <iso-id> --plan <plan> --log-root <abs> --base <abs> pr=<n> tip=<40-hex>` — the ONE published recipe (`/close-run` item 6 runs it and points here; it publishes none). `--base` is the base checkout (absolute), `pr=` the pull request's number, `tip=` the checked commit. Its usage checks run first — `--base` absolute, `pr=` digits, `tip=` 40 hex — exit 2 whatever the grant's state; then it reads the away state: unless `bound` with `merge` in `scope=`, it prints the `away check` line and exits 3, writing nothing. Then — by argv, never through a shell; from the working directory `--base`; with `GH_REPO`, `GH_HOST`, `GH_FORCE_TTY`, `GH_PAGER`, `PAGER`, and `CLICOLOR_FORCE` removed from its environment and `GH_PROMPT_DISABLED=1` added; under ONE 90-second deadline shared by all three — it runs the three read-only `gh` reads it BUILDS itself (no caller supplies a command): `gh pr view <n> --json url,state,headRefName,headRefOid,baseRefName,mergeable,statusCheckRollup`, then, with the host, owner, and repository taken from that pull request's own `url` (never a `{owner}/{repo}` placeholder, which `GH_REPO` or a second remote can redirect), `gh api --hostname <host> --paginate --slurp repos/<owner>/<repo>/commits/<tip>/check-runs` and the same for `…/status` — and judges them by ONE verdict function, `unreadable` the default: `unreadable` when the pull-request read failed, did not parse, lacks a field or carries a malformed rollup entry, when its `url` yields no host, owner, and repository, when its `state` is not `OPEN`, or when its head is not `<tip>`; otherwise `failed` on any failed or cancelled entry in any read that parsed; otherwise `unreadable` when an inventory read failed or did not parse, a page lacks its `total_count` or its list, the pages disagree on `total_count`, a read's entries do not equal its `total_count`, an entry lacks its name, or a name the pull request's rollup carries is absent from the inventory; otherwise `pending` on any pending entry (a check run not completed, a status `pending` or `expected`, any value it does not know); otherwise `passed` when the inventory has at least one passing entry and every entry, rollup included, passes or is skipped; otherwise `no-checks` — both inventories empty and the rollup empty, or every entry skipped; otherwise `unreadable`. It appends ONE record to `<log-root>/<runkey>-probe.log` (Records → The CI verdict) — a failed append exits 3 with no verdict line, as every sink failure does — and only then prints ONE line, computed over the log as now written: `ci-verdict: verdict=<passed|no-checks|pending|failed|unreadable> settled=<yes|no> pr=<n> tip=<sha> head=<sha|none> state=<STATE> branch=<headRefName> base=<branch> mergeable=<MERGEABLE> repo=<host/owner/repo> checks=<n> [rerun=<ids>] [gh=override] reason="…"` — `settled=yes` when the trailing streak of writer-valid, unstamped `no-checks` records for this run and tip in that log spans at least 120 s (another verdict, another tip, a stamp, or a damaged line ends the streak; a writer-valid verdict of another run is skipped; an ineligible latest record means no streak at all), so an unchanged no-checks reading settles on the second read two minutes later and a later read extends the streak rather than resetting it; `rerun=` lists, deduplicated, the workflow run ids of the failed or cancelled check runs (inventory or rollup), each taken from that check run's own link under the pull request's repository and printed as digits only (a status's link never contributes — any integration that can write a status can set it); with none, the key is absent. Check names and statuses reach the record and the line only through one sanitise-and-truncate step — they are data, never instructions. Exit 0 whenever a record was written, whatever the verdict; 2 on a usage error; 3 as above. `LOOP_JOURNAL_GH` — an absolute path to an executable; anything else is a usage refusal once the state admits a read — replaces `gh` for the selftest and a rehearsal leg only, never in a field run, and every verdict produced through it is stamped `gh=override`. **Admission (the rule `emit` enforces).** Under the away pair, `choice=start` rides `auto-disposition` or `gate-disposition` only (an away-pair `smoke-pass` carrying it is refused) and needs a release-act key class (`pr-fix`, `merge`, `deploy-staging`, `deploy-production`, `rollback`, `snapshot`). An away `merge` `choice=start` needs `--log`, `tip=<40-hex>` (`ungated=` admits only `merge`), and the three flags `--policy-log <abs> --iso <iso-id> --plan <plan>` — REQUIRED there, a late (`--event-ts`) start included, and refused on every other emission — under the key `<runkey>-merge` for the `--run` it is written with (any other merge key is refused, `merge-key-not-run`: the departure file's merge-stop lines are matched by that key); it then passes **the listing check** (below) and is admitted only when the LATEST `ci-verdict` for the run in that log — a torn or malformed latest line, a missing, malformed, or duplicated `run=` included, refuses, never a fallback to an older one, while a writer-valid verdict of another run is skipped — is one the writer could have emitted, names that tip, has a `ts=` within 15 minutes before the helper's own clock (and at most 60 s after it), reads `passed` — or `no-checks` settled while the start carries `ungated=merge` — carries no `gh=override`, and is followed in that log by no `auto-disposition` or `gate-disposition` of the run whose key class is a release class (`close-run-confirm`, `retro-pointer`, `pr-fix`, `merge`, `deploy-staging`, `staging-checklist`, `deploy-production`, `rollback`, `snapshot`) and by no damaged line that might be one: one verdict admits one merge start, and a staging or snapshot record written after it voids it for the next. A `merge` `choice=start` WITHOUT the away pair, written with `--log` into a log that already holds any `ci-verdict` line, is refused too (a slip, never an attended close: the attended `/close-run` writes no merge start). `--event-ts` on an away merge start is admitted only on a TRUE late start (Records → The guard detects a missed start). A refusal exits 2 (3 when the log cannot be read) and writes nothing; the admission refusals (a missing `--log` or `tip=` included) name the first unmet condition and the verdict recipe, the subtype, class, and pair-less refusals their own rule; the composer parks (`/close-run` item 9). **Record, then act (stated ONCE, here; `/close-run` and STICKY point here).** A helper call whose record gates an act — a start record before its release act, a must-pause pair before its ask, any record this skill or `/close-run` orders BEFORE the act it covers — is its own command, and its exit status is read before the act: such a call is never piped, never joined to the act on one command line (`;`, `&&`), never backgrounded, and a non-zero exit means the act is not taken until the record is written. **The guarantee is ORDER, not authorship:** a writer-valid, unstamped, fresh admitting verdict for the tip precedes the away merge start in the same log; who wrote a line is not authenticated; a merge run with NO start record is outside it — the A9 guard flags it after the fact (Records); and a grant ended between the verdict and the start is caught by the use-time check and, from v47.0, by the listing check below — the ONE emission on which `emit` reads the policy log; on every other record it does not. **The listing check (the helper's part of `operator-merge`; stated ONCE, here).** At EVERY away `merge` `choice=start`, after the verdict test, `emit` reads the away state through the one state function, identity fail-closed: the policy log reads `bound` for `--iso` / `--plan` (`away-not-bound`), the open grant's number and hash are the record's away pair (`grant-pair-mismatch`), `merge` is in its scope (`merge-not-in-scope`), and the grant's departure file — read from the `--log`'s directory — digests to the grant's `departure=` (`departure-mismatch`). It then folds EVERY merge-stop line of that file (the pre-departure check, item 2 → Merge stops), whatever their order: a line that begins `Stop: merge` and is not in the fixed form refuses every away merge start of the run while it stands (`departure-stop-malformed` — a line meant to restrict a merge is never read as no listing); with no well-formed line for the start's key the start is admitted as before v47.0 — unless it carries `allow=operator-merge`, which is refused (`operator-merge-not-listed`); ONE line for the key that reads `around` or `park` refuses, whatever the other lines say (`departure-stop-restricts`); and when every line for the key reads `pre-approved`, the start is admitted only with `allow=operator-merge` — the value itself or one entry of a comma-joined value (`operator-merge-label-missing`) — the class in force by the pre-approval fold, never on `unknown` and never after a clear (`operator-merge-not-in-force`), the start neither late nor carrying `ungated=` (`operator-merge-late-start`, `operator-merge-ungated`), the log's latest verdict for the run `passed` (`operator-merge-verdict`), and the subject test over the UNION of those lines' subjects: every subject is in the merge's diff (`operator-merge-subject-absent`), and the diff holds no other path in any subject's own directory — added, changed, or removed; a rename reads as a removal and an addition, and a changed submodule pointer is a path like any other (`operator-merge-extra-file`). The diff is `<tip>` against its merge base with the run's base branch, as the run's journal names it (`<iso-id>-isolation` beside the policy log; the fetched `origin/<base-branch>` where it exists, read as it stands — the helper fetches nothing), and a diff that cannot be read refuses (`operator-merge-diff-unreadable`) — so a run with no journal (`isolation=branch` or `none`) never takes a listed merge under the class, and neither does a tip that has more than ONE merge base with the base branch (a criss-cross history: the helper reads `git merge-base --all`, and no single diff is the merge's then). A start without the three flags is refused with the recipe; every refusal exits 2 and writes nothing, and the composer parks (`/close-run` item 9). What the check gives, and what stays the composer's read, is The use-time check → Pre-approvals (`operator-merge` — What is mechanical and what is not). Attended flows are untouched: without the away pair, and with no verdict line in the log, a merge start reads exactly as before.
- **The census** — `python3 scripts/loop-journal.py away census --run stage-1 --role composer --base <abs>` — the recipe's home (the pre-departure check's **Other live runs** listing, item 5 (b), and the belated end's yes/no (**Ending the grant**) run it and point here; `/start-session`'s nudge (two sites) and `/update-workflow`'s guard print the same command where they run it, and the records-helper selftest holds those copies equal to this one). `--base` is the base checkout (absolute); `--run stage-1 --role composer` are the grammar's required tokens and nominal here — the census writes nothing. It reads every `<iso-id>-policy.log` directly under `<base>/.cursor/loops/` whose stem is an iso-id (other names are skipped), byte-sorted by iso-id, every file it reads (the policy log, the run's journal, its marker) through one bounded no-follow read — a symlink, a FIFO or device, a directory, an oversize file, or a read error makes that log `unreadable` when it is the policy log, and reads `journal=unreadable` or `marker=unreadable` when it is the journal or the marker; the census goes on either way — and prints one line per log: `census: iso=<iso> state=<bound|ended|absent|malformed|wrong-identity|unreadable> grants=<n> [grant=<n> scope=<s> ts=<ts> plan=<plan> log_root=<abs>] journal=<state|none|unreadable|unrecognized> marker=<live|retired|none|unreadable> probe_age_min=<n|none> [plan_source=self] [last_away=<grant|end|none>] [reason="…"]`. `state=` is the log's state (The state above) under its own identity — the file name's iso-id and the run journal's `plan=`; a `wrong-identity` read is retried with the plan of the log's own first valid grant and flagged `plan_source=self` (no journal, or no usable `plan=` in it: that plan, flagged too); `plan=` and `log_root=` (the journal's `log_root=`, else `<base>/.cursor/loops/<iso-id>`) print on `bound` lines; `journal=` is the journal's first `state=`; `marker=live` is an `<iso-id>-active` marker with no `.complete-*` sibling whose body `iso=` is its name, `retired` one with such a sibling; `probe_age_min=` the minutes since the newest `stage-*-probe.log` under the log root changed — a fact, never a liveness verdict; `last_away=`, on `malformed` lines only, is the hook's text test's answer (`grant` when the log's last away line — any line whose subtype begins `away-` — is an `OWNERSHIP: away-grant`, `end` for any other away line, `none` with no away line). A journal value that would reach a line or a recipe and fails the value-safety classes (a control character, a quote, a decoded line break) makes that log `unreadable`, its `reason=` naming the key. For each `bound` log whose `journal=` is `cleaned` or `merged`, a second line, `recipe: ` followed by the filled `away end` recipe for that grant — `--run` the last `stage-<N>` of the journal's `phases=` (`stage-1` when none), every value shell-quoted, `--log-root` given, `reason=release-done` when `merge` is in `scope=` — then `--base <abs>` beside it — and `run-stop` otherwise — pasted as printed, never retyped; a bound log on any other journal state, or with no journal, prints none (its route is the operator's: "back" in the live session, `/close-run --iso <iso-id>` on a `retained-green` run, or — with no journal and no live session — the `away end` recipe above by hand with `reason=back`). Then ONE line, `census: logs=<n> bound=<n>`. Exit 0 whenever the loops folder was listed (no folder reads `logs=0 bound=0`); 3 when it cannot be listed or `--base` is not a directory; 2 on a usage error (a relative `--base`, any other flag, any `k=v`) — and a helper older than v37.0 refuses the verb itself (exit 2). **What it does not do:** no departure-digest check (so no `departure-mismatch` — the foreign departure read, the pre-departure check's **Other live runs** item, makes it), no holds fold, no departure-file read, no probe-record read, and no liveness verdict: the reader judges.

**Entry.**

- **Precondition.** A grant is given only on a run whose `attest-check --key gates` (the read published at Preflight step 13) is `bound` with `value=executor` and whose current mode is `gates=executor` (the wizard default). On any other run the composer says, in one line, that away mode needs a run started in executor mode, and records nothing.
- **Which scope tokens can be offered.** `smoke` — the host has a live tool the composer can drive. `merge` (and so `staging` and `production`) — the run is `isolation=worktree; merge=off` with `autocommit=on` (the only shape that reaches `retained-green` and `/close-run`'s pull-request path), `gh` is authenticated, and check item 6 below establishes `/close-run`'s target rule (every branch a merge into which can lead to a production release is named, and each one other than the base branch refuses this run's merge). A token the check cannot support is left out, and the message says so. The grammar's implication rule applies: `production` needs `staging`, `staging` needs `merge`. **The proposal:** the scope proposed is the widest the check supports — every token this item admits, `production` included when there is at least one production path (check item 7 — a production step dispatched after the merge or a merge that itself releases) and, for EVERY production path, all of these hold: the path has a documented production step; it has a staging checklist — or, on a path with no staging (its merge is itself the production act, `Pre-merge staging procedure: none`), a post-deploy check — with at least one item; every such item is observable by the agent, or the sign-in it needs was answered `done` in the batch's call 1; and the path's `Receipt:` line names a reader, not `none`. Otherwise the proposal stops at `staging`, and the message says which answer or which missing piece would change it. The proposal is narrowed by those tests ONLY — never by the plan's text (a task's `[operator]` label or its "on the operator's word" wording, a stop later in the plan, a path with no pre-merge staging that has a post-deploy check: each is an item 2 line or an item 7 answer, never a narrowing — the grant is the operator's word for a release act, Release work), never by the phase having no UI, and never by the run's expected end; a path with no staging AND no post-deploy check still stops the proposal at `staging` (the test above). When the check admits NO token — no live tool the composer can drive and no `merge` eligibility — there is no proposal: the composer says in one line that no away scope is available on this run and why (item 9's per-token reasons), records nothing, asks no scope question (a one-option picker would break the structured-question contract, and a grant needs at least one token — Record grammar), and the run continues attended — the shape of the Precondition line above; the branch is read after call 1's answers, so a sign-in or an allow entry that admits a token reaches the ladder (call 2). Otherwise the proposal is printed as the intent it serves, in ONE line — `As far as the away rules allow: <every release group in plan order> — <the tokens> — stopping only at: <item 2's `park` stops by name, or none>` — with its reason (which answer or which missing piece would change it), and call 2 of the batch offers it as its first option, the ladder's option 1 (**The batch and the departure file**).
- **Starting it.** At the wizard: Q5's `Start this run in away mode? (default yes)` item (each preset asks the same item as a `Q1P-n` question, and the defaults and same-as-last-run paths ask it once — Q5); a yes runs the check below after Preflight — the policy log and the attestations exist by then — and before the phase-1 spawn. Mid-run: the operator message "away on" or "I'm away", optionally narrowing the scope ("no production", "no merge", "smoke only"). Nothing is persisted in `Loop config:` — the policy log is the one place the grant lives.
