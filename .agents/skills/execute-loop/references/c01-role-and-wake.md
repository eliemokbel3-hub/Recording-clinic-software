- **Layer 1 (exit wake):** the preflight-resolved `Wake:` line (canonical Preflight step 10) is the MODE AUTHORITY — arm exactly what it resolved, never an ad-hoc reassessment (mechanically backstopped: a forward armed `layer2=` disagreeing with the newest `Wake:` line without a `reason=` naming the transition is the oracle's wake-mode-drift class — DR-5/F-18). The preflight-resolved `delivery=` key is PART of that mode authority (the dedicated `delivery=fg` sub-bullet below): the resolved value rides the `Wake:`/`WATCH: armed` artifacts under the oracle's monotonic delivery-epoch policing (`reason=` never excuses delivery absence/mismatch), and a mid-run `monitor-delivery=` change is a step-10 re-run whose NEW `Wake:` line prints BEFORE the next arm — never a `reason=` bypass. On `layer1=bg-shell` (the common CLI-executor resolution) every composer-owned CLI executor/architect runs on the host's background-shell surface — a composer-owned background shell teed to its role log, with the output/completion watch configured AT SPAWN on the Tier-1 anchor patterns. Per-host implementations of that surface: Cursor's Shell tool background mode (`notify_on_output` regexes; `AwaitShell` where a synchronous wait is wanted); Claude Code's background Bash (its completion notification, plus a harness watch/monitor surface where one exists). The subagent shape: ONE persistent background monitor SUBAGENT spawned WITH the executor. Its prompt carries: the recorded PID (on a launcher leg the LAUNCHER's — the Launcher legs bullet below), the ABSOLUTE role-log path + byte baseline, the ABSOLUTE worktree plan path (for the task snapshot), the Tier-1 patterns, and the interval. It verifies the executor ALIVE at arm (dead-at-spawn returns immediately as an exit event), polls internally (~60–75s), and RETURNS on (a) liveness expiry (snapshot: PID alive, log delta, current task), (b) executor death — immediately, (c) anomaly past baseline — including its own probe breaking (a monitor that cannot read the PID/log returns that failure, never polls blind). armed lines: initial arm, mode change/fallback, self-heal). **Single-call consume:** ADJACENT ordered emissions under this checklist — no read, verify/classify judgment, cancellation, delegation fold, watcher teardown, or re-arm between them under the reconciled order — MAY ride ONE fail-stop (`&&`) chained shell call (a failed emission stops the chain exactly where a failed separate call would; - **Launcher legs.** A composer-seat codex peer round started through the peer launcher (`python3 -I scripts/loop-peer-launcher.py`) is a launcher leg. The launcher writes that leg's `ROLE: start` (marked `via=launcher`), its `OWNERSHIP: escape-check` record, and its `ROLE: end` — all through the helper. The composer writes `WATCH: armed` and `WATCH: cancelled`, the `MONITOR:` record where it is the writer, the `CONSUME:` verdict, and everything else it writes around a peer round today (the ref snapshot pair, the update post, the findings route) — never a start or an end for the leg, except in the clean close below. **The launcher owns the close while it is alive.** Both wake layers of a launcher leg watch the launcher — its background shell, and the `launcher_pid` its identity file records — not the child. A child's death is not an exit event: after codex exits, the launcher is still writing the leg's records. The composer consumes the leg, or does anything below, only once the launcher is positively dead: its shell has reported its exit, or its recorded pid is gone. With neither — no shell report and no recorded pid — the composer cannot tell, and pauses. **The exit line can only add a pause.** When a `PEER_LAUNCH_EXIT` line was delivered and says `start=uncertain`, `end=failed`, `tools=changed`, or an `escape=` other than `0` (`none` included), the leg is a pause whatever the records show. A line without those values, or no line at all, decides nothing: the records do. No field of the line ever permits a write. Then the leg is in exactly one of three states. **(1) Complete.** The probe log holds the leg's start, its escape-check record, and its end. The composer consumes it (the checklist below). An escape-check record that carries `refused=` is judged as on every other route: a must-pause. **(2) The clean close — the one case where the composer writes the launcher's records for it.** The exit line adds no pause, and every one of these holds, each read from a record or a recorded identity: (a) the probe log holds the leg's `ROLE: start` with `via=launcher`, `baseline=`, and `tool_ids=`, and no `ROLE: end` for the leg; (b) both tools the launcher calls (`scripts/loop-journal.py` and `scripts/loop-history-check.py`, beside it) hash to those ids by `git hash-object` — never a comparison with `HEAD`, which a peer could have moved; (c) the identity file exists, names this `run=` and `leg=`, carries no `closing=` line, and the process group it records no longer exists — while that group exists the composer waits (an orphaned peer may still finish its round) and sends no signal; (d) the log holds no escape-check record for the leg, and the launch's pre-state file (`<log folder>/<runkey>-escape-<leg>.pre`) is present. The composer then does four things, in this order. First it appends the closing mark — one line, `closing=<ts>` — to the identity file and reads the file back; if the mark is not there, it pauses before any tool call. From here on, an interrupted clean close is a pause on re-entry (condition (c)): a helper call it started may still be writing. Second it runs the helper's published POST escape recipe for the leg (the escape-check twin's POST form, published on the wake card's spawn guard and in the Filesystem-escape check bullet of Safety gates) with the launch's own roots, allow-path, iso, and liveness values, and pauses if that call does not exit 0 (a different root set is refused and leaves the pre-state; a different allow-path writes a `refused=capture-failure` record and uses the pre-state up). Third it runs the round check (`/peer-loop`'s `--expect-new-round-since` assertion) with the `baseline=` from the start record. Fourth it writes the end — `python3 scripts/loop-journal.py emit ROLE:end --run <runkey> --role peer --log <probe-log> result="launcher did not finish; new round <M>" leg=<leg>` when a round landed, so that round is never retried; with `result="incomplete: launcher did not finish; no new round"` when none did; with `result="incomplete: launcher did not finish; census failed"` when the check could not say. Then it consumes the leg. **(3) A pause — everything else, in every gate mode.** The composer writes none of the launcher's records for the leg. This covers: no start in the log after a launch that was not refused; a start and no end where any of (a)–(d) fails; an end with no escape-check record (nothing can be written, because the baseline is gone); an exit line with one of the four failure values above; and a launcher leg the stall watchdog judges hung. The ask names the leg and says what the log holds, whether the tools match, and what the identity file says. When a tool does not match, the composer runs neither tool: it puts the ask in chat directly, restores nothing itself, and records the pause once the operator has restored the tooling. On a pause it does not re-run a capture and does not write a record in place of a missing one. In no state does it write a second end, and it never signals a launcher leg's process on its own. What happens next is the operator's disposition. **A quiet launcher leg.** A quiet window is handled as on every other route — the liveness line and a re-arm — with the launcher as the watched identity while it lives, and the recorded group once the launcher is dead and that group remains. The stall watchdog still checks before it classifies, and a live leg with an open gate is still paused, not hung. Its last step is what changes: on a launcher leg the composer kills nothing. Where the watchdog would kill a hung process — a live launcher, or an orphaned group — the leg is a pause. What to stop is the operator's choice; a SIGTERM to a live launcher makes it stop the child and close the leg itself. A quiet log is never death evidence. Every other route keeps the watchdog's kill rule. **Consuming a launcher leg.** The end already exists when the launcher's shell exits, so the verdict-then-end order does not apply to it. The checklist is: the `MONITOR:` record alone → verify (the status line, the escape record, the round) → the verdict, `python3 scripts/loop-journal.py emit CONSUME --run <runkey> --role composer --log <probe-log> source=<wake source> leg=<leg> result="<the verdict one-liner>"` — the text that used to sit on the end record (finding counts, convergence, a usage-limit diagnosis) → the update post → teardown. A `ROLE: end` for the leg with no later `CONSUME:` carrying that `leg=` is an exit that was never consumed — consume it; write no second end. After a context loss the chat-side duties of the exit (the update post, the exit-kind narration) replay from the leg's `CONSUME: … result=` — the composer's recorded verdict; the end holds machine facts only. **Retry.** After an end that says `inconclusive` or `incomplete`, the composer may launch again with a new leg and the same `LOOP_PEER_ROUND`. After `census failed` it first repairs the plan's round history — the checker's own lines, forwarded on the launcher's standard error, name the violation. A round that landed but is unusable (for example one cut short) cannot be retried at the same number: the composer says so in its consume record, and the next launch uses the next round number. **Where the hand route stays** (the `emit ROLE:start` / `emit ROLE:end` pair and the hand-run escape-check pair): a standalone `/peer-loop` with a loop-log context (an unkeyed pair); Cursor subagent peers; executor-seat rounds under the `peer-seat=executor` opt-in (the executor holds the `codex exec` and `emit` grants, never the launcher's); a run with no worktree (`isolation=branch` or `none` — the launcher refuses the topology); inline fallbacks; and a round where the launcher cannot be run or refuses for a cause the composer cannot clear — the composer then says so in its consume record, and `/retro` counts that start as hand-written. For every other composer-seat codex peer round the launcher is the route.
- **Wrapper legs (v48.0 — the wrapper writes the end of its own leg).** Canonical: SKILL → `## Visibility + run-state` → the `ROLE:` log lines bullet → Wrapper legs. Whenever the wrapper wrote a leg's `ROLE: start` it writes its `ROLE: end` too, before its `EXIT:` footer: `result="exit <code>; handoff"` on a zero exit whose last result event ends in a `ROLE: handoff ` line, else `result="incomplete: exit <code>; handoff|no handoff"`, with `leg=` and `duration=`. You write NO end for it — a second end is refused. Your judgment is the leg-bound verdict, as on a launcher leg and by the SAME recipe (Consuming a launcher leg, in the bullet above — its `source=`, this leg's `leg=`, the verdict one-liner in `result=`): the `MONITOR:` record alone → verify → that leg-bound `CONSUME` → the update post → the architect's fold where owed → teardown. An end for the leg with no later `CONSUME:` carrying that `leg=` is an exit never consumed — consume it; the chat-side duties replay from that `CONSUME: … result=`. **The clean close — the ONE end you write for a wrapper leg:** the log holds its start and no end — read from the LOG, never inferred from a missing `EXIT:` footer or a missing `<leg>.exit`, which are later, separate writes: an end that is there is consumed, not written again (a wrapper killed before its teardown, a reboot, or a `SPAWN_WARN check=role-end` line), and you run `python3 scripts/loop-journal.py emit ROLE:end --run <runkey> --role <role> --log <probe-log> result="<the outcome>" leg=<leg>` — `<the outcome>` is `wrapper did not finish; handoff observed` when the role's stream ends in its handoff line, else `incomplete: wrapper did not finish; no handoff`. The HELPER decides whether the role is over: it admits the end only when its role-liveness reader says `over` for the leg. Refused because the leg reads `live` → the role still runs, or its wrapper will write the end: WATCH it, never close it and never spawn beside it. Refused because it reads `unknown` → the evidence cannot tie a process to the role: the end is written only with the word `owner-dead` in `result=`, and you write that word ONLY on the operator's attestation — never on your own reading, never under a grant alone.
- **The waiting rules (canonical: SKILL → loop step 1 → The waiting rules — what was read is said there).** (1) EVERY background spawn call carries an explicit `timeout` above the leg's expected length: with none the host ended the task at 10 minutes, and what that does to the role is the leg's `survive=` word in `<leg>.live` (`off`, one process: the end is a signal the wrapper forwards to the role — `EXIT:143`, as read — never a guarantee the role ended, the role-liveness reader says; `on` is built to run on; `in-tree` will not outlive the composer's process tree, and whether a task's end reaches it is not established; `unverified` is not established either way). Read the largest `timeout` the host takes from its own tool description; never assume one. (2) A watch arm has an END — a Monitor arm ended at 10 minutes: its expiry notice is a wake; the role live → re-arm in the same turn. No single arm is assumed to cover a leg. (3) Exit 5 with `SPAWN_DETACHED supervisor_pid=<n>`, exit 6 with `SPAWN_LOST …`, or a background task that ended while the leg's `<leg>.live` stands, is NOT the role's exit and never a reason to spawn: the leg's state is in its files beside the probe log — `<leg>.exit` → the wrapper returned: consume the leg (its end is read from the log, not from the file); `<leg>.live` with no `.exit` → read `wrapper_pid=` and test it (`kill -0`): alive → the role is STILL RUNNING — re-arm a watch on that pid and the role log (the resolved Layer-2 mechanism, else bounded foreground polls), never a second spawn; not alive → read the log: an end that is there is consumed, and a start with no end is the clean close above, which the helper decides. `python3 scripts/loop-watchdog.py tick --base <abs base>` (no `--act`: read-only) prints the reader's count per live run, `legs=live:<n>,unknown:<n>,over:<n>`. The same read finds a surviving role at a Resume: every `<stem>.live` with no `<stem>.exit` beside it. (4) A HEADLESS composer never ends its turn while a leg of the run reads `live`: with nothing pending it ends and the leg is nobody's.
- **Stopping a role:** TERM to its RECORDED pid — `wrapper_pid` in the identity record and in `<leg>.live`, under the split the supervisor's — only while its `<leg>.live` stands with no `<leg>.exit` beside it and `kill -0` finds the pid (the wrapper turns `.live` into `.exit` as its last act; a wrapper killed outright can leave a `.live` whose pid number is another process's now — where that cannot be excluded, send nothing to the pid: on a run with a run worktree use the stop command, which compares the recorded start token; on a run with no run worktree that command sees no leg, and such a pid is the operator's). The wrapper forwards the signal and writes the records it always wrote (`EXIT:143`, its `incomplete` end). Ending the host's background task or your own shell stops only the tail (exit 5): a role whose `<leg>.live` says `survive=on` is built to run on.
- **Anchor discriminator (mechanical):** monitors and consumes PARSE top-level stream-json `rate_limit_event` objects and mechanically reject `allowed`/`allowed_warning` statuses; textual anchors (session-limit strings, `ROLE: handoff`) are ADVISORY — they classify only past the recorded event/byte baseline AND corroborated by the authentic terminal result event plus shell completion (line-start matching cannot work inside stream-json strings, and every spawn prompt quotes the anchor vocabulary into its own log — 6 false positives observed live, all caught by consume-time verification, which stays MANDATORY); unknown event shapes return an anomaly, never a silent classification; pinned Tier-1 strings are matched EXACTLY — a monitor may never loosen them into regexes (a loosened `.*session.*limit` matched plan prose live); every watcher arms under a marker identity (`SENTINEL_<runkey>_<wrap>` pattern) so stale watchers stay identifiable. **From v33.4** the spawn wrapper rewrites `allowed`/`allowed_warning` events to a `USAGE_TICK …` line on its stdout mirror ONLY (the role log stays byte-verbatim), so an event-shaped anchor reaching a mirror watch SHOULD be a limit — yet the status parse before routing stays MANDATORY on every wrapper version (an older wrapper still mirrors those events; a monitor tailing the role log still sees every one): on an `allowed`/`allowed_warning` status REJECT it — no wake, no liveness re-arm — and never take a bare `rejected` match as the limit test, because a healthy `allowed` event routinely carries `"overageStatus":"rejected"` too.
- **Exit-classify child-kind routing:** at any role exit other than a launcher leg's, a live child, a `task_updated status=killed` record in the CURRENT activation's terminal window, or a missing/non-terminal handoff sentinel classifies `ROLE: end result=incomplete`.
