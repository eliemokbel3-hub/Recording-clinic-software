- **Journal line family (ADDITIVE, optional-emit — admitted from two observed harness runs).** Alongside the required wake families above, canonical grammar ADMITS one ADDITIVE journal family — composer-written run-state breadcrumbs that survive context loss: `CONSUME:` / `CLASSIFY:` / `ADOPT:` / `KILL_DUP:` / `OWNERSHIP:` / `VERIFY_OK:` / `VERIFY_FAIL:` / `SENTINEL_ARMED:` / `SENTINEL_FIRE:` / `SPAWN:` / `IDENTITY:` / `NOTIFY:` plus the two wrapper-NATIVE tee shapes `EXIT:<code>` (no space) and `SPAWN_WRAPPER_START ts=<iso> …` (colonless) — both pinned exactly as the wrapper emits them (the wrapper's OTHER probe-log records — its `ROLE: start`, `OWNERSHIP: escape-check`, and `OWNERSHIP: exit-census`, DR-1's enumerated set — are HELPER-emitted admitted shapes, never new line-starts). Emission is OPTIONAL: a downstream composer that never journals stays fully conformant; parsers and `/retro` RECOGNIZE the family and MAY ignore it (advisory context, never required input); the companion STICKY card MANDATES emission for composers following it — run-config requires what canon admits. Shape rules: every journal type except the two wrapper shapes is COLON-terminated (`TYPE: key=value …`, the `ROLE:` key=value vocabulary, strings quoted — and a quoted value must contain NO double-quote character: the helper's quote grammar has no escape, so an embedded `"` REFUSES the whole emission (Constraint-13 input safety) — use single quotes inside values when quoting config text like `labels=""` into a `reason=`/`detail=` rationale); the `VERIFY_OK:` colon is PINNED (live variance observed — three colonless occurrences in one run; historical logs carry them, new emissions never do); `VERIFY_OK: children=<n>` is the ADMITTED pre-exit live-child-check shape on that type (loop step 1's atomic-exit rule — a key on the existing type, never a new line-start); the v32 TB.3 watch/sentinel trio (admitted from the run-7 F-2 evidence — 28 of that run's 34 unknown line-starts were hand-echoed `SENTINEL_FIRE:`/`SPAWN:`/`VERIFY_FAIL:` vocabulary) is TOOL-EMITTED like every family: `SPAWN:` (spawn-event narration; REQUIRES `role=` — the WRITER, per the `--role` identity-owner rule — + `child=<the spawned role>` + `detail=`) and `VERIFY_FAIL:` (failed-verification narration; REQUIRES `role=` + `detail=`) are composer writes on the D8 idle clock, while `SENTINEL_FIRE:` (the armed sentinel's quiet-window fire evidence; `role=` optional enum-checked, `id=`/`reason=` additive free keys) is EXCLUDED from the composer-write clock — a sentinel fires precisely when the composer is quiet, so its lines never reset the idle gap the D8 clock measures; the armed sentinel shell invokes `python3 scripts/loop-journal.py emit SENTINEL_FIRE --run <runkey> --role composer --log "<probe-log>" [id=<sentinel id>] reason=quiet-window`, never a raw `echo` into the probe log (the run-7 hand-echo is exactly what this admission retires); `CONSUME:` names its wake source with `source=<...>` — `source=` is the ONE key, and the earlier `wake=` variant is RETIRED (recognize it in historical logs, never emit it) — the ONE-key clause pins the WAKE-SOURCE key, and additive per-source keys ride alongside it: `source=idle-reentry` (the idle re-entry checkpoint record) REQUIRES numeric `gap_min=<whole minutes>`; `NOTIFY:`'s verb slot carries the pinned outcome-STATE vocabulary {`sent`, `queued`, `failed`, `retried`, `batch-flushed`, `skipped`} with `mode=<immediate|queued>` AND `epoch="<activation id>"` REQUIRED on every non-`skipped` emission and `batch=<batch-key>` on flushed members and their batch-level `failed`/`retried` records — the delivery contract is Safety gates → Notify-at-gate (`sent`/`skipped` are the pre-v31 verbs; a MODE-LESS `sent` is recognized in historical logs, never emitted forward — the retired-shape pattern; values on the existing type, never a new line-start); and `OWNERSHIP:`'s admitted subtype vocabulary is {`auto-disposition`, `label-snapshot`, `phases-extended`, `commit`, `smoke-pass`, `gate-disposition`, `must-pause`, `escape-check`, `config-change`, `profile-switch`, `exit-census`, `sticky-ack`, `config-snapshot`, `config-revoke`, `away-grant`, `away-end`} — set-equal to canonical's emit sites by construction (`away-grant` / `away-end` are the away grant's records, written only by the `away` subcommand — grammar in **Away mode**; v32 D1: `config-snapshot` is the run-start `high-auto=` authority attestation — REQUIRES `role=composer` + `iso=` + `plan=` + `epoch=` + `key=high-auto` + `value=<on|off>` + the tool-DERIVED identity-binding `config_hash=`, FIRST-wins per policy log, contemporaneous; `config-revoke` is the monotonic one-way mid-run disable — REQUIRES `role=composer` + `key=high-auto` + `epoch=<N from 1>`, effective at its append, idempotent on retry; both live in the iso-keyed policy log per Preflight step 13; `label-snapshot` is their RETIRED predecessor — recognized in historical logs, never emitted forward): `sticky-ack` is the composer's run-start STICKY-read receipt (`role=composer` + the helper-computed, mirror-compared `sticky_hash=` REQUIRED — round-4 S-A; emitted at the Preflight-tail loop-entry gate via `emit OWNERSHIP:sticky-ack --repo <checkout>`, and the oracle's `missing-sticky-ack` whole-file duty requires its line BEFORE the run's first `SPAWN_WRAPPER_START` in same-file append order, cross-file fallback STRICT `ack.ts < spawn.ts` only), `exit-census` is the WRAPPER's post-`wait` survivor census (`role=` + `leg=` + `children=` REQUIRED — DR-1 item 4; a distinct subtype, deliberately NOT `VERIFY_OK:`, so the role's pre-handoff self-check stays meaningful), `phases-extended` is Run isolation's phase-range record (its required keys live there), `commit` REQUIRES `hash=<commit hash>` + `seat=composer` (**Auto-commit (git-safety)**), `smoke-pass` records a phase's green live-user smoke (loop step 6) — or, with `smoke_by=agent`, an agent-run smoke such as the away live smoke (**Away mode**), `gate-disposition` records the operator's gate decision (loop step 6 — or, carrying the away pair, a decision the composer took under a bound away grant; **Away mode**; REQUIRES `key=` + `choice=`, its `ts=` anchoring the re-fire epoch any re-fired `NOTIFY:` cites), `must-pause` records the fail-closed route itself (Notify-at-gate, Safety gates; REQUIRES `key=` and is PAIRED same-`ts=`/same-`key=` with its immediate `NOTIFY:` emission — a considered-and-declined auto route writes THIS record, never a bare `skipped` token on `auto-disposition`), `escape-check` records the per-headless-activation filesystem-escape evidence (Filesystem-escape check, Safety gates; REQUIRES `role=`, `result=<clean|dirty>`, `before=`/`after=` digests, and the `roots=` manifest — `result=` must AGREE with digest equality across every manifest root other than the one named by the optional `edit_surface=<root>:<changed|unchanged>` key; the optional `attributed=`/`attributed_age=` pair is advisory on `dirty` — v33.0 D4), `config-change` records every mid-run `Loop config:` rewrite (the `Loop config:` bullet below; REQUIRES `key=` + `from=` + `to=`), and `profile-switch` records a usage-exhaustion account-switch outcome (Usage-exhaustion recovery; REQUIRES `from=` + `to=` + `transferred=<yes|no>` + `alive=`); on the `high-auto=on` HIGH auto-route (Safety gates' composer-seat policy), the `auto-disposition` record ADDITIONALLY REQUIRES the attestation PAIR `authority_check=<the snapshot's config_hash, echoed whole — exact 12-hex>` + `authority_epoch=<count of prior valid revocations>` — the record-side proof the authority check ran (the hash convention is the config-snapshot rule, Preflight step 13; elsewhere on `auto-disposition` the pair stays additive-optional, and the label-era `label_check=` key is recognized in historical logs, never emitted forward); the cap transitions bind their classes mechanically — `cap-raise=+1` pairs `class=cap-raise` and `cap-accept=close` pairs `class=cap-accept`, both `mode=immediate` (Termination's wire contract); subtypes on the existing type, never new line-starts. The reserved-vs-additive fence: the canonical prefixes — `Wake:` `ROLE:` `WATCH:` `MONITOR:` `DELEGATION:` `Loop config:` — remain RESERVED for canonical-shaped lines only; a journal line never rides a canonical prefix, and composer narration goes to chat, never the probe log. The family is CLOSED (operator ruling; ledger-4e evidence: 16 invented phase-close bookkeeping lines across `PHASE:`/`COMMIT:`/`PUSH:`/`PR:`/`SMOKE:`/`MUST-PAUSE:`/`DOCUMENT:` prefixes in one run): a composer NEVER invents a new line-start type — phase-close/commit/push/PR/smoke bookkeeping belongs in chat and the plan/handoff artifacts (or the admitted `OWNERSHIP:`/`NOTIFY:` records where their shapes genuinely fit), and an unadmitted prefix in a probe log is misrouted narration that a census flags as unknown-type, never grammar. ONE recorded journal-family shape on a canonical prefix is admitted: `WATCH: cancelled ts=<iso> run=<runkey> role=<role> reason="..."` — the cancel-at-exit artifact. Identity keys are ADDITIVE-OPTIONAL on canonical lines: `ROLE: end` and `WATCH: armed` MAY carry `shell=` / `pid=` / `claude=` / `session=` where known — the ONE `ROLE: end` shape is otherwise unchanged and remains the only end-line form. Late-bound identity (`IDENTITY:`) — explicitly reconciled with the timestamp-authority clause on the `ROLE:` bullet below, which is UNCHANGED: a role's session id learned after its `ROLE: start` was written is recorded as one `IDENTITY: update ts=<iso> run=<runkey> role=<role> session=<id>` line, NEVER by rewriting or backdating the `ROLE: start` line; the spawner-written `start`/`end` lines remain the run's ordering truth exactly as that clause states, and an `IDENTITY:` line is an additive record whose own `ts=` carries the same authority as any other line its writer emits (composer-written = authoritative wall clock; role-written = advisory) — the two clauses COMPOSE: a late id is NEW KNOWLEDGE appended in write order, never a correction of an existing line. Probe logs append MONOTONICALLY in write order; a late-written EVENT line keeps `ts=` as the event time and ADDS `logged_ts=<iso>` when the two differ (ordering stays truthful without backdating). And the ts-form pin, which applies to EVERY probe-log artifact line, canonical and journal alike: `ts=` values are REAL clock reads in local ISO-with-offset (`date -Iseconds`) — never UTC-`Z`, never composed, rounded, or future-dated from memory (fabricated and rounded timestamps were both observed live, and a fabricated role-handoff timestamp forces `/retro` onto composer lines; the timestamp-authority clause already treats role-written `ts=` as advisory — this pin fixes the FORM for every writer). v33.0 ADDITIVE KEYS (helper-validated, oracle-admitted; no new type, subtype, class, or state): `pass=<phase-or-slice>.p<N>` + `peer_round=<k>` + `cap=<N>` ride an orchestrated `ROLE: start role=peer` (all three or none — the per-pass cap counter, D3) and, as a two-key `pass=`+`cap=` bundle, the cap-transition records; `residue=deferred` rides a `cap-accept=close` record whose executor verdict was `defer-residue` (D2); `edit_surface=<root>:<changed|unchanged>` + the advisory `attributed=<foreign iso> attributed_age=<min>` ride `OWNERSHIP: escape-check` (D4); `rec=<executor|composer>:<disposition>` rides `OWNERSHIP: must-pause` and `gate-disposition` (D6). The composer prose for these keys: loop step 4's per-pass cap keys + Termination's cap row (D2/D3), the Filesystem-escape check (D4), the MUST-PAUSE surfacing bullet (D6) — all in Safety gates unless named; the helper refuses a malformed value.
- **Stall watchdog (check-then-classify).** If a spawned role's streaming surface stops growing for ~10 minutes, the composer CHECKS before acting — never kill-on-timeout. (A turn-based composer gets the ~10-minute observation from the two-layer wake contract above: the monitor subagent's liveness-window return IS the observation trigger, its snapshot supplying the streaming-surface evidence, with the sleep-sentinel wake timer as the fallback on hosts without subagents. With Q5 liveness OFF the quiet-window wake is disabled too, so a turn-based composer's autonomous stall detection narrows to anchor/exit wakes — the watchdog's ~10-minute observation applies where a quiet-window wake path is configured; without any concrete wake path, a stalled role goes unnoticed until the user asks.) An alive role that recorded an open gate is PAUSED, not hung: a MUST-PAUSE surfacing looks identical to a stall on the streaming surface, and killing it would destroy a valid wait. The check is backend-shaped — CLI backends: check the pid is alive; Cursor subagent: check the transcript/agent status and cancel/respawn if dead. Kill only a demonstrably-hung process (e.g. a codex stdin-hang), and only by its RECORDED identity — the spawn's own PID (a pidfile or the composer-recorded value) or an exact full-path command match, NEVER a broad `pgrep -f` pattern kill (a pattern sweep matches unrelated processes — another run's roles, the composer's own tooling; observed downstream) — then report what was killed and why. A role that died on a usage limit is DEAD-on-limit, not hung — route it to **Usage-exhaustion recovery** instead of the kill path. **Stopping a wrapper leg (by its RECORDED pid, never by ending the composer's shell).** A wrapper-spawned role's recorded identity is `wrapper_pid` — on its identity record and in its `<leg>.live` file — and under the wrapper's split that pid is the SUPERVISOR's, not the pid of the composer's background shell, which holds only the tail. To stop the role, send TERM to that recorded pid — but only while the leg's `<leg>.live` stands with no `<leg>.exit` beside it and `kill -0` finds the pid: the wrapper turns `.live` into `.exit` as its last act, so that pair is the wrapper unless it was killed outright and its number has been taken since. Where that cannot be excluded — an old leg, a small pid range — send nothing to the pid: on a run with a run worktree the stop command (**Away mode** → Stopping an away run) compares the recorded start token before every signal, at the price of stopping every leg of the run; on a run with no run worktree that command sees no leg, so there a pid that cannot be tied to the wrapper is the operator's to deal with. The wrapper forwards the signal to the role and writes the records it always wrote (`EXIT:143`, the footer, and its own `incomplete` end). Ending the host's background task, or the composer's shell, is not a way to stop a role whose `<leg>.live` says `survive=on`: it ends the tail (exit 5, `SPAWN_DETACHED`), and the role is built to run on (loop step 1, the waiting rules — what was read of that, and what was not). **Launcher-leg exception.** On a launcher leg the check and the classification stay and the kill does not: the composer kills nothing there, and a leg judged hung — a live launcher, or an orphaned child group — is a pause (**`ROLE:` log lines** → Launcher legs). Every other route keeps the rule above.
- **Usage checkpoint (warn-only).** At preflight (baseline) and in loop step 9 before spawning the next phase's executor, probe the account pools of the CLI backends in use and report one line per pool, warning when a pool is ≥80% used — the fixed default, overridable per invocation (persisted as the optional `usage_warn=` run-settings key below). The between-phase cadence cannot see mid-phase burn — a single long phase can exhaust a pool that was comfortably under threshold at its start (observed live: 45% at preflight, dead mid-phase) — so additionally: at preflight, warn when a pool's remaining headroom looks smaller than a rough per-phase burn estimate (from the plan's phase sizes and any prior run's observed burn; still warn-only); re-probe when resuming an executor mid-phase; and rely on the heartbeat's tier-1 error-string / `rate_limit_event` watch to catch an in-flight limit death immediately (routing to Usage-exhaustion recovery). The loop NEVER pauses, stops, or throttles on usage numbers — the numbers inform the user; the user decides. Probes (short timeout; any failure = one "probe failed" / "not exposed" line, then continue): **claude** — `"<pinned claude>" -p "/usage" --output-format text </dev/null` (per-profile: prefix with the profile's `CLAUDE_CONFIG_DIR` — under `router=on` the ROUTED folder, read from the live role's identity record `profile_dir=`, never the `Loop config:` line's fallback — under loop step 1's identity-value ambiguity rule: an ambiguous folder is one "probe failed" line, never a prefix; the headline `Current session` / `Current week` percentages are official server-side numbers); **codex** — the `app-server` JSON-RPC `account/rateLimits/read` method (pipeline recipe in `docs/integrations/cross-agent-orchestration.md` → Usage / rate-limit probes); **Cursor subagent** backend — "not exposed" (no usage surface exists).
- **`ROLE:` log lines (canonical definition).** Every role activation gets one `ROLE: start` and one `ROLE: end` line in the phase's probe log (placement pinned — the Writer responsibility clause below) — the same greppable key=value family as `DELEGATION:` lines, strings quoted:

  ```text
  ROLE: start ts=<iso> run=<runkey> phase="..." role=<composer|executor|architect|delegate|peer|advisor|reviewer> backend=<cursor-subagent|codex|claude-p|live-session> model="<slug>"
  ROLE: end ts=<iso> run=<runkey> role=<...> result="<one-liner>"
  ```

  `run=<runkey>` is the run's log prefix (here `stage-<N>`). A `start` line MAY additionally carry `effort="<level>"` and/or `profile="<name>"` — additive optional keys, present only when the wizard resolved an explicit effort level or a `claude -p` account profile for that role; absence is legal (inherit-effort / default-profile roles omit them), and `/retro` needs no change — it defers to this definition. A `start` line MAY also carry `grants_include="<scoped grant shapes>"` — an additive-OPTIONAL audit key (the granted verification-command shapes carried in the spawn), never required, and a COMPOSER-written `ROLE:` key only, never a wrapper-tee key. Forward `ROLE: start`/`ROLE: end` pairs additionally carry a shared `leg=<activation key>` — a PER-ACTIVATION identity, REQUIRED on forward pairs and NEVER REUSED within a run: mint a fresh value per activation — repeat work gets a suffixed key (`peer-verify-r2`, never a bare repeated `peer-verify`; run-4's sequential reuse is recognized-historical, not the forward convention), and the oracle's scorer-selected `--forward-legs` mode enforces both legs (`missing-leg` / `reused-leg`) while historical corpora replay without the flag and keep the aggregate fallback (e.g. `leg=phase-b-fix`; run-4's composer already emitted the key live): the spawner stamps the SAME value on an activation's `start` and its `end`, so interleaved same-role activations pair EXACTLY instead of by aggregate (run, role) state — the aggregate matcher R28-HIGH-01 proved lets an unmatched end consume a DIFFERENT open activation of the same role, so opposing missing-start/missing-end errors cancel (run-4's 28/26 read as "off by two" while the true damage was ~8 malformed activations). A `ROLE: end` with NO open activation to close — no open start with the same `leg=`; for a leg-less end, no open activation of that (run, role) at all — is the END-WITHOUT-START defect class: the oracle flags it as a whole-file violation instead of silently accepting it (retro evidence gap #2). Records predating the key fall back to the aggregate matcher: a leg-less end closes the most recent open activation of its (run, role), and a leg-carrying end whose leg matches nothing may close the most recent leg-less open activation (the recognized run-4 shape) before it is a violation. The `role=` vocabulary is a CLOSED enum — the values in the fence above and nothing else: a SPAWNED reviewer is an activation like any other spawned role, with its own `ROLE: start`/`ROLE: end` pair, distinct from an in-session `/review-loop` round, which is NOT an activation and logs `ROLE: round` only (the round rule below, unchanged). Backend truthfulness pin (one mapping, F13): an interactive Cursor composer session is `backend=live-session` — `model=` carries the specificity (e.g. `model="composer"`); `cursor-subagent` names only a genuinely spawned Cursor subagent. The `end` line MAY carry best-effort usage fields — `turns≈<n>` / `tokens≈<n>` / `duration=<seconds or h:mm:ss>` — only where the backend exposes them; absence is legal and is reported as "not exposed", never guessed (Cursor subagents expose no token counts to the composer; `codex exec` / `claude -p` sometimes print usage; timestamps always work). The `end` line — and `WATCH: armed` — MAY additionally carry the identity keys `shell=` / `pid=` / `claude=` / `session=` where known: additive-optional, admitted with the journal family (the **Journal line family** bullet above). **Writer responsibility (lifecycle placement PINNED — the probe log):** the spawning session OWNS the pair for each role it spawns — appended to the phase's `<runkey>-probe.log` at spawn and on observed completion (the spawner knows the backend, model, and timestamps) — with the wrapper as its delegated emitter of BOTH lines on wrapper spawns (the start since DR-1, single-emitter; the end from v48.0 — Wrapper legs, below), the peer launcher as its delegated emitter of BOTH lines on a launcher leg (Launcher legs, below), and every composer-written lifecycle record tool-emitted via the helper (`emit ROLE:start` / `emit ROLE:end` — never hand-authored, Constraint 8). ROLE-LIFECYCLE records — `ROLE: start`/`ROLE: end` with the identity keys admitted on them, plus `IDENTITY:` updates — live in the PROBE LOG: it is the composer's channel and the census's corpus scope, so lifecycle written elsewhere is invisible to every pairing/window assertion. The pre-pin text underdetermined this and two compliant runs chose opposite placements on the same skill text: the runs-#3/#4 probe-log placement IS the pinned convention; the v31patch-line runs' tee-log placement is a RECOGNIZED historical variance (recognize on replay, never emit forward). The role's tee log is the child's streamed output — the composer appends no lifecycle records there, and the wrapper's probe-log contribution is exactly the DR-1 enumerated emission set (Backends): its native START/`EXIT:` pair plus the helper-emitted `ROLE: start` / escape-check / exit-census records — for wrapper-spawned roles the wrapper IS the `ROLE: start` writer and, from v48.0, the writer of the matching `ROLE: end` as well (Wrapper legs, below — the composer writes that end only in the clean close stated there; single-emitter ownership; a composer-authored start beside the wrapper's is the duplicate-start violation). **Launcher legs.** A composer-seat codex peer round started through the peer launcher (`python3 -I scripts/loop-peer-launcher.py`) is a launcher leg. The launcher writes that leg's `ROLE: start` (marked `via=launcher`), its `OWNERSHIP: escape-check` record, and its `ROLE: end` — all through the helper. The composer writes `WATCH: armed` and `WATCH: cancelled`, the `MONITOR:` record where it is the writer, the `CONSUME:` verdict, and everything else it writes around a peer round today (the ref snapshot pair, the update post, the findings route) — never a start or an end for the leg, except in the clean close below. **The launcher owns the close while it is alive.** Both wake layers of a launcher leg watch the launcher — its background shell, and the `launcher_pid` its identity file records — not the child. A child's death is not an exit event: after codex exits, the launcher is still writing the leg's records. The composer consumes the leg, or does anything below, only once the launcher is positively dead: its shell has reported its exit, or its recorded pid is gone. With neither — no shell report and no recorded pid — the composer cannot tell, and pauses. **The exit line can only add a pause.** When a `PEER_LAUNCH_EXIT` line was delivered and says `start=uncertain`, `end=failed`, `tools=changed`, or an `escape=` other than `0` (`none` included), the leg is a pause whatever the records show. A line without those values, or no line at all, decides nothing: the records do. No field of the line ever permits a write. Then the leg is in exactly one of three states. **(1) Complete.** The probe log holds the leg's start, its escape-check record, and its end. The composer consumes it (the checklist below). An escape-check record that carries `refused=` is judged as on every other route: a must-pause. **(2) The clean close — the one case where the composer writes the launcher's records for it.** The exit line adds no pause, and every one of these holds, each read from a record or a recorded identity: (a) the probe log holds the leg's `ROLE: start` with `via=launcher`, `baseline=`, and `tool_ids=`, and no `ROLE: end` for the leg; (b) both tools the launcher calls (`scripts/loop-journal.py` and `scripts/loop-history-check.py`, beside it) hash to those ids by `git hash-object` — never a comparison with `HEAD`, which a peer could have moved; (c) the identity file exists, names this `run=` and `leg=`, carries no `closing=` line, and the process group it records no longer exists — while that group exists the composer waits (an orphaned peer may still finish its round) and sends no signal; (d) the log holds no escape-check record for the leg, and the launch's pre-state file (`<log folder>/<runkey>-escape-<leg>.pre`) is present. The composer then does four things, in this order. First it appends the closing mark — one line, `closing=<ts>` — to the identity file and reads the file back; if the mark is not there, it pauses before any tool call. From here on, an interrupted clean close is a pause on re-entry (condition (c)): a helper call it started may still be writing. Second it runs the helper's published POST escape recipe for the leg (the escape-check twin's POST form, published on the wake card's spawn guard and in the Filesystem-escape check bullet of Safety gates) with the launch's own roots, allow-path, iso, and liveness values, and pauses if that call does not exit 0 (a different root set is refused and leaves the pre-state; a different allow-path writes a `refused=capture-failure` record and uses the pre-state up). Third it runs the round check (`/peer-loop`'s `--expect-new-round-since` assertion) with the `baseline=` from the start record. Fourth it writes the end — `python3 scripts/loop-journal.py emit ROLE:end --run <runkey> --role peer --log <probe-log> result="launcher did not finish; new round <M>" leg=<leg>` when a round landed, so that round is never retried; with `result="incomplete: launcher did not finish; no new round"` when none did; with `result="incomplete: launcher did not finish; census failed"` when the check could not say. Then it consumes the leg. **(3) A pause — everything else, in every gate mode.** The composer writes none of the launcher's records for the leg. This covers: no start in the log after a launch that was not refused; a start and no end where any of (a)–(d) fails; an end with no escape-check record (nothing can be written, because the baseline is gone); an exit line with one of the four failure values above; and a launcher leg the stall watchdog judges hung. The ask names the leg and says what the log holds, whether the tools match, and what the identity file says. When a tool does not match, the composer runs neither tool: it puts the ask in chat directly, restores nothing itself, and records the pause once the operator has restored the tooling. On a pause it does not re-run a capture and does not write a record in place of a missing one. In no state does it write a second end, and it never signals a launcher leg's process on its own. What happens next is the operator's disposition. **A quiet launcher leg.** A quiet window is handled as on every other route — the liveness line and a re-arm — with the launcher as the watched identity while it lives, and the recorded group once the launcher is dead and that group remains. The stall watchdog still checks before it classifies, and a live leg with an open gate is still paused, not hung. Its last step is what changes: on a launcher leg the composer kills nothing. Where the watchdog would kill a hung process — a live launcher, or an orphaned group — the leg is a pause. What to stop is the operator's choice; a SIGTERM to a live launcher makes it stop the child and close the leg itself. A quiet log is never death evidence. Every other route keeps the watchdog's kill rule. **Consuming a launcher leg.** The end already exists when the launcher's shell exits, so the verdict-then-end order does not apply to it. The checklist is: the `MONITOR:` record alone → verify (the status line, the escape record, the round) → the verdict, `python3 scripts/loop-journal.py emit CONSUME --run <runkey> --role composer --log <probe-log> source=<wake source> leg=<leg> result="<the verdict one-liner>"` — the text that used to sit on the end record (finding counts, convergence, a usage-limit diagnosis) → the update post → teardown. A `ROLE: end` for the leg with no later `CONSUME:` carrying that `leg=` is an exit that was never consumed — consume it; write no second end. After a context loss the chat-side duties of the exit (the update post, the exit-kind narration) replay from the leg's `CONSUME: … result=` — the composer's recorded verdict; the end holds machine facts only. **Retry.** After an end that says `inconclusive` or `incomplete`, the composer may launch again with a new leg and the same `LOOP_PEER_ROUND`. After `census failed` it first repairs the plan's round history — the checker's own lines, forwarded on the launcher's standard error, name the violation. A round that landed but is unusable (for example one cut short) cannot be retried at the same number: the composer says so in its consume record, and the next launch uses the next round number. **Where the hand route stays** (the `emit ROLE:start` / `emit ROLE:end` pair and the hand-run escape-check pair): a standalone `/peer-loop` with a loop-log context (an unkeyed pair); Cursor subagent peers; executor-seat rounds under the `peer-seat=executor` opt-in (the executor holds the `codex exec` and `emit` grants, never the launcher's); a run with no worktree (`isolation=branch` or `none` — the launcher refuses the topology); inline fallbacks; and a round where the launcher cannot be run or refuses for a cause the composer cannot clear — the composer then says so in its consume record, and `/retro` counts that start as hand-written. For every other composer-seat codex peer round the launcher is the route. **Wrapper legs (v48.0 — the wrapper writes the end of its own leg).** Whenever the spawn wrapper wrote a leg's `ROLE: start` it writes that leg's `ROLE: end` too — through the helper, before its `EXIT:` footer (which stays the log's last line), on a normal exit and on a forwarded-signal one, with survival on or off: `result="exit <the footer's code>; handoff"` when that code is 0 and the last result event of the leg's stream ends in a `ROLE: handoff ` line, else `result="incomplete: exit <code>; handoff|no handoff"` (`incomplete` is the word the same-round retry rule looks for), with `leg=` and `duration=<whole seconds since the start was written>`. That end holds machine facts only. The composer therefore writes NO end for a wrapper leg — a second end for the leg is refused — and its judgment is the leg-bound verdict, exactly as on a launcher leg and by the same published recipe (Consuming a launcher leg, above — its `source=`, this leg's `leg=`, the verdict one-liner in `result=`): the `MONITOR:` record alone → verify → that leg-bound `CONSUME:` → the update post → the architect's fold where one is owed → teardown. A wrapper leg's `ROLE: end` with no later `CONSUME:` carrying that `leg=` is an exit that was never consumed — consume it, write no second end; after a context loss the chat-side duties replay from the leg's `CONSUME: … result=`. A post-START exit that never wrote the start writes no end, and none is owed. **The clean close — the ONE case where the composer writes a wrapper leg's end.** The probe log holds the leg's start and no end — and that is read from the log itself, never inferred from a missing `EXIT:` footer or a missing `<leg>.exit`, which are later and separate writes (a wrapper stopped after its end and before its footer, or whose footer append failed, leaves an end with no footer: such a leg is consumed, not closed) — after a wrapper killed before its teardown (it writes neither the end nor the footer), a reboot, or a `SPAWN_WARN check=role-end` line on the wrapper's stdout (the helper refused the wrapper's own end; the exit code is unchanged — read on Linux only; a host whose Python launcher runs the interpreter as its own child would meet it on every leg) — and the role's work is over. "Over" is the helper's read, never the composer's: `python3 scripts/loop-journal.py emit ROLE:end --run <runkey> --role <role> --log <probe-log> result="<the outcome>" leg=<leg>` — `<the outcome>` being `wrapper did not finish; handoff observed` when the role's stream ends in its handoff line, else `incomplete: wrapper did not finish; no handoff` — is admitted, for a leg the log's folder holds evidence of (a `<leg>.live` / `<leg>.exit` file, or an identity record naming the run and the leg), only when the role-liveness reader says `over` for it. While the leg reads `live` the call is refused, nothing written — its wrapper will write the end itself, or a role that outlived its wrapper is still running: watch it (loop step 1, the waiting rules), never close it. While it reads `unknown` — the evidence cannot tie a process to the role, as after a wrapper that died before it recorded one — the call is refused unless `result=` carries the word `owner-dead`, which the composer writes ONLY on the operator's attestation that the role is dead (the same word admits the close — `/close-run`), never on its own reading and never under a grant alone. A composer still acting on text from before v48.0 that writes an executor leg's end meets one of these refusals; neither loses a record. Then it consumes the leg as above. Every OTHER activation — a Cursor subagent, a CLI role started without the wrapper, a live session, the hand-route peer rounds above, an inline fallback — keeps the rule that follows. On every other role's exit wake the OBSERVING/SPAWNING session writes that role's `ROLE: end` as the FIRST of its closure records — after the verify-then-classify read and its `CONSUME:` verdict record (required on `/execute-loop` runs; optional only at the grammar-admission layer), before the update post and the kind-classification narration (the exit branch of the return-handling duty in **Wake arming artifacts**; the reconciled v32.5 order); a live-session role (executor/architect) appends its own lines to the phase's `.cursor/loops/<runkey>-probe.log` directly, creating the file if absent (its historical `stage-<N>-executor.log` self-append is the same recognized tee-log variance). **Timestamp authority:** the composer (the spawning session) is the SOLE timestamp authority for the lines it writes — `start`/`end` `ts=` values carry the spawner's wall clock and are the ordering truth for the run. A spawned role's self-written `ts=` is ADVISORY only: headless sessions emit junk wall-clock (observed live: placeholder `ts=<date>T00:00:00` from two executors in one run), so the spawn prompt passes the current wall-clock time at spawn as the role's anchor (loop step 1), and consumers treat a role-written `ts=` as approximate, never as ordering truth. In-session `/review-loop` rounds are not activations — they emit a single per-round `ROLE: round` line (`role=reviewer`) through the helper instead (`emit ROLE:round`, open to any seat; the recipe is `/review-loop`'s). The per-phase status line mirrors each role's backend/model from these lines.
- **`ROLE: handoff` exit sentinel (same `ROLE:` family — no new prefix).** A spawned executor's REQUIRED final output line classifies its exit machine-readably:

  ```text
  ROLE: handoff ts=<iso> run=<runkey> reason=<phase-complete|composer-run|must-pause> [gate="<one-liner>"] [suites="<what the composer should run>"] [consults=<reserved>/<cap> refusals=<n> dangling=<n>]
  ```

  Written by the role itself as its last act (unlike `start`/`end`, which the spawner writes) — its `ts=` is therefore advisory per the timestamp-authority rule above: anchored on the spawn prompt's wall-clock carry plus elapsed time, useful but never ordering truth. The sentinel is preceded by the mechanical live-child check: immediately before its final message the role writes `VERIFY_OK: children=<n>` (Journal line family) counting its still-live child tasks — a handoff following a `VERIFY_OK: children=<n>` with `n` > 0 is a contract violation (the role must keep waiting), and an absent `VERIFY_OK: children=` record before a handoff marks the exit unverified for the census. The optional consult counters appear only on advised executors (Optional advisor); the composer reconciles them against the phase's `CONSULT:` ledger. `reason=phase-complete` = the phase's work is done; `reason=composer-run` = the executor needs the composer to run named commands and resume it (see loop step 3); `reason=must-pause` = an open gate recorded per the record-and-end contract. **Absence of a handoff line on exit = a crash or limit-death** — the composer classifies via the heartbeat's error-string watch and routes limit-deaths to Usage-exhaustion recovery; without it, exit classification is manual archaeology (observed live: a failed resume cost ~7 minutes before detection). The same honesty rule governs the spawn wrapper's exit footer: an ABSENT `EXIT:<code>` line means the composer CLASSIFIES the exit in COMPOSER VOICE — its own `CLASSIFY:`/`ROLE: end` records naming the evidence (shell completion status, the log tail; v48.0 — for a wrapper leg the footer's absence says nothing about the leg's `ROLE: end`, a separate and earlier append: an end already on the log is the wrapper's and is consumed, and only a start with no end takes the composer's, the clean close of **`ROLE:` log lines** → Wrapper legs, admitted by the helper only once the role-liveness reader says `over`) — and NEVER synthesizes the missing `EXIT:<code>` line into the probe log: a wrapper-tee line only the wrapper may write, written by anyone else, is fabricated history.
