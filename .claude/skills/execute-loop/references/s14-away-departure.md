# Away mode, part 2 — the pre-departure check, the batch and the departure file
Previous: s13-away-entry.md. Next: s15-away-grant-and-stops.md. Words such as above and below may point into those files.

Contents, in order: The pre-departure check; Blocking / you can unblock now; the checklist, items 1 to 9; The batch and the departure file, call 1 and call 2; the departure file's lines; an answer the batch did not settle.

**The pre-departure check.** Started at the wizard or mid-run — the two ways above — the composer sends ONE message — **What the run will do** first: item 9's intent line, then one line per release group in plan order naming its pull request and the release acts the proposed scope covers for it (built; its pull request opened and merged on green CI from inside this run — the group close, Termination → Group end; staged and checklist-checked; dispatched) or what waits for the operator (a build-only scope: "left ready; its pull request waits for your merge click, then the run goes on" — v40.0: no line promises a question at a group boundary) — then the blocking block, then items 1–9 in this order — and then asks the question batch (**The batch and the departure file** below). **While you are away** — three lines the message carries directly after What the run will do, whatever the scope: the nudge — `Nudge: armed every 30 minutes while the grant is bound — about 1.0M–1.4M cache-read tokens per hour of an idle composer (read at about 238k tokens of context; it grows with the context)`, or `Nudge: not armed — <why>` (The nudge says which composer arms one); the watcher — the `watcher:` line as it reads now and what `Watcher takeover` will be pre-filled to, with the reason (check item 4); and how to stop the run — `Closing this session or quitting the app is not a way to stop this run: its roles are built to run on, and a watcher may continue it. Say "back" here to end the grant and take the run back. From outside this session, run from the base checkout: python3 scripts/loop-watchdog.py stop --iso <iso-id> — it stops the run's roles and the watcher's continuation.` (Stopping an away run; on a run with NO run worktree the last sentence is left out, and so are the words "and a watcher may continue it" — that command sees none of such a run's roles, and no watcher continues such a run). **Scope-aware:** items 6 and 7 are always computed — the scope proposal reads them (Which scope tokens can be offered) — but they are printed, asked, and written only when the proposed scope carries `merge` or `production`; a build-only proposal (`smoke`) prints neither item, the blocking block leaves out their lines, and its batch is the scope question and whatever call 1 has to ask (call 1 runs only when it has something to ask — from v47.0 that includes item 5's usage fallback wherever none is set, and the `Usage fallback:` line is written on EVERY departure file, a build-only one included; from v48.0 call 1 always has one question, `Watcher takeover`, and its line too is on every departure file). A later widening that adds `merge` or `production` prints, asks, and writes them then (**Ending the grant** → Widening):

**Blocking / you can unblock now** — a reorder, not a computation: the lines of items 2, 1, 4, 5, 6, and 7 that the operator can act on before leaving, printed first (and again in their items): every stop ahead with its `Stop:` disposition — each `now` stop among the unblockables, each `park` with the dependent it blocks, the plan error a same-group dependent on a release act makes, and the block of merges the `operator-merge` class would take (item 2); the usage fallback where none is set (item 5: with no answer the departure does not bind); each open `[decision]` task with its recommended option and each `[pending-hardening]` task (item 1); each missing login or permission with its consequence, and each write command the scope needs that is not yet allowed (item 4); the no-checks merge (item 6); each checklist or post-deploy item that needs a sign-in, and each production path whose `Receipt:` is `none` (item 7). Nothing in it is derived that those items do not already hold; with nothing to unblock it says `none`.

1. Plan decisions still open — each `[decision]` task without `Chosen:` in the remaining phases of the plan, every group (Run isolation → **Release groups** — one run builds them all, so each is asked once, here), with a recommended option — and any task marked `[pending-hardening]`.
2. Stops — every stop already open in this run (an unresolved `must-pause`); every open hold (the `held=` list of the `away check` read: each with its `hold_id`, class, and path; a hold is honoured for the whole run until the operator clears it by name, The operator's word wins below); and any step the plan names that is an irreversible production data change (stop 3 below) or a scope question; and every planned stop ahead under the proposed scope — a release act the scope, an answer, or a missing permission leaves to the operator, and a plan phase that needs production before it can continue — each with its disposition line (below; an act an existing rule parks when it is reached — a write command not pre-approved (The use-time check) — is written `park` with that rule as its reason, never `around`). **Merge stops (ONE fixed form, which the helper reads).** A planned stop that is the MERGE of this run's own pull request is of one of two kinds, and both are written in the form below and no other: `kind=stop-3` — a merge whose diff will carry an irreversible production data change (stop 3 below — a migration, named by its path); `kind=reserved` — a merge the project's own rules (its `AGENTS.md` — "workflow edits are operator merges", say) or the plan reserve for the operator, named by the files that rule covers. The line: `Stop: merge key=<the merge start's key> kind=stop-3|reserved subject=<repo-relative path>[,<path>…] — pre-approved | around | park — <reason>; depends: <…>` — single spaces and the em dash as shown; `key=` is the `stage-<N>-merge` key the close of that release group writes its merge start under (the group's last stage); each `subject=` path is repo-relative, in the hold records' path alphabet `[A-Za-z0-9._/-]+`, with no empty, `.`, or `..` segment; indentation and ONE list marker — a bullet (`- `, `* `, `+ `) or an ordered one (`2. `, `2) `) — may precede it; behind any OTHER lead — a quote mark (`> `), emphasis or other markup, an opening `<!--` — the line is not of this kind: the helper does not read it and `away lint` says nothing about it, so a merge stop is never written that way. `around` or `park` (the dependency read below decides which, as for every stop) means the merge itself waits for the operator, and the helper refuses its start; `pre-approved` is written only on call 1's `operator-merge` `yes` (**The batch and the departure file**). One merge may have several such lines — a migration and a reserved workflow in one release group, one line per reason — and they are read together: ONE `around` or `park` among them vetoes the merge whatever the others say. The helper reads every line of the file that begins `Stop: merge` followed by anything but a name character (`Stop: merge-queue setup` names another act) and sits outside a FENCED block — a line in an indented code block, or on a line of its own between `<!--` and `-->`, is read as well, so an example line belongs in a fence — and any such line NOT in the fixed form is malformed: `away lint` reports it (`merge-stop-malformed line=<N>`), `away grant` warns the same, and no away merge start of the run is admitted while it stands (Record grammar → The listing check). So no other line of the file begins `Stop: merge`: the ordinary merge the grant's release work takes has no line of this kind (an `[operator]` merge task that is neither kind keeps the task-named line below, which the helper does not read), and a merge with no merge-stop line is admitted as before v47.0. The message prints every merge-stop line the `operator-merge` class would cover in ONE block under this item, headed `Merges I will take on green CI unless you say no (operator-merge):` — each with its key, kind, and subjects — so the default is read, not assumed; with no such line the block is left out. The heading is the MESSAGE's form, before call 1 — as `now` is for a stop: the departure file holds the merge-stop lines themselves under item 2, each with the disposition the answers gave it (`pre-approved`, `around`, or `park`), and NO such heading — a line that reads `around` or `park` is not a merge the composer will take. What a `pre-approved` line admits, and what it never does, is The use-time check → Pre-approvals (`operator-merge`). **The stops' dispositions (stated ONCE, here).** For every PLANNED stop ahead — an act the run can leave unperformed: an `[operator]` task (the plan template's Tasks legend), a four-stops act the plan names as a step (a key ceremony, an irreversible production edit), a step the plan says needs production before it can continue — this item writes ONE line: `Stop: <task or act> — now | around | park — <reason>; depends: <the buildable tasks that need it, or none>`. `now` — its preconditions are already met and the operator can do it before leaving: asked in call 1 as `done | skip | agent` (**The batch and the departure file**; v44.0 — `agent` is OFFERED only for a task whose act is neither a four-stops act, nor an always-the-operator's item, nor a release act (the grant's `scope=` governs those — a merge, a dispatch), nor one the plan says needs the operator in person: a public artefact fetched at a pinned source, a job re-run, a public record read — the acts "The composer decides" names as the composer's that are not release acts; the plan template's Tasks legend says what "operator-supplied" means) and recorded in the departure file's `Answers` block as its `Operator task:` line (the form there); an answer the batch did not settle is written `skip`, and `done` or `agent` is never inferred; a line written twice in one `Answers` block for the same operator task counts as `skip`; `done` → the task is marked 🟩 on the operator's word and gets no `Stop:` line; `agent` → one `pre-approval` record `allow=operator-task path=<the task's ID token>` with the act's class in `detail=`, written right after the grant and read back on the `away:` line (Records → A pre-approval; The use-time check → Pre-approvals): the task is then the composer's under the grant — performed when the plan reaches it, recorded with `allow=operator-task`, marked 🟩 with the record named in the handoff note — and gets no `Stop:` line; an `agent` answer on a task the rule excludes is not offered, and a record written for one anyway is not honoured (the act parks or waits as its own rule says); `skip` → `around` or `park` by the dependency read — and that is the line the departure file holds: `now` is the message's form before call 1; the file is written after the batch (items 1–9 as confirmed — **The batch and the departure file**), so a `now` stop is written there with its read disposition in place of `now`, its reason naming the answer (answered `skip` in call 1, or unanswered → `skip`), never left `now` in item 2 or in any copy of the line the file carries; a `done` stop has no line anywhere in the file; and the file's intent line (item 9) names every `park` line the file holds, or `none`. `around` — the DEFAULT: no buildable task depends on it — the disposition of a release act the grant's own release work takes after the close (the merge, a dispatch) and of a planned four-stops act, whenever nothing buildable in the closing group depends on it (the dependency read has precedence: a same-group dependent makes even a release act `park`, and is the plan error below); the task stays open and `[operator]` (the label is what lets the phase close: a planned four-stops act with no label is selected by `/execute`, met as its stop's condition when the executor reaches it, and written `park` by the parenthetical above, never `around`), the phase and the group close around it (the done test — Run isolation → **Release groups**), the handoff note lists it under Open blockers, and no journal record is written (Records → A decision with no open pause: nothing paused). `park` — a buildable task depends on it — binding on the composer: when the executor stops on the dependent (`/execute` hard stop 1: the task cannot be implemented as written) or the dependent — a task of the phase being closed — is still open at that phase's close (a dependent in a LATER phase of the group parks when that phase reaches it or closes around it; the current phase still closes), the composer writes the must-pause pair for `key=<runkey>-operator` with `reason=operator-task` (Records → A park; a park, never a hold; its notice naming the act) and never adapts, reorders, or defers the task — a `park` line is not a "the composer decides" row; the operator's clear is the act done: the composer marks the task 🟩 on their word and closes the park with the operator's `gate-disposition` (STICKY §7 GATE-DECISION; no away pair). A buildable task that depends on a release act its own group's close must precede — the merge, a dispatch — is a plan error: the blocking block names it (move it to the next release group before leaving); left as it is, it parks. A dependent in a LATER group is normal release chaining and never parks the earlier group's release. A stop with no line — a task appended mid-run, a departure file written before v39.0 — is decided by the same read: a dependent → the park pair when the dependent is reached; none → `around`, the handoff note the record. The lines and the read cover PLANNED acts only: the four stops and the always-the-operator's items met as CONDITIONS in flight — a CRIT finding, missing commit-boundary evidence, a records disagreement, no runnable peer, an open hold, an unresolved pause, a confirm inside another skill — keep their own behaviour (they pause, park, or notify as the stops lists and the disposition table say), and no `Stop:` line, `around` disposition, or dependency read clears, waives, or bypasses one of them. A `Stop:` line is never a production-hold item: the `Stop:` prefix separates it from the hold items this item lists, and the production hold (Release work) does not fire for an `[operator]` task left for the operator. Attended (no grant), the same read with no question: a phase closes around an open `[operator]` task, the handoff note lists it, and the task is the operator's through `/execute`'s interactive branch whenever they choose. The lines are derived ONCE, at this run's departure, and already cover every release group of the plan (one run builds them all); a widening carries them with the rest of the file (**Ending the grant** → Widening (3)).
3. Production-affecting items ahead (a new dependency, variable, migration, deploy config) that will follow the executor's recommendation.
4. Tools, logins, and permissions — `gh` auth, the live smoke tool, the access the documented deploy steps need. Each command family the scope needs is run once now in a harmless read-only form, so any permission prompt appears while the operator is present. A step with no harmless form is probed by what can be read: for a pre-production snapshot step, a policy simulation — `aws iam simulate-principal-policy` for the action the step names (or the read form of the plan-named family); for a production path that deploys through a host environment, that environment's protection rules (`gh api repos/{owner}/{repo}/environments` — a required reviewer or a wait timer is named with the park it causes). A read-only probe never pre-approves the write command (a permission allowlist matches by command prefix), so this item also lists each write command the scope needs — as the documented steps run it, `/close-run`'s own included (its push, its pull request, the one re-run of a failed check, and the merge), such as `gh pr merge`, `gh workflow run`, or `aws rds create-db-snapshot` — and, under `router=on`, the ONE entry the router's unattended calls need beside the read-only `status --json` probe run here: the bounded runner's (since v45.0 the re-pick's `pick --failed=…`, the transcript copy of the Switch-account transaction (Usage-exhaustion recovery) and the final close's `release --run=…` (Mechanical close enforcement) each run as `python3 scripts/loop-run-bounded.py … -- …`, so the runner's prefix is the one a permission allowlist matches; on a Claude Code composer, Preflight step 15's read — The runner's permission — decides "not yet allowed") — a re-pick that stalls on a permission prompt no one is present to answer is a dead role, not a park — with the exact allow entry the host needs for it, added to the main checkout's untracked local project settings (on Claude Code) — a file the composer does NOT hold alone: on Claude Code from 2.1.211, off Windows, every Claude Code session started in the checkout or a worktree reads it too; from v46.3 a role this loop spawns does not (Preflight step 16 — the one statement, with what the shield is not; for the runner's entry, the runner's own refusal of a spawned role guards against accidental use only — Preflight step 15 states its limits; the placement only the composer's session holds is a launch flag, `claude --allowedTools …`) — never in the profile's user settings, a committed project settings file, or the worktree — a spawned role's own grant set carries only the `emit` and `escape-check` shapes of the helper — and removed by the operator once this run's LAST grant has ended — one run covers every release group of the plan, so that is the plan's last grant (a widening's end is not that: grant n+1 still relies on them); call 1 of the batch asks each one, and a write command not allowed parks its act (The use-time check — which also states the ONE exception, the runner's entry: no runner call and no park). **From v48.0 this item reads three more things, each printed as one line.** (a) *The watcher* — Preflight step 17's identity command run now, its `identity:` and `watcher:` lines shown as they are (a watcher that is not running, is stale, runs another script, does not watch this base, or whose last tick on this base failed is named with the line's own remedy; none of them blocks the departure). (b) *The watcher script's own entry* — `Bash(python3 scripts/loop-watchdog.py:*)`, read and, while no grant is bound, offered as Preflight step 17 states it: without it every wake's identity write, and a `stop` the composer runs at the operator's word, prompts. (c) *Whether a headless composer could work here — the read behind `Watcher takeover`'s pre-fill, stated once, here.* A watcher takeover prompts nobody: a command that is allowed only by a prompt the operator would answer is REFUSED there, and a takeover refused its first helper call can neither work nor write the must-pause that parks the run. So the item reads whether each command the composer itself runs is allowed WITHOUT a prompt by a settings file a headless session started in the composer's own directory reads — the three files of Preflight step 15's read and the `settings.json` of the composer's own config folder, each read whole, under step 15's hit rule (the exact shape, or a rule that subsumes it): the helper (`python3 scripts/loop-journal.py …` — the full shape, not a role's `emit` / `escape-check` pair), the spawn wrapper (`bash scripts/loop-spawn-wrapper.sh`), the peer launcher (`python3 -I scripts/loop-peer-launcher.py`), the watcher script, and, under `router=on`, the bounded runner. One line: `Headless composer: every shape allowed (<files>)` or `Headless composer: not allowed without a prompt — <the shapes missing>`. A shape that is missing is not added by this item — it is the operator's to add or leave; left missing, `Watcher takeover` is pre-filled `off` with that reason. The run's permission tier is named; when it is `perms=bypass` or a blanket interpreter grant, the message says in plain words that spawned agents are not technically prevented from running the `away` command. A missing item is named with its consequence.
5. Usage headroom and the usage fallback: every departure, whatever its scope, answers what takes over when the executor's account runs out, on ONE `Usage fallback:` line of the departure file's `Answers` block (**The batch and the departure file**). With `profile-fallback=` already set, this item states the dir and nothing is asked; with none set on a `claude -p` executor or architect backend, it lists the accounts probe's eligible profiles, best first, for call 1's question; on any other executor backend the line is `n/a`. `router=on` changes nothing here — the fallback is the router's last-resort tier (Usage-exhaustion recovery); under `router=on` also the router line — Step 0's `Router:` line re-read now (`status --json` under the runner, Preflight step 15): the current picks, the record count, and how many of the run's three re-picks are already reserved (Usage-exhaustion recovery). On a `cloud=on` host, one line: the grant, the departure file, and the report live only on this machine.
6. The CI gate found on the base branch ("none found" is said plainly), and the ungated merge — asked at every departure whose proposed scope carries `merge` or `production` (scope-aware, above), whatever gate was found (a path-filtered CI can leave a records-only pull request with no checks at all): may a pull request whose check inventory is complete and settled with no checks (`/close-run` item 6's `verdict=no-checks settled=yes` — nothing ran, or every check was skipped) merge? Call 2 of the batch asks it, recommending `merge` and saying what it means since v36.0 — a no-checks merge goes ahead only where no workflow that a pull request, or a push to the run branch, can start watches a path in the diff (`/close-run` item 6), so a code diff whose CI did not fire still parks — and the departure file records `Ungated merge: merge|hold`. Then whether the host itself refuses to merge a pull request that is behind its base (GitHub's "require branches to be up to date"; an answer the composer cannot read counts as no), recorded `Host refuses out-of-date merge: yes|no`; and which branches a merge into can lead to a production release, by any route — a push-fired workflow, a workflow chained to one (`workflow_run`), or a deploy outside workflow files — with, for each such branch other than the base branch, whether the host refuses a merge into it by this run (a required approving review, or a merge restriction this login does not pass). The question is about the branch whose merge causes the release, not the ref the deploying workflow runs on: an environment's deployment-branch rule answers it only where every production workflow is fired directly by a push to the branch it runs on. The composer proposes the list from the default branch's workflow files and the hosting configuration; the confirmation confirms it. An answer the composer cannot establish and the confirmation does not confirm counts as: a merge into any branch may release to production, and nothing refuses the merge.
7. Every deploy a merge can fire, read from the **fetched base branch** (never the worktree): each file under `.github/workflows/` that a push to the base branch can start — any filename, with or without a path filter, and any workflow chained to one by `workflow_run` — with its trigger, its filters, and its class (staging, production, or not a deploy); one explicit line for deploys that fire on a push with no workflow file (a hosting platform's own git integration — read `AGENTS.md` → Tech Stack → Hosting): `On-push deploys outside workflow files: none`, or each one with its class; and a list, by path, of the repo's other release-configuration files (the hosting platform's config, the scripts or compose files the deploy steps run, as far as the workflow definitions show them — the confirmation corrects the list; never a Markdown file — the membership rule below). Per release path: the staging steps, how the staging and production deployment histories are read, the staging checklist, the production step, the post-deploy check, and the rollback step — and, for a path where the merge itself releases to production, the pre-merge staging procedure (how the pull request's head reaches staging before the merge) — each quoted with its file, the heading text (the ATX line's text after its opening `#` markers, never the opening markers — Records → The effective set and accepted versions, its comparison contract, which `--heading` reads), and blob id. A procedure whose heading holds a double quote — text no record can carry — is entered instead as a whole file: its file and blob id, with the words `heading none (whole file)` on the bullet and no heading text; such a bullet is a whole-file path for every reader (Records → The effective set and accepted versions — its opening sentence) — the ONE exception to the membership rule below, which speaks of a Markdown file recorded WITH a heading — and this item says what that costs: an edit anywhere in that file, not only in the quoted block, is recorded and notified as a changed version. Each production step and each rollback step gets one of three classes: **pinned** — both parts hold: it is told the exact commit or artifact to release or return to, AND the machinery that runs it is held to the version that was checked by something a later change to those files cannot remove (two shapes count: a release fired by the push itself, which the host runs as the workflow stands in the pushed commit, and a step the documentation shows is run from a ref the host does not let move, which the confirmation confirms); **revision-only** — it is told the commit, but its machinery follows a branch that can move (a `workflow_dispatch` reads its workflow file from the branch it is dispatched on; a check written inside that workflow does not make it pinned, because the change it guards against can remove the check); **branch-following** — it releases whatever the branch holds when it runs. A pinned step is the first admissible shape and needs no acceptance (a merge that itself releases to production with no pre-merge staging procedure needs it whatever its class — Release work item 5); a revision-only or branch-following step runs unattended only where the departure file records `Unpinned production accepted: yes` for its production path — the operator accepting the check-then-act window there — and then only through Release work item 5's checks; otherwise production on that path waits for the operator. The **release machinery set** — every workflow file, every quoted file, every listed release-configuration file — is recorded with its path and blob id on the fetched base. What the confirmation (call 2) confirms is the READING, never the bytes: each workflow's trigger, filters, and class, the membership list, and the quoted procedures with their headings — the blob ids are the comparison's baseline, and a later change to any of them is re-read and recorded by the reader that finds it, never parked (Records → The effective set and accepted versions; `/close-run` items 4 and 5). **Membership of a Markdown file.** A Markdown file (`*.md`, at any path — `AGENTS.md`, every `README.md`, `docs/runbook.md`, the plan file, any `.md` this file quotes a procedure from) is in the set ONLY as a quoted-procedure file — its file, the heading text, and the blob id — and is never a listed release-configuration file: its whole blob is never compared, so a change to it outside a quoted block is no machinery change; what a changed quoted block of such a file does at a reader is the comparison contract's Markdown branch (Records → The effective set and accepted versions — stated there once, never here). Workflow files and non-Markdown release-configuration files are listed and compared exactly as before. "None documented" — a checklist with zero items included (on a path whose merge itself releases to production with no pre-merge staging, its post-deploy check stands in for the staging checklist) — means production on that path stays a stop. A rollback step counts only if the confirmation confirms it and it is pinned. A **production path** is every release path with a production step — a step dispatched after the merge, or a merge that itself releases to production. Per production path, beside that quoted evidence, the item also shows the lines the batch settles (their formats: **The batch and the departure file**): the step's class; for a revision-only or branch-following step, for a path whose merge itself releases to production where item 6 does not find that the host refuses to merge a pull request behind its base, and for every path whose merge itself releases to production with no pre-merge staging procedure whatever the host's protection — whether the operator accepts the check-then-act window on that path (on a no-staging path, releasing with no staging included) (`Unpinned production accepted`, proposed `yes` when the scope proposal carries `production`; `/close-run` reads it for such a merge); for a path whose merge itself releases to production, its pre-merge staging procedure, or `none`; the pre-production step — a step taken before production, such as a database snapshot — quoted with its file and blob id, or `none`; and the repo's own rules that hold production, read from `AGENTS.md` (its standing or deploy rules, such as a quiet window for a kind of deploy) and quoted with file and heading, or `none` — a production act they hold parks. And one evidence line per production path, `Receipt: <reader>|none`: the quoted deployment-history reader that yields both identities of the deploy's own record — the application it released and the machinery it ran — for a dispatched step, that workflow's runs; for a deploy the push itself runs, the run with `event=push` whose `headSha` is the merge commit; for a workflow chained by `workflow_run`, the chained run bound through its triggering run; for a deploy outside workflow files, the provider's own deployment record; `none` when no quoted reader yields both. `Receipt:` is evidence, not an answer; a path whose line reads `none` is never proposed `production`.
8. Other live runs (**Coordinating with other runs**). From v37.0 the item also carries two parts the departure file records. **The listing** — written from the census (Record grammar → The census) at every departure and every widening, never reused or compared (a widening keeps the file's earlier bytes, so its fresh listing sits in the Widened section and supersedes the one above it): each OTHER bound grant's iso-id, `scope=`, `plan=`, and `log_root=`; and, per production path, the other runs whose bound `production` grant covers it, by **the foreign departure read**: for each such run, `away check` (Record grammar) with THAT run's identity — `--policy-log` its `<base>/.cursor/loops/<iso-id>-policy.log`, `--iso` its iso-id, `--plan` and `--log-root` the census line's `plan=` and `log_root=`, `--run stage-1` (the check is read-only and ties nothing to the run key) — must print `state=bound` with no `departure-mismatch`, and only then is its `<log_root>/away-<n>-departure.md` (`<n>` the line's `grant=`) read, ONCE, immediately after the check: its EFFECTIVE item 7, its **Widened at grant** sections included, names the paths it covers. - **Call 1 — what the operator can unblock now:** each sign-in a checklist item or a deploy step needs (`done | skip` — the operator signs in now, in the host's pane; the agent never enters a credential); each write command item 4 lists that is not yet allowed (`done | skip` — `done` once the operator has added that exact allow entry; `skip` parks that act, and the departure file names it — the runner's entry alone parks nothing on `skip`: The use-time check's one exception); each open `[decision]` task (its options, the recommended one first); each `now` stop of check item 2 (`done | skip`, and from v44.0 `agent` where item 2 offers it: `done` is the operator's word that the act is done before leaving, `skip` leaves the stop to item 2's dependency read, `agent` makes the task the composer's under the grant; the answer is the departure file's `Operator task:` line); the usage fallback (check item 5), asked ONLY when the executor or architect backend is `claude -p` and the run has no `profile-fallback=`: which profile takes over when the executor's account runs out — the accounts probe's eligible profiles, best first, then `none` last (more than four options: the contract's over-limit rule).
