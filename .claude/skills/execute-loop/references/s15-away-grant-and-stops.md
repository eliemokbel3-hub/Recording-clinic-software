# Away mode, part 3 — the grant, the use-time check, and what stops, waits or is decided
Previous: s14-away-departure.md. Next: s16-away-release-work.md. Words such as above and below may point into those files.

Contents, in order: The grant; The use-time check; The four stops; Always the operator's; the table of waits; The composer decides; Production hold; The operator's word wins; The away live smoke.

**The grant.** The batch answers — or, on a degrade, the typed reply — are the confirmation. The composer then runs the read (`away check`, Record grammar above) — the next grant number is its `grants=` count plus one — writes `<log-root>/away-<n>-departure.md` as above, lints it BEFORE the grant binds — `python3 scripts/loop-journal.py away lint --run <runkey> --role composer --policy-log <abs> --iso <iso-id> --plan <plan> --log-root <abs>`: read-only (no record, no file), it reads the departure file the next grant would read and prints, on stdout, one `away-lint: <warning>` line per warning — the very warnings `away grant` prints on stderr: the two described below and, from v46.4, `heading-has-double-quote line=<N>` for each line outside a fenced block that quotes a heading holding a double quote (a best-effort read of free text: a spelling it does not know is not warned about, and a second quoted phrase on the line can warn needlessly), and from v47.0 two more words — `usage-fallback-missing`, printed FIRST, when the file holds no answered `Usage fallback:` line (the one word `away grant` never prints as a warning: it REFUSES such a file, below), and, LAST, `merge-stop-malformed line=<N>` for each line that begins `Stop: merge` and is not in the fixed form (check item 2 → Merge stops) — then `away-lint: file=<base name> warnings=<n>`, exit 0 with or without warnings; a missing or unreadable departure file is `away grant`'s own refusal — and fixes each warning in the departure file first (one it reads as needless, or accepts as below, stands — never `usage-fallback-missing`, which refuses the grant, and never `merge-stop-malformed`, which left standing refuses every away merge start of the run), then lints again: a `usage-fallback-missing` by writing the line from call 1's answer (asking it, if it was never asked); a `merge-stop-malformed` by rewriting that line in the fixed form; a `markdown-without-heading` or `item7-section-not-found` by the correction named below, made in the file with no grant yet to end; a `heading-has-double-quote` by rewriting that procedure's entry in check item 7's whole-file form and telling the operator so, with its cost as item 7 states it, in the line printed after the grant — then runs the `away grant` recipe (Record grammar above) with the confirmed `scope=` and the `allows=` kv built from call 1's `yes` answers (the kv omitted when every class is `no`), reads the verb's stderr for its `away-warning:` lines (the helper scans the departure bytes it just read, authorises nothing, and warns: `away-warning: markdown-without-heading file=<path>` for every bullet of the file's LAST item 7 block (`## 7.` or `### 7.` — a Widened section's included — to the next heading of equal or higher level, fenced blocks skipped, a bullet joined with its indented continuation lines) whose backtick token's first word is a `.md` path while the bullet carries no `heading` — the path printed only when it matches `[A-Za-z0-9._/-]+`, else `file=<unprintable, line N>`; `away-warning: item7-section-not-found` when no such block exists; a warning, never a refusal — the exit, the record, and the digest are of the unchanged bytes — with ONE exception from v47.0, the single departure check that refuses: a departure file with no answered `Usage fallback:` line is refused `departure-missing-fallback` (exit 2, nothing written), after the file is read and before any warning line is printed; every other check, `merge-stop-malformed` included, stays a warning at the grant), and acts on them while still present: a `markdown-without-heading` warning names a Markdown file the set would compare by its whole blob — one `refreshed` record per reader that finds it changed (recorded, never parked) — so the composer either re-quotes that file as a procedure (its file, heading text, and blob id — check item 7's membership rule) by ending this grant at once (`away end … reason=back` — nothing has run under it) and giving the corrected departure file as grant n+1 by a plain `away grant` (the same-scope correction — **Ending the grant** → Widening), or leaves it and accepts those records; `item7-section-not-found` on a grant whose scope carries `merge` means the file lacks its item 7 block — the same correction; on a build-only grant the line is expected (a build-only file has no item 7) — then prints ONE line: the grant number, its scope, the `allows=` it carries, and `Say "back" to end it.` Then the nudge: a composer that arms one arms it now, for this grant, and writes its identity with the timer's tag; every other composer prints its one `Nudge: not armed — …` line (The nudge, below). A refused grant records nothing, arms nothing, and is reported as it stands. In every away recipe both paths are ABSOLUTE and under the base checkout (the helper refuses a relative one): `--policy-log` is `.cursor/loops/<iso-id>-policy.log` (Preflight step 13), `--log-root` the run's log root (`.cursor/loops/<iso-id>/` under worktree isolation, `.cursor/loops/` otherwise), and `--plan` the same plan string the step-13 snapshot carries (after teardown, the journal's `plan=` value); after the run has closed, `<runkey>` is the last phase's `stage-<N>`, as `/close-run` Step 1 derives it.

**The use-time check.** Every site that acts under the grant — each disposition below, the away live smoke, each release step, the fix cycle, and every wake (STICKY §7) — first runs both reads: `away check` (Record grammar above) must print `state=bound` with the needed token in `scope=`, and `attest-check --key gates` (Preflight step 13) must read `bound` with `value=executor`, with the run's current mode `gates=executor`. Any other answer behaves exactly as with no grant: the item pauses or waits as it would without away mode. `departure-mismatch` (the departure file edited or gone), `ended`, `absent`, `malformed`, and `wrong-identity` are all "no grant"; a `malformed` log is also an always-the-operator's item. A `departure-mismatch` read at an act is also a park with notice: the composer writes the must-pause pair for that act — a release act's `<runkey>-<class>` key (Records → A park); an item that already pauses without away mode writes only its own pause, never a second — the record first, then the ask composed from the block the helper prints — and the act is not taken, so the operator hears at once rather than finding the run waiting in silence. An act whose write command the departure file records `Pre-approved: <command shape> no` is not taken either: it parks the same way — the must-pause pair for its key class (a `/close-run` step with no class of its own, such as the push or the re-run, parks under `merge`), written before any `start` — rather than run a command the host would stop on a permission prompt with nobody there. **The ONE exception to that park — the runner's entry.** Under a bound grant whose departure file reads `Pre-approved: python3 scripts/loop-run-bounded.py no`, the composer makes NO runner call and writes NO must-pause pair for it — none of the runner's calls is a release act with a key class — and each call's own existing records are written as its row already says; every other write command keeps the park above, unchanged. A call inside a running session takes the outcome its row of Preflight step 15's disposition inventory gives a call that did not answer (for the release, the one reported line says the release was not run — the bindings lapse on the router's own 24 hours, or the operator runs it on return; the manual switch is the operator's and does not arise under a grant). A resume in a new session runs none of step 15's router items — (a) through (g), every one a runner call or built on one — and that session's spawns carry no `LOOP_ROUTE_BIN` — each role launches on the folder the composer passes (on a resume: on the folder the resume pin finds — Backends), the rule Preflight step 6 already states for a non-routed spawn; the `Loop config:` line is NOT changed (a key change under a grant is always the operator's — Always the operator's, item 5) and ONE line is printed, `Router: on — not used this session (runner not allowed under the grant)`; the next attended session resolves the router as step 15 (a) always does. **Holds.** The same `away check` line carries the run's open holds — `holds=<n|unknown>` and `held="<hold_id> <class>[ path=<p>][; …]"` (Records → A hold). A release act whose class and departure path match an open hold — a hold of that class carrying the act's path, or one with no `path=`, which is class-wide — parks: the must-pause pair for its `<runkey>-<class>` key with `reason=operator-hold`, written before any `start`, the act not taken. So does a merge while a `merge` hold is open, or while a hold of a deploy class is open on ANY path in its firing set (`/close-run` item 3 — a held push-fired production deploy holds the merge that would fire it). And `holds=unknown` — a hold line the writer could not have emitted (a torn write, a hand edit), a `hold_id` naming two holds, or a probe log or log root that cannot be read or listed — parks EVERY release act: a bad hold line never clears (validity is judged on bytes alone and the log is append-only), so the operator takes the release attended or starts a new run; an I/O cause lasts only while it persists. A match is on the act's departure path as check item 7 names it (Records → Keys on existing records, `path=`), never on free text. **Pre-approvals.** The same `away check` line carries ` parks=` (the strict production-park count — Record grammar; this run's own line is informational, and the coordinated wait reads it with ANOTHER run's identity — Records → A foreign clear and a coordinated wait) and ` allows=<n|unknown>[ allowed="<class>[ path=<p>][ limit=<n>][; …]"]` — the pre-approval fold, ONE fold serving this line and `away report` §1: the bound grant's `allows=` entries are the EARLIEST instructions, then its `pre-approval` records (Records → A pre-approval) in reader order — stage-ordered, then append-ordered — and the LAST DISTINCT instruction per class (+ `path=`) wins: an `allowed` opens the class with its `limit=` (a later `allowed` after a `cleared` re-opens it; a later `allowed` with another limit replaces the limit — the operator's latest word, never the maximum), a `cleared` closes it (one with no prior allow closes nothing), a retry of the same instruction (the same `instr=` with identical values) is ignored wherever it sits, and the same `instr=` with differing values is a conflict. **The six classes and what each admits:** `records-merge` — merge a records-only pull request whose NAMED required check is kept from running by path filters (never over the watched-path test or an `Ungated merge: hold` answer — `/close-run` item 6); `pr-fix-cycles` — `limit=<n>` reviewed fix cycles per close (a bare entry is `limit=3` — The fix cycle; `/close-run` item 11); `ci-advisory-fix` — bump or allowlist a new dependency advisory on a dependency the pull request's diff does not touch, through the reviewed fix leg, counted against `pr-fix-cycles` (`/close-run` item 11; the Production hold reads the item as listed by the departure file while this allow is open); `foreign-merge` — clear a foreign commit the docs-only auto-clear does not, under the coordinated wait (Release work item 5's foreign-merge check; Records → A foreign clear and a coordinated wait); `operator-merge` (the ONE statement of what it admits; stop 3, `/close-run` → **Under an away grant**, and the plan template's Tasks legend point here) — the merge of the run's own pull request that the departure file LISTS as the operator's, when ALL of these hold: (1) `merge` is in the grant's scope and the class is in force under the bound grant — never on `allows=unknown`, never after a `cleared`; (2) the departure file holds a merge-stop line for this merge in the fixed form (the pre-departure check, item 2 → Merge stops), and every such line for its key reads `pre-approved`; (3) the admitting verdict for the tip is `passed`, and the start carries no `ungated=` and is not a late (`--event-ts`) start; (4) the subject test — every `subject=` path of those lines is in the merge's diff, and the diff holds no other path, added, changed, or removed, in any subject's own directory (a migration is usually not written at departure, so it is covered by its path: what the file says is what the run's reviews passed); (5) the merge does not itself deploy production — the prospective firing set (`/close-run` item 3) holds no production-class deploy: such a merge waits for the operator; (6) for `kind=reserved` on workflow files — each changed workflow's classing read (`/close-run` item 3) is `not-a-deploy` with none of the cannot-classify markers (an `environment:` key, a secret reader, a `pull_request_target` or `workflow_run` trigger added), and the diff touches no workflow that produced one of this pull request's required checks (green CI would be self-certified there); (7) every other admission is unchanged — the never-list, the Production hold, holds, the target rule, the use-time check. It NEVER covers a stop-3 act that is not a merge (a dispatch, a hand-run backfill, a deletion, a secret rotation), and never stops 1, 2, or 4. **What is mechanical and what is not.** The helper checks (1)–(4) at the merge start (Record grammar → The listing check). Conditions (5) and (6), and the stop-3 read of the REST of the diff — an irreversible change the departure file never listed — stay the composer's read, as stop 3 is everywhere else (`/close-run` item 3). The guarantee is therefore exactly this: the START RECORD of a merge the departure file lists is written only as its lines allow, and a start that claims the class is consistent with the grant and the file — the merge follows its record by **Record, then act**; it is NOT a guarantee that an unlisted destructive change cannot be merged — nothing shipped gives that. A mid-run `allowed` re-opens the class after a clear and never changes what the file lists: a line written `around` or `park` still vetoes, and lifting one takes a full re-departure (**Ending the grant** → Widening); `operator-task` — per task, `path=<the task's ID token>`: the composer performs that planned `[operator]` task itself (check item 2's `agent` answer — its exclusions are stated there, once). **The use-time check:** an act a park would otherwise stop, whose class `allowed="…"` lists, proceeds and is recorded with `allow=<class>` on its own record — the record before the act, as every act's (a merge start — for `operator-merge` the listing alone is not enough: its seven conditions hold too, and the start carries `allow=operator-merge`, alone or comma-joined with another class's label, which the helper checks; a `pr-fix` start, a foreign clear; an `operator-task` act is an `auto-disposition` `key=<runkey>-operator choice=done allow=operator-task path=<task id> rec=composer:operator-task` with the away pair — the decision recipe, Records — written before the act and named in the handoff note beside the task's 🟩); a class not listed leaves the park as written; `allows=unknown` — printed whenever the state is not `bound`, on a doubtful line whose raw text contains `-pre-approval` (torn, merged onto a torn predecessor, separator-damaged, undecodable, or one the writer would refuse), on an unreadable log or log root, or on a grant `allows=` the grammar refuses — and an `away:` line with NO ` allows=` suffix at all (a v43.0 helper — Older helpers below) is read as `unknown` — parks every such act: NOTHING proceeds on `unknown`, and the cause joins `reason=`. The composer reads this suffix only, never the records by eye, and never the departure file: a departure-time answer is the grant's kv, a mid-run answer a record — with ONE exception from v47.0: WHICH merges `operator-merge` reaches is the departure file's merge-stop lines, read by the helper at the merge start (and by the composer for the class's conditions (5) and (6)); whether the class is in force is still this suffix. **Mid-run — the operator's instruction in chat.** An instruction given while a grant is bound — "merge the rest yourself once green", "ignore this check going forward", "you can download the fonts", or its withdrawal, "stop merging on your own" — is recorded AT ONCE as a `pre-approval` record (`choice=allowed` with its class, its `path=` for `operator-task`, its `limit=` for `pr-fix-cycles`, `detail=` the operator's words under the hold recipe's normalisation; `choice=cleared` for the same class and path when it withdraws one — Records → A pre-approval), then READ BACK on the `away:` line — equality with the requested effective entry: after an `allowed`, the class (with its `path=` and its `limit=`) listed in `allowed="…"` with that limit; after a `cleared`, the class (and path) absent; `allows=` itself moves only when an entry opens or closes — a limit replacement, a retry of the same instruction, or a clear of an already-closed class leaves the count unchanged and is still read back by the entry — a record whose entry does not read back so is a park, never an assumption, and `allows=unknown` parks — and honoured for the rest of the grant until cleared by name. Pre-approvals are grant-scoped: a widening carries the EFFECTIVE set into grant n+1 — except `foreign-merge` and `operator-merge` across a widening that adds `staging` or `production`, which are asked again (**Ending the grant** → Widening (5)). **Older helpers.** Under a v43.0 helper (a hand copy — `/update-workflow` applies the whole set) `away grant … allows=` is refused (`allows= is not accepted by `away grant``, exit 2, nothing written): the refused grant is reported as it stands (The grant), never retried without the kv, and the run stays attended; a kv-less grant's `away:` line carries neither ` parks=` nor ` allows=`, which this check reads as `unknown` (nothing proceeds on a pre-approval); and `run-close --grant` is refused as an unknown flag (`/close-run` Step 7's group form — the close waits for the matching helper). Under a v35.0 helper the `away ci-verdict` call is refused as a usage error — that helper admits neither `--base` nor the verb, which alone is refused as unknown: a refused verdict call is a park (`/close-run` item 6), never a hand read. A hold write refused as an UNKNOWN SUBTYPE falls back to v35.0's conversation-only hold — stated in the handoff note and `<log-root>/away-<n>-notes.md` — on that refusal only; a hold write refused for its CONTENT (its class, its `path=`, a missing `detail=`) is normalised and retried, never a fallback. The departure file is written once, before `away grant`, and never edited after it; running notes go to `<log-root>/away-<n>-notes.md`.

**What stops, what waits, and what is decided while a grant is bound.**

**The four stops.** The run pauses and notifies, exactly as a MUST-PAUSE does today, for:

1. a verified CRIT;
2. a scope expansion that is CRIT, or production-impacting (the disposition table's Production-impacting row's categories — a new dependency, env var, migration, deploy config, parity drift — or stop 3), read from the executor's route record: its effective `severity=` and its `impact=production|none` (STICKY §7's judgment values — the executor states it from its verified triage, the composer copies it and never judges impact itself); an absent or malformed `impact=` is stop 2 (below that line the disposition table's row applies);
3. an irreversible production data change — any step that deletes or overwrites existing production data or schema in a way that redeploying the previous version does not undo: a migration that drops, renames, or narrows a column or table holding data; a backfill that overwrites values; deleting stored files or records; rotating or revoking a production secret — with ONE exception, by pointer: the MERGE of the run's own pull request that carries such a change, when the departure file lists it `pre-approved` and every condition of the `operator-merge` class holds (The use-time check → Pre-approvals — the one statement); a stop-3 act that is not a merge, and an irreversible change in a merge's diff that the departure file never listed, stay this stop;
4. usage or auth exhaustion that neither the router's re-pick (under `router=on`, v41.0 — Usage-exhaustion recovery) nor `profile-fallback=` resolves.

**Always the operator's.** Away mode does not touch these; each keeps its behaviour without away mode, pauses, and notifies:

1. a disagreement among the authority records (the policy log, the `config-change` stream, the `Loop config:` line), and a `malformed` away log;
2. missing commit-boundary evidence;
3. no runnable cross-family peer;
4. a review-integrity failure;
5. switching the run's permission tier (to `perms=bypass` or a blanket interpreter grant), changing its read roots or `Loop config:` keys, or widening the grant's own scope;
6. a confirm inside any skill other than this run's `/execute-loop`, its `/document` passes, its scoped `/review-plan`, and `/close-run`'s pull-request path;
7. anything another rule forbids outright (the never-list in `/close-run`).

Every other item of the residual MUST-PAUSE list (Safety gates — the composer-seat policy bullet), and every other wait inside the skills named in item 6, is disposed without the operator:

| Wait | While a grant is bound |
|---|---|
| Production-impacting (new dependency, env var, migration, deploy config, parity drift) | Follow the executor's recommendation, unless it is stop 3 |
| A scope expansion below stop 2's line (not CRIT, `impact=none` on the route record) | Follow the executor's recommendation, recorded `rec=executor:<choice>` on the route Records states (an `auto-disposition` with `--epoch` when no pause is open; a `gate-disposition` when it closes a surfaced pause): `Include in plan` appends the `[pending-hardening]` task and runs the scoped `/review-plan` before it is built (the existing route); `Fix now`; `Defer` with its `Risk if deferred:`; no recommendation → one verification leg, then **The composer decides** |
| A verified regression recommended Accept / Defer | Follow the recommendation |
| HIGH Accept / Defer / Include-in-plan | Follow the recommendation |
| A `[decision]` task without `Chosen:` | Follow the option the executor recommends and record it as `Chosen:`; no recommendation → the composer decides |
| A task marked `[pending-hardening]` | The composer runs the scoped `/review-plan` on it; that pass's gate items follow this table |
| The live-user-smoke pause | The away live smoke (below) when `scope` has `smoke`; otherwise it stays a pause |
| `/fix` stop-on-failure | Follow the executor's recommendation for the failed fix; a second failure on the same finding → the composer decides |
| A missing, ambiguous, or conflicting recommendation | One fresh verification leg to obtain one; still none → the composer decides |
| The raise budget / `peer-max` ceiling | Follow the executor's cap verdict; none → the composer decides |
| An unattributed dirty escape check | The composer decides |
| Executor-declared uncertainty | The composer decides |
| A run-collision confirm | The composer decides (key class `run-collision`) |
| A role needs a named command permission not on the confirmed list | The composer may add that one permission, quoted in the record (key class `grant-add`); never a tier change, never a release write command whatever the scope (the push, the pull request, the re-run, the merge, a deploy dispatch, a snapshot), and never `away` |
| `/document`'s asks (loop step 7, the run-end pass, inside `/close-run`) | Follow the recommendation the ask leads with; its lessons step follows its own unattended rule — nothing is written to the lessons store, candidates go to the handoff note |

- **"The composer decides"** means: choose the option that keeps the run moving and is REVERSIBLE — easiest to undo, smallest in effect; never one that needs a stop or an always-the-operator's item; never one that discards work. Parking is the LAST choice, taken only when every option is irreversible or an always-the-operator's item. An act the operator could do from their chair that the composer can also do — fetch a public artefact at a PINNED source (an immutable commit id with a recorded digest, never a tag or a branch), open or merge a records pull request, re-run a job, read a public record — is the composer's under the grant, recorded (the plan template's Tasks legend says what "operator-supplied" means; check item 2's `agent` answer pre-approves such a planned task). Record it with `rec=composer:<choice>` and the reason in `detail=`. A question the composer would otherwise put of its own accord is decided the same way, never asked (Safety gates → **The composer's own questions**).
- **Production hold.** Production — a merge that itself releases to production included — waits for the operator when, under this grant, the run accepted or deferred a HIGH finding or a verified regression, or disposed a production-impacting item the departure file does not list (a production-impacting item disposed under an OPEN pre-approval of its class — a `ci-advisory-fix` under its allow — counts as listed by the departure file, so production does not wait on it; a clear of that class before production resumes makes the item unlisted again and this hold fires; the HIGH-finding and regression conditions are independent and untouched) — or when such an item, from an earlier grant of this run, is carried forward by the departure file's **Widened at grant** section and the operator has not cleared it by name there (**Ending the grant** → widening) — never for a `Stop:` line: item 2's `Stop:` lines are dispositions, not hold items, and an `[operator]` task left for the operator is not a production-impacting item, so this hold does not fire for it. The conditions above are RE-DERIVED at Release work item 5's **Final admission to a production act** — from the records and the `allows=` reading as they stand immediately before the act, after any wait — so an exemption cleared during a wait parks before any `start`. A merge to a non-production base and staging still proceed.
- **The operator's word wins — a hold is a record.** An instruction to hold or skip a NAMED RELEASE ACT (`pr-fix`, `merge`, `deploy-staging`, `deploy-production`, `rollback`, `snapshot` — "hold Path A's production release", "skip the merge") is recorded AT ONCE as `OWNERSHIP: hold` (Records → A hold) under the current run key — after the close, the last phase's `stage-<N>` — whether a grant is bound or not, before one, or after the run has closed with release work in flight; `path=` is the act's departure path spelled as check item 7 names it, or NO `path=` (class-wide) when the operator's words cannot be matched to one path exactly or the path falls outside the hold path alphabet, `detail=` naming the path in their words. Then it is READ BACK: the composer runs `away check` and confirms the hold is listed in `held=` — a hold not listed (written to the wrong directory, say) is a park, never an assumption. It is obeyed for that act for the WHOLE RUN — at every use-time check and every wake, under this grant, a later one, or a widening — until the operator clears that act BY NAME: the composer records the same subtype with `choice=clear`, the hold's own class and `path=` (or none — the fold matches all three), and `clears=<the hold's hold_id, as held= prints it>`, reads it back (`holds=` one lower), and, where the act had parked, closes the park with the operator's `gate-disposition` (STICKY §7 GATE-DECISION — the operator's own decision, so no away pair); the act proceeds at its next use-time check, and the clear stays listed in the report. A hold never ends the grant unless the instruction says so. An instruction about any other named act (a non-release step, a phase) keeps today's behaviour — obeyed for that act, in conversation and the handoff note, with no hold record.
- A stop or a wait does not end the grant.

**The away live smoke** (the live check a person would otherwise do; loop step 5's "agent smoke" is the tests and build).

- **Who:** the composer, driving the host's live tool — never the phase's executor.
- **What:** every smoke item the plan's Validation section names for the phase, plus the phase's task-level acceptance lines that are visible in the running app.
- **How:** per item — expected, observed, evidence (a screenshot path or the captured text), verdict. An item the composer could not observe is a FAIL, never a pass by inference. A control that is absent is recorded as absent, not as "correctly hidden", unless the plan says it must be hidden for that role.
- **What is observed must be this phase's build.** The composer smokes only an instance it can show is served from this run's worktree — one it started from the worktree for this smoke, or one whose serving process it has confirmed runs there. An occupied port that belongs to another run or another checkout is never used under a grant (the attended loop may reuse one — loop step 5); with no instance it can bind, the items cannot be observed and fail. The worktree's state (`git status --short` and a `git diff` digest) is read before the first item and after the last, and no leg may run between the two reads; a difference between them, or any leg that ran in that interval (a change made and then restored leaves equal digests), voids the smoke and it is run again. No commit is required first — the smoke still precedes the phase commit.
- **Record:** the results and their evidence go under the log root, never the worktree — `<log-root>/<runkey>-away-smoke.md` — then ONE `smoke-pass` record with `smoke_by=agent` and the away pair (the recipe in Records below); `smoke-pass` is always the smoke evidence, and the commit gate is unchanged — a UI-bearing phase still needs its `smoke-pass`. Where the smoke gate already has an open `must-pause` for that run key and key (the run paused for the smoke before the grant covered it), a passed smoke also closes it with an away `gate-disposition`; a smoke run before any pause needs no second record; a failed smoke leaves the pause open.
- **Failure:** the failed items go to the executor as smoke feedback through loop step 6's triage contract, and the smoke is run again. After two failed cycles on the same item the composer decides.
- **Checklists:** a staging checklist (Release work below) is checked the same way, item by item.
