## Preflight (before the first phase)

1. **Load the plan.** Confirm an approved saved plan exists in `.cursor/plans/` (not in `completed/`), read its `Lifecycle State` (must be `Active`), tasks, phases, and `Current State / Handoff Note`. A `Paused` plan is REFUSED by name: surface its `Paused since:`/`Paused reason:` fields and the explicit `Paused → Active` transition (`/load-plan`'s resume option) — the loop never flips the state itself. If none, stop and point at `/load-plan` or Plan Mode → `/review-plan`. Then print the plan's release groups — every group with its phase headings, the current group marked — the group holding the first phase not done, a done phase counting as done whether a run visited it or not (Run isolation → **Release groups**; a plan with no tag prints one group) — and, on a resume, the closed groups counted from the journal's `merged_stage_<N>` keys — reading the plan and writing nothing (the 🟩 write of a closed group's `[operator]` release acts is the group close's, on the worktree copy — Termination → Group end; never this step's). **The `merge=auto` refusal.** A plan with a release tag whose resolved merge item is `auto` is REFUSED here by name — the line names the key and the shape a tagged plan needs, `isolation=worktree; merge=off` with the in-run group close (Release groups) — and nothing is created; the key keeps its single-group meaning on an untagged plan. On a tagged plan this step also validates the `groups=` key sub-step 2b will write (Release groups: strictly increasing, each a phase's last stage, the last equal to `phases=`'s). **The nudge (one line, here only).** When the resolved scope is `one-phase` and work would remain after this run — a phase after this one that is not done (Release groups) other than a trailing `Step H` (the hardening of the group before it — Release groups; a trailing `Step H` alone does not fire the line) — print ONE line after the groups: on a plan with no tag, `This run stops after this phase (scope=one-phase). To build the remaining phases unattended, run scope=all; to ship one pull request per phase, tag each remaining phase heading (PR-<n>) first — Run isolation → Release groups.`; on a tagged plan, `This run stops after this phase (scope=one-phase); the plan's release tags are not used until scope=all — Run isolation → Release groups.` Never under `scope=all`, never when nothing remains after this run; the line changes nothing — `scope=one-phase` still stops (Termination → User stop).
2. **Cross-repo read roots (re-derived each run; no `Loop config:` key).** Scan the plan for reference paths outside this repo (a companion repo, a reference checkout the plan cites) and confirm the read-root list with the user. Carry `--add-dir <path>` for each confirmed root on every `claude -p` EXECUTOR/ARCHITECT spawn this run (loop step 1); a native-subagent delegate runs inside the architect's session and inherits its roots and its permission context (the Grants rule at the wizard Close). Confirmed roots are READ-ONLY reference material: the spawn prompt states this explicitly (do not edit an added root unless the plan expressly scopes a cross-repo write and the user confirmed it), and the filesystem-escape baseline extends to each confirmed external git root (see Safety gates); flag a confirmed non-git root — it has no escape-check surface — for an explicit user-confirmed exception. Peers stay current-repo-only by default — a peer reviews this repo's changes; extend a peer's roots only when a phase's review genuinely needs the reference repo. When the scan finds no out-of-repo paths, this step is silent — no confirm fires. Backend limits in the Backends `claude -p` note.
2b. **Run isolation + ownership claim (a lettered sub-step, deliberately not a renumber — steps 3–11 keep their numbers; dry-run-aware).** Apply the Q5-resolved `isolation=` mode per the canonical contract in **Run isolation (worktree-per-run)** below: every editing mode performs the serialized ownership-marker claim (rescan-gated — see the canonical bullet); `isolation=branch` additionally creates or checks out its Q5-named branch in the base checkout (non-isolating — no journal, no worktree); `isolation=worktree` additionally records the base baseline, runs the pre-creation source-state gate, checks branch/path collisions, then writes the intent journal and creates the run branch + worktree in that order (journal-before-git-mutation). A dry-run PRINTS the resolved isolation actions — base/branch/path/authority — and creates NOTHING: no branch, worktree, journal, marker, plan transfer, or `Loop config:` write. Under `isolation=none` this sub-step is the marker claim only, and every other preflight step behaves exactly as it does without isolation.
3. **State the caps and scope** resolved by the wizard. Add one ADVISORY line self-assessing the composer's own context headroom — on EVERY wizard path, reuse-last and defaults included: a multi-phase run is safest orchestrated from a fresh or lightly-used session, so when this session's context is already substantially consumed, say so and recommend starting the run from a fresh composer before the first spawn. Advisory only — self-assessed (no auto-detection exists), it never blocks or gates preflight; if compaction hits mid-run anyway, the **Resume contract** (Visibility + run-state) is the recovery path. **Context pressure mid-run (judgment duty, prose by design):** the composer is the run's ONLY long-lived seat — executors, reviewers, and peers are always fresh per activation, so composer context is the only context that accumulates; compaction is SURVIVABLE by construction (the STICKY rehydrate card + the Resume contract recover from disk truth), so NEVER recommend abandoning or restarting the RUN mid-run for context reasons — the correct moves are the every-wake STICKY re-read, leaning on disk state over remembered intent, and (between phases, when pressure is genuinely high) a deliberate composer session handover through the Resume contract; the run itself continues.
4. **Establish the executor's model family.** When the executor's model was resolved by the wizard from probed choices — a custom menu pick, the recommended defaults, or a revalidated reuse-last config — the family is known by construction; no question needed. Only for the live-session backend, ask the user which model family is loaded — do not self-detect; the user is the source of truth. Either way, the cross-family peer family MUST differ from it.

Skipped under dry-run (a dry-run spawns no executors) and for live-session / Cursor-subagent executors. **Under `architect=on` with a `claude -p` architect (the delegate pin probe; the recipe, the reader, and its three prints are stated ONCE here):** the throwaway seat is an ARCHITECT, so beside the gate command it performs ONE trivial delegation — `subagent_type="<the stored subagent_type=>"` (the `Loop config:` value step 5 verified — never a literal name), NO `model` and NO `effort` parameter, the delegate echoing one line — and the probe prompt says: write NO `DELEGATION:` record and no staging file (the probe is not a leg; the exit consume's activation rule below excludes it by construction). PRESENT but SHARED by another in-session participant — the architect's own resolved model (read from the same role log's `init` event `model` field, the field beside the `permissionMode` the tier detector already reads, else the `Loop config:` executor group's `model=` when it is a full ID, else unknown) or a Mechanism-N advisor's model (the `advisor=` group under Mechanism N — `--advisor` rides the probe spawn and the advisor's engagement lands in this same aggregate, Optional advisor; 7. **Validate cross-family.** If the peer family does not differ from the executor family, or no cross-family peer is runnable, **mark the peer pass inconclusive and stop for direction** — never silently substitute a same-family peer.
8. **Filesystem-escape baseline.** Record the main checkout's `git status --short` so each phase can confirm headless spawns touched only expected files. Under `isolation=worktree` this baseline splits into TWO roles: the ACTIVE worktree's `git status --short` is the per-spawn edit-surface baseline (executor edits appear there — the wrapper's `LOOP_EDIT_SURFACE=worktree` for executor/architect/delegate spawns, reported as `edit_surface=` and excluded from the `result=` verdict; peers declare none and carry `LOOP_ALLOW_PATH` for the plan + sidecar instead — D4), and the BASE checkout's status is recorded separately as the base-non-interference + merge-precondition proof — see **Run isolation (worktree-per-run)**; the composer resolves the run's liveness value ONCE here for `LOOP_LIVENESS`/`--liveness` (the attribution freshness basis) and passes THIS run's iso-id as `LOOP_ISO`/`--iso` on every spawn and twin; without isolation, unchanged.
9. **Tee-log rotation.** Before the first spawn, rotate any existing `.cursor/loops/` logs matching this run's key prefixes — `<runkey>-*.log`, including `<runkey>-probe.log` — with a timestamp-suffix rename (e.g. `stage-1-executor.log` → `stage-1-executor.log.<YYYYMMDD-HHMM>`), so each run's logs contain only its own lines. Tee logs append and run keys get reused (observed live: a reused `stage-1-executor.log` carried a prior run's `ROLE: handoff` — a stale exit sentinel is a false anchor for the wake contract's output watch): rotation protects the Layer-1 anchor watch from stale-anchor false positives and keeps `/retro`'s per-run corpus clean. Rotation is PREFLIGHT-scoped: NEVER rotate a log a LIVE role is appending to — a mid-run rotation severs the tee and the armed watch mid-stream (observed downstream); rotation runs here, before the first spawn, and a mid-run re-rotation is legal only after the writing role is confirmed dead (the stall watchdog's check). Under `isolation=worktree` the same rotation runs INSIDE the run's per-run log root `.cursor/loops/<iso-id>/` (see **Run isolation (worktree-per-run)**). A dry-run PRINTS the intended rotations and renames NOTHING (the dry-run no-write contract).
10. **Wake-mode resolution (the `Wake:` artifact).** Resolve the host's wake predicates ONCE, here — never re-assessed ad hoc at spawn time: Layer 1 from the composer's actual spawn surface (`bg-shell` = a composer-owned background shell with an output watch; `AwaitShell` where a synchronous wait is wanted); on a Claude Code composer host, the background Bash surface with its completion notification (the same per-host names the companion STICKY card carries) — and Layer 2 from what the host actually supports AND the run's Q5 liveness setting (`monitor` = the background monitor subagent OR a persistent harness-native watch tool — either implementation resolves as `monitor` (the two-shape clause on Layer 2, Visibility + run-state);
