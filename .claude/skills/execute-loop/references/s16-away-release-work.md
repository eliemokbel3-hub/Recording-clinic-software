# Away mode, part 4 — release work
Previous: s15-away-grant-and-stops.md. Next: s17-away-fix-cycle-nudge-watcher.md. Words such as above and below may point into those files.

Contents, in order: Release work, items 1 to 7: the order at the end of the run; after the green close; staging before a merge that releases to production; staging after the merge; production, with the final admission and the foreign-merge check; a failure after the merge; nothing is written to the base checkout after the merge.

**Release work** (`scope` has `merge`). This section owns the order at the end of the run, the staging procedure in both its forms, production and its foreign-merge check, a failure after the merge, and the no-writes rule (the group close and its tail are Termination → Group end — v40.0); `/close-run` owns the recorded confirm, the deploy search and the release-machinery rule, the machinery comparison before and after the merge, the checks wait, the target rule, the production-releasing merge, the merge itself, the one re-run, and the never-list — and for a merge that itself releases to production it follows the pre-merge staging procedure defined here. The applicable-procedure rule every step below names — the procedure block as read at the act's own comparison target — is stated once at Records → The effective set and accepted versions. Every value a step below places in a command — a workflow path or a ref from the departure file, a run id or a commit from a tool's JSON — is data, checked before it is used, as `/close-run`'s **Journal values are data** rule checks a journal value: a workflow must be one the release machinery set lists (named by its path or by its file name), a ref must pass that rule's branch check, a run id must match `^[0-9]+$`, and a commit `^[0-9a-f]{40}$`; any other value a documented step passes (an input such as an environment, a database or snapshot identifier) must be the value the departure file's quoted step names, or one the composer minted (a correlation value); a value that fails its check parks the act.

1. **Order at the end of the run.** The composer runs `/retro` before the completion handoff (on a non-final release group, scoped to the group's stages, before its group close — Termination → Group end), while the plan is still Active, so the `Retro report:` pointer the green close needs is written without a question. Where a pointer must be written on a Completed plan (`/close-run` Step 4, after a fix cycle included), the bound grant with `merge` in scope is the confirmation `/retro` asks for, recorded as ONE away decision of key class `retro-pointer` (`choice=confirm`, `rec=composer:confirm`, `detail=` naming the report's path), written before `/retro` writes the pointer.
2. **After the green close** — `retained-green` on the final group; on a non-final group the group's phases done with the journal still `active` (Termination → Group end) — the composer applies **Coordinating with other runs**, then runs `/close-run --iso <iso-id>` (with `--group stage-<N>` on a non-final group) — its pull-request path only. The grant stands in for its confirm table, as `/close-run` states. From v47.0 the release pass is inside that close, before the merge: `/close-run`'s release stamp (its Flow 1 step 2a) names the release and its pull request on the status surfaces and, on the final close of a Completed plan with no open `[operator]` task, archives the plan pair under the grant — so no `/document` pass and no prompt follow the merge. The plan FILE is then at `completed/<the same name>` beside its recorded path, while every `away` verb and `attest-check` keeps taking the journal's `plan=` string (`/close-run` Step 1 — the two values and their one resolver).
3. **Staging before a merge that releases to production** (`/close-run` decides that the merge releases to production and calls this): after an admitting `away ci-verdict` (`/close-run` item 6 — `verdict=passed`, or settled `no-checks` under `Ungated merge: merge`), run item 4's machinery comparison (a quoted-procedure file by its quoted block — the effective set's comparison contract), then follow the path's pre-merge staging procedure as the comparison contract's applicable-procedure rule selects it (the block at this comparison's `--to`) — the staged tree must be the tree the merge will release, so the base branch's tip is an ancestor of the pull request's `<tip>` — then check the staging checklist as in item 4, and record both (key classes `deploy-staging` and `staging-checklist`) with `tip=<sha> base=<sha>` in `detail=`. That evidence is bound to that pair: a new tip or a moved base voids it, and staging runs again on the new pair (where the base moved, the merge-forward runs first — The fix cycle's rule, v44.0: a clean merge-forward within the ten-attempt bound — the bound read before any preparation — re-runs staging on the new pair, each re-stage counted against that same bound — clean meaning an empty or, from v47.0, a records-only delta; any other takes the cycle The fix cycle's step 1 routes it to). Item 5's shared prerequisites (a) then run before the merge, and its receipt (c) after it; the merge's pin and the refresh after the last long prerequisite are `/close-run`'s (**Under an away grant**, item 7), never restated here. A path whose departure file records `Pre-merge staging procedure: none` has nothing to stage: its merge is itself the production act, on the terms `/close-run` item 7 states for that route, with item 5 (a) before it and (c) after it.
4. **Staging after the merge** (`scope` has `staging`; the ordinary path): immediately before the staging step, run the **machinery comparison** — fetch the base and compare the release machinery set with the departure file's effective set — each path by its blob id, a quoted-procedure file by its quoted block's bytes (Records → The effective set and accepted versions, which defines the set and its comparison contract; a present but unreadable or partial set block parks, never falls back); a file that changed, a workflow file that is new, or one that is gone — whichever branch brought the change — is RE-READ and RECORDED (`/close-run` item 5's record — the requote, the `refreshed` version with the composer's classing read on a workflow, or the audit record for a listed file gone or a heading missing or ambiguous — never a park; the comparison narrows the check-then-act window to seconds without closing it — accepted for merges and staging, and for production only on a path whose window the departure file accepts, item 5); then follow the path's staging steps as the comparison contract's applicable-procedure rule selects them (the block at this comparison's `--to`); wait for the deploy to finish (at most 60 minutes; still running then, it parks — a bounded wait that ends at the first read that settles it: Visibility + run-state → the chunked-poll heartbeat); check the full staging checklist — the checklist as the applicable-procedure rule selects it — the way the away live smoke checks items (an item that cannot be observed fails — except an item whose sign-in the departure file records `Sign-in: <surface> skip`, which is left to the operator: the checklist then parks — the must-pause pair for key class `staging-checklist` is its record, never a `failed` outcome — with no rollback); record key classes `deploy-staging` and `staging-checklist`, each naming the revision staging held (a push-fired staging deploy's start was written after the merge's admitted start — Records → A push-fired deploy — so only its outcome is written here). The checklist counts for the merge commit only if staging held that commit from the start of the checklist to its end: read the staging deploy's commit before and after, and read the staging path's deployment history (the staging workflow's runs, or the hosting platform's deployment list, as the departure file names it) over the whole interval — any staging deployment other than the one being checked that started or finished between the first read and the last voids the checklist, and so does a history that cannot be read or is incomplete; equal commits at the two ends are not enough. An observation made against a deployment address that serves one fixed revision is bound to it and needs no history; if another merge replaced it meanwhile, the checklist is void for this release and production waits. Item 3's checklist is checked by the same rules.
5. **Production** (`scope` has `production`) — a production act is a dispatched production step or a merge that itself releases to production (a **production path**, check item 7). A condition of the admission or of (a), or one of (b)'s gates before the dispatch, that does not hold means production waits for the operator: it parks before the act (the must-pause pair, key class `deploy-production`; on a merge path `/close-run`'s park, the pull request left open). After the act, a receipt (b) cannot bind parks and notifies with no rollback, like a post-deploy check whose binding cannot be established; a receipt (c) that is missing or wrong, and a failed check, are item 6's failure after the merge.
   - **Admitted on the path.** The path's staging checklist — or, on a path with no staging (`Pre-merge staging procedure: none`), its post-deploy check — is in the departure file with at least one item, and every staging checklist item passed on the commit being released; every per-path line check item 7 shows for that path (their formats: The batch and the departure file) is present in the departure file — a line the composer could not establish is missing, and a missing line is never read as `none`; the step is not a stop; and its class admits it: **pinned**, both parts (check item 7), is the first admissible shape and needs no acceptance, except as follows; the departure file must record `Unpinned production accepted: yes` for that path for a revision-only or branch-following step, for a merge that itself releases to production on a base whose departure file does not record `Host refuses out-of-date merge: yes`, and for every merge that itself releases to production with no pre-merge staging procedure (`Pre-merge staging procedure: none`), whatever its class and the host's protection.
   - **(a) Before every production act — the shared prerequisites, in this order, before the irreversible step:** the path's `Receipt:` line names a reader, not `none`; the repo's own rules (`Repo rules holding production`) do not hold this act; the production hold does not apply; **Coordinating with other runs** is applied again; the pre-production step (`Pre-production step`, unless `none` — the step as the applicable-procedure rule selects it) is taken — a snapshot is recorded `snapshot` `choice=start` before it is taken and `choice=done`, with its identifier in `detail=` and `path=` the production step it protects (spelled as Records → Keys on existing records states for `path=`), once it reads available, waited for at most 60 minutes; a snapshot that fails, does not read available in time, or cannot be taken (its cloud permission missing — named; a write command answered `Pre-approved: … no` never reaches this point, The use-time check) is recorded `choice=failed` and parks; and then, after any such wait, the route owner's admission — (b)'s last reads on a dispatched step, `/close-run` item 7's refresh on a production-releasing merge — runs **Final admission to a production act** (below) immediately before the act (the repo's rules read again, the Production hold re-derived, item 4's machinery comparison — for a step run from a protected ref, the machinery at that ref too, `--to` that ref — and the rest of its list): ONE invocation per admission attempt, the route owner's, never an extra one here.
   - **(b) Before a dispatched step only — after (a), in this order:** **Coordinating with other runs** is applied once more (after (a)'s waits — the read in (a) can be an hour old by then) and finds no other run claiming or using that workflow's release lane; where the workflow takes no correlation input (the exclusivity route below), the concurrency read follows it (never taken from this run's departure file): the census (Record grammar → The census) and the foreign departure read (the pre-departure check's **Other live runs** item) must show no other live run whose bound `production` grant covers this path — one that does parks `deploy-production` as unbound, before any `start`, naming that run; then, as the last reads before the dispatch (a coordination read can take time), **Final admission to a production act** (below) in full — the coordination and concurrency reads just made are its item (6), one fetch serves its machinery comparison and its tip equality, and a coordinated wait inside its foreign-merge check returns to these last reads (the owner's return rule); `deploy-production` is recorded `choice=start` (with `path=`), and the production step — as the comparison contract's applicable-procedure rule selects it, the block at that comparison's `--to` — is followed with that commit; then the run is bound to this dispatch, whichever route below binds it — a correlation value identifies the receipt, never permits the lane. Where the workflow accepts an input the run exposes, the composer passes a correlation value it mints and the receipt is the run that carries it (read back from the run's `name`, `displayTitle`, or inputs). Otherwise ownership is exclusivity plus the difference: the concurrency read above found no other live run holding that workflow's release lane, the fresh coordination read above found no other claimant, and the before/after difference of the workflow's dispatch runs on that ref — `gh run list --workflow <file> --event workflow_dispatch --branch <ref> --json databaseId,headSha,createdAt,status`, read before the dispatch and again within a bounded wait of 10 minutes — has exactly one member created at or after the dispatch time. Anything else — two or more new runs, none within the wait, a member created before the dispatch, another live run holding the lane — leaves the receipt unbound: record `choice=failed` naming the reason and park. A run that merely matches the revision and the machinery is never this dispatch's receipt.
   - **(c) After every production act — the receipt, then the check.** Confirm from the deploy's own record that it released that commit AND ran the approved machinery — two separate identities, which need not be the same commit: the application (the commit or documented artifact the deploy's own record says it released) and the machinery (for a workflow run, `gh run view <run-id> --json headSha` names the commit the workflow ran from, and the release machinery set at that commit equals the departure file's effective set under its comparison contract — each path by its blob id, a quoted-procedure file by its quoted block's bytes, `--to` that commit (Records → The effective set and accepted versions)). The record is the one the path's `Receipt:` reader yields (check item 7): for a dispatch, the run (b) bound; for a merge, the merge commit is the expected application identity — a chained run counts only through its triggering run, the push-fired run on the merge commit, and the parent's success is never the deploy's receipt; a provider's deployment record supplies the application identity, and the machinery is the release machinery set at the merge commit, read the same way (a quoted-procedure file by its quoted block). No receipt within the bounded wait (60 minutes from the act, as the checks wait; it ends at the first read that settles it — Visibility + run-state → the chunked-poll heartbeat), or one naming another revision or other machinery, is a failure after the merge (item 6), however healthy the endpoint — proof of what merged is not proof of what production ran; but a run (b) bound, or the push-fired run, that is still queued or running at the bound is not yet a receipt either way: it parks and notifies with no rollback, so no rollback races a release still in flight. Then run the documented post-deploy check — as the applicable-procedure rule selects it — bound to that deployment the way item 4 binds a checklist (the production deployment history shows no other deployment from the receipt to the end of the check, or the check addresses a deployment that serves one fixed revision), and record `deploy-production` `choice=done` naming both identities (`choice=failed` on any failure here). A post-deploy check whose binding cannot be established, or with an item whose sign-in the departure file records `Sign-in: <surface> skip` (left to the operator, as item 4 states for a checklist), is neither a pass nor a failure of this release: `deploy-production` is recorded `choice=done` naming both identities, with `detail=` saying why the check could not be completed (never a passed check), and it parks and notifies, and no rollback is run on it.
   - **A merge that itself releases to production** runs (a) before the merge — then **Final admission to a production act** (below) as `/close-run` item 7's refresh after the last long prerequisite, the foreign-merge check its last read, `<tip>` the recorded base tip before the merge — and (c) after it, never (b)'s dispatch-only reads: its pre-act identity evidence — the ancestor check, that refresh, `--match-head-commit`, and the tree equality after the merge — is `/close-run`'s (**Under an away grant**, items 7 and 10), and its staging, where the path has a pre-merge staging procedure, is item 3's.
   - **Final admission to a production act (stated ONCE, here; (a), (b), the merge bullet above, the foreign-merge check's allow clause, Records → A foreign clear and a coordinated wait, `/close-run` item 7, and the Production hold point).** The reads taken IMMEDIATELY before every production act — a dispatch, or a merge that itself releases to production — and taken AGAIN — entered again by the route owner, from the first read — after ANY prerequisite between a first admission and the act that actually waited (the pre-production step's snapshot wait, a coordinated foreign-run wait that wrote a `waiting` record, pre-merge staging, the merge route's checks wait and re-bind): every read is of the current state, never a reading taken before the wait. The list, in this order: (1) the use-time check — `state=bound` with the token, `holds=` / `held=` (an applicable hold parks), `allows=` (`unknown` on either parks); (2) the Production hold RE-DERIVED from the run's records as they now stand and the `allows=` reading just taken — an accepted or deferred HIGH finding, a verified regression, a production-impacting item the departure file does not list, where an item disposed under a pre-approval counts as listed ONLY while its class is still open in `allowed="…"` at this read (a class cleared during the wait makes its item unlisted again and the hold fires); the Production hold paragraph owns the conditions, this is where they are re-read; (3) the repo's own rules (a window they name can open during a wait); (4) item 4's machinery comparison with its own fresh fetch — the route owner's fetch when one immediately precedes this list, `/close-run` item 7's Step 2 fetch on the merge route — (a quoted-procedure file by its quoted block, under the effective set's comparison contract; on a step run from a protected ref, the machinery at that ref too — `--to` that ref); (5) the identity binding — on a dispatched step, the base tip that fetch read equals the commit whose staging checklist passed (one fetch for both: no later fetch replaces the tip just checked); on a production-releasing merge, the fetched base tip and `<tip>` equal the recorded pair (`/close-run` item 7's pair rule — the one statement of the merge's binding and of what a changed pair voids); (6) on a dispatched step, **Coordinating with other runs** and the concurrency read ((b)'s reads — another live run's `production` grant covering this path parks `deploy-production` as unbound, before any `start`); (7) the foreign-merge check on the tip read at (4) — a new foreign commit in the range takes the check again (the docs-only clear, the allow's wait, or the park, as the check states). Then, with every read passing, control is back with the route owner for the act — on a dispatched step (b)'s `deploy-production` `choice=start` and the step; on a production-releasing merge `/close-run` item 7's pair check and item 9's merge start on the fresh verdict. What passes is RETAINED and what fails takes its EXISTING route: unchanged identities at (5) keep the staging evidence and the `snapshot` `choice=done` — a snapshot is never repeated to re-read a hold, and a wait budget is never restarted (one per close — this group's on the group route — and per path, read from the FIRST `waiting` record for that path in this close); changed identities at (5) take the route's own outcome — on a dispatched step the admission does not hold and item 5 parks before the act (the must-pause pair, key class `deploy-production`; a dispatch has no re-stage route); on a production-releasing merge `/close-run` item 7's pair rule — the evidence void, Release work item 3's staging again on the new pair, the merge-forward where the base moved; a hold now applying, a Production hold re-derived as firing, a failed rule, a failed comparison, a found claimant, or a foreign commit that parks → the existing park (the must-pause pair, key class `deploy-production`; on a merge path `/close-run`'s park) before any `start` — never the act on the pre-wait reads. A wait inside (7) — the coordinated wait — that actually waited ends by RETURNING to the route owner that entered this list, never by re-entering the list alone: on a dispatched step item 5 (b)'s last reads; on a production-releasing merge `/close-run` item 7's refresh after the last long prerequisite (the use-time check, the fresh fetch, the re-bind — a fresh `away ci-verdict`, which the helper's 15-minute admission bound needs — the target rule, the merge-queue read, items 3–5); each runs its own route-specific admission afresh and then this list again, and the retention rule above and the wait budget travel with the return (unchanged identities keep the staging evidence and the snapshot; the budget is not restarted). Nothing here is new authority: every read is one of the owners named, taken at the moment that counts.
   - **The foreign-merge check — an unattended production act never ships another run's unreleased work.** Run as (b)'s last read before a dispatch, with `<tip>` the base tip (b)'s machinery comparison fetched, and as (a)'s last read before a merge that itself releases to production, with `<tip>` the recorded base tip before that merge. **The range:** `<released>` is the commit of the path's last SUCCESSFUL production deployment, read through its deployment-history reader (check item 7); it must match `^[0-9a-f]{40}$`, resolve in the fetched base, and be an ancestor of `<tip>` (`git -C "<base>" merge-base --is-ancestor <released> <tip>` exits 0) — an unreadable, malformed, or non-ancestor `<released>` parks. The listed commits are `git -C "<base>" rev-list --first-parent <released>..<tip>`; a range that cannot be read parks. **Admitted:** this run's OWN-RUN SET under the provenance rule stated once in Run isolation → **Release groups**: the run's own merge commits — every `merged_stage_<N>` sha and the final `merge_commit=` — and, FIRST-PARENT within every slice, each closed group's commits (`git -C "<base>" rev-list --first-parent <merged_stage sha>^2 ^<that group's baseline>`) and the current group's (`git -C "<base>" rev-list --first-parent <run tip> ^<the current baseline>`), a group's baseline the journal's `base_head` for the first group and the previous group's `ff_stage_<N>` sha after it — a merge-forward's second parent never qualifies, and a commit a fast-forward imported (another run's merge, reachable from an `ff_stage` sha but outside the set) is foreign, whether its group is current or closed; another run's merge is admitted only once a successful deployment covers it (`<released>` moves), so it is foreign while its own production is parked. **Foreign:** any other listed commit whose first-parent diff — `git -C "<base>" diff --no-renames --name-only <c>^1 <c>` (a rename lists both paths) — touches the production path's firing set: the paths whose change fires that path's workflow, read by `/close-run` item 3's matching from its filters (no filter, or one the read cannot evaluate, puts every path in the set); a commit with no first parent, or a comparison that cannot be read, parks. Never `git diff-tree` on the commit alone: on an ordinary merge commit it prints no paths, which would admit a foreign merge as empty. A commit outside the firing set is shipped-but-unrelated and admitted (another plan's records-only commit, say). **The docs-only clear.** A foreign commit whose first-parent diff lies ENTIRELY within the fixed alphabet `**/*.md`, `docs/**`, `.cursor/**` — regardless of the firing set's filters (those bytes may deploy; the operator accepts that for docs) — is cleared with ONE record, `key=stage-<N>-foreign-merge choice=cleared rec=composer:docs-only commits=<sha>[,<sha>…] path=<production path>` with the away pair (Records → A foreign clear and a coordinated wait; the class sits outside the release classes, so the record never voids a CI verdict, and the report lists it under §3), and the act proceeds. **The allow.** Any other foreign commit, while the `away:` line's `allowed="…"` lists `foreign-merge`, takes the coordinated wait that Records paragraph states: cleared at once (`rec=composer:coordinated`, recorded with `allow=foreign-merge`) when a COMPLETE readable scan of the base's journals names no live run as its source; otherwise a `choice=waiting` record, one message where the host has a channel, and a re-check at the checks-wait cadence while the owning run's production on this path is parked or held — or while that state cannot be read — then the clear once it lifts, and — when the wait actually waited — the return to the route owner that entered **Final admission to a production act** (above — its return rule: item 5 (b)'s last reads on a dispatched step, `/close-run` item 7's refresh on a production-releasing merge, each running its own admission afresh and then the list again, this check re-evaluated on the refreshed tip; the one statement of what the re-entered reads keep and of the budget); the one stop is the close's 60-minute wait budget (one per close and path, read from the first `waiting` record — never restarted by a re-entry), `reason=foreign-merge-waiting [foreign_run=<iso>]`. **The park (no allow, or `allows=unknown`):** key class `deploy-production`, `detail=` naming the foreign commits; the operator's clear, given attended, is the acceptance. Every commit placed in these commands passes the preamble's commit check first.
6. **A failure after the merge** — a deploy that fails or times out (its run ended so; one still queued or running at the wait's bound is item 5 (c)'s park, not this), a failed checklist item, a failed post-deploy check: the release parks with the must-pause pair, so the operator is notified at once. Nothing is fixed. Where the operator confirmed a pinned rollback step for that path at departure, the composer runs it once — the step as the comparison contract's applicable-procedure rule selects it, the block at the comparison below's `--to` — but only once the forward deploy this failure concerns reads finished (a bounded wait that ends at the first read that settles it — Visibility + run-state → the chunked-poll heartbeat) — its run (the one (b) bound, the staging step's own run, or the merge's push-fired or chained run) completed, or the provider's record final, read through that act's own reader — the path's `Receipt:` reader for a production act, the staging deployment-history reader check item 7 quotes for a staging deploy (as Records → A push-fired deploy reads it), never one act's reader for another's state; one still queued or running, or whose state cannot be read, parks with no rollback (item 5 (c)'s in-flight rule — an immediate failure such as `/close-run` item 10's tree or machinery mismatch reaches this before any receipt wait), so no rollback races a release still in flight. The rollback is checked the way item 5 checks production: item 4's machinery comparison first (and the machinery at a protected ref, where the step runs from one), then the deploy's own record of the revision it returned to and the machinery it ran — records key class `rollback` naming the revision it returns to, and then parks and notifies whatever the rollback's result. The rollback's class is its own, read independently of the forward step's: after a failed production act of any class — an accepted revision-only or branch-following step included — a rollback step that is itself pinned and departure-confirmed runs once as above, and a revision-only or branch-following rollback is never run.
7. **After the merge nothing is written to the base checkout** beyond `/close-run`'s own steps — the group close's fast-forward of the base checkout is one of them (the helper's `group-ff` leg, run by `/close-run`'s group route — Termination → Group end), and the group's `[operator]` 🟩 write and its bookkeeping commit land in the WORKTREE, never the base. Release records go to `<log-root>/stage-<N>-probe.log` (the log `/close-run` already uses) and the report to the log folder; the BASE plan copy is not edited after the merge (the worktree copy's 🟩 write is Group end's — v40.0; and from v47.0 the plan's archive move rides the run's own pull request — `/close-run`'s release stamp — so it reaches the base by the merge, never by a write after it).
