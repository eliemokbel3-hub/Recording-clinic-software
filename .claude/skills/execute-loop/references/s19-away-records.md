# Away mode, part 7 — records for acts on the operator's behalf
Previous: s18-away-stop-and-end.md. Next: s20-usage-commit-coordination.md. Words such as above and below may point into those files.

Contents, in order: Keys on existing records; A decision with no open pause; A decision that closes an open pause; An agent-run smoke; A release act; A push-fired deploy; the guard; The CI verdict; A hold; A set refresh; A pre-approval; A re-baseline; A foreign clear and a coordinated wait; The effective set and accepted versions; A park; Flush; The report.

**Records for acts on the operator's behalf** (tool-written, never hand-typed; a release act is recorded BEFORE it is taken).

- **Keys on existing records.** A decision taken on the operator's behalf under a bound grant carries the away pair `away=<n> away_check=<the grant's config_hash>` with `choice=<what was done>` and `rec=<executor|composer>:<the recommendation followed>`. It is an `OWNERSHIP: auto-disposition` when no `must-pause` is open for that run key and key, and an `OWNERSHIP: gate-disposition` for that same run key and key when one is — the record that closes a pause. `rec=` rides an `auto-disposition` only beside the away pair. `OWNERSHIP: smoke-pass` gains `smoke_by=<agent|operator>` (absent reads as `operator` — with the away pair the writer requires the key from v46.4; `smoke_by=agent` needs no grant) and may carry the away pair; the existing free-text `by=` is left alone. The pair is both or neither, `away=` a positive integer and `away_check=` 12 lowercase hex, admitted on those three subtypes only. Keys keep the form `<runkey>-<class>`; the classes for acts that are not findings are `close-run-confirm`, `retro-pointer`, `pr-fix`, `merge`, `deploy-staging`, `staging-checklist`, `deploy-production`, `rollback`, `snapshot`, `decision`, `grant-add`, `run-collision`, `continuation` (the class of the retired boundary parks — recognized on historical records, never written from v40.0), `operator` (Away mode item 2's parks), `set-refresh` (A set refresh below — a requoted, refreshed, re-baselined, or audited release machinery entry; never a release act, never in the report's release-act section), and `pre-approval` (A pre-approval below) and `foreign-merge` (A foreign clear and a coordinated wait below) — both outside the release classes, so neither voids a CI verdict, and the report files them under §3. The judgment value `impact=production|none` rides the executor's scope-expansion route record beside `severity=` (STICKY §7; The four stops, item 2). The free key `foreign_run=<iso>` names ANOTHER run on a `foreign-merge` record — never `run=`, which is tool-owned (the writer refuses a caller-supplied one) and is THIS run's stage identity on every record. A record of a path-bearing class (`deploy-staging`, `deploy-production`, `rollback`, `snapshot`) carries `path=<the production path, as check item 7 names it>` — spelled ONE way: the workflow file's repository-relative path (`.github/workflows/<file>`); for a step with no workflow file, the name the departure file gives its path; for a `snapshot`, the path of the production step it protects; a `hold` follows the same rule within the hold path alphabet `[A-Za-z0-9._/-]+`, and outside it is written class-wide (A hold below) — a documented free key on the disposition records, as `via=launcher` is, never a validated one there: required when one merge fires more than one path of a class, recommended always; an absent `path=` is its own value, so a record without it pairs as records always have. The emit does not read the policy log — whether a pair matches a grant is the report's check — with ONE exception: an away `merge` `choice=start`, where the helper requires the bound grant's own pair and reads its departure file (Record grammar → The listing check).
- **A decision with no open pause** — `python3 scripts/loop-journal.py emit OWNERSHIP:auto-disposition --run <runkey> --role composer --log <probe-log> [--policy-log <abs> --iso <iso-id> --plan <plan>] --epoch "<activation id>" key=<runkey>-<class> choice=<what was done> rec=<executor|composer>:<the recommendation followed> away=<n> away_check=<config_hash> [tip=<40-hex>] [ungated=merge] [allow=<class>] detail="<why>"` (`<config_hash>` is the `config_hash=` the `away check` line prints; `tip=<40-hex>` — the checked commit — and, on the no-checks route, `ungated=merge` are REQUIRED on an away `merge` `choice=start`, which is admitted only on a fresh verdict for that tip (Record grammar → The CI verdict → Admission); on any other disposition record the helper checks both keys' formats and refuses neither. The three flags `--policy-log <abs> --iso <iso-id> --plan <plan>` — the `away check` read's own values, `--plan` the journal's `plan=` string — are REQUIRED on an away `merge` `choice=start`, a late one included, whose key is `<runkey>-merge`, and are given on NO other record: the helper refuses them there (Record grammar → The listing check). `allow=<class>` is written when the act rides a pre-approval (The use-time check → Pre-approvals) — `allow=operator-merge` on the start of a merge the departure file lists `pre-approved`, never beside `ungated=merge`). A residual-gate disposition keeps the key that gate already uses — a finding route passes `--round <n> --id <ID>` and its `severity=` in place of `key=`, per STICKY §7's DISPOSITION-TIME checklist — and every existing rule stands: a CRIT never auto-disposes, and a HIGH finding route still carries its `authority_check=`/`authority_epoch=` pair. Only dispositions that would have paused without the grant carry the away pair; what `gates=executor` already auto-disposes keeps its records unchanged.
- **A decision that closes an open pause** — `python3 scripts/loop-journal.py emit OWNERSHIP:gate-disposition --run <runkey> --role composer --log <probe-log> [--policy-log <abs> --iso <iso-id> --plan <plan>] key=<the open pause's key> choice=<what was done> rec=<executor|composer>:<the recommendation followed> away=<n> away_check=<config_hash> [tip=<40-hex>] [ungated=merge] [allow=<class>] detail="<why>"` (no `--epoch`, as for every `gate-disposition`; a finding-route pause passes `--round <n> --id <ID>` in place of `key=`; `tip=`, `ungated=merge`, the three flags, and `allow=<class>` exactly as on the recipe above — an away merge `choice=start` that closes an open `<runkey>-merge` park rides this shape and needs them too). It says truthfully that the composer closed the pause under grant n, not the operator, and it is never written for a stop or an always-the-operator's item. The two routes decide a stop-2 disposition too: a scope expansion the executor routed BELOW stop 2's line with no open pause is the `auto-disposition` above, with `--epoch` and its NOTIFY; one the executor surfaced as a must-pause and the composer then disposed under the grant is this `gate-disposition`, without `--epoch` (the writer refuses it here) and with no new notice — both carrying `rec=executor:<choice>` and the away pair (the disposition table's row; `away report` §4 lists them).
- **An agent-run smoke** — `python3 scripts/loop-journal.py emit OWNERSHIP:smoke-pass --run <runkey> --role composer --log <probe-log> smoke_by=agent away=<n> away_check=<config_hash> detail="<log-root>/<runkey>-away-smoke.md"`. With the away pair `smoke_by=` is REQUIRED: `emit` refuses a `smoke-pass` that carries the pair without it (`bad-smoke-by`, exit 2, nothing written).
- **A release act** is recorded before it is taken (`choice=start`) and its outcome after, read from the real state — the pull request, the workflow run, the deployed app — as a second record for the same key and `path=` (`choice=done` or `choice=failed`), both with the decision recipe above. A branch that parks or ends the act before its own outcome rule is reached — a head mismatch that parks, a fix cycle parked partway, a release parked by item 6 before a deploy's receipt is read — records that outcome `choice=failed` with `detail=` naming the park, so no park leaves a `start` open. A session that dies between the two leaves a `start` the report flags. The acts are `pr-fix`, `merge`, `deploy-staging`, `deploy-production`, `rollback`, and `snapshot`; a `staging-checklist` is a check, recorded as its single outcome. A pre-production snapshot is `snapshot`: `choice=start` before it is taken, then `choice=done` with the snapshot's identifier in `detail=` once it reads available, or `choice=failed`.
- **A push-fired deploy** — for each path the departure file names that a merge fires — has its `choice=start` written right AFTER the merge's `choice=start` is ADMITTED (the merge start first: the helper admits it only on a fresh verdict, and a refused merge start writes no deploy start and is a park), still before the merge command: an attempted trigger, never a deployment, with `detail=` naming the workflow and saying `run=pending` (inside `detail=`, never a second `run=` key). Its outcome binds the path's receipt — the reader its `Receipt:` line names (check item 7; on a staging path, the staging deployment-history reader item 7 quotes), within the bounded wait (60 minutes from the merge) — as `choice=done|failed`; on a production path that one outcome is Release work item 5 (c)'s `deploy-production` record (both identities verified, written after its post-deploy check), never a second outcome. A merge whose outcome is not `done` (still open, queued, merged into another base) reconciles every such start at once with `choice=failed detail="merge <state>; no deployment receipt bound"` — never a deployment success — and the park stands; a receipt that never appears within the wait is `choice=failed` too.
- **The guard detects a missed start; it does not prevent the act.** The report's section 6 flags, per act and per `path=`, `started; outcome not recorded — check the real state` and `outcome recorded with no start before it`. An `emit` of an `auto-disposition` or `gate-disposition` with `--log`, the away pair, an act-class key, and `choice=done|failed`, whose most recent start-or-outcome for that run, key, grant, and `path=` in that log is not a `start` (a start counts on either subtype; a late start, below, answers only the outcome before it, never a later one), prints on stderr `warning: <key> outcome recorded with no start before it — record starts before the act` (with ` path=<p>` after the key on a record that carries one), writes the record unchanged, and exits 0 — never a refusal. The report and the warning share one pairing owner, but the report also applies its grant join, window, and unmatched-record checks, which `emit` cannot (on an outcome record it does not read the policy log — the one emission that does is an away merge start, v47.0, The listing check): where the two differ the report is authoritative and the warning advisory. A missed start is recovered with a late start: the same key and `path=`, written with `--event-ts <the act's time>` — strictly before the outcome's `ts=` — and `detail=` saying it was recorded after the act. The report then labels it `late start — recorded after its outcome`, keeps the outcome's flag, and counts nothing open; a late start not backdated before its outcome reads as an ordinary open start. For an away `merge` start that recovery is the ONE case `--event-ts` is admitted (v35.1, D9 (b)) — a TRUE late start: it answers an outcome of its own identity (run, key, grant, `path=`) recorded with NO start before it and not already answered, with a `ts=` strictly before that outcome, judged by the same pairing owner the report uses over the log's writer-valid disposition records plus the candidate (a torn or damaged `auto-disposition` / `gate-disposition` line anywhere in that log refuses it); it is a record repair, admitted without a verdict — though from v47.0 not without the grant: it takes the three flags like every away merge start, so the grant its pair names must still be bound and the departure file's merge-stop lines are folded (a line reading `around` or `park` for its key, or a malformed one, refuses it), and it never rides `operator-merge`: for a merge the file lists `pre-approved` no late start is admitted at all — refused without the label and refused with it — so that merge's missed start stays the report's flag (Record grammar → The listing check) — and one unmatched outcome licenses one repair — an outcome that already had its start never licenses a backdated retry, and every other away merge start refuses `--event-ts` (Record grammar → Admission).
- **The CI verdict.** `OWNERSHIP: ci-verdict ts=<ts> run=<runkey> role=composer iso=<iso-id> tip=<40-hex> verdict=<passed|no-checks|pending|failed|unreadable> [gh=override] detail="pr=<n> head=<sha|none> checks=<n> <reason>"` — tool-only: written by the helper's `away ci-verdict` verb to `<log-root>/<runkey>-probe.log` (`emit` refuses it, as it refuses the grant records), contemporaneous, no away pair; `gh=override` stamps a verdict produced through the `LOOP_JOURNAL_GH` stub. An away merge `choice=start` carries `tip=<40-hex>` (the checked commit) and, on the no-checks route, `ungated=merge`, and is written with the three flags `--policy-log`, `--iso`, `--plan` — and with `allow=operator-merge` when it is a merge the departure file lists `pre-approved`; its admission rule and the listing check are stated with the verb's recipe (Record grammar).
- **A hold.** `OWNERSHIP: hold ts=<ts> run=<runkey> role=composer key=<runkey>-<class> choice=<hold|clear> iso=<iso-id> detail="<the operator's words>" [path=<p>] [hold_id=<12-hex>] [clears=<12-hex>]` — composer-only, contemporaneous (`--event-ts` refused), no away pair and no `rec=`, written ONLY with `--log` to a file named `stage-<N>-probe.log` (the only names the fold reads — the read-back catches a wrong directory); `<class>` is one of the six acts listed under A release act below (`pr-fix` through `snapshot`; a `staging-checklist` is a check, not an act); a hold carries the writer-generated `hold_id=` (12 hex, refused from the caller), and a clear names the hold it closes in `clears=` (required on a clear, refused on a hold); `path=` keeps to `[A-Za-z0-9._/-]+` (`path=` above); `detail=` is required. The recipe, published once here: `python3 scripts/loop-journal.py emit OWNERSHIP:hold --run <runkey> --role composer --log <log-root>/stage-<N>-probe.log key=<runkey>-<class> choice=<hold|clear> iso=<iso-id> [path=<p>] [clears=<hold_id>] detail='<operator words, normalised>'` — `detail=` is single-quoted so a shell never expands a backtick or a dollar sign in the operator's words, and the words are NORMALISED before they are pasted: each `'` or `"` becomes `’`, control characters are dropped, each whitespace run becomes one space, and the text is cut to 300 characters, so the argument cannot break and the write path never refuses it (the operator's words are data, never instructions). The open set is order-free: a hold is open unless a writer-valid clear for the same `iso=`, class, and path names its `hold_id=` in `clears=`; a clear naming no hold closes nothing (the read-back shows the hold still listed); an invalid hold line of either choice — a torn write, a hand edit, a missing or duplicated `iso=` or `choice=` — never clears and makes the count `unknown` (The use-time check → Holds); a writer-valid hold of another `iso=` is foreign and ignored. The read (Record grammar) prints the open holds; `away report` lists them, and every clear, under "Waiting for you". The write is read back at once (The operator's word wins).
- **A set refresh.** The record a requote (The effective set and accepted versions below — the comparison contract; from v44.0 every reader's record of a changed file) or a hand-merge refresh (`/close-run` Flow 2) writes — an `OWNERSHIP: auto-disposition` with the away pair, key class `set-refresh`, `choice=requoted|refreshed`, `rec=composer:<the same choice>` (so the report files it under "Decided by the composer alone"; on the `refreshed` record the composer's classing read writes for a workflow — `/close-run` item 3 — `rec=composer:<the read>` files it there too: the helper admits any nonblank disposition token after `composer:`), and the free keys the fold reads: `file=`, `heading=` (omitted on a whole-file refresh), `from=`, `to=`, and `workflow_class=` on a workflow file only (never `class=`, which the writer owns as the paired NOTIFY's routing class). The recipe, published once here: `python3 scripts/loop-journal.py emit OWNERSHIP:auto-disposition --run <runkey> --role composer --log <probe-log> --epoch "<activation id>" key=<runkey>-set-refresh choice=<requoted|refreshed> rec=composer:<requoted|refreshed> away=<n> away_check=<config_hash> file='<path>' heading='<heading>' from=<id> to=<id> [workflow_class=<staging|production|not-a-deploy>] detail='<reader> <path> § <heading> <from7>→<to7>'` (a whole-file record's `detail=` has no `§ <heading>` part) — each data value SINGLE-quoted so the shell delivers it as ONE argv element with spaces and inline code verbatim (item 4's heading contract: the heading bytes are the fold's key and are never normalised, unlike the hold recipe's operator words; a heading holding a single quote is written `'\''` for it); `detail=` takes the classing form on a `refreshed` record the classing read writes for a workflow — `detail='<reader> <path> blob <the version's 40-hex blob id, as the ls-tree listing prints it> class <workflow_class>'` — the one field `away report` §3 prints that can carry the version's identity, which the once-per-version rule reads (The effective set and accepted versions below); `from=`/`to=` are the reader's printed `from=`/`to=` verbatim — a commit id or a blob id, never a hand `rev-parse` (for a file outside the effective set, `from=none` and `to=` its blob id as the `ls-tree` read prints it — The effective set and accepted versions below); `heading=` is omitted on a whole-file refresh (a headingless record covers whole-blob readers only); `workflow_class=` rides a workflow file only, read from the merged workflow as check item 7 classifies one; a `"` anywhere in a value makes the emit refuse — no record, and the reader parks. It is never a release act (no `start`/`done`), never voids a CI verdict, and is read only by the helper's fold (`/close-run` item 4's recipe with its `--log-root`/`grant=`/`away_check=` trio) under the grant whose pair it carries. **The audit form.** A listed file REMOVED, a quoted heading MISSING, or a heading AMBIGUOUS at a reader is recorded on the same key class with `choice=removed|heading-missing|heading-ambiguous` and `rec=composer:<the same choice>` — the recipe above with `file='<path>'`, `heading='<heading>'` on the two heading choices (none on `removed`), the reader's printed `from=`/`to=`, no `workflow_class=`, and `detail='<reader> <path> § <heading> <verdict>'` — which the fold NEVER keeps (its whitelist is `requoted | refreshed | rebaselined`): never an accepted version, never a refusal, listed by the report under §3; one per file (and heading) per grant — a later read finding the same state with the record present writes nothing. A `rebaselined` record is the helper's alone (A re-baseline below): the composer never emits one.
- **A pre-approval.** A standing answer the composer acts on later — the departure-time classes on the grant's `allows=` kv (Record grammar), and every mid-run instruction and every per-task `agent` answer as THIS record: an `OWNERSHIP: auto-disposition` with the away pair, key class `pre-approval`, the free keys the fold reads — `instr=<12 lowercase hex>` (the instruction identity, minted by the composer ONCE per operator instruction, e.g. `python3 -c 'import secrets; print(secrets.token_hex(6))'`, and carried unchanged on a retry, so the fold reads the retry as a replay — the `hold_id=` precedent), `choice=allowed|cleared`, `allow=<records-merge|pr-fix-cycles|ci-advisory-fix|foreign-merge|operator-merge|operator-task>` (`operator-merge` from v47.0 — no `path=`, no `limit=`), `path=<task id>` on `operator-task` only (REQUIRED there — the task's ID token in the alphabet `[A-Za-z0-9._-]+`: `T2.3`, `H1`, `T3.S2`; a step named in prose is written by its token, `H` for "Step H"; an id carrying a space, `;`, `/`, or any other byte is refused by the writer, never normalised), `limit=<positive integer>` on `pr-fix-cycles` only, `rec=composer:allow` on an `allowed` and `composer:clear` on a `cleared`, and `detail=` the operator's words under the hold recipe's normalisation (each `'` or `"` → `’`, control characters dropped, whitespace runs collapsed, 300 characters) — the writer validates every one of these and refuses the rest (`bad-preapproval-choice`, `missing-allow`, `bad-allow`, `missing-instr`, `bad-instr`, `missing-preapproval-path`, `bad-preapproval-path`, `path-on-class`, `limit-on-class`, `bad-limit`, `bad-preapproval-rec`, `missing-away-pair`); the fold refuses nothing and reads the same rule (a line it would refuse is `allows=unknown`). The recipe is the decision recipe above (A decision with no open pause — `--epoch` given, the NOTIFY paired), with `key=<runkey>-pre-approval instr=<12-hex> choice=<allowed|cleared> allow=<class> [path=<task id>] [limit=<n>] rec=composer:<allow|clear>` in place of its `key=` / `choice=` / `rec=` values, `detail='<the operator's words, normalised>'` single-quoted as the hold recipe quotes them, and `--log` a file named `stage-<N>-probe.log` (the only names the fold reads — the read-back catches a wrong directory). Never a release act; never in `AWAY_RELEASE_CLASSES`; read by ONE fold (The use-time check → Pre-approvals) that `away check` prints as ` allows=`/`allowed=` and `away report` §1 lists as "Pre-approvals in force" and "Cleared"; an `operator-task` record for a task the `agent` rule excludes (check item 2) is not honoured.
- **A re-baseline (helper-written, unpaired).** `OWNERSHIP: auto-disposition ts=<ts> run=stage-<N> role=composer key=stage-<N>-set-refresh choice=rebaselined to=<the group's MERGE COMMIT, 40 hex> rec=composer:group-ff away=<n> away_check=<config_hash>` — no `file=`, no `heading=`, no NOTIFY twin, no `epoch=` field (the shape `emittable_record` accepts; the paired writer's `epoch=` rides the NOTIFY line only, and an `epoch=` field on an OWNERSHIP line is refused) — written DIRECTLY by the helper's `run-close` `group-ff` leg, like `run-close`'s own report, `ci-verdict`, and the grant, into the stage probe log `--log` names, when the composer passes `--grant <n> --away-check <config_hash>` on the group close (`/close-run` Step 7's group form; the trio from the use-time `away check` line) — once BOTH checkouts hold the fetched base and BEFORE `ff_stage_<N>` is written, after a whole-log existence check that keeps it to ONE record per `to=` under the grant (Run isolation → Mechanical close enforcement → The re-baseline: the normal path, the key-absent replay, and the already-closed branch all run it; `rebaseline-conflict` and `rebaseline-unreadable` refuse); the leg prints `group-ff: rebaselined at <log>:<line>` on stderr after its report, which the composer quotes. What it means (The effective set and accepted versions below): the accepted VERSION of every file present at `<to>` for `quoted-block`'s fold — block mode the heading's block at `<to>:<file>`, blob mode the blob; a file absent there, or a heading missing or duplicated there, gets no version from it — never set membership, never a change to the reader's verdict contract; `to=` is the merge commit, not the fetched tip, so anything another actor landed after the merge reads `changed` and is recorded at the next read. `emit` never writes it: the composer never hand-writes one, and a composer-shaped `rebaselined` line carrying `file=` or `heading=` is skipped by the fold and is no evidence for the close (the helper appends the genuine record as the repair).
- **A foreign clear and a coordinated wait (Release work item 5's foreign-merge check; the records and the mechanics, stated once here).** `OWNERSHIP: auto-disposition … key=<runkey>-foreign-merge choice=cleared rec=composer:docs-only|coordinated commits=<sha>[,<sha>…] path=<production path> [foreign_run=<other iso>] away=<n> away_check=<config_hash> detail="…"` and `… choice=waiting rec=composer:coordinate commits=… path=… [foreign_run=<other iso>] … detail="…"` — the decision recipe above with `--epoch` (no pause is open), `path=` the production path as check item 7 names it, `commits=` the foreign commits comma-joined, `foreign_run=` the OTHER run's iso-id (never `run=` — Keys on existing records). **The docs-only clear** (the fixed alphabet — the check states it) writes `cleared rec=composer:docs-only` and proceeds. **The coordinated wait** (the `foreign-merge` pre-approval open on the `away:` line): *finding the commit's run* — scan every `<base>/.cursor/loops/<iso>-isolation` journal for the commit: a GROUP merge is the journal's `merged_stage_<N>="<ts> <sha> <tag>"` value, a FINAL merge its `merged="<ts> <sha>"` value (or the by-hand `merged=<ts> commit=<short> note=…` shape); `merge_commit=` is a field of the `OWNERSHIP: run-close` report record, never a journal key. *Discovery is COMPLETE* only when the `<base>/.cursor/loops` listing succeeds, every `*-isolation` journal it lists is read (a listed journal that cannot be opened or decoded is a DISCOVERED-BUT-UNREADABLE candidate, never a non-owner), and every journal's merge fields are interpretable (a present `merged=` whose value cannot be read, or a present `merged_stage_<N>` not in the `<ts> <sha> <tag>` shape, is an UNINTERPRETABLE merge identity, never "no merge recorded"); a listing failure, a discovered-but-unreadable journal, or an uninterpretable merge identity with NO readable journal naming the commit is INCOMPLETE discovery → UNRESOLVED → the wait, unless a READABLE journal names the commit (a merge commit has one source run — the doubtful journal is irrelevant to it) or `<released>` already covers it (not foreign at all). *Its production state* — read from that run's probe logs under its log root (the journal's `log_root` key when absolute, else `<base>/.cursor/loops/<iso>` — the census's rule), with the EXISTING folds and never a "latest record" pick: `away check` run with THAT run's identity (the invocation the foreign departure read already makes — the pre-departure check's **Other live runs**) — its ` holds=`: any open hold of class `deploy-production` whose `path=` equals this production path OR is absent (class-wide) means parked, `holds=unknown` unresolved; its ` parks=` — the STRICT production-park fold (Record grammar): an open `deploy-production` must-pause whose `path=` equals this path OR is absent (class-wide — `path=` is recommended, never required, so a valid single-path production park can carry none, and a missing path never proves a different lane) means parked, one naming a DIFFERENT path is not applicable (positive evidence of another lane), `parks=unknown` unresolved. A `merged` or `cleaned` journal is NOT evidence its production ran — only a `deploy-production` outcome record there, or `<released>` moving to cover the commit, is. *Three outcomes*: (1) a COMPLETE readable scan with no journal naming the commit → cleared at once under the allow, `rec=composer:coordinated`; (2) a journal names it and its state is readable → an open park or hold → the wait; none → cleared; (3) discovery INCOMPLETE with no readable owner identified, a named run whose log root or probe logs cannot be read, either fold `unknown`, or its journal `cleaned` while its grant is still bound → UNRESOLVED, handled as the wait (fail closed — never cleared as unparked). *The wait*: the `waiting` record is written ONCE (`foreign_run=<iso>` when the owner is identified; on incomplete discovery NO `foreign_run=` — never an invented iso — and `detail="discovery-incomplete: <cause>"`, the cause naming the listing failure, the `<iso>-isolation` file that could not be read, or the journal whose merge identity could not be interpreted); ONE message where the host has a channel (**Coordinating with other runs**), naming the commit, the path, and this run; the re-check at the checks-wait cadence (`/close-run` item 6's loop; on incomplete discovery it re-runs the discovery itself) while ANY applicable hold or park stays open or discovery stays incomplete; it ends with `choice=cleared rec=composer:coordinated` (the park lifted, `<released>` moved to cover the commit, or the grant ended with the park released) — and then, because a wait that actually waited (a `waiting` record written) has aged every read taken before it, control RETURNS to the route owner that entered Release work item 5's **Final admission to a production act** — item 5 (b)'s last reads on a dispatched step, `/close-run` item 7's refresh after the last long prerequisite on a production-releasing merge — which runs its own route-specific admission afresh (the merge's fresh verdict and re-bind among them) and then Final admission's list again (the one statement — the list, what an unchanged identity keeps, what a changed one takes, the budget one per close and path from the FIRST `waiting` record, never restarted by a re-check or a return), this check re-evaluated on the freshly fetched tip; the act proceeds only once that route's admission and the list pass, or — at the close's 60-minute wait budget, item 6's precedent — the park: key class `deploy-production`, `reason=foreign-merge-waiting [foreign_run=<iso>]` (the iso absent on incomplete discovery, the same `detail=` carrying the cause).
