# The per-phase loop, part 2 — steps 4 to 9, and phase detection

Contents, in order: 4 cross-check, the peer pass, with its seats, the takeover and the per-pass cap keys; 5 smoke; 6 pause if needed, with the smoke-feedback routing; 7 document, and the progress line; 8 commit; 9 discard and advance. Then Phase detection + bounded discretion.

4. **Cross-check** — run `/peer-loop` (default-on per the wizard cadence): a fresh cross-family peer runs `/peer-review` headless → each finding is verified against the code and `/fix`ed → a fresh peer re-reviews → to convergence/stalemate/cap. Skippable only as the wizard cadence licenses (under non-trivial-phases-only: genuinely trivial phases; under plan-end-only: every phase before the last) or on an explicit user call — step 3's cadence-is-config rule. **Who drives it is `peer-seat=` policy — COMPOSER SEAT BY DEFAULT:**
   - **Composer seat (DEFAULT — every backend): the composer drives `/peer-loop`**, spawning each cross-family peer round itself and routing each finding to the executor to verify and `/fix` over the TWO-LEG resume path (defined in the takeover clause below — the same routing, with the executor's completed-and-resumable session resumed per leg rather than a dead one; the executor holds the phase context, and the composer never verifies or fixes findings itself) — under `isolation=worktree`, against the WORKTREE checkout: the diff and the authoritative plan live there (see **Run isolation (worktree-per-run)**). On a run with a run worktree, a codex peer round at this seat is started through the peer launcher, which writes the round's `ROLE: start`, escape-check record, and `ROLE: end` itself; the composer writes that leg's `CONSUME:` verdict and never its pair (Visibility + run-state → **`ROLE:` log lines** → Launcher legs, which also lists the rounds that keep the hand route; the recipe: the companion STICKY card §4 step 8). Every peer spawn prompt the composer builds carries `/peer-loop`'s STRUCTURAL read-scope steering (its step-2 prompt invariants, v32.3): the pinned diff + explicit file list as the review surface, closed historical Findings-Log rounds named not-reading-material, security-shaped or grammar-quoting content framed as prose-to-review, and records treated as current AS OF their closing round (the finishing seat writes Last-reviewed; fix-refreshed record currency is not a finding — invariant (d), v32.5) — steering is structural, never re-learned after a filter death. The default is EVIDENCE-FORCED, and it is the SEAT, not the foregrounding: across the run-3 harness corpus 0/9 executor-seat peer rounds completed while 7/7 composer-seat rounds did — including a BACKGROUNDED composer-seat peer that completed fine. Preferred composer-seat peer-round wait (a stated preference, never a mandate; the preflight-resolved `Wake:` line stays the mode authority, and no `Wake:`/`WATCH:` grammar changes): where the run resolved a Layer-1 `bg-shell` surface and delivery is not `fg`, run the peer round as a composer-owned background shell teed to its role log (a launcher leg is not teed: the launcher appends codex's output to the peer log itself, its shell carries status lines only, and the peer log is the log the liveness layer watches) with the preflight-resolved Layer-2 mechanism armed (a monitor only where `layer2=monitor` resolved; the resolved sentinel or the legal `layer2=none` continuation otherwise) — Layer 1 wakes on anchors/exit and the resolved Layer 2 covers quiet windows, no foreground turn spent waiting (the v31phaseE-observed shape ran monitor-armed). Where a foreground wait applies (resolved `delivery=fg`, surface-less hosts), composer-seat child waits follow the chunked-poll heartbeat rule (Visibility + run-state): bounded foreground polls of up to min(the liveness interval, ~10 min) each (~10 min flat under liveness OFF), with a `[<runkey>]` heartbeat line at least once per liveness interval (liveness OFF: at least every ~10 minutes of waiting) while a round runs — a multi-tens-of-minutes silent wait over a live peer is a violation, not patience (observed live). Each default-seat peer spawn is ALSO bracketed by the commit-authority boundary — the same commit/ref/reflog snapshot at spawn and fail-closed compare at exit used for executor/architect activations (**Auto-commit (git-safety)**); the `git status` escape check below is necessary, not sufficient. The composer seat is also the ONLY topology for executors without a validated in-executor peer-spawn route: `codex exec` (v32.3 scope boundary, not a capability claim — current codex has native `multi_agent` orchestration, probed working under `-s read-only` at 0.147.0, but the in-executor `/peer-loop` route on codex — its grants, wake artifacts, and escape checks — is not implemented or field-validated in v32.3, so the composer seat stands for codex on both tiers this release; the older network rationale — `workspace-write` denying network for a NESTED `codex exec` process — is true of the shell-nesting route only, never the native path), an ungranted SCOPED `claude -p` executor, and a `claude -p` executor running degraded after Step 0's environment-readiness pause — its binary failed the isolation probe, so the pause's no-in-executor-peer-pass consequence stands regardless of grants.
   - **Executor seat (documented OPT-IN — `peer-seat=executor`, validated peer-spawn-route backends only): the executor runs `/peer-loop` in-session**, accepting `/review-loop`'s convergence chain-offer directly per the wizard cadence instead of offering it to an absent user — step 3→4 as one continuous in-executor flow, the executor verifying findings and applying `/fix` without per-round composer round-trips and supplying `/peer-loop`'s orchestrated-mode config from the spawn-prompt carry (step 1): its own family, the resolved peer row, the cap, and the run key. Legal ONLY under the explicit Q5 opt-in persisted as `peer-seat=executor` (absence = the composer seat; fail-closed) on a backend in the validated in-executor peer-spawn route set: a Cursor subagent (Task tool), the live session, and — verified live — a `claude -p` executor granted the **fixed peer-spawn grant list**: `Bash(codex exec:*)` + `Bash(git status:*)` + `Bash(git diff:*)`. The grant list is fixed per backend pair and NEVER derived from plan text (agent-authored plan prose is an injection vector for `--allowedTools`); it is displayed in the wizard close table and logged in the executor's `ROLE: start` context, and it rides the close table and the spawn ONLY on an opt-in run — a composer-seat run passes no peer-spawn grants. The grant list is a SCOPED-tier concept — under `perms=bypass` it is MOOT: a bypass `claude -p` executor is always peer-spawn-capable, no grant needed. An opt-in executor-seat round keeps its hand-written records — the executor's own `emit ROLE:start` / `emit ROLE:end` pair and its hand-run escape-check pair; the peer launcher is composer-only and is never granted to it.
   - **Opt-in failure falls back to the composer seat:** if an opt-in executor's peer spawn fails (grant denied, CLI missing, spawn error), the executor reports the failure and the composer drives `/peer-loop` — the default seat — instead: the peer pass is never skipped and never marked converged on a failed spawn.
   - **Peer spawns run foregrounded — never background-and-end-turn.** A headless executor terminates at turn end: a peer round spawned in the background and "awaited" via a completion notification is orphaned the moment the executor ends its turn (observed live, 2026-07-03 — the run died mid-pass; RECURRED 2026-07-19 downstream despite the rule, so it is stated mechanically): each peer `codex exec` runs in the foreground of its shell call and is waited on synchronously — no `&`/`nohup`/disown, no harness background flag, no spawn-then-check-later — and the same rule binds EVERY child a headless role spawns (peer rounds, Mechanism-C consults, a shell-invoked delegate), not peers alone. When one foreground wait cannot span a long child (a harness per-call time cap), stay in the SAME turn and re-enter bounded foreground waits — each poll command bounded ≤2 minutes (the proven headless-poll ceiling: a longer single wait trips harness caps and reads as a hang to watchdogs) — until the child completes; ending the turn while the child runs is the failure, whatever the intent to check back.
   - **Composer takeover mid-pass (the opt-in seat's recovery; its TWO-LEG resume path is also the default seat's canonical per-round routing).** If an opt-in executor dies mid-`/peer-loop` (crash, limit-death, an orphaned round — on the default composer seat there is no executor-owned pass to orphan), the composer takes the pass over — routed by AUTHENTICATED child kind, never by assumption: an executor exit with a live child, a `task_updated status=killed` record in the CURRENT activation's terminal window, or a missing/non-terminal handoff sentinel classifies `ROLE: end result=incomplete` (on a wrapper leg the wrapper has already written that end, `incomplete: …`, so the composer's own finding — a live child, a killed task — goes on the leg-bound `CONSUME:`'s `result=`, and it writes no end: Visibility + run-state → **`ROLE:` log lines** → Wrapper legs), and recovery routes on what was actually interrupted — parse the top-level system task events for the current role's `session_id`, binding each `task_id` to its `task_started`/`background_tasks_changed` description: a bound PEER child (or an open peer round in the Findings Log) → THIS takeover; any OTHER executor child → resume the incomplete executor from the plan handoff instead, never fabricating a peer round; watcher-only or stale prior-activation records → no takeover; unknown/unbound event shapes → an anomaly for manual verification, never a success classification (one live teardown killed a peer AND its watchdog — kind-blind takeover would invent peer rounds). The takeover: the composer resumes `/peer-loop` from the plan's Review Findings Log state — round numbering continues from the last logged round, and the composer closes any open round block, branching on the round's `Source:` — a code peer round gets today's behavior (verify outstanding findings against the code, drive `/fix`); a plan peer-review round (`Source:` ending `plan peer-review`) resumes the planning-session amendment/disposition path with plan-diff convergence instead — never `/fix`, never code verification. Never restart the pass from round 1 and never mark it converged on an interrupted round. Resume-first once the takeover round closes — TWO SERIALIZED LEGS, both returning to the DEAD executor's session over its BACKEND-CORRECT resume route (the same routes loop step 6 pins: claude `--resume <session-id>` — the id held by its `IDENTITY:` journal record, Visibility + run-state; codex `codex exec resume <session-id>`; Cursor subagent resume-by-id; a live-session executor re-engaged in-session), never a cold spawn while a resumable session exists (session memory catches peer false positives; skipped live on two concurrent runs): **leg 1 is VERIFICATION-ONLY** — the resumed executor verifies each outstanding finding and writes the verified classification onto the round (materiality + verified severity + the one-line evidence note, originals preserved — Safety gates' executor-verified triage) plus the scope/impact facts — the v33.0 LEG-1 BRIEF REQUIREMENTS (D2/D6/D9): each tuple carries the `surface=production|test-harness|docs` qualifier and a `rec=<disposition — evidence>` recommendation line for EVERY finding and every gate the executor records (the recommendation the composer's ask leads with, D6), and under `cap-raise=executor` the brief ends with the round's `Cap verdict:` line (Termination's cap row) — then records-and-ends WITHOUT entering `/fix` (the ONE exception: a verify-then-fix leg that qualifies — below), so the verified tuple reaches the COMPOSER as durable round state BEFORE any fix; the composer then disposes each finding at its seat (the composer-seat policy + the authorization snapshot, Safety gates) — `gates=strict` and every ineligible case SURFACE here; under `gates=executor` the composer follows each `rec=` outside the ONE residual MUST-PAUSE list; **leg 2 — only for findings the composer routes to fixing** (an eligible fix-biased route fires ONCE) — resumes the same session into `/fix`. **The verify-then-fix leg (ONE leg for a round of plain MED and LOW fixes; the default composer seat, a code round, `gates=executor` only).** When the composer's `attest-check --key gates`, run immediately before the spawn, reads `executor` bound and unrevoked — and the peer labelled no finding of the round HIGH or CRIT (such a round is never briefed this way) — the leg-1 brief carries the fixed line `Leg mode: verify-then-fix`. The leg does LEG 1's work IN FULL first: it verifies each finding AND its proposed fix and writes the verified tuples block, before any edit. It then continues into `/fix` in the SAME activation only if ALL hold: every finding verified `severity=med|low` with a `rec=` of `Fix-now` (an `invalid` finding needs no fix and blocks nothing); none is a regression, a scope expansion, or production-impacting; the leg declares no uncertainty; and the round is not at its cap. Otherwise it records and ends exactly as leg 1 does, and the round goes on over the two legs above. It writes ONE line in the round, `Leg route: verify-then-fix` or `Leg route: verify-only`. The composer then writes the same per-finding disposition pairs as on the two-leg route — AFTER the fix, on this route: the ONE place a disposition record follows its act — and a `Leg route: verify-then-fix` line beside ANY tuple that did not qualify is a review-integrity pause. Every other brief keeps the two legs: no line, another `gates=` mode, an attestation read that is not `bound` with `value=executor`, the opt-in executor seat, a plan peer-review round. What is kept, as the lesson has it: verification of the finding and of its proposed fix precedes every edit, and no route skips leg 1's work. A finding already carrying the verified tuple (e.g. a record-and-end gate record that includes it) skips leg 1 and starts at the composer decision. Only a FAILED resume falls back to a fresh executor from the plan handoff note (the same resume-then-fresh fallback shape as Usage-exhaustion recovery — a pointer, not a second definition). **Round-record ownership (the F13 rule):** the SEAT THAT FINISHES a round owns its `Review History` line — a takeover UPDATES the dead executor's PENDING (unfinished) round entry in place rather than allocating a new round number, and a resume AFTER a closed round allocates the next number; duplicate round numbers and out-of-file-order entries are integrity failures, never bookkeeping variants. **Round ALLOCATION for NEW rounds (the r36 collision, T18a2):** in-session `/review-loop` rounds CONSUME round numbers exactly like peer rounds — a NEW round, any seat, any source, allocates from max(existing round numbers across the plan's `Review History` lines AND `Review Findings Log` `### Round N` headings) + 1, never from the last round of its own kind (a peer brief that counts only peer rounds re-creates the collision); this clause scopes to NEW allocations ONLY — the takeover updates-pending-in-place rule above is untouched. On EVERY composer-takeover path — before acting on the recovered round state — the composer RUNS the mechanical full-history check `python3 scripts/loop-history-check.py <plan path>` (the shipped checker, by its exact installed path) and stops the loop on a failure, exactly as the step-3 assert.
   - **Escape checks follow the spawning session:** whoever spawns the peer inherits `/peer-loop`'s per-round `git status` filesystem-escape checks — the composer on the default seat (on a launcher leg the launcher runs the composer's pair for it); an opt-in in-executor peer pass means the executor runs them. Under `isolation=worktree` a composer-seat peer spawn is cwd-pinned to the WORKTREE like every other spawned role (D4's invariant — a peer spawned with cwd=base produced the only base-side dirt in eight field runs), its helper-twin pair carries `--iso <this run> --liveness <the resolved value>` and `--allow-path worktree:<the authoritative plan path>` (+ its `findings-*.md` sidecar; through the launcher the same three values ride `LOOP_ISO` / `LOOP_LIVENESS` / `LOOP_ALLOW_PATH`) — the peer's ONLY legal writes, filtered out of the worktree digest so a permitted round append stays `clean` while any other worktree change stays `dirty`; a peer declares NO edit surface.
   - **Per-pass cap keys (MECHANIZED on the `ROLE: start role=peer` record; the composer supplies the values).** The peer cap is the per-PASS round budget: the counter restarts at 1 at every `/peer-loop` start — a phase pass, a gate/slice pass, or a re-invocation over the same slice. At each start the composer MINTS an invocation-unique pass id `pass=<phase-or-slice>.p<N>` (N = the invocation ordinal over that phase/slice — `stage-3.p1`, then `stage-3.p2` for a re-invocation; helper form `<slice>.p<N>`), and EVERY peer activation's start carries `pass=<id> peer_round=<k> cap=<N>` — wrapper-spawned peers through `LOOP_PASS`/`LOOP_PEER_ROUND`/`LOOP_CAP` (the wrapper appends them to its own `ROLE: start` and validates through `--read-log "$LOOP_PROBE_LOG"` — the read-only prior-record source; the write still lands once through its retained descriptor), composer-seat codex peers through the SAME three variables on the peer launcher, which puts them on the start it writes and refuses a launch with any of them missing; hand-route codex peers (**`ROLE:` log lines** → Launcher legs) through `emit ROLE:start … --log <probe-log> pass= peer_round= cap=` (the same three keys ride `SPAWN … child=peer` additively). Scope is ORCHESTRATED-ONLY: a start with NONE of the three keys is a standalone `/peer-loop` and is accepted unchanged; SOME but not all three REFUSES (partial grammar is the error, absence is not). The helper sequences against the actual prior log: `peer_round ≤ cap`; `peer_round` = the previous same-pass start's + 1 — the ONE admitted exception is the inconclusive-retry, where the SAME `peer_round` is accepted after the previous same-pass activation closed with a `ROLE: end result=` naming `inconclusive`/`incomplete` (the census assertion failed — no round appended, no budget spent), while a same-round start over an OPEN activation or after a completed round refuses; `cap=` is BOUND to the pass's recorded budget — the seed `cap=` of the pass's first keyed start plus every valid same-pass cap transition logged before this start (an automatic `cap-raise=+1` counts +1; an operator `gate-disposition key=cap-raise|peer-cap choice=raise pass=<p> cap=<N+k>` counts +k, once); a larger or smaller `cap=`, or a transition attributed to another `pass=`, refuses. GRANDFATHERING: a pass with NO prior keyed start seeds from any `peer_round ≤ cap` — a v33.0 composer resuming a v32.5-started run restarts the counter per this clause, never `SPAWN_REFUSED`. Cap-transition records (`cap-raise=+1` / `cap-accept=close` auto-dispositions and `gate-disposition key=cap-raise|peer-cap|peer-cap-accept`) carry their OWN two-key bundle `pass=`+`cap=` — both (orchestrated) or neither (standalone/legacy) — never `peer_round=`; a keyed transition needs `--log <probe-log>` (load-bearing: the helper validates the recorded cap against the pass's budget — an automatic raise records budget+1, an operator raise its larger cap, an accept-close the current budget). No pass-close record exists: a pass's cap rides its OWN records, so `config-change key=caps` stays legal at any time and affects only passes started after it — a raise NEVER rewrites the `Loop config:` `caps=` value (`/retro` reports any `config-change key=caps` coinciding with an open pass as an audit line). Findings-Log round numbers stay global and are never compared to the cap; `/retro` reports rounds-per-pass, raises-per-pass, and verdict counts from these records.
   - **MUST-PAUSE inside an in-executor peer pass (the opt-in seat):** the spawned executor records the open gate (plan handoff note + its final message) and ENDS its run; the composer relays it to the user — a spawned executor never blocks in-session waiting for a human (see Safety gates).
5. **Smoke** — run the phase's agent smoke (tests / build / the payload-sync check where applicable) per the plan's `Validation / Verification`. When the executor backend cannot run approval-gated shell commands (and has not been granted them via scoped `--allowedTools` — see Backends), or the run carries `verify=composer` (the preflight harness probe proved the granted commands do not work — Preflight step 6), the composer runs the smoke. Two routing/advisory rules from live runs: suites that source `.env` (DB/integration suites reading secrets or connection strings from the environment) are COMPOSER-RUN by default regardless of grants — secrets never ride spawn grants, an env-prefixed invocation breaks exact-match grant shapes (see Backends), and a sandboxed role cannot reach localhost services anyway; and when a runnable smoke needs a dev server in a multi-app repo, CHECK THE PORT first — an in-use port means a live instance already exists (the user's own, another run's): reuse it or surface the collision, never start a fighting second instance or blind-kill the holder. Under `isolation=worktree`, composer-run smoke — like every composer-run verification suite this run, the step-3 `reason=composer-run` suites included — executes against the WORKTREE checkout (see **Run isolation (worktree-per-run)**).
6. **Pause if needed** — if the phase touched UI-bearing or runnable behavior, OR any MUST-PAUSE gate fired (see Safety gates), **hard-pause and surface to the user** for a live user smoke test and/or the gate disposition. Do not proceed on the user's behalf — except under a bound away grant — see **Away mode**: the away live smoke takes the user smoke's place when `scope` has `smoke`, and a gate is disposed by that section's lists and table. When the pause closes with the user's smoke PASS, the composer writes the phase's `OWNERSHIP: smoke-pass ts=<iso> run=<runkey>` record (Journal line family, Visibility + run-state) — the mechanical precondition step 8's commit checks on UI-bearing phases (**Auto-commit**). And when a surfaced gate closes with the operator's decision, the composer records the decision itself: `OWNERSHIP: gate-disposition ts=<iso> run=<runkey> key=<gate key> choice=<disposition> detail="…"` — the record whose `ts=` anchors the fresh activation epoch any re-fired `NOTIFY:` cites (Notify-at-gate, Safety gates). Expect UI-bearing phases to be **multi-cycle/assisted**: "look → tweak → look again" is the normal shape; a single pause is the floor, not the model. **Smoke-pause routing default (message interpretation while the pause is open).** The composer's DEFAULT interpretation of ANY user message during this pause is smoke feedback — batched and relayed to the executor for assessment WITHOUT the user having to say so ("send this to the executor" is implicit, never required wording). PRECEDENCE runs before the default, in order: (1) a clear answer to a currently-OPEN composer-surfaced prompt — a gate disposition ("1", "accept all recommendations", "override item 3"), a usage-recovery choice, a user-only environment-verification answer — is consumed by that open prompt and never relayed as feedback; a MIXED message ("2; also the Save button is still clipped") consumes the disposition for the open gate and relays the remaining feedback verbatim; (2) an explicit run-mechanics directive addressed to the composer (pause/stop/cap/config changes, a direct question about run state) is handled by the composer. Only after both checks does the feedback default apply — and only then does genuine ambiguity RELAY-WIN. The composer acknowledges with ONE line naming the batched items and the relay — never "want me to relay this?" (the duties-are-never-asks style, Safety gates) — and never assesses, answers, or acts on the feedback itself. **Clarification ownership:** the composer never originates content-clarifying questions about feedback — it batches the user's wording VERBATIM, marking unresolved uncertainty for the executor to assess; when the EXECUTOR raises a clarification, the composer relays that executor-authored question to the user and routes the answer back without interpretation (a headless executor raises it via the record-and-end path — the Headless seam below); run-mechanics questions stay composer-handled. **Smoke-feedback triage (routing contract).** When the live-user-smoke pause returns feedback, never apply it ad hoc — route every item, however small it looks: the composer batches ALL feedback items and relays the batch to the phase's executor (backend-correct resume syntax: `--resume <session-id>` is claude-only, a codex executor resumes via `codex exec resume <session-id>`; a live-session executor receives it in-session; an executor that cannot be re-engaged is replaced by a fresh executor spawned from the plan handoff note — plan state is on disk, so no context is lost). **The composer NEVER implements feedback fixes itself — relay is the whole duty** (user-reported: composers patched smoke feedback directly; positive routing alone did not hold). Recorded rationale, one sentence: a composer-authored fix bypasses the phase's review + peer gates, guesses without the executor's build context, drains the orchestration session's context on implementation output, and — on a deliberate billing split — burns the composer's pool for the executor's work. **Relay fidelity is BIDIRECTIONAL and mechanical:** in the executor→user direction the composer PRINTS the executor's handoff/assessment/MUST-PAUSE brief verbatim by reading the artifact into the chat via a tool call (the plan's handoff-note section, or the role's handoff brief file — the operator-brief artifact, loop step 1), never re-typing or compressing it from memory; a short TL;DR and a disposition menu may be ADDED around the text, never substituted for it (summarize-instead-of-relay drops operator-relevant detail — observed live: a 10-item per-item assessment with code refs reduced to dot points), and a long brief prints in full — length is the operator's information, never the composer's to trim. Role-binding, not exceptions: a live-session executor IS the executor role (the same session implementing is that role doing its job), and a user-confirmed usage-exhaustion takeover (option 3 in Usage-exhaustion recovery) REASSIGNS the executor role to the live session — both are role reassignments, not prohibition exceptions; `verify=composer` and the degraded-shell exact-commands mode stay out of scope — running named verification commands is not authoring fixes. The executor runs the batch through `/execute`'s Deferral Confirmation Gate, presented — for user-authored smoke feedback ONLY — as **one compact table**: every item with a recommended disposition (`Include in plan` for anything UI-touching or potentially multi-surface; `Fix now` — executor-implemented like every accepted disposition here — reserved for genuinely trivial single-site items, still design-doc-bound when UI-touching), then a single confirm with per-item overrides ("accept all recommendations, or override by number"). The batch table is an explicitly-scoped presentation variant: these items are the user's own requests given moments earlier, not agent-discovered risks, so one-at-a-time prompting is fatigue without safety value — the canonical one-at-a-time gate shape is unchanged everywhere else. `Include in plan` items append 🟥 task(s) to the plan, each carrying a user-smoke provenance note (which pause, verbatim ask), and the whole batch then gets ONE scoped `/review-plan` per `/execute`'s `Include in plan` handler and `/review-plan`'s **Scoped mode** (the canonical definitions — not restated here); that scoped pass consults the design doc for UI-touching task(s) and enumerates sibling surfaces app-wide (feedback names an INSTANCE of a pattern; the Coverage lens finds every surface the pattern touches — the observed failure mode is making the named column sortable and missing the rest). The executor then implements via `/execute` and the user re-smokes — the multi-cycle shape above. Headless seam: the gate items follow the headless auto-disposition contract, and a clarification the executor cannot answer records-and-ends per MUST-PAUSE surfacing (both in Safety gates).
7. **Document** — the **composer** runs `/document` (interactively, so its confirm gates — lessons distillation, the bloat guard, plan sync — work), explicitly naming the governing plan. This is deliberately composer-run, not executor-run: the executor's plan/handoff updates have already landed on disk by this step, and `/document` is git-diff-driven, so the composer loses no needed context. Under `isolation=worktree` the composer runs it against the WORKTREE checkout — the phase's code and the authoritative plan copy live there (see **Run isolation (worktree-per-run)**). The run-end interactive `/document` (see Termination) owns the final lessons + bloat-guard pass. **`PROGRESS` line (CHAT-ONLY):** after this phase's close (after step 8's commit record; STICKY's PHASE-CLOSE item 7) post ONE chat line `[<runkey>] Progress: phases <done-range> done · phase <n> in progress · <remaining-range> remaining · <NN>%` — the DENOMINATOR from the isolation journal's `phases=` range (flat `branch`/`none` runs: the plan's phase headings), done/in-progress from the plan's task checkboxes (a done phase is done — Run isolation → **Release groups**; the first phase not done is in progress), the percentage from the plan's `Overall Progress`. No desktop notice (no NOTIFY class exists for it and every notice needs its paired record), no probe-log line (narration never enters the journal — the closed family); `/retro` names it as not log-derivable.
8. **Commit (default ON)** — unless auto-commit was opted out at the wizard, the COMPOSER commits only this phase's files per **Auto-commit**: commits are composer-seat-only with the seat-attributed `OWNERSHIP: commit … hash=<commit hash> seat=composer` record, and on a UI-bearing/runnable phase the commit is REFUSED until the phase's `OWNERSHIP: smoke-pass` record exists (step 6's pause closed with the user's PASS). If opted out, leave the changes staged-for-review and note it. Never push (the `/close-run` carve-out in **Run isolation (worktree-per-run)** aside).
9. **Discard + advance** — discard the executor. If more phases of the current release group remain (Run isolation → **Release groups**; a plan with no tag is one group) AND scope allows auto-advance AND no stop condition fired: run the usage checkpoint (probe the CLI pools in use and report the warn-only line — see Visibility + run-state; never pause on the numbers), update the run-state note (see Visibility + run-state), then return to step 1 with a fresh executor for the next phase. When none remain, Termination decides: a LATER group with a phase not done → **Group end** (the group close, then the next group's first phase from step 1 under the same `scope=all`); none → Group done. **`[pending-hardening]` gate:** a task carrying the `[pending-hardening]` marker (an auto-appended Include-in-plan recording — Safety gates' composer-seat policy) is NOT spawnable work — the phase advance REFUSES to hand a marked task to any executor; the ONLY remover is a successful scoped `/review-plan` over the marked task(s), which the composer may run at this boundary (a failed or aborted hardening leaves the marker in place, and `/execute`'s own task selection refuses the marker independently).

## Phase detection + bounded discretion

- **Unit = a phase** (a plan-defined task group). If the plan groups tasks into phases, use those. If the plan is a flat task list, the composer groups **contiguous low-risk tasks** into a phase and **isolates** foundational, security, schema, or shared-invariant tasks into their own early phase.
- **Plan-time grouping decides where reviews happen** — the premium planner made that risk judgment with full context, so it is auditable and deterministic.
- **Run-time discretion is add-only:** on a surprise (a phase turns out riskier than planned), the composer MAY checkpoint EARLIER — split a phase, review sooner — but MUST NEVER skip a planned checkpoint or merge a foundational task into a batch to avoid a review.
- **Release groups:** a split phase inherits its source heading's release-group tag, and no phase is moved across a tag (Run isolation → **Release groups**).
