    **The composer runner (the ONE statement — v46.0: `scripts/loop-run-bounded.py`, on every host; in v45.0 and v45.1 it was the helper's `run-bounded` subcommand, which the helper now refuses — exit 2, a `REFUSE:` line naming the script, nothing run; v46.1: the runner itself refuses under a spawned role's environment — The runner's permission, below).** Every router call the COMPOSER makes — or the session running `/close-run`, for the release — Step 0's `--version` and `status --json`, (a)–(d) above, the re-pick and the manual switch (Usage-exhaustion recovery), the release (Mechanical close enforcement), the rehearsal legs — runs under the bounded runner. Nothing is resolved for it: it is a committed script — a thin entry that loads the records helper beside it (`scripts/loop-journal.py`) and calls the helper's one runner implementation — under the `python3` every run already requires, so no host lacks a runner and no router call is ever made bare (a finite tool wait is not evidence that a process stopped); the scripts' own picks are NOT composer calls — the wrapper's one-shot and the launcher's function run through the helper's collector, which owns its own bound. The published recipe — ONE line, the same on Linux, macOS, WSL, and a Windows-native host:

    ```bash
    python3 scripts/loop-run-bounded.py --timeout 20 --kill-after 2 -- <cmd> [args…]
    ```

    The runner runs `<cmd>` in its own process group (a Job Object on Windows) and stops the WHOLE group at the deadline, by the host's means: on POSIX, SIGTERM to the group, then SIGKILL after the `--kill-after` grace; on Windows there is NO graceful stop — the Job is terminated at once (no signal reaches the command), so the grace is not a cleanup window there and a command gets no chance to finish a write. After the command exits, on every exit path, it sweeps any member its census still finds. Both streams are captured to FILES, so a descendant holding a stream open cannot stall the composer. That no descendant survives the call holds only when the stop and the census SUCCEEDED: a stop, kill, or sweep the host refused, or a census that could not answer, turns the exit into `125` with the cause named on stderr (`… survivors may remain`; `census failed — survivors unknown …`) — `125` beside such a line is never proof that every descendant stopped — and on Windows a grandchild started in the instant before the command is assigned to its Job escapes both the census and the kill (the documented residual: `docs/integrations/cross-agent-orchestration.md` → Host setup → A Windows-native loop host). The captured streams are REPLAYED after the exit — the command's stdout on stdout (`status` is read whole from it), its stderr on stderr, then the runner's ONE summary line LAST on stderr (`run-bounded: exit=<n> elapsed=<s> timed_out=yes|no killed=yes|no`). The DISPOSITION is read from the EXIT CODE alone — never from the summary line (a command can print a look-alike in its own output) and never from the replayed text alone: `0` success; `124` the deadline and `137` the kill after the grace, both `timeout`; `125` the runner's own failure (its cause is the stderr line before the summary — a cleanup or census failure among them, after which the group may have outlived the call; or, with NO summary line and nothing run, the ONE `loop-run-bounded:` line naming a `scripts/loop-journal.py` beside the script that is missing, does not load, or lacks a function the script calls — an install where only one of the two files was updated), `126` a command that could not be invoked, and `127` a command not found; any other value the command's own exit status — each of those the call's own failure unless its row below reads the value. Under `set -e` the status is saved on the call's own line (`rc=0; <the recipe> || rc=$?`). A mistake in the recipe's own arguments is the runner's `REFUSE:` (exit 2, nothing run); the runner requires neither `--run` nor `--role` (both are accepted, and validated, when given) and writes no record. An environment assignment a call carries rides BEHIND the `--`, through `env` — `python3 scripts/loop-run-bounded.py --timeout 20 --kill-after 2 -- env CODEX_HOME=<dir> codex login status` — never in front of the runner (a leading assignment keeps a permission allow rule from matching the call, so the call would prompt with the runner's line present; the command still inherits the rest of the runner's environment). The disposition per call — the COMPLETE inventory: (1) `--version` (Step 0's detection, Q1's reuse revalidation, (a)'s resume re-resolution) → not detected / UNAVAILABLE; (2) `status --json` (Step 0's line, (c)'s and (g)'s candidate list, (d), the rehearsal reads) → read whole; a timeout ⇒ the line says `status did not answer` and (c) and (g)'s candidate half are skipped with that line (the fallbacks are still checked); (3) `pick --failed=…` — the automatic re-pick → no answer, the last-resort tier; the manual Switch account → noted, the switch proceeds (both Usage-exhaustion recovery); (4) `release` (Mechanical close enforcement) → one reported line; (5) `claude auth status` / `codex login status` as the re-pick's positive verify (Usage-exhaustion recovery) → not verified — no answer; (6) `-- env CODEX_HOME=<empty temp dir> codex login status` as (b) → the check FAILS (a timeout is not a logged-out answer) → codex rounds unrouted; (7) (c)'s `diff -q` per file and `diff -qr` for `agents/` → `1` a difference, `0` equality, anything else — a timeout, an unreadable or blocking object — `could not compare <path> for <candidate>`, the advisory continuing; (8) the transcript copy of the Switch-account transaction (Usage-exhaustion recovery) — not a new call, named for completeness: under `router=on` it runs under the same recipe with `--timeout 60 --kill-after 5`; a timeout or a partial copy FAILS the transaction BEFORE any resume — the failed-switch disposition, the three-option pause, the partial copy left for the operator, nothing resumed on it (a quiet file after a kill is not equality; a partial copy is not a transfer). Ordinary peer rounds keep their unbounded wait — the liveness watchdog is their bound; nothing here applies to them.

    ```bash
    python3 -c '
    import copy, errno, json, os, stat, sys, tempfile
    path, rule = sys.argv[1], sys.argv[2]
    folder = os.path.dirname(path)
    MISSING = object()
    state = {"stage": "checking the settings file", "tmp": None, "replaced": False}
    def stop(why):
        head = "written but not verified" if state["replaced"] else "not written"
        sys.stderr.write("runner-permission: %s: %s\n" % (head, why))
        sys.exit(3)
    def one_key_each(pairs):
        obj = dict(pairs)
        if len(obj) != len(pairs):
            stop("the settings file repeats a key")
        return obj
    def load():
        try:
            fd = os.open(path, os.O_RDONLY | NOFOLLOW | NONBLOCK)
        except FileNotFoundError:
            return MISSING, None
        except OSError:
            stop("the settings file is a link or cannot be opened")
        st = os.fstat(fd)
        if not stat.S_ISREG(st.st_mode) or st.st_nlink != 1:
            os.close(fd)
            stop("the settings file is not a regular file with one name")
        with os.fdopen(fd, "rb") as fh:
            raw = fh.read()
        try:
            return json.loads(raw.decode("utf-8"), object_pairs_hook=one_key_each), st
        except ValueError:
            stop("the settings file is not valid JSON")
    def main():
        try:
            if not stat.S_ISDIR(os.lstat(folder).st_mode):
                stop("the settings folder is a link or not a directory")
        except FileNotFoundError:
            stop("the settings folder does not exist")
        before, st = load()
        data = {} if before is MISSING else copy.deepcopy(before)
        if not isinstance(data, dict):
            stop("the settings file is not a JSON object")
        perms = data.setdefault("permissions", {})
        if not isinstance(perms, dict):
            stop("permissions is not an object")
        allow = perms.setdefault("allow", [])
        if not isinstance(allow, list):
            stop("permissions.allow is not an array")
        if rule in allow:
            print("runner-permission: already present")
            return
        allow.append(rule)
        try:
            payload = (json.dumps(data, indent=2, ensure_ascii=False, allow_nan=False) + "\n").encode("utf-8")
        except (ValueError, RecursionError):
            stop("the settings file holds a value that cannot be written back as UTF-8 JSON")
        state["stage"] = "writing a temporary file beside the settings file"
        fd, state["tmp"] = tempfile.mkstemp(dir=folder, prefix=".settings.local.", suffix=".tmp")
        with os.fdopen(fd, "wb") as fh:
            fh.write(payload)
        if st is not None:
            os.chmod(state["tmp"], stat.S_IMODE(st.st_mode))
        os.replace(state["tmp"], path)
        state["tmp"] = None
        state["replaced"] = True
        state["stage"] = "reading the settings file back"
        after, _ = load()
        if after is MISSING or after != data or after["permissions"]["allow"].count(rule) != 1:
            stop("the settings file was replaced and its content is not what was written; look at it")
        print("runner-permission: added")
    NOFOLLOW = getattr(os, "O_NOFOLLOW", None)
    NONBLOCK = getattr(os, "O_NONBLOCK", None)
    if NOFOLLOW is None or NONBLOCK is None:
        stop("this host cannot open a file without following a link; add the line by hand")
    try:
        main()
    except Exception as e:
        left = ""
        if state["tmp"] is not None:
            try:
                os.unlink(state["tmp"])
            except OSError:
                left = "; a temporary file may remain: %s" % os.path.basename(state["tmp"])
        what = errno.errorcode.get(e.errno, "an operation") if isinstance(e, OSError) else type(e).__name__

    ' '<M>/.claude/settings.local.json' 'Bash(python3 scripts/loop-run-bounded.py:*)'
    ```

    The add command's contract — the records-helper selftest extracts the block from this text and runs it on fixtures. *Where it runs:* a host whose Python has no `O_NOFOLLOW` or no `O_NONBLOCK` (Windows) gets ONE refusal for every call — `runner-permission: not written: this host cannot open a file without following a link; add the line by hand`, exit 3, nothing read or written; a missing flag is never treated as zero. *The destination is the file it is named as:* the parent, `<M>/.claude`, exists and is a real directory (not a link); the file is opened without following a link and without blocking, and the open descriptor is checked BEFORE anything is read from it — a regular file with exactly ONE link. A symbolic link (dangling included), a file with a second name (a hard link), a FIFO, or a directory at that path each end promptly with `runner-permission: not written: <reason>` on stderr and exit 3. Only a path that does not exist counts as an empty object — an existing file whose content is the JSON value `null` is an existing non-object and is refused. *The shape:* the content is UTF-8 and parses as a JSON object in which no object repeats a key; `permissions` is absent or an object; `permissions.allow` is absent or an array; otherwise exit 3, nothing written. *The change:* when the array already holds the exact string, it prints `runner-permission: already present` and exits 0 with nothing written. Otherwise the one string is appended (the keys created when absent) and the whole object is serialised — two-space indentation, non-ASCII text kept as it is — and encoded to UTF-8 bytes BEFORE any temporary file is created: a value that cannot be written back (a JSON-escaped lone surrogate in any string; a number JSON cannot hold, `NaN` or an overflowing float) is refused with `not written`, never altered or dropped. The bytes go to a new temporary file in the same directory, with the old file's mode, which is then renamed over the path — a replacement, never an in-place write. Key order and every other value are preserved. *Its own read-back:* after the rename it re-reads the path the same way and requires that the parsed object equal the parsed original with exactly the one element appended, and that the string occur exactly once in `permissions.allow`; only then does it print `runner-permission: added` and exit 0. *Two failure lines, and nothing else:* every failure — a refused state, a filesystem error, any other exception the program raises, at any step — ends with exit 3 and ONE stderr line, never a traceback. Before the rename the line is `runner-permission: not written: <reason>`: the settings file is untouched and the command's own temporary file is removed (when it cannot be removed, the line says a temporary file may remain and names it). After the rename the line is `runner-permission: written but not verified: <reason>`: the file was replaced, the read-back failed or did not match, and the command writes nothing further. *No recovery write, ever:* no restore and no delete of the settings file, at any point — after `written but not verified` the operator, who is present, looks at the file and repairs it; the composer does not. *What it cannot promise:* the checks and the rename are not one atomic step, so a file swapped in between by another process is replaced by the new content. (4) `git -C '<M>' status --porcelain -- .claude/settings.local.json` prints nothing — output there is reported as it stands, and the composer does nothing more to the file. (5) ONE line, from the command's own: after `added`, `Runner permission: added to <file> — delete that line to withdraw it`; after `already present`, `Runner permission: present (<file>)` — a success, nothing written; after `not written`, the advisory line with the command's reason; after `written but not verified`, `Runner permission: <file> was replaced but could not be verified — <reason>; look at it before the next run`, and the composer does nothing more to the file. A command the host declines to run (its own prompt answered no, a sandbox, `dontAsk`) is `skip`. Nothing is written anywhere else — no record, no `Loop config:` key, no plan line, no other settings file — and nothing at all under a bound grant, to a tracked or a user-level file, or from a session whose checkout is not `M`. This is the settings write the Setup-remediation classification (below) requires a confirm for; the one question is that confirm. **What the read cannot see** — files only: allow rules merge across more sources than these, a `deny` or an `ask` rule anywhere wins, and a launch flag, the permission mode, a managed policy and an in-session approval are in no file it reads, so a miss does not prove a prompt and a hit does not prove none. **What the runner's own refusal is (stated here ONCE — the question above, the installer's sub-note and the orchestration doc point here).** With a non-empty `LOOP_ROLE` in its environment — the spawn wrapper requires the variable on every spawn and passes its whole environment to the role — the runner writes ONE stderr line, `REFUSE: loop-run-bounded is the composer's runner — LOOP_ROLE is set in this environment, which marks a spawned role's shell; nothing was run`, and exits 2, before it loads the helper or reads an argument (an empty `LOOP_ROLE` is unset; `--role` on the command line is not consulted; a composer whose own shell carries the variable is refused the same way and unsets it). It exists because the local settings file is not the composer's alone: on Claude Code from 2.1.211, off Windows, a Claude Code session started in the checkout or any worktree reads the main checkout's `.claude/settings.local.json`; from v46.3 a role this loop spawns does not (step 16), and the refusal stays for a runner line a role holds some other way — the profile's settings, a committed settings file, a loop older than v46.3. The refusal is a guard against ACCIDENTAL use, and it holds only while the role's inherited environment is intact. It is NOT a boundary, and these are the ways it fails: a role that clears `LOOP_ROLE` in front of the command runs the runner — one assignment statement, no file edited, nothing in a diff; a role runs its own worktree copy of the script and may edit it — visible in the phase diff, prevented by nothing; a role holding a broad interpreter grant or `perms=bypass` needs no runner; a Cursor subagent or a live-session leg shares the composer's own permission context and environment. From v46.3 a spawn the loop makes reads no local settings file (step 16); that is not a promise that a role cannot reach the runner — the limits above and step 16's stand. Add or keep the line only on a host where every Claude Code session started by hand in the checkout or its worktrees may run a command through the runner unasked, and keep it out of the profile's settings and out of any committed settings file, which a spawned role still reads.

16. **Role settings shield (appended step — steps 1–15 keep their numbers; THE ONE statement of what a spawned `claude -p` role reads).** **The statement.** Every `claude -p` role this loop spawns is started with `--setting-sources user,project`: the spawn wrapper renders the two arguments on every spawn and every resume, on both tiers, from a constant that no `LOOP_*` variable, file, plan text or `Loop config:` key reads, changes or removes (Backends → Spawn wrapper); a command line a session builds by hand from a published example — the Backends invocation line (the inline fallback), `/peer-loop`'s standalone peer — carries them because the example does. Started that way, a role reads no local settings file — neither the main checkout's untracked `.claude/settings.local.json` (the file a Claude Code session in any worktree of the repo reads from 2.1.211, off Windows) nor its own checkout's — so it loads nothing from such a file: no `allow`, `deny` or `ask` rule, no `env` value, no hook, no `permissions.additionalDirectories` entry. A native subagent started inside a shielded role is shielded with it, and a session started without the flag is shielded from the resume that carries it. The exclusion is Claude Code's act on the flag, observed at 2.1.322 (`docs/integrations/cross-agent-orchestration.md` → What a spawned `claude -p` role reads); the version line below says when it may be incomplete. What still reaches a role: the profile's user settings, the checkout's committed `.claude/settings.json`, managed settings, and the spawn's own flags (`--allowedTools`, `--add-dir`). **What the shield is not.** It is no promise that a role cannot reach the bounded runner or the full records helper: on a run that grants a broad interpreter shape such as `Bash(python3:*)`, or runs `perms=bypass`, no grant boundary exists for either; a rule in the profile's user settings or in a committed `.claude/settings.json` still reaches every role, and the runner's own refusal (step 15 → The runner's permission) stays as the defence for a runner line placed there — a guard against accidental use, with the limits stated there; a Claude Code session started by hand in the checkout or a worktree, and a loop older than v46.3, still read the local file. Nor does it clean the environment a role inherits: the wrapper passes its whole environment to the role, so a variable the spawning session already holds — one a Claude Code composer's own session took from that file's `env` map included — still reaches the role that way; the `env` keys the line below names are the ones a role no longer loads from the file. And it hides no file: a role can still open a local settings file as a file wherever its tools and grants reach it (a shape such as `Bash(grep:*)` reads any path), so a secret written there is not kept from a role. **Roles it does not apply to:** a Cursor-subagent executor and a live-session leg run in the composer's own session and read what it reads; a `codex` role reads no Claude Code settings at all. **When it runs** — ONCE per preflight, a dry-run included, on every composer host, when at least one role of the run uses the `claude -p` backend; not on a resume. It asks nothing, writes nothing, calls no helper and no runner, and emits no record; a bound away grant changes nothing about it. **Where in the order** — the read and the lines come BEFORE the first shielded spawn of the preflight: step 6 invokes them ahead of its `claude -p` harness probe (the run checkout of step 2b and step 5's version check are done by then), and at this numbered place the step prints only if it has not printed in this preflight — a dry-run, or a run whose only `claude -p` role is a peer, makes no `claude -p` harness spawn at step 6. **The read** — `M/.claude/settings.local.json`, where `M` is the main checkout as step 15 → The runner's permission → The read defines it (the definition only — none of that paragraph's conditions apply here; not read when `M` is unknown), and the run checkout's own `.claude/settings.local.json` when the run checkout is not `M`. Each is read whole with the host's file-read tool. A missing file is skipped. A file that is not a JSON object — a zero-byte file included — prints `Role settings shield: could not read <file>`, counts as holding none of the five kinds, and the step continues. The five kinds: `permissions.deny` rules, `permissions.ask` rules, `env` keys, `hooks` event names, and `permissions.additionalDirectories` entries. **The line** — exactly one of two forms, printed after the read: `Role settings shield: on — spawned claude -p roles read no local settings file` when neither file holds any of the five kinds; otherwise, once per file that holds any, `Role settings shield: on — roles no longer get from <file>: <kinds>`, where `<kinds>` lists only the kinds present, in this order — `deny <n> (<each rule, verbatim>)`, `ask <n> (<each rule, verbatim>)`, `env <each KEY>`, `hooks <each event name>`, `additionalDirectories <n>` — followed by one sentence: `Move what a role must keep to the committed .claude/settings.json or the profile's settings; a read root rides --add-dir (step 2).` An `env` VALUE is never printed, in this line or anywhere in the step. **The version line** — when the version string step 5's version check printed for the role's pinned `claude` binary is below 2.1.314, one more line: `Role settings shield: Claude Code <version> is older than 2.1.314 — an excluded settings file may still supply some settings; update the CLI`; when step 5 printed none for that binary, or it does not parse as three dotted numbers: `Role settings shield: Claude Code version unknown — the shield is complete from 2.1.314`. The step runs no command of its own for this. Never a stop.

17. **Composer identity and the watcher (appended step — steps 1–16 keep their numbers; THE ONE statement of the identity write, of the `watcher:` line, and of the watcher script's permission — the Resume contract, the pre-departure check, and the companion card point here).** Once sub-step 2b has written the run's marker or journal, and again at every Resume whose `seat` read does not say `mark=yes` (the Resume contract reads the seat line FIRST: a mark that stands is the operator's stop, and this write would lift it — **Away mode** → the wake rule), the composer runs — from its own shell, never through a role, and not on a dry-run —

    ```bash
    python3 scripts/loop-watchdog.py identity --base "<abs base>" --iso <iso-id> [--nudge-tag <tag> --nudge-grant <n>] [--state-dir "<abs dir>"]
    ```

    (`--state-dir` only finds the watcher's heartbeat: it is passed exactly when the operator started `watch` with one — without it such a watcher reads `not running` — and is omitted otherwise.)

    **What it writes.** The run's composer identity record, `<base>/.cursor/loops/<iso-id>-composer` — ten `key=value` lines, `session pid pid_start entrypoint exec config_dir cwd host nudge ts`, read from the session's own environment — and, the first time, the run's two seat files beside it, `<iso-id>-seat` and `<iso-id>-seat.gate` (**Away mode** → The watcher and the seat), created only on a host with file locks, on a filesystem that takes them, and for a run whose log folder is `<base>/.cursor/loops/<iso-id>`. The two nudge flags travel together and are passed exactly while a nudge timer is armed (**Away mode** → The nudge); without them the record reads `nudge=none`.

    **What it prints** — two lines, shown to the operator as they are:
    - `identity: iso=<iso-id> host=<claude-code|unknown> session=<first 8 characters|none> pid=<n|none> entrypoint=<value|unknown> nudge=<tag>:<grant>|none seat=<created|present|none(host)|none(log-root)|none(no-locks)> mark=<none|stands|cleared|clear-failed>`. `host=unknown` — the host exposes no session id, or no process id for the session — means no watcher takeover is ever offered for this run; so does every `seat=none(…)`: a host without file locks (every Windows host), a run whose journal names another `log_root=`, a run with no journal — a run with no run worktree, which the watcher does not judge — or with one that does not establish its log folder: it cannot be read, it is empty or cut short ahead of its `state=`, or its `log_root=` is there and cannot be used — empty, unsafe, or not an absolute path (all three `none(log-root)`), a filesystem that takes no lock.
    - ONE `watcher: …` line — the read of the watcher's heartbeat for this base, in one of six wordings: `watcher: heartbeat fresh (<n> s) — watching this base`; `watcher: not running (no heartbeat in <dir>) — start it outside any agent session: <the start command>`; `watcher: heartbeat stale (<n> s) — start it outside any agent session: <the start command>`; `watcher: restart the watcher — it runs a script that differs from the installed one …` (printed only when the installed script's hash differs from the one in the heartbeat — after an update that changed the watcher script; the heartbeat carries ONE hash, of the script the watcher was started from, so a watcher over two bases whose installed scripts differ prints it for the other base whatever is restarted — bring that base to the same version); `watcher: running, but it does not watch this base — restart it with --base <base> as well`; `watcher: running, but its last tick on this base FAILED (<word>) — …` (the word is `exit-<n>`, `signal-<n>`, `timeout`, `not-started` or `no-script`). "Fresh" says the watch process wrote its heartbeat lately and the last tick it ran for this base ended 0, or it has run none yet — never that a run was judged rightly. The line is ADVISORY: no wording of it stops Preflight or a Resume, and the composer NEVER starts the watcher itself — `watch` and `tick --act` refuse inside an agent session, where a watcher would die with the session's process tree; the operator starts it, as a user service or from a terminal.

    **The exit code is read, three ways.** Exit 2 — a refused argument, or a refused write: under a held seat the refusal names the holder (`seat-held`) — a watcher takeover is this run's composer right now, so this session writes NOTHING for the run, says so, and goes on only after the operator's stop (**Away mode** → Stopping an away run). Exit 3 with NO `identity:` line — the record was NOT written and nothing changed: the record that stood, and a no-takeover mark if there is one, stand as they were; say so and run the command again. Exit 3 AFTER an `identity:` line that reads `mark=clear-failed` — the record IS written, and the no-takeover mark could not be removed: takeover stays off for this run until the mark is removed or the command is run again; the identity write itself is complete (whether the run goes on is the stop's wake rule, below). `mark=cleared` is the ordinary line of the first identity write after an operator's stop: an interactive composer's write — one made with no `LOOP_SEAT` in its environment — is the ONE thing that lifts the mark; a takeover's own write never does. At a Resume, `mark=cleared` and `mark=clear-failed` are also the cue of the stop's wake rule (**Away mode** → Stopping an away run): the operator stopped this run, and nothing is resumed or spawned before their word.

    **What the record is for, and its limit.** The watcher reads it to tell whether this run's composer process is gone, and trusts none of it unchecked. The shipped `SessionStart` hook does not refresh it — that hook still writes nothing — so after an app restart the record can name a dead process beside an open window until this step runs again: any session that returns to a run takes the Resume contract FIRST. A run with no identity record — one started before v48.0 — is notified about and never taken over.

    **The watcher script's permission (a Claude Code composer only — the runner's rule of step 15, by pointer, with this script's line).** The script is the composer's and the operator's tool: it is on NO role's grant list, and every subcommand refuses under a role's environment (`LOOP_ROLE` set: one stderr line, exit 2, nothing done — a guard against accidental use, not a boundary, exactly as the runner's is). Its permission line is `Bash(python3 scripts/loop-watchdog.py:*)`. Before this step's first call a Claude Code composer makes step 15's read — the same three files, the same hit rule with this line (and `Bash(python3 scripts/loop-watchdog.py *)`) in the runner's place — and prints `Watcher permission: present (<file>)` or `Watcher permission: not found in <the files read>`. On a miss the offer is step 15's, under every one of its conditions (the main checkout known and equal to the session's checkout, not the home directory, no away grant bound, not yet asked in this session): ONE `add | skip` question, whose text states the line, the file's absolute path, that the line pre-approves EVERY subcommand of the script — `stop` among them, which ends a takeover and stops the run's roles — that every Claude Code session started in this checkout or its worktrees reads the file while a role this loop spawns does not (step 16), that the script's refusal of a spawned role stops accidental use only, and that deleting the line withdraws it. On `add`, the write is step 15's two git checks and its add command exactly as published, with `'Bash(python3 scripts/loop-watchdog.py:*)'` as the command's second argument (the program's own lines keep their `runner-permission:` prefix — it is the same program); otherwise ONE advisory line, `Watcher permission: not added — to allow the watcher script, add "Bash(python3 scripts/loop-watchdog.py:*)" to permissions.allow in <M>/.claude/settings.local.json`. Without the line a composer is asked at each call; a wake with nobody present then stalls on the prompt, which is why the pre-departure check reads it again (**Away mode** → check item 4).
