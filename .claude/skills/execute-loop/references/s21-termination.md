## Termination

Stop and report when any of these holds:
- **Group end (the group close; stated ONCE, here; not a stop — the run continues).** No phases of the current release group remain — each a done phase (Run isolation → **Release groups**) — while a LATER group holds a phase not done. The composer PERFORMS the group close itself, never offers it (STICKY §2 duty 3), in this order: `/retro` scoped to the group's stages (its Step 0 group scope — the report named by the group's last stage, so each group has its own report and the group's pull-request body cites it); the interactive `/document` pass (per loop step 7 — the plan stays Active: no completion handoff, which is Group done's on the final group only); the final commit when `autocommit=on`; **Coordinating with other runs**; then `/close-run --iso <iso-id> --group stage-<N>` (`<N>` the group's LAST stage — the identity every record, journal key, probe log, and retro file of the group already carries) on its group route — the records commit, the push (a remote branch the host auto-deleted after an earlier group's merge is recreated by it), the group's ONE pull request (its title carrying the group tag), then under a bound grant the checks wait and the merge under Release work items 2–3 above and `/close-run` → **Under an away grant** items 3–10 as written (item 9 parks before any merge on a repository that allows no merge commit; item 11's fix cycle is per group close) — or, attended, the wait for the operator's merge click (`/close-run` Flow 1 step 4's named pause point) — then the helper's `run-close --run stage-<N> --outcome group-merged --merge-commit <sha>` (Run isolation → Mechanical close enforcement, which states every refusal): it binds the merge commit — in the fetched base, on the base branch's first-parent chain, exactly two parents, `<sha>^2` the run-branch tip — writes `merged_stage_<N>` and its `cell=group-merge` record, then its fast-forward leg moves the base checkout AND the worktree to the one fetched sha of `origin/<base-branch>` and writes `ff_stage_<N>` with its `cell=group-ff` record (Release groups states the provenance those keys give) — under a bound grant with `merge` in scope the call carries `--grant <n> --away-check <config_hash>` from the use-time `away check` line (`/close-run` Step 7's group form), and the leg writes the `rebaselined` re-baseline into `<log-root>/stage-<N>-probe.log` BEFORE `ff_stage_<N>` and prints `group-ff: rebaselined at <log>:<line>` on stderr, which the composer reads and quotes in the group's summary (Mechanical close enforcement → The re-baseline; **Away mode** → Records → A re-baseline); the journal stays `active` and nothing is torn down. A `group-ff` refusal (`detail=base-not-fast-forwardable`, or from v46.4 `detail=checkout-not-ready` or `detail=fetch-failed` — Mechanical close enforcement names what each covers) is a park — the must-pause pair for key class `merge` with `reason=` carrying the refusal's own `detail=` word (`reason=base-not-fast-forwardable`, as before, when that is the word), its notice naming the side and git's words — never a rebase, reset, or switch; the replayed helper call runs that leg alone once the operator has cleared it. A `merge-parent-mismatch` refusal (a squash, a rebase, a fast-forward hand merge, a tip passed as its own merge commit) parks the same way, its notice naming the route — merge with a merge commit. Then Release work items 4–6 for the scope (staging after the merge, production, a failure after the merge) as they apply to this group's merge; THEN the `[operator]` 🟩 write — each of this group's `[operator]` release acts that was taken — by the grant's release work, or by the operator's own merge click or hand merge (their word; the `group-merge` record is the evidence either way) — is marked 🟩 on the WORKTREE plan copy, the evidence named in the handoff note (the `group-merge` record for the merge; item 5's records for a dispatch) — AFTER the fast-forward, so the plan copy (the one file both sides touch) is clean when `--ff-only` runs, and never on the base copy (Release work item 7) — and its bookkeeping commit on the run branch by the composer at once (`autocommit=on`; the `OWNERSHIP: commit` record as for any commit), so the worktree is clean before the next spawn; then loop step 9's usage checkpoint and run-state note, and the next group's first phase's executor from loop step 1 — nothing asks whether to continue, and the grant, where one is bound, stays bound (**Away mode** → Ending the grant: `release-done` fires after the final close only). A park at any step keeps the grant bound and the run waits; the operator's clear, or a hand merge found at the next wake (`/close-run` Step 3's shipped-tip route per group, the sha read from the merged pull request's `mergeCommit`) resumes the close at its first incomplete step. Every step of this tail — the group record, the fast-forward, the release records, the 🟩 write and its commit, the spawn — is resumed by **the group tail's first-incomplete-step contract** (Run isolation → Pause / crash / resume), read from the journal's keys and the probe log's records, never from git state alone; a group's pull request found CLOSED without merging takes `/close-run` Step 3's disposition (a park — key class `merge`, `reason=pr-closed` — under a grant; the operator's word attended), never a silent re-open. A tagged plan under `merge=auto` never reaches this paragraph: Preflight step 1 refuses it.
- **Group done** (the Phases-done close; v36.0) — no phases of the current release group remain — each a done phase (Run isolation → **Release groups**; a plan with no tag is one group, so this is its last phase) — and the group is the plan's FINAL one (a later group holding a phase not done takes **Group end** above instead — v40.0); the composer PERFORMS the run-end duties itself, never offers them as menu options: it runs the completion handoff (the plan's completion-state decision pass via `/execute`) on the plan's FINAL group only — the current group is final when no LATER group holds a phase not done (later groups whose phases are all done count as done) — and only when no `[operator]` task is open in the plan: otherwise the run-end duties run as written, the plan stays Active, the handoff note lists the open tasks under Open blockers, and the operator completes the plan after the merge through `/execute` (its interactive branch marks each `[operator]` task 🟩 on their word — the grant's records the evidence for an act the release work took — and its completion pass follows; the plan template's Tasks legend) — so the COMPOSER's handoff, when it runs, lands before the final commit and the close, never after the merge; the operator's completion pass through `/execute` is the one post-merge completion, on their own hand (Release work item 7: the composer never edits the plan after the merge) — and a non-final group's close skips the handoff and the plan stays Active, because this same run builds the next group from it (Group end above — v40.0: one run per plan) — runs the final interactive `/document` pass (per loop step 7), and — when `autocommit=on` — makes the final commit. (that pass is the pre-merge one; the release wording that names the pull request, and — where the handoff left the plan Completed with no open `[operator]` task — the plan pair's archive move, are `/close-run`'s release stamp, inside the close and before the merge: its Flow 1 step 2a.) The only run-end action it RECOMMENDS is `/retro` (the run report: what happened, what it cost, what failed and why) — under `isolation=worktree`, pointed at the run's base-side log root `.cursor/loops/<iso-id>/` for logs and at the WORKTREE for the plan (see **Run isolation (worktree-per-run)**). The remaining user calls are `/close-run` (the close, run by the operator or by an agent acting on the operator's request: the records commit, ONE pull request or the `--no-pr` local close, the push that happens ONLY inside it under its confirm table — the `/close-run` carve-out in **Run isolation (worktree-per-run)** — and the helper's squash-verified `merged → cleaned` teardown) and any user-only environment verification legs — except under a bound away grant with `merge` in scope — see **Away mode** → Release work: the composer itself runs `/retro` before the completion handoff and `/close-run` after the green close.
- **Stalemate** — a phase's `/review-loop` or `/peer-loop` produced no new verified progress; stop and report rather than burn rounds.
- **Cap reached** — a composed loop hit its max-round cap. A cap has exactly THREE legal outcomes — RAISE, SURFACE-AND-ASK, or (under `cap-raise=follow` or `executor` ONLY) the RECORDED `cap-accept` closure — and NEVER a silent close: recording convergence, advancing the phase, or closing the pass at cap without one of the three is a contract violation, a flat or rising trajectory with no co-incident gate still SURFACES (it is never quietly closed), and accept-closure is legal ONLY as the explicitly recorded `cap-accept=close` transition below — an unrecorded close remains the violation in every mode (under `ask`/`auto-plus-one` the outcomes stay the pre-v32 two: RAISE or SURFACE-AND-ASK; r9 PR-MED-019). Under `cap-raise=ask` — and in every standalone loop — SURFACE-AND-ASK: report remaining findings and offer to raise the cap for one more round; the ask PAUSES INDEPENDENTLY — the run holds at the cap while the ask is open, whatever other gates are in flight. Under `cap-raise=auto-plus-one` (retained mode), the composer auto-raises the cap by EXACTLY +1 — ONCE per pass, act-and-inform (journal `OWNERSHIP: auto-disposition cap-raise=+1` + the notify-at-gate notification as ONE paired same-ts/key emission, `mode=immediate`) — ONLY when ALL of: every verified finding from the cap round is already applied (nothing pending), the trajectory is CONVERGING (severity-weighted finding count strictly declining round-over-round), and the reviewer/executor recommendation is continue; a second raise on the same pass, a flat or rising trajectory, or pending unapplied findings surfaces the cap-stop exactly as `ask` (the SURFACE-AND-ASK outcome) — genuine non-convergence belongs to the operator. Under **`cap-raise=follow`** (the v32.5 `Loop config:` DEFAULT, operator-set — D2; `cap-raise=` decides cap-stops INDEPENDENTLY of `gates=`, every key combination legal — exact for actual AT-CAP stops; the v32.3 pre-cap early tail accept-close at this bullet's tail is the ONE gates-sensitive exception, requiring BOTH validated keys): at every surfaced cap the composer FOLLOWS the residue-routing recommendation ALREADY computed by the rule below, act-and-inform — no new judgment is introduced, only the disposition of an already-computed recommendation flips from ask to act-and-inform: raise-recommended ⇒ raise by EXACTLY +1 (the `cap-raise=+1` pair above); accept-recommended ⇒ **`cap-accept`** — a NEW explicit recorded transition with a PINNED wire contract (PR-MED-014): journal `OWNERSHIP: auto-disposition cap-accept=close` + its paired `NOTIFY: … class=cap-accept mode=immediate` as ONE paired same-ts/key emission (both admitted writer/oracle shapes, mirroring the `cap-raise=+1`/`class=cap-raise` binding). PRECEDENCE is a PINNED TOTAL ORDER, fail-closed, less-autonomous-wins on overlap (PR-MED-001/PR-MED-014): (1) pending unapplied findings ⇒ SURFACE; (2) stalemate ⇒ STOP (unchanged); (3) CRIT/HIGH regression ⇒ SURFACE; (4) tail-signature ⇒ SURFACE; (5) accept-close; (6) raise — a records-only residue that ALSO matches the tail signature resolves to (4) SURFACE, never (5). The tail-signature STOP (D2's hard bound — lessons.md "stop on the signal") = 2 consecutive docs-only or same-family-defensive-completion rounds (the EXISTING skew vocabulary — no new terms) with no CRIT/HIGH regression, evaluated by the composer from the last two rounds' finding classes — prose-defined here, a judgment duty by doctrine (D4), not a new tool. HARD BUDGET: at most +2 cumulative follow-raises per pass, then SURFACE. A missing, ambiguous, or conflicting recommendation ⇒ SURFACE (fail-closed). An absent or malformed `cap-raise=` key fails closed to `ask`. Residue routing (at any SURFACED cap offer, and the recommendation `follow` executes): recommend raising the cap one confirmation round when the final round's unconfirmed residue touches code or shipped prose at MED+, and accepting cap-closure when the residue is records-only plan-file bookkeeping — a release-end whole-diff hardening pass re-covers it (rule proven across three live cap gates). **Early tail-signature accept-close (STRICTLY PRE-CAP; not a cap event):** after each CLOSED peer round mid-pass with `round < cap` — `/execute-loop`-orchestrated COMPOSER-SEAT CODE-mode peer passes ONLY — when the last 2 consecutive closed rounds match THIS bullet's tail signature (reused verbatim, never redefined) with no verified finding pending unapplied and no CRIT/HIGH regression, the composer accept-closes the pass EARLY under BOTH policy keys VALIDATED from the plan's current `Loop config:` line as `gates=fix-biased` AND `cap-raise=follow` — act-and-inform with the SAME guardrails and record pair as the at-cap follow closure (`OWNERSHIP: auto-disposition … cap-accept=close` + paired `NOTIFY: … class=cap-accept mode=immediate`; existing admitted shapes, no new grammar). Under `ask`/`auto-plus-one`/`gates=strict` — and on ANY absent, malformed, conflicting, or stale read of either key — the branch fails closed to SURFACING the recommendation (so `gates=strict; cap-raise=follow`, the self-hosting restore combination, always surfaces; an implementation may never key on `cap-raise=` alone). At `round == cap` the branch is SKIPPED and this bullet's at-cap contract owns the outcome unchanged, per mode: on the eligible pass's validated `cap-raise=follow`, the tail signature at cap SURFACES via item (4) of follow's pinned order, never accept-closes (less-autonomous-wins at the boundary); `ask` surfaces-and-asks at cap, and `auto-plus-one` keeps its unchanged three-condition raise predicate above, decided independently of `gates=` — the tail veto is follow's item (4) only, never an added veto on the other modes. The operative round-close branch lives in `/peer-loop`'s termination check (one of v32.3's two precisely-scoped child edits — see Safety gates' composer-seat policy); executor-owned in-session `/review-loop` chains, PLAN-REVIEW-mode passes, executor-seat opt-in passes, and standalone `/peer-loop` are all ineligible and keep their existing contracts. **Under `cap-raise=executor` (the v33.0 wizard DEFAULT, operator-set — D2; `follow`'s predicate, +2 budget, precedence order, and bounds above are byte-untouched — `executor` is a MODE beside them, never a fourth outcome):** every LEG-1 verify brief (loop step 4) REQUIRES a **`Cap verdict:`** line on the round's verified-tuple block — `raise <+n> | accept | defer-residue` + materiality (`production-behavioral | test-harness | docs-only`) + one-line evidence. At cap the composer runs `follow`'s PINNED TOTAL ORDER above with exactly TWO differences: the recommendation input is the executor's verdict (never composer-computed residue routing), and item (4) — the tail signature — is DECIDED BY THE VERDICT (accept ⇒ `cap-accept=close`; raise ⇒ raise) instead of SURFACING; items (1) pending unapplied findings ⇒ SURFACE, (2) stalemate ⇒ STOP, (3) CRIT/HIGH regression ⇒ SURFACE, and (5)/(6) accept-close / raise are unchanged. A `raise` verdict is executed as exactly ONE `OWNERSHIP: auto-disposition … key=<cap key> cap-raise=+1 pass=<p> cap=<N+1>` record with its paired `NOTIFY: … class=cap-raise` per cap event (`+1` remains the only legal raise token — one cap event, one delivery identity); a verdict of `raise +n` with n > 1 is honoured ONE increment per cap event, the next cap event re-consulting the (possibly refreshed) verdict, within an EXECUTOR-MODE per-pass raise budget of **+3 cumulative** — after which `peer-max` (the executor-scoped `Loop config:` key; wizard default 12; absent → the +3 budget alone) SURFACES ONCE per pass with the verdict attached, and the operator's disposition may lift it for this pass. `defer-residue` ⇒ `… cap-accept=close pass=<p> residue=deferred` (the same `cap-accept` wire shape and `class=cap-accept` pairing) + the residue recorded as a Deferred item with `Risk if deferred:`. A missing, ambiguous, or conflicting verdict ⇒ SURFACE (fail-closed). The v32.3 pre-cap early tail accept-close branch above is NOT EVALUATED under `cap-raise=executor` — it neither closes nor surfaces (its eligibility predicate names `gates=fix-biased` + `cap-raise=follow` only, and its fail-closed-to-SURFACE clause is for a malformed or conflicting read of THOSE modes, never a pre-cap ask generator for executor mode): a mid-pass tail signature simply continues to the next round, and the verdict decides at cap. The mode-general "a flat or rising trajectory … still SURFACES" sentence at the head of this row is the no-silent-close rule (a cap-stop always reaches the composer seat as a cap EVENT, never quietly closed — the same reading `follow`'s "at every surfaced cap" already gives it); under `cap-raise=executor` that event is DISPOSED by the verdict through the order above — the trajectory is neither a veto nor an ask: a flat or rising trajectory with `raise` recommended raises (+1, within budget), with `accept` recommended accept-closes, and only items (1)–(3), the +3 budget / `peer-max` ceiling, and a missing/ambiguous/conflicting verdict surface an ask. `peer-max` and the +3 budget are executor-scoped and invisible under `follow`/`ask`/`auto-plus-one`; every cap transition of a peer pass carries the D3 `pass=`+`cap=` bundle (loop step 4), and a raise NEVER rewrites the `Loop config:` `caps=` value. **The in-session review loop's cap (recorded, never only narrated).** A cap event of the executor's own `/review-loop` reaches the composer on the executor's handoff and is decided by this row like any other; its verdict is RECORDED with the UNKEYED, standalone form of the same transitions — `emit OWNERSHIP:auto-disposition … --log <probe-log> --epoch "<activation id>" key=<runkey>-review-cap cap-accept=close detail="review-loop round <k> of <cap>: <why>"` for an accept-close, and `emit OWNERSHIP:gate-disposition … --log <probe-log> key=cap-raise|peer-cap|peer-cap-accept choice=<raise|stop|accept> detail="review-loop round <k>: <what was decided>"` for a raise, a stop at the cap, and an accepted residue — the loop and its round named in `detail=`, and NO `pass=`/`cap=` bundle: a review loop has no pass id, and the helper refuses the keyed form for it (a cap transition never carries `peer_round=`, and a keyed one needs a keyed peer start to seed its pass). Inside a grant's window the `away report`'s section 8 lists these records. **The docs-only LOW close (a convergence, not a cap event).** On a composer-seat CODE-mode peer pass under `gates=executor`, a PRE-CAP round whose every verified finding is LOW and docs-only on a docs surface (or `invalid`), with no class-closure claim and a fix delta inside the docs floor, closes the pass converged with no confirm round — `/peer-loop` step 4 owns the rule and its mechanical read; it is written where convergence is written (the fix leg's `CONSUME:` `result=` begins `docs-only-low-close`, and the round's Review History line carries the same word first in its outcome text), is never one of this row's cap outcomes, and at `round == cap` is not evaluated.
- **MUST-PAUSE** — a gate surfaced for the user; the loop waits for the disposition.
- **Review-integrity failure** — `/review-loop` returned without reporting its per-round `Review History` integrity check (the composer's step-3 assert); stop and surface rather than run blind on skew/escalation.
- **User stop** — the user asked to stop, or the scope was one-phase-and-stop (`scope=one-phase` stops after its phase and starts nothing further — Release groups).
- **Isolation close (every stop path above).** Under `isolation=worktree`, every termination resolves through the per-close-path outcome table in **Run isolation (worktree-per-run)**: a green Phases-done close with `merge=auto` runs the canonical merge-back preconditions there; every other stop retains the worktree/branch/journal with the worktree plan authoritative and the handoff stating the continuation. Under a bound away grant whose `scope=` carries no `merge`, the loop's own close — the `retained-green` close, or the `merge=auto` merge-back — ends the grant `run-stop` once the helper's `OWNERSHIP: run-close` record reads `verdict=complete` (**Away mode** → Ending the grant). Never a push (the `/close-run` carve-out in **Run isolation (worktree-per-run)** aside — run next by the operator, or by an agent acting on the operator's request, after a `retained-green` close; or, under a bound away grant with `merge` in scope, by the composer itself — see **Away mode**).

Every stop path FIRST flushes any pending queued LOW/MED notification batch (the Notify-at-gate queue, Safety gates) — ONE desktop batch notice plus one `batch-flushed` record PER DELIVERED MEMBER, or its policy-suppressed settlement under `notify=action-only` (the member records still land, carrying `detail="policy-suppressed notify=action-only"`; only the desktop notice is muted), all sharing the flush's `batch=` key (never an invented batch-level success record; a failed flush leaves members `queued` per Notify-at-gate) — before the run ends: a stop with unflushed queued notices is an incomplete stop.

**Persist-before-close (the CANONICAL close-contract order; runs on every run whose resolved config carries `persist=on` with the compatibility invariant holding — `isolation=worktree|branch` AND `autocommit=on`, the Q5 item's applicability rule; `persist=off` runs skip straight to the isolation-close resolution).** The wizard resolved and DISPLAYED the authority (the close table's `Persist:` line); the close contract runs the steps, composer-seat, in this TOTAL ORDER — flush queued records → `/retro` while the plan is still Active → secret-pattern sweep → materialize → plan pointer update → commit on the run branch → close:
1. **Flush queued records** — the flush duty above (shared step: the persist path adds no second flush semantics; a failed flush fails THIS order too; a member's policy-suppressed settlement under `notify=action-only` is a SETTLED member, never a failure — D5).
2. **Run `/retro` while the plan is still Active** — pointed at the run's base-side log root and the authoritative (worktree) plan copy per the Phases-done bullet; Active-state timing is LOAD-BEARING: `/retro`'s pointer rule skips Completed-state plans (a `Paused` plan stays pointer-writable — `/retro`'s v32 named exception), so a close that ran lifecycle transitions first would strand the report pointer-less.
3. **Secret-pattern sweep** over the assembled evidence content (the retro report body + the probe-log tail below) BEFORE anything is written to a tracked path: scan for credential shapes — `key=value`/`export` lines whose name matches `*TOKEN*`/`*SECRET*`/`*KEY*`/`*PASSWORD*` with a non-placeholder value, bearer/OAuth literals, PEM blocks, and long high-entropy token-shaped strings. ANY hit FAILS the step: report the finding's location class (never the matched bytes), retain the transient logs, and do not materialize or commit — wrapper/journal output is grammar-constrained, so the expected leak channel is free-text `detail=`/prose (the Accepted-Assumptions trigger this sweep discharges).
4. **Materialize ONE bounded tracked evidence file** `docs/retros/retro-<runkey>-<YYYY-MM-DD>.md` — the retro report plus a BOUNDED probe-log tail appendix (the final stage's probe log, last ~200 lines; total file ≤ ~200 KB — over-bound content is truncated-with-marker at the tail appendix only, never the report body), COPIED out of the gitignored logs root: `.cursor/loops/` stays uncommitted and gets NO ignore exception; `docs/retros/` is the tracked home (created by v32; keep its README stub). One run = one file; a same-day re-run overwrites it (the `/retro` overwrite rule carried through).
5. **Plan pointer update** — rewrite the plan's `Retro report:` pointer line (replace-not-stack, `/retro`'s rule) to name the TRACKED `docs/retros/` path — the durable artifact; the gitignored original dies with an ephemeral host.
6. **Commit on the run branch** — composer-seat, under the wizard-confirmed autocommit/persist authority (the close table WAS the confirm): the evidence file + the plan pointer, with the `OWNERSHIP: commit` tool emission like any composer commit; never a push (the `/close-run` carve-out in **Run isolation (worktree-per-run)** aside).
7. **Lifecycle close/cleanup** — only now does the stop path proceed to the isolation-close resolution (the per-close-path outcome table in **Run isolation (worktree-per-run)**), EXECUTED by the run-close helper per **Mechanical close enforcement** there: the close is refused "complete" without the helper's `OWNERSHIP: run-close` record carrying the path's expected verdict.

Failure at ANY step retains the transient logs and REPORTS THE GAP — the close is never declared complete over a failed or skipped persist step (a run that cannot persist its evidence closes as a reported-incomplete stop, keeping its non-green retention semantics; the operator decides the disposition).

Never loop past a stop condition without explicit user direction — except under a bound away grant — see **Away mode**, which says which stops the composer disposes and which still wait.
