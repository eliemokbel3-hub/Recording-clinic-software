# Away mode, part 6 — stopping an away run and ending the grant
Previous: s17-away-fix-cycle-nudge-watcher.md. Next: s19-away-records.md. Words such as above and below may point into those files.

Contents, in order: Stopping an away run, three ways in; The composer's side of the stop command, the wake rule; what each way leaves running; Ending the grant, messages while away, and the report, with The belated end, Widening and The reminder line.

**Stopping an away run (ONE protocol, three ways in. A grant is ended only as Ending the grant states — "back" / "away off", "autonomy off" or a `config-revoke key=gates`, a widening's end of the grant it replaces, and the automatic ends; an ordinary message never ends one, and the stop command ends none).** Closing the session or quitting the app is NOT one of them: the run's roles are built to run on, and where a watcher runs with takeover on, the run is continued (what was read about a composer's death, and what was not — an app quit among it — is **Backends** → Roles that outlive the composer).

1. **The stop command** — the operator's, from any terminal, or the composer's at the operator's word: `python3 scripts/loop-watchdog.py stop --iso <iso-id> --base "<abs base>"` (without `--base` it reads the checkout the script sits in — right from the base checkout, and a refusal, `no run … pass --base`, from a run worktree's copy). It writes the durable no-takeover mark `<iso-id>-notakeover` — no takeover starts for this run from then until an interactive composer writes its identity (Preflight step 17) — ends a live takeover by signalling its process group, and stops each leg that does not read `over`: a TERM to its wrapper and to its role's group. It prints `stop: iso=<iso-id> mark=<written|FAILED> gate=<taken|none|busy> takeover=<none|ended|held|unknown>[ pgid=<n>]`, one `stop: leg=<leg> was=<word> wrapper=<…> group=<…> now=<word>` line per leg it touched, and then EITHER `stop: done — takeover is off for run <iso-id> until an interactive composer writes its identity; its live roles were stopped`, exit 0, OR one `stop: NOT COMPLETE — …` line per thing it could not finish, exit 3. It never reports a stop it did not complete; an exit 3 is read line by line, and what it names is the operator's to deal with. **What it does NOT do.** It signals a number read from a file only while that file's recorded start token proves the number is still that process, and a GROUP only while its leader runs under that token. So a role that has ended and left a background process behind — a group whose leader is gone — is NOT ended by `stop`: its line names the group (`… The leader of group <n> is gone and a process remains in it …`), that group is not signalled, and the operator looks at it and ends it by hand. The proof is per TARGET, never per leg: for every leg that does not read `over`, the wrapper and the role's group are each signalled only on their own evidence, so on a leg whose word is `unknown` a target that proves itself may still be sent its TERM while one that does not is left alone — the leg's line says which (`wrapper=` and `group=` each read `signalled`, `over`, `unknown` or `changed`) — and a leg that is not `over` afterwards is named, exit 3. On a Windows host no start token can be read, so no target proves itself: every leg in flight reads `unknown` there, and `stop` writes the mark and reports. A role that is RUNNING is stopped — on a run whose leg files `stop` can see: it reads the run's log folder (`<base>/.cursor/loops/<iso-id>`, or the journal's `log_root=`), so on a run with no run worktree — no journal, its leg files in the flat log root, where a leg's file cannot be tied to one run — it reads no leg and stops none, says so on one `NOT COMPLETE` line, and exits 3 (the mark is written, and a takeover ended, all the same); there each role is stopped by a TERM to its recorded pid (Visibility + run-state → the Stall watchdog bullet → Stopping a wrapper leg). A run whose journal does not establish its log folder — it cannot be read, it says nothing (an empty file, one cut short), or its `log_root=` is there and cannot be used (empty, unsafe, not an absolute path; an absent `log_root=` is the default folder, and one that is there is never replaced by it) — gets the same answer — exit 3, never `done`: the default folder is read and a leg that proves itself there is stopped, and the line says a role whose files are elsewhere was not seen. **What it leaves untouched:** the grant — `stop` ends none — and a composer SESSION that is still alive: the command signals a takeover and the run's roles, never an interactive composer. Such a session wakes on its stopped role's exit, and it honours the stop by the wake rule below: it resumes nothing, spawns nothing, and parks. That rule is the composer's own reading of the mark — nothing in the helper or the wrapper refuses a spawn while the mark stands — so an operator who wants more than a rule also says "back" to an open session (way 2) or closes it.
2. **"back" or "away off"**, typed to an interactive composer (Ending the grant). When a takeover holds the seat, the composer's FIRST step is `python3 scripts/loop-watchdog.py stop --iso <iso-id> --base "<abs base>" --takeover-only` — the operator's word is its authority, and without it the grant's end would be refused as a non-holder's write. `--takeover-only` ends the takeover and leaves the roles running (`… its roles were left running`). Then, the seat free: the identity write that was refused before (Preflight step 17), `away end` with `reason=back`, the nudge cancelled, and the report. The roles keep running: the run goes on, attended.
3. **"autonomy off"** — the same first step, then its own sequence (Ending the grant).

**The composer's side of the stop command — the wake rule.** The stop command signals no composer, so a composer that is alive learns of it from the run's no-takeover mark, and reads the mark where the stop would otherwise be undone: before EVERY spawn and every resume of a role, with or without a grant, by `python3 scripts/loop-watchdog.py seat --base "<abs base>" --iso <iso-id>` (read-only; its first line ends `mark=yes` or `mark=no`). `mark=yes` means the operator ran the stop command for this run. The composer then resumes NOTHING and spawns NOTHING — not the leg the command stopped, which its wrapper has ended `incomplete`, and not the next phase: it consumes what has ended (the leg-bound `CONSUME:` — a record of what happened, never a restart), writes the must-pause pair under the key `<runkey>-operator-stop` (Records → A park) so that the stop is on the run's log and the watcher reads the run as parked, cancels the nudge as at any park that leaves nothing to do — but WITHOUT the identity write that otherwise follows a cancel: an interactive identity write lifts the mark, and the operator's mark is not lifted before their word (the record keeps its old `nudge=` until then; the run reads parked, so nothing acts on it) — and waits. At a Resume the read comes BEFORE the identity write (the Resume contract's first v48.0 duty): `mark=yes` there is the same stop, honoured the same way, and the identity is not written until the operator's word — so the mark is never lifted before the pause is on the run's log. One case is left to the identity line itself, a mark written between that read and the write: an `identity:` line that reads `mark=cleared` or `mark=clear-failed` (Preflight step 17) FOUND the mark, so the stop was run — and after `mark=cleared` the mark itself is gone, so the pair is written before anything else is done and is what keeps the stop. (One mark is not a stop to honour: the composer's OWN, written by the `--takeover-only` stop it has just run at the operator's "back" or "autonomy off" — there the operator's word is already given, and the identity write that follows lifts it.) Only the operator's word lifts it: "back" ends the grant as always, with the run theirs to direct; a word to go on is the pause's `gate-disposition`, after which the composer writes its identity once more — lifting a mark that still stands — and then resumes; if that write reads `mark=clear-failed` the mark is still there and the next `seat` read would say `mark=yes` again, so the composer says so and resumes only once the mark is gone (removed by the operator, or by the command run again) — it never reads a standing mark as anything but a stop. What the rule does not reach: a call the composer had already issued when the stop arrived; it binds the next spawn or resume.

What each leaves running: the stop command — no takeover and no role (or it says which it could not end, and exits 3), with takeover off for the run, and, untouched, the grant and any composer session still alive — which parks at its next spawn or resume by the wake rule above; "back" — the roles and the run, attended, with no grant; "autonomy off" — the same, with the gates mode changed. A run stopped by the command is picked up again by an interactive composer through the Resume contract.

**Ending the grant, messages while away, and the report.**

- "back" or "away off" → when a watcher takeover holds the run's seat, the stop command with `--takeover-only` FIRST (Stopping an away run, above); then the `away end` recipe (Record grammar above) with `reason=back`, the nudge cancelled (The nudge), then the report — one per grant this run gave (`grant=<n>`), where a widening gave more than one.
- "autonomy off", or a `config-revoke key=gates`, ends the grant FIRST: the same first step as "back" when a watcher takeover holds the seat — the stop command with `--takeover-only` — then `away end` with `reason=autonomy-off`, the nudge cancelled, then the toggle or the revoke as Safety gates states it.
- With `merge` in `scope=`, the release work the scope covers finishing → `away end` with `reason=release-done` and `--base <abs>` (REQUIRED beside `--log-root` on this reason: the helper reads `<base>/.cursor/loops/<iso-id>-isolation` and admits the end only while its state is `merged`, `cleaned`, or `retained-green`, refusing `run-not-closed state=<s>` on `active`, `merging`, `paused`, `crashed/recovery-needed`, `merge-failed`, or any other state, an absent or unreadable journal, or a wrong `iso=` — nothing written; Record grammar states the gate), then the report — after the FINAL group's close (Termination → Group done; `/close-run`'s final route — the one grant covers every release group of the plan, so it ends once; the timing after the final merge is this bullet's rule, not the helper's: its gate admits `retained-green`, the loop's own stop, and only its in-flight refusal stands between a premature end and the final merge) and after every other release step the scope covers has finished (a parked step keeps the grant bound — the next sentence). A park — at any group, the final one included: a merge park, a staging or production park, a `group-ff` refusal — keeps the grant BOUND and the run waits: no end is written at a park, the departure file's `Stop:` lines and the `away check` line show it, and the operator's clear or a hand merge resumes the close (Termination → Group end). While an act parked in flight has no outcome, the helper refuses this end — reported once, never retried, the grant left bound for The belated end below.
- **The belated end (stated ONCE, here).** Whoever finds a bound grant on a run that has CLOSED — its journal `merged`, `cleaned`, or `retained-green` (the helper's gate, the `release-done` bullet above — a run with a group still to build has not closed, and its grant stays bound) — and whose covered release work is DONE — every step the scope covers finished; a park, at any group, keeps the grant bound and the run waiting for the operator's clear or a hand merge (the `release-done` bullet above), so a parked run owes no end — runs the end: the composer on a wake (STICKY §7) — each open `start` settled first from the real state as Widening (1) settles it, then the end; or `/close-run`, on a close the grant does not cover (its **Under an away grant** section's closing paragraph names those routes), after that route's own helper record and ONE yes/no that prints the run's census line (Record grammar → The census — its journal, marker, and probe age; a live composer between two acts is the case the question exists for). The end and its report precede the route's final line. On every end by these sites `reason=` is by SCOPE — `release-done` with `merge` in `scope=`, `run-stop` without (the helper checks membership only; nothing routes on it) — `grant=<n>` is the one the `away check` line prints, whatever its state token, `--log-root` is always passed, and with `release-done` so is `--base <abs>` (the helper then refuses that end `run-not-closed state=<s>` on an `active`, `merging`, `paused`, `crashed/recovery-needed`, or `merge-failed` journal), so the helper refuses an automatic-reason end (`release-done`, `run-stop`) — exit 2, nothing written, the open act named — while the grant's window holds a release `start` with no outcome, and refuses it too when the log root cannot be listed; a refused end is reported once and never retried: the grant stays bound for the operator.
- The run stopping with no release work in scope — a grant whose `scope=` carries no `merge`, ended at the loop's own close (Termination: the `retained-green` close, or the `merge=auto` merge-back) once the helper's `OWNERSHIP: run-close` record reads `verdict=complete` (a refused close keeps the grant); a `branch` or `none` run, which has no journal and writes no such record, ends it at its Phases-done stop → `away end` with `reason=run-stop`, then the report. A `paused`, `crashed/recovery-needed`, or `merge-failed` close is not the run stopping: the grant stays for the resume.
- **The report after an end.** Every `away end` passes `--log-root` (Record grammar above) — and, with `reason=release-done`, `--base <abs>` too (the closed-run gate, the `release-done` bullet above); after its own line the helper then prints the `away report` recipe for the grant it ended, every flag filled from the end's arguments and `--out <log-root>/away-<n>-report.md` — the ONE report location (Records → The report). The composer runs that printed line as printed, never retyped, then prints the report. Without `--log-root` the printed line carries the literal `<log-root>` (twice), which the composer fills with the absolute log root, quoted, before running it.
- **Widening** — an operator message that widens the scope ("also do production"); a corrected departure file at the SAME scope (The grant — a warning the composer acts on while present) is asked the same way and written by its own two calls, stated below — it is not a widening. It is the operator's own word, given while present; nothing widens a grant otherwise (Always the operator's, item 5). No new verb and no new `reason=`: the grant is ended and a wider one given — from v47.0 in ONE helper call, `away grant … widens=<n>` ((5) below), which writes grant n's end and grant n+1 together; until that call grant n stays bound. For the nudge a widening is what it is for the records, an end and a new grant: once that call has written both, the composer cancels grant n's timer and arms grant n+1's with a new tag, then writes its identity with it (The nudge — a firing of grant n's that was already queued is stale by its own grant number and resumes nothing); the same-scope correction's end-then-grant pair does the same. A corrected departure file at the SAME scope is not a widening for the helper (`widens=` needs a strictly wider scope and a new file that begins with grant n's bytes): that correction is `away end … reason=back` — nothing has run under the grant — then a plain `away grant` with the corrected file — the batch asks nothing again, and since the helper carries nothing into a plain grant, its `allows=` is (1)'s snapshot of the departure classes still open, each with its effective limit, the `operator-task` approvals re-created as (5) states. (1) No release act may be in flight: for each path, an act whose `start` has no outcome (the report's `started; outcome not recorded — check the real state`) gets its outcome first, read from the real state and recorded (Records → A release act) — the composer waits for it. Then, while grant n is still BOUND, ONE `away check` read: `allows=unknown` STOPS the widening here — the grant stays bound, nothing proceeds on `unknown` — and its `allowed="…"` list, grant n's final effective pre-approval set, is kept as the carried snapshot in `<log-root>/away-<n>-notes.md` (the running-notes file), because after (5) the `away:` line reads grant n+1's set and the records are never read by eye — the helper carries the departure classes itself ((5)), and the snapshot is what (5) re-creates the `operator-task` approvals from; a resume after (5) that finds no snapshot re-reads grant n's set from `away report … grant=<n>` §1 ("Pre-approvals in force" and "Cleared" — the same fold over the selected grant, ended included; Records → The report), never from the records by hand and never as an empty set. (2) Nothing is ended by hand: grant n stays BOUND through (3) and (4), and its end is written by (5)'s one call. (3) `<log-root>/away-<n+1>-departure.md` is written: grant n's departure file's BYTES, unchanged from the first to the last (the helper admits the widening only when the new file begins with them, so a widening adds lines and never removes or edits one: the `Confirmed claimants:` line is thereby carried byte for byte (a widening confirms no claimant — a contender first seen here appears in the listing only; a source line that is missing stays missing; from v40.0 nothing compares the line — that item), the `Usage fallback:` line stands, and a merge-stop line that reads `around` or `park` still vetoes its merge after the widening, whatever a later line says — lifting a restriction takes a full re-departure: `away end … reason=back`, a new pre-departure check, a plain grant) — followed by a dated **Widened at grant n+1** section holding the pre-departure check's **Other live runs** listing written fresh from the census (Record grammar → The census — it supersedes grant n's listing, which stays above as history, and is left out of the path-by-path comparison below), any merge-stop line the widening adds, and the re-confirmed delta for the new tokens, with its answers — every line the widening batch asks again, a rediscovered path's lines, and each hold-or-clear answer below — in the section's own `Answers` block (The batch and the departure file); the release machinery inventory re-read at the current fetched base and compared with grant n's, path by path, under the effective set's comparison contract (Records → The effective set and accepted versions) — for the CARRIED-EVIDENCE decision this comparison reads the fold (item 4's recipe with its `--log-root`/`grant=`/`away_check=` trio — the contract's accepted versions): a path whose every blob id is unchanged, a quoted procedure's file by its quoted block's bytes — a path `same` through an accepted version (`matched=<ts>`) included — carries its items 6–7 evidence forward with no question (its acceptance line apart when `production` is new, (4)); a `changed` quoted block of a quoted-procedure file (Markdown or not — v44.0) is re-read and keeps its evidence too, never a park — its new version carried into (4)'s complete set block, no record (a record written now would bind to grant n, which (5) ends — the block is the carrier under n+1); while a changed, added, or removed workflow file, a quoted procedure whose block is missing or ambiguous (never the rest of its file), or a release-configuration file voids that path's carried evidence (its class, quoted procedures, `Receipt:` reader, checklist, rollback step, and acceptance lines): the path is rediscovered as item 7 discovers a path at a first departure and re-confirmed in the widening batch, or the widening parks it — the operator's choice in that batch. The Widened section is authoritative for a rediscovered path and for every answer the widening batch asks again, grant n's text for the rest of an unchanged one, and a refreshed blob id is never written beside grant n's classification. The section also lists, by name, grant n's unresolved production-hold evidence — each HIGH finding accepted or deferred, each verified regression accepted or deferred, each production-impacting item disposed that grant n's file does not list, read from the run's `away=<n>` records — and every item an earlier Widened section carried that the operator has not cleared, each with its hold-or-clear answer from this widening batch. (4) The widening batch (the same contract and the same two-call order) asks only what is new: the unblockables and the scope for the new tokens (when the widening adds `staging` or `production`, the `foreign-merge` and `operator-merge` classes AGAIN, in this added block (their reach grows with the scope, so the helper does not carry them across such a widening; `operator-merge` is asked only where the file, old lines and added ones, holds a merge-stop line — call 1's rule); when `production` is new, also each production path's `Unpinned production accepted` line — asked afresh even on an unchanged path, since grant n settled it without production in scope; when grant n was build-only and the widening is the first to carry `merge` or `production`, items 6–7 are computed, printed, asked — the ungated merge and the items 6–7 confirmation — and written in the Widened section exactly as at a first departure, scope-aware above), the confirmation of each rediscovered path, the set confirmation when the re-read release machinery set differs from the FILE's effective set — compared WITHOUT the fold (against the file's set block, never the grant's records — so every path that differs from the file is named in the ONE question, a path `same` only through an accepted version (`matched=<ts>`) included, listed as "accepted under grant n (`set-refresh` <ts>, class <c>)" with its current blob id; a yes writes the COMPLETE current set block holding the accepted version itself — a workflow with the matched record's `workflow_class=` — so grant n+1's departure file carries it and no record of grant n is ever read under n+1; a no leaves the old set standing and the run continues on it — the next reader under n+1 records the difference against it, v44.0: a record, never a park) (Records → The effective set and accepted versions — the set block's rule), and one hold-or-clear question per carried hold item; adding the `production` token clears nothing — only the operator's named clear does, and the production hold reads every item not cleared. (5) The new file is linted (`away lint` — The grant; it reads the file grant n+1 would read) and then ONE call is made: the `away grant` recipe (Record grammar) with the wider `scope=`, `widens=<n>` appended, and an `allows=` naming only what (4) answered `yes` afresh. The helper admits it only while grant n is the bound grant, the new scope is a STRICT superset of grant n's (`widen-scope-not-wider`), no release act of grant n is in flight (`widen-act-in-flight` — (1)), none of the three folds the `away check` line prints reads `unknown` (`widen-unknown`), grant n's own departure file still digests to its `departure=`, and the new file begins with that file's bytes (`widen-not-prefix`); a refusal writes nothing and leaves grant n bound. It then writes the two EXISTING record shapes in one write — grant n's `away-end` with `reason=back`, then grant n+1 — and prints three lines: `away: ended …`, grant n's report recipe (run as printed, the report then printed — The report after an end), and `away: granted …`. `widens=` is stored on neither record. **What carries (grant n's EFFECTIVE set; by the helper):** the departure classes in force under grant n, which the helper writes into grant n+1's `allows=` itself, each limit written out (`pr-fix-cycles:<n>`), a cleared class omitted, an entry the call names replacing the carried one — except that a widening adding `staging` or `production` carries neither `foreign-merge` nor `operator-merge`: they ride grant n+1 only when the call names them again ((4)). **What does not:** the per-task `operator-task` approvals and the accepted-version records, which bind to grant n. Right after the call, one `pre-approval` record per still-open `operator-task` approval — the snapshot (1) kept, or the report's §1 on a resume — is re-created with a NEW `instr=` and bound to grant n+1 (a cleared one is not re-created — cleared history is never replayed), and the accepted versions reach grant n+1 through (4)'s set block; then the read-back: `away check` on grant n+1 must list in `allowed="…"`, after those records, exactly the carried classes, the classes named afresh, and those approvals. **An interrupted widening** — one write is not a transaction, and the helper undoes nothing — has four outcomes, each with its retry and none needing a new record: nothing was written → the same call again; the end landed and the grant did not → the run is UN-GRANTED, never widened: the retry is refused (`widen-prior-ended`) and prints the plain `away grant` to type at the new scope and file, the carried classes as its `allows=`; the grant line is torn → the policy log reads `malformed`, already an always-the-operator's item, and nothing proceeds; both landed and success was not reported → the retry finds grant n+1 bound at the requested scope with its file intact, prints its `away: granted` line again, and writes nothing. In no outcome does the scope grow without the complete new grant. The reminder line now names grant n+1. Narrowing a named act needs no new grant: record a hold (The operator's word wins) — holds are run-scoped, never tied to a grant, so a widening carries every open one by construction, and `holds=` on grant n+1 reads what it read on grant n.
- Any other operator message while a grant is bound: answer it, then print the `away report` so far. The grant is unchanged. A message that answers an open stop is consumed as it is without away mode (loop step 6's precedence).
- **The reminder line.** Every reply the composer sends while a grant is bound ends with: `Away grant <n> is still in force (scope: <scope>). Say "back" to end it.` Beside it, from v48.0, whenever the reply is one the operator may read as a goodbye — the line after a grant, an answer to "I'm leaving", the pre-departure message — ONE more line: `Closing this session or quitting the app is not a way to stop this run: its roles are built to run on, and a watcher may continue it. Say "back" here to end the grant and take the run back. From outside this session, run from the base checkout: python3 scripts/loop-watchdog.py stop --iso <iso-id> — it stops the run's roles and the watcher's continuation.` (Stopping an away run, above; on a run with NO run worktree the last sentence is left out, as in the pre-departure message).
- The report is the helper's output, printed verbatim by reading it (the relay-fidelity rule) — never composed or retyped by hand.
