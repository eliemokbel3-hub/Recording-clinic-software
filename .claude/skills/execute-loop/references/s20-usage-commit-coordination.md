## Usage-exhaustion recovery (claude pools)

When a `claude -p` role's run actually FAILS on a usage limit — a limit-rejection error mid-run, or a spawn refused on an exhausted pool; detected via the heartbeat's tier-1 error-string / `rate_limit_event` watch or an exit with no `ROLE: handoff` line — the composer MUST-PAUSEs and offers three options. The trigger is the FAILURE, never a probe percentage: the usage checkpoint stays warn-only (see Visibility + run-state), and this section adds recovery from a hard failure, not a threshold action. **Automatic fallback FIRST when `profile-fallback=` is configured (`Loop config:` key; executor/architect seat only).** On the run's FIRST usage-exhaustion of the executor/architect, BEFORE the three-option pause: (1) record the DECISION as the act-and-inform pair `python3 scripts/loop-journal.py emit OWNERSHIP:auto-disposition --run <runkey> --role composer --log <probe-log> --epoch "<activation id>" key=profile-fallback detail="<exhausted pool → fallback dir; the limit evidence>"` (a hand-supplied topology key on the existing owner; `class=auto-disposition`; the helper COMPUTES `mode=queued` for a severity-less topology auto-disposition — delivered in the phase batch at `normal` urgency; the switch itself is narrated in chat); (2) run the "Switch account" transaction below to the configured `profile-fallback` dir — session transfer, then (under `architect=on` with `agent_loc=profile`, v43.0) re-run Preflight step 5 in the new profile dir before the respawn — the definition moves with the profile — then `--resume` under the new `CLAUDE_CONFIG_DIR`, the alive-check, the `Loop config:` rewrite, the fresh `ROLE: start`, and the `OWNERSHIP: profile-switch` OUTCOME record (an outcome record, never a pair owner); (3) resume. Ordering is decision pair → switch → resume; a failed switch or a failed resume falls through to the normal usage-exhaustion `must-pause` pair (the outcome record stays truthful — `alive=` names the failure). ONE fallback per run: the counter is the count of `key=profile-fallback` DECISION records in the run's probe logs (never memory, never the outcome records — a decision and its outcome count once); a second exhaustion pauses with the three options. Absent `profile-fallback=` ⇒ this paragraph is inert and the pause below fires exactly as before. Under an away grant the key's presence or absence is the operator's own departure answer (Away mode → the pre-departure check, item 5, and the departure file's `Usage fallback:` line): a named profile was set before the grant bound, and `none` there means the run stops here, on stop 4. **The router branch (under `router=on`; stated ONCE, here: Away mode's stop 4, the Switch account option below, the peer paragraph, STICKY §7, and the orchestration doc point here).** The trigger is a role DEAD on a limit — an exit carrying the limit evidence, NEVER a warning-class heartbeat event alone (`--failed` rests the folder's whole pool for 30 minutes for EVERY run on the host) — whose identity record carries `route_run=`; a pinned role (no `route_run=` — a manual switch's or a last-resort leg's, loop step 1) goes straight to the three-option pause with no re-pick and the counter unchanged. The composer counts the run's `key=profile-fallback` DECISION records across its probe logs — the cap is **3 per run, ONE counter for every role** (executor/architect, a `claude -p` peer, the codex peer) — and with three already written the fourth exhaustion pauses WITHOUT a pick. Under three — the values the pick will copy (the identity record's `route_run`, `route_phase`, and `profile_dir`; the launcher's `codex_home`) first held to loop step 1's identity-value ambiguity rule, an ambiguous one taking the three-option pause with no reservation and no pick: (1) FIRST write the decision pair — the RESERVATION — `python3 scripts/loop-journal.py emit OWNERSHIP:auto-disposition --run <runkey> --role composer --log <probe-log> --epoch "<activation id>" key=profile-fallback detail="router re-pick <n>/3 reserved: --failed=<failed short>; <the limit evidence>"` (the same key, class, and computed `queued` mode as the pair above; `--failed` rests the pool before the router answers, so an attempt that then fails a check, fails its verify, or is interrupted after the pick is ALREADY consumed — the record is on disk, and a resume never un-reserves it); (2) run the re-pick under the runner (Preflight step 15, inventory row 3): `"$LOOP_ROUTE_BIN" pick --agent=claude --run=<the identity record's route_run> --role=<role> --phase=<the identity record's route_phase> --model=<the role's model> --failed=<the identity record's profile_dir> --json` — every value COPIED from the identity record and the role's `Loop config:` row, never retyped; every flag `--flag=value`, a flag omitted when its value is empty; NO `--pid` (the resume's wrapper re-ask attaches `--pid=$$` and gets the binding back); (3) hold the answer to the wrapper's answer rule FIRST — before any auth call, any copy, or any `LOOP_PROFILE_DIR`: the shape by the same `python3 -I` parse the wrapper uses (`route_schema` an integer equal to 1; `dir` a string, absolute, no control byte — a lone surrogate counts as one — no `"`, no non-space Unicode whitespace (v42.0 `unicode-space`); `sticky` a boolean) and the folder checks as the same shell tests (`-d`, `-O`, not group- or world-writable, realpath outside the worktree and every read root — the wrapper's usage header is the one statement; its refusal 6 the mechanical backstop): a failure is the no-answer path and the candidate is never written to; (4) THEN verify it — the transfer recipe's verify-first step: `python3 scripts/loop-run-bounded.py --timeout 20 --kill-after 2 -- env CLAUDE_CONFIG_DIR=<answer> "<pinned claude>" auth status` reporting a bound logged-in identity and `.credentials.json` present in the folder (inventory row 5 — a timeout is not verified); an answer EQUAL to the failed folder is no answer; (5) narrate the target on ONE `ADOPT:` line, `<failed short> → <answer short>` — never a second counted decision; (6) run the Switch account transaction below onto the answer: the transcript copy under `loop-run-bounded.py --timeout 60 --kill-after 5` (the composer runner, inventory row 8 — a timeout or a partial copy fails the switch before any resume), under `architect=on` with `agent_loc=profile` the Preflight step 5 re-run in the new profile dir before the respawn (never the case under `router=on`, where `agent_loc=project` is forced and the definition does not move), the resume through the wrapper with `LOOP_PROFILE_DIR=<answer>` AND `LOOP_ROUTE_BIN` set AND `LOOP_PHASE=<the identity record's route_phase=>` byte for byte (the routed-resume phase rule — the Resume contract, Visibility + run-state: the re-pick was made with that phase, so the binding answers only to it; the wrapper's re-ask returns the binding — sticky and equal — and attaches `--pid=$$`; its router lines, BOTH when two print, journaled as `ADOPT:` — loop step 1), the alive-check, the fresh `ROLE: start`, and the `OWNERSHIP: profile-switch` outcome record exactly as that option states them; the `Loop config:` line is NOT rewritten (the role's fallback did not change) and NO `config-change` is emitted. NO ANSWER (the router's word, a failed shape or folder check, or a failed verify) ⇒ the `profile-fallback=` dir is the LAST-RESORT TIER: the same transaction onto it, narrated on the reservation's `ADOPT:` line as `no answer: <word>; last resort → <dir>` (already counted — no second decision), the leg spawned WITHOUT `LOOP_ROUTE_BIN` and PINNED for the rest of the phase (loop step 1: no `route_run=` on its identity record; this first pinned resume carries `LOOP_PHASE` = the routed record's `route_phase=` read before the spawn, every later one today's phase label — the Resume contract's rule; a further exhaustion in the phase → the pause; the next phase routes again — a fresh spawn has no resume guard, so a router that answered on the next ask would otherwise move the role off the verified last resort). No `profile-fallback=` dir, a last-resort transaction that fails (its switch or its resume — the outcome record stays truthful), or the fourth exhaustion ⇒ the three-option pause below exactly as today. ONE fallback per run stays the rule under `router=off`; this branch exists only under `router=on`.

```text
The <role>'s claude account pool is exhausted (run failed on a usage limit).
1. Wait — the pool resets at <reset time — the structured session/week resets fields, headline text when unparsed, or resetsAt>; resume after it passes
2. Switch account — continue the same session under a different Anthropic account
3. Continue in composer — the live session takes over as the executor
```

- **Wait** — hold the run; after the reset time passes, resume the same role (`--resume <session-id>` — the roles in this section are `claude -p` by its trigger) and continue where it stopped.
- **Switch account** — under `router=on`, when the role's identity record carries `route_run=` (a ROUTED identity — the same discriminator the router branch above and loop step 1 use), FIRST run the bounded `"$LOOP_ROUTE_BIN" pick --agent=claude --run=<route_run> --role=<role> --phase=<route_phase> --model=<model> --failed=<the identity record's profile_dir> --json` (the re-pick's own argv, the values copied from the identity record — the router branch above — under loop step 1's identity-value ambiguity rule, an ambiguous value sending no pick, the switch then proceeding as for a pinned role; the runner, Preflight step 15; its answer is NOTED on one line and never used: the operator's choice stands), so the binding is dropped and the pool rested, then resume WITHOUT `LOOP_ROUTE_BIN` under the chosen profile — this FIRST pinned resume carrying `LOOP_PHASE` = the routed record's `route_phase=`, read BEFORE the spawn (its rewrite of the record drops the route keys — the wrapper writes them only on a spawn made with the variable) — the pin for the rest of the phase (loop step 1): no `route_run=` on the identity record, every later resume without `LOOP_ROUTE_BIN` and with today's phase label (the routed-resume phase rule — the Resume contract, Visibility + run-state), a further exhaustion in the phase straight to this pause with no re-pick and the counter unchanged (a manual switch is never counted); the next phase routes again. A role ALREADY pinned — its identity record carries no `route_run=` (the wrapper writes the key only on a spawn made with `LOOP_ROUTE_BIN`) — has no binding to drop and no identity values to send: its switch proceeds with no pick and stays pinned. Then, on every run, pick from the switch menu, reconciled to the Q1R display shape (structured session/week % + reset times alongside each identity, freshness-sorted idle-first per the sharing advisory's recent-repos signal and its completeness rule — only complete snapshots rank as idle; DISPLAY reconciliation only: the usage checkpoint's log-line format in Visibility + run-state is byte-unchanged), or run the wizard's guided new-profile flow (pin-the-binary + bogus-dir probe + browser OAuth + the `.credentials.json` artifact check), then **transfer the session** (live-verified; recipe detail in `docs/integrations/cross-agent-orchestration.md` → multi-account): copy the session transcript jsonl (its filename IS the session id) plus the session-env entry from the old profile's `projects/` store into the new profile's matching paths, under `architect=on` with `agent_loc=profile` re-run Preflight step 5 in the new profile dir before the respawn (the definition moves with the profile), `--resume <session-id>` under the new profile's `CLAUDE_CONFIG_DIR`, and run a short alive-check. Then rewrite the `Loop config:` line (replace-not-stack) to the new profile, write a fresh `ROLE: start` carrying the new `profile=` key, and record the switch outcome: `OWNERSHIP: profile-switch ts=<iso> run=<runkey> from=<old identity/profile> to=<new identity/profile> transferred=<yes|no> alive=<alive-check outcome>` — the failed role's exit is recorded as the limit failure — on a wrapper leg by the composer's leg-bound `CONSUME:` verdict, the wrapper's own `ROLE: end` reading `incomplete: …`; on any other route by the `result=` of the `ROLE: end` the composer writes. If the resume is rejected, fall back to a **fresh executor from the plan handoff note** — no work is lost either way, since all code, findings, and plan state are on disk.
- **Continue in composer** — the live session takes over as the executor for the rest of the phase. Re-validate the cross-family rule first: if the composer's model family no longer differs from the configured peer's, the peer pass is inconclusive — stop for direction (Preflight step 7's rule), never silently proceed same-family.

A `claude -p` **peer** hitting a limit needs no session transfer — peers are fresh per round. Offer the same three options, where "switch account" simply respawns the round fresh under the chosen profile and updates the peer row in `Loop config:`. Under `router=on` a `claude -p` peer DEAD on a limit takes the router branch above FIRST: the same re-pick with `--role=peer` and `--failed=<its own identity record's profile_dir>`, the answer held to the answer rule and then verified, the decision pair and the ONE counter, then a FRESH respawn of the round under the answer with `LOOP_ROUTE_BIN` set (the wrapper's re-ask returns the binding) — no transfer, no `profile-switch` record, no peer-row rewrite; no answer ⇒ the `profile-fallback=` dir is its last resort too, the respawn WITHOUT `LOOP_ROUTE_BIN` and pinned for the rest of the phase; no dir, a failed respawn, or the fourth exhaustion ⇒ the three options. The composer-seat **codex peer** (a launcher leg) has its OWN branch — nothing Claude-shaped applies: the re-pick with `--agent=codex`, `--role=peer`, the launcher identity file's `route_run` / `route_phase`, and `--failed=<its codex_home=>` (the flag OMITTED when that value is not an absolute path — a relative inherited home is recorded as it is and never reaches the router; loop step 1's identity-value ambiguity rule applies to it as to every copied value), the answer held to the answer rule first, then verified by `python3 scripts/loop-run-bounded.py --timeout 20 --kill-after 2 -- env CODEX_HOME=<answer> codex login status` reporting logged-in (inventory row 5; an answer equal to the failed home is no answer), the decision pair and the same counter, then a fresh launcher round under the answer with the recipe's `LOOP_ROUTE_BIN` line (the launcher's re-ask returns the binding); no answer ⇒ the next round WITHOUT that line, on the launcher's inherited environment — the peer row's configured home, today's behaviour — when that home differs from the failed one, pinned for the rest of the phase like every last-resort leg, else the three-option pause; `profile-fallback=` is never a codex home and the Claude verify never runs for it. The stall watchdog's check step routes here too: a role that died on a limit is DEAD-on-limit (recover per this section), not hung — do not kill-and-report it as a hang.

## Auto-commit (git-safety)

Default **ON**; opt-out at the wizard (Q5). The wizard close-table confirm is the commit authorization — see the wizard **Close**.

**Commit authority is COMPOSER-SEAT ONLY (mechanical, all permission tiers).** No executor, architect, delegate, or peer EVER creates a commit or advances ANY repository ref — an executor-side path to git (a container or nested shell whose grants reach `git commit`, a bypass tier's unrestricted shell) is a `perms=scoped`-class ESCAPE, never an authorization: bypass lifts permission prompts, never commit authority, and the prohibition binds identically on scoped, bypass, and container-shaped paths. The spawn prompt states it (loop step 1), and the composer enforces it with BOUNDARY EVIDENCE: at each executor/architect activation the composer snapshots the repository's COMMIT/REF/REFLOG state — the checkout HEAD alone is INSUFFICIENT and was disproved live (`git commit` then `git reset --hard <captured-head>` leaves HEAD byte-equal while the executor commit survives in the reflog, and a side-ref advance moves no checkout HEAD), so the snapshot covers the ref set and reflog tips, not one pointer — and compares it at EVERY ownership transition (handoff, exit, takeover, resume): ANY commit or ref advance attributable to the executor activation FAILS the boundary and stops the loop; MISSING or unexpectedly-changed ref/reflog evidence fails CLOSED — stop and surface, never assume clean. The SAME bracket covers every OTHER non-composer activation that can reach the repository's git metadata — each default composer-seat peer spawn first among them (loop step 4; a routine write-capable activation, e.g. `codex exec -s workspace-write`): snapshot at spawn, same fail-closed compare at its exit — because the peer's `git status` escape check alone cannot see a commit-then-reset or a side-ref advance; an opt-in executor-seat peer runs inside its enclosing executor activation's bracket, needing no separate one. Every commit that lands carries a SEAT-ATTRIBUTED journal record: `OWNERSHIP: commit ts=<iso> run=<runkey> hash=<commit hash> seat=composer` (Journal line family, Visibility + run-state), TOOL-EMITTED — `python3 scripts/loop-journal.py emit OWNERSHIP:commit --run <runkey> --role composer --repo <checkout> --log <probe-log>` persists to the probe log (without `--log` the record prints to stdout, unpersisted), derives `hash=` via git rev-parse (never composer-typed; `sha=` refuses — F-23) and stamps `seat=composer` — `seat=composer` is REQUIRED, and a commit record carrying any other seat is itself a violation, not an attribution (a "paired" `seat=executor` record satisfies pairing while reproducing the breach). With `--log` the helper refuses (exit 2, nothing written) a `hash=` that log already records — the usual cause: HEAD did not move, so the commit did not happen — and `--allow-repeat-hash` skips that refusal, only when the same commit is meant to be recorded again in that log (the companion STICKY card §1 states the rule beside the recipe). Role reassignment is the one legal transition: a live session that has been acting as the executor transitions BACK to the composer seat — recording the reassignment — BEFORE any commit, which is then a composer-seat act. **UI-bearing/runnable phases add a mechanical precondition:** the phase's commit is REFUSED until that phase's `OWNERSHIP: smoke-pass` record exists — written by the composer only when the live-user-smoke pause (loop step 6) closed with the user's PASS, or, under a bound away grant (see **Away mode**), when the away live smoke passed (`smoke_by=agent`) — so `autocommit=on` can never commit UI-bearing work nobody has smoked; a refused commit surfaces the missing record, never silently skips the requirement.

When on, each per-phase commit obeys the repo Git Safety rules:
- stage ONLY that phase's files, by EXACT path — `git add -- <path> [<path> …]` — never `git add .`/`-A`/`-u` or directory/pattern adds: on a tree carrying parallel work (another run's edits, retained dirt, a multi-track working tree) anything broader sweeps foreign files into the phase commit (observed downstream),
- surface `git status` + a diff summary before committing,
- use a clear, human-sounding commit message (no AI / workflow jargon),
- and **never push** (the `/close-run` carve-out in **Run isolation (worktree-per-run)** aside).

Under `isolation=worktree`, staging and the commit run in the WORKTREE checkout on the run branch — the worktree plan copy included when the phase changed it (see **Run isolation (worktree-per-run)**) — and the branch-`main` warning below is moot there: commits land on the run branch and reach the base only via the canonical merge-back close path.

If the branch is `main`, warn that a later manual push may deploy before the user pushes.

## Coordinating with other runs

A standing prompt, not a mechanism — it applies in every loop run, before any merge or deploy (**Away mode** → Release work, item 2), and `/close-run` carries the same text:

Coordinate with other running agents. Before you merge or deploy, find out which other runs are live and whether their plans touch the same files, migrations or release lane. Where they overlap, talk to the other agent and agree who goes first. Never wait on another agent indefinitely: if you hear nothing, check the real state yourself (open PRs, running deploys) and proceed when it is clear. Write down what you agreed in the plan's handoff note, or in the run's log folder once the run has merged.

Live runs are read from the run records the way `/start-session` classifies them (the journal's state and the ownership marker), never guessed. Where the host has no way to message another session, skip the talking and check the real state. Other runs' away grants are read the same way, never guessed: the census lists every policy log on the base with its state, scope, plan, and log root (**Away mode** → Record grammar → The census) — many live runs may each hold a bound grant, and what one run's grant means for another's release is stated where it is read (Release work item 5 (b), and the pre-departure check's **Other live runs** item, where the foreign departure read is stated).
