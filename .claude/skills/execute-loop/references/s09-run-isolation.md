## Run isolation (worktree-per-run)

The canonical isolation contract — the lifecycle behind Q5's `isolation=worktree|branch|none` + `merge=auto|off` resolution and the close-table `Isolation:` line, executed at preflight sub-step 2b. Every isolation-conditional site elsewhere in this skill is a one-line pointer back here, and every one of them behaves exactly as before under `isolation=none` — the only machinery that runs on every editing mode (worktree AND `branch`/`none`) is the ownership marker below.

- **The isolation-run ID (`<iso-id>`).** Minted by the composer at wizard close for every editing run: collision-resistant and filename-safe (recommended shape: `<repo-or-plan-slug>-<YYYYMMDD-HHMMSS>-<short random suffix>`), and DISTINCT from the phase-scoped `<runkey>` (`stage-<N>` — the log prefix, which recurs across runs and can never safely key retained-by-default artifacts). The intent journal, the ownership marker, the run branch, the worktree path, and the per-run log root ALL derive from the iso-ID. The `ROLE:` `run=<runkey>` phase grammar is UNTOUCHED, and the journal records the run's phase-key family so recovery maps phase logs → the one isolation record.
- **Per-run log root (worktree runs).** Run logs stay under the BASE checkout, in the per-run LOG ROOT subdirectory `.cursor/loops/<iso-id>/`, holding the UNCHANGED per-phase names (`stage-<N>-<role>.log`, `<runkey>-probe.log`, `<runkey>-<role>-prompt.txt`). The journal records the log root, and rotation (preflight step 9), wake/probe paths (step 10 + Wake arming artifacts), and `/retro` ingestion all route through it — via ABSOLUTE paths carried in spawn prompts (loop step 1) — so two concurrent runs sharing a `stage-1` phase can never rotate, wake on, or ingest each other's files; the `[<runkey>]` chat breadcrumbs are per-composer-session and unchanged. **Worktree-local role records are census inputs (run-2 LOW-E; generalized at v31.1).** An in-executor peer round's `WATCH:`/`ROLE:` lines — and any scoped role's helper-emitted records (`DELEGATION:`/`ROLE:`/`VERIFY_OK:` and the other journal-family lines; observed live downstream) — may land in worktree-local `.cursor/loops/` files when a SCOPED role's grants deny base-side appends (its file tools reach only the worktree; the fixed peer-spawn grant list stays path-free by design — a base log-root write grant would be run-derived, breaking loop step 4's never-derived rule). Those files are part of the run's probe corpus: at that phase's exit consume the composer copies them VERBATIM into the base log root (filenames preserved; a composer-owned base-side write, like tee redirection), so `/retro` ingestion and any post-run census see those records and worktree teardown loses nothing. ONE pinned exclusion: the delegation STAGING identity `stage-<N>-delegation.<leg>.log` (Optional delegating executor's spawned-architect channel) is EXCLUDED from this generic verbatim copy — those bytes reach the canonical `<log-root>/stage-<N>-delegation.log` ONLY through the validated `fold-delegation` promotion, which runs BEFORE any generic copy at that exit consume (a verbatim-copied staging file impersonating the canonical file is the bypass this exclusion kills; a refused fold leaves the canonical destination untouched), and the generic copier keeps every other admitted local record file. Non-isolated runs keep today's flat `.cursor/loops/` paths.
- **Backend-keyed worktree location** (resolved and displayed at Q5; applied here): CLI executors (`claude -p` / `codex exec` — cwd-pinnable anywhere) → a sibling dir OUTSIDE the base checkout, default `<base-parent>/<repo>-wt/<iso-id>`; workspace-bound executors (Cursor subagent / live session — file tools confined to the workspace) → the nested gitignored `.cursor/loops/wt/<iso-id>` (legal git; the ignored container never appears in base status). A CLI executor's location is a DEFAULT, not a capability limit — a cwd-pinnable executor may use ANY writable location, the nested container included; under `cloud=on` (Q1C) the composer resolves it through the writability-probed chain sibling → `$HOME/<repo>-wt/<iso-id>` → nested, first writable wins (cloud VMs commonly mount the repo under an unwritable parent — observed live), and on any host an unwritable sibling default SHOULD offer the nested/`$HOME` fallback before the menu below. Only a backend for which ALL candidate locations are unwritable/unreachable makes worktree isolation UNAVAILABLE — Q5 then warns and requires an explicit confirm to switch backend or drop to `none`; NEVER a silent base-checkout fallback.
- **Creation order at sub-step 2b (worktree mode; pinned).** (1) Record the base baseline — base realpath, current branch, HEAD, `git status --short` — the journal's durable fields. (2) Perform the ownership claim (below; every editing mode does this much). (3) Run the PRE-CREATION SOURCE-STATE gate: classify ALL relevant NON-IGNORED base dirt, tracked AND untracked — non-plan tracked changes, OR named untracked project inputs the plan depends on, REFUSE worktree isolation unless the user explicitly chooses a safe reversible copy/snapshot of the named files into the worktree (base copies preserved; the transfer recorded in the journal) or switches modes (`none`/`branch`, with the concurrent-edit warn) — the executor never silently builds against bare HEAD while the plan's expected source state sits uncommitted base-side; ignored runtime artifacts (`.cursor/loops/` content) are NEVER swept into a transfer set; a `merge=auto` run never starts over retained base dirt that would doom the clean-base merge precondition — normalize to `merge=off` with a note, or re-ask at close; an uncommitted/untracked ACTIVE PLAN is transferred COPY-not-move (the base copy retained; the journal records the plan-sync status) — or the spawn refuses. (4) Detect collisions: the derived run-branch name and worktree path must not already exist — a true full-iso-ID collision refuses and re-mints; existing unrelated branches/worktrees are untouched. (5) Journal-before-git-mutation: write the intent journal (state `intent`) via write-then-ATOMIC-rename, THEN create the run branch + worktree (state `created`), transfer the plan copy when required, and mark `active` before the phase-1 spawn. A failure anywhere BEFORE creation completes leaves NO partial artifacts and an unchanged base — pre-journal exits are SELF-CLEANING: on every refusal path between the claim (2) and the journal rename (5) (a source-state refusal, a collision refusal) the composer removes its OWN just-created marker before returning (the ordered-write removal rule binds only from journal creation onward), so a refusal leaves zero artifacts; a pre-journal CRASH leaves at most the marker, recovered under the journal-less worktree-marker disposition (the ownership-marker bullet below). Dry-run: print the resolved actions, create nothing (sub-step 2b's dry-run branch).
- **The registry is an ATOMIC INTENT JOURNAL** — `.cursor/loops/<iso-id>-isolation` (NO `.log` suffix: deliberately outside the step-9 rotation glob), base-side, gitignored, greppable `key=value` lines carrying discovery-critical facts ONLY — paths + authority/sync status + the base baseline + state; it never re-encodes `isolation=`/`merge=` (the `Loop config:` line owns those). State field: `intent → created → active → merging → merged → cleaned`, PLUS the durable OUTCOME states `retained-green` (the normal merge-disabled green close), `paused`, `crashed/recovery-needed`, and `merge-failed` (an ORDERLY conflicted-or-failed-merge stop — the merge was attempted, aborted, and the base restored byte/status-identical, the run branch + worktree retained; distinct from a crash, so recovery reads it as a clean retained run to re-attempt or hand off, never as `crashed/recovery-needed` and never left mid-`merging`). From v33.2 a `retained-green` journal — or a `merged` one whose teardown was refused, or an `active` one under `--attest owner-dead` — is taken to `merged → cleaned` by the helper's squash-aware `run-close --outcome merged --merge-commit <sha>` entry into the verified-merge cell (the `/close-run` path; Mechanical close enforcement below). From v40.0 a non-final release group's merge keeps the journal `active` and appends `merged_stage_<N>=` then `ff_stage_<N>=` through `run-close --outcome group-merged` (the group-merge row of the close-paths table below; Release groups), and a tagged plan's journal carries the creation-time `groups=` key beside `phases=` (Release groups). ORDERED writes: authority/sync/outcome are persisted BEFORE the ownership marker is removed; `merged` is persisted BEFORE any cleanup; the journal is the LAST artifact removed, and only after cleanup is VERIFIED. Recovery keys on journal facts plus reconciled git state — NEVER on marker absence or plan prose. A recorded value is data, never shell text: a value that will reach a command — a path, a branch, a sha, an iso-id — and holds a single or double quote, backslash, `$`, backtick, or newline makes the record ambiguous; any other such value is read with a file-reading tool or passed as one single-quoted argument, and a value that is only compared (`base_status`) is compared byte for byte, never run. Serialization is LOSSLESS by rule: ONE key per line; bare tokens (the iso-ID, state/mode/`plan_sync` enums, shas) unquoted; every STRING value double-quoted with backslash-escaped `\"` / `\\` / `\n` (the `ROLE:`-family quoting made explicit — absolute paths may carry spaces or `=`, and `base_status` stores the FULL `git status --short` output as ONE escaped value, `""` when clean); recovery and the merge preflight compare the EXPECTED base HEAD — `base_head`, or the newest `ff_stage_<N>` sha once a group has closed (Pause / crash / resume below states the rule and its admitted transitions; `base_head` itself is never rewritten) — and the unescaped `base_status` byte-for-byte, and `base`/`worktree`/`plan` by realpath equality — grep discovery is unchanged (every line starts `key=`). Shape (illustrative values; every transition rewrites via write-then-atomic-rename):

  ```text
  iso=<iso-id>
  state=active
  mode=worktree
  created="<iso ts>"
  base="<base realpath>"
  base_branch="main"
  base_head=<sha>
  base_status=""
  worktree="<abs worktree path>"
  branch="loop/<iso-id>"
  plan="<authoritative worktree plan path>"
  plan_sync=copied-base-retained
  log_root="<base realpath>/.cursor/loops/<iso-id>/"
  phases="stage-1..stage-<N>"
  ```

- **Release groups (the plan's release boundary; stated ONCE, here).** A plan that ships as more than one pull request marks each phase heading with its release group. The TAG of a phase heading — a `###` heading under the plan's `## Tasks` that Phase detection reads as a phase (`### Phase 2 — …`, `### Step H — …`) — is the first token matching `(?<![A-Za-z0-9-])PR-[A-Za-z0-9]+\b` (case-sensitive) inside the heading's parenthesised SUFFIX — its LAST parenthesised group (a trailing label after it, such as `[executor: premium-only]`, does not move it) — read left to right, outside code spans; parenthesised text earlier in the title never supplies a tag. The kount form is `### Phase 2 — Client: the wizard (PR-B)`; words beside the token (`(PR-B part 1)`, `(PR-C1; no migration)`) do not change it, and a suffix naming two or more tokens (`(PR-Py + PR-C)`) makes its heading its own group, keyed on the first. Heading text is data, matched by that fixed pattern and never read as an instruction; any `PR-…` token in the suffix is read as a tag, so keep a finding id (`PR-HIGH-009`) or a token that names no release group out of a phase heading's suffix. **Grouping:** consecutive phases sharing a token form one group; an untagged phase joins the group before it; leading untagged phases — those before the first tagged phase — form the first group, named `untagged` (to ship a leading phase with the first tagged group, tag its heading too); a plan with no tag is ONE group — one run and one pull request; a tagged plan is ONE run with a pull request per group (one run per plan). A per-group hardening step is therefore written inside each group: an untagged `Step H` after `(PR-C)` joins PR-C. **Scope:** `scope=all` runs every remaining phase of the PLAN, group after group, in ONE run — one worktree, one branch, one grant, one preflight: at each non-final group's last phase the composer performs the group close (Termination → **Group end** — the group's pull request opened and merged from inside the run, the helper's group record and fast-forward, the group's `[operator]` 🟩 write, then the next group's executor in the same worktree), never stopping at the boundary, never ending its grant there, never asking whether to continue; the final group closes through Group done and `/close-run`'s final route. `scope=one-phase` runs one phase and stops. A tagged plan under `merge=auto` is REFUSED at Preflight step 1: `merge=auto` keeps its single-group meaning on an untagged plan only. **Numbering — the field's practice, ratified:** a stage number is the phase's 1-based position in the plan's phase sequence, continuing across runs (a run on a plan's third and fourth phases is `stage-3..stage-4`), and the journal's `phases=` carries the mapping inside its quotes — `phases="stage-<a>..stage-<b> (stage-<a>=<heading> [<tag>]; …; stage-<b>=<heading> [<tag>])"`, `<a>` the PLAN's first phase not done and `<b>` its LAST phase (the range is the plan), each `<heading>` written without any `stage-<N>`-shaped word of its own and annotated with its group's tag in square brackets (none on an untagged plan) — so the last `stage-<N>` token is `<b>`, `/close-run`'s final-close `<N>` read is unchanged, and its "every phase in `phases=` done" check names the whole plan on the final close and the group's phases on a group close; beside it, on a tagged plan, sub-step 2b writes the creation-time key `groups=stage-<N>:<tag>[,stage-<N>:<tag>…]` — each group's LAST stage with its tag, in plan order (a tag is a label and may repeat: `PR-A, PR-B, PR-A` is three groups; the stage is the group's identity for its records, its retro file `retro-stage-<N>-<date>.md`, its probe log, and `/close-run --group stage-<N>`), validated at Preflight step 1 — strictly increasing, each a phase's last stage, the last equal to `phases=`'s last stage; absent on an untagged plan — and read by the helper's `--run stage-<N>` checks (`group-not-in-journal`, `group-is-final`); the `<runkey>` stays `stage-<N>`. Preflight step 1 prints every group with its headings, the current one marked (on a resume, the closed ones counted from the journal's `merged_stage_<N>` keys), so a mis-grouped plan is seen before any spawn; Phase detection's split phases inherit their source heading's tag. **Provenance (stated ONCE, here; read by the foreign-merge check, Release work item 5).** A non-final group's close appends `merged_stage_<N>="<ts> <merge sha> <tag>"` and then `ff_stage_<N>="<ts> <sha>"` to the journal (the state stays `active`; the keys are distinct per group by construction and survive the final `merged=` write): the first group's baseline is the journal's `base_head`; group k+1's baseline is the `ff_stage` sha of group k — the fetched base both checkouts took after group k's merge, other runs' merged work included; a closed group's own commits are `rev-list --first-parent <its merged_stage sha>^2 ^<its baseline>`, the current group's `rev-list --first-parent <run tip> ^<its baseline>` — FIRST-PARENT within every slice, so a merge-forward's second parent (the base merged into the run branch to repair a conflicting pull request) never qualifies; the run's own-run set is the union of those slices plus its own merge commits, and a commit imported by a fast-forward or by a merge-forward is another run's work, whether its group is current or closed. **A done phase (stated ONCE, here).** A phase is done when every task that is not 🟩 is an `[operator]` task — read from the plan copy's task markers alone; the dispositions (item 2 of the departure file under a grant, the handoff note's Open blockers attended — **Away mode**) are the composer's record, never this test's input. A phase made only of `[operator]` tasks is therefore done before any run visits it — nothing in it is buildable and its acts are the release work's; a release group made only of them is a plan error (the template's Tasks legend). The helper records a non-final group's merge as `cell=group-merge` and the fast-forward of the base and the worktree that follows it as `cell=group-ff` (`run-close --outcome group-merged`).
- **Phase-range extension (`phases=` currency).** The journal's `phases=` field is the run's SOLE phase-range authority and must stay CURRENT — from v40.0 the range is the PLAN (every phase not done, every release group — Release groups above), so an extension is only ever a phase ADDED to the plan mid-run: approving such a phase (extending beyond the recorded range — a target that is not a phase of the plan is refused; an added phase joins the group its heading's tag names) atomically rewrites the journal's `phases=` field ONLY — and the `groups=` key beside it in the same write when the added phase moves a group's last stage — the same write-then-atomic-rename, every other field byte-preserved — BEFORE the first newly-added phase's executor spawn, AND appends one `OWNERSHIP:`-family record naming the old→new range to the CURRENT phase's `<runkey>-probe.log` — the newest probe log in the run's log root; the extension happens before the added phase's log exists (journal-family grammar, Visibility + run-state — e.g. `OWNERSHIP: phases-extended ts=<iso> run=<runkey> from="stage-1..stage-5" to="stage-1..stage-9"`), so the extension is verifiable from the log stream without diffing journal rewrites (a run extended stage-5→stage-9 with the journal still advertising the original range, observed live — the extension was verifiable only externally). The `-active` ownership marker stays ownership/liveness-only and never carries a phase key; `branch`/`none` runs have no journal and gain no new field.
- **The ownership marker (every editing mode — worktree AND `branch`/`none`).** `.cursor/loops/<iso-id>-active`, base-side, gitignored: iso-ID, mode, checkout realpath, created-at, plus a backend-shaped liveness identity keyed to the RUN-LIFETIME OWNER — the composer/orchestrating session that holds the claim across phases (agent/session/watch identity; where the owner is itself one real dedicated process, its PID + executable/start identity) — with the current per-phase executor's PID at most an OPTIONAL, per-spawn-refreshed SECONDARY field: per-phase executors are discarded at every phase boundary, so a dead child PID is never staleness evidence against a live run. Acquisition is a serialized checkout-scoped claim whose rescan GATES activation: create THIS run's marker, then atomically rescan for other markers claiming the same checkout — a run that scans CLEAN (its own marker the only claim) proceeds unconfirmed; a run that SEES ANY contender, whenever the contender appeared, NEVER proceeds unconfirmed — it surfaces the collision for an explicit user confirm or refusal (headless: MUST-PAUSE record-and-end) — so AT MOST ONE run, the clean-scanning first claimant, ever becomes an unconfirmed editor. The deterministic iso-ID tie-break (lowest byte-order) ORDERS the surfaced arbitration only — it names the presumptive owner presented at the confirm — and never licenses a contender-observing run to proceed on its own. Stale-marker reconciliation is CONSERVATIVE: unknown liveness ⇒ warn/refuse, never delete-as-stale by guess. The marker is removed on close — for worktree runs only AFTER the journal's authority/sync/outcome write (the ordered-write rule); on crash it is reconciled, never blindly deleted. A journal-less marker recording `mode=worktree` marks the PRE-JOURNAL crash window (the claim-to-journal-rename gap at sub-step 2b — no journal, run branch, or worktree exists yet) and its disposition is TOTAL: validate the recorded run-lifetime owner exactly as above — live or unknown liveness ⇒ retain + warn/refuse; a conclusively-dead owner with ZERO matching git/isolation artifacts (no journal, no run branch, no worktree at the iso-ID's derived names) ⇒ remove ONLY the ownership-proven marker, base untouched; ANY matching artifact found ⇒ retain + surface (the journal contract owns recovery from there). The `branch`/`none` concurrent-edit warn (Q5) keys on THESE markers — never on broad `pgrep` sweeps or stale log prefixes.
- **Authority + the per-close-path outcomes (stated ONCE — here).** The WORKTREE plan copy is AUTHORITATIVE from spawn: run-state + `Loop config:` writes target it from creation onward, composer git duties and fallbacks (peer, verification, smoke, `/document`) run against the worktree, and the escape baseline splits per preflight step 8. Close paths — every termination resolves through exactly one row:
  - **Verified merge-back** (green close — the Phases-done termination — with `merge=auto`) → the BASE becomes authoritative again; cleanup may proceed (worktree removed, run branch deleted, journal → `cleaned` only after verification). The SAME cell is entered later by `/close-run` — the squash-verified transition `retained-green | merged (re-entry) | active (attested owner-dead) → merged → cleaned` via the helper's `--merge-commit <sha>` path: `<sha>` reachable from the fetched remote base (the local ref only where no remote ref exists), the tip an ancestor of that base (fast path) or `git merge-tree --write-tree <sha>^1 <tip>` == `<sha>^{tree}`, then `merged="<ts> <sha>"` written and the teardown entered. Either entry then releases the run's router bindings when `claude-switch-route` resolves (the router release, Mechanical close enforcement below).
  - **Green close, merge disabled** (`merge=off`) → RETAIN worktree + branch + journal (state `retained-green`); the worktree plan stays authoritative; the handoff states the continuation — normally `/close-run` (the records commit → ONE pull request or the `--no-pr` local ff-only close → the helper's squash-verified `merged → cleaned` teardown), run next by the operator or by an agent acting on the operator's request — or, under a bound away grant with `merge` in scope, by the composer itself (**Away mode** → Release work).
  - **A non-final group's merge** (the group close, inside a live run; Termination → Group end) → the helper's `run-close --run stage-<N> --outcome group-merged --merge-commit <sha>` (Mechanical close enforcement below): the journal STAYS `active` with `merged_stage_<N>="<ts> <sha> <tag>"` appended, then `ff_stage_<N>="<ts> <sha>"` once its fast-forward leg has moved the base checkout and the worktree to the one fetched sha of `origin/<base-branch>`; NO teardown — the worktree, the run branch, and the journal continue into the next group, and the final group closes through the verified merge-back row above.
  - **Pause / crash / resume** → worktree authority is KEPT under the journal contract (`paused` / `crashed/recovery-needed`); any resume reconciles the journal against `git worktree list`, refs, the recorded base state, and any extant close lock (the close-lock recovery rule below) BEFORE any merge, authority switch, or deletion; ambiguity retains ALL artifacts and stops without touching the base. **The expected base HEAD (stated ONCE, here).** The recorded-base comparison every reader makes — this rule, the journal contract above, and the Resume contract (Visibility + run-state) — is against the EXPECTED base HEAD: the newest `ff_stage_<N>` sha when one exists, else the immutable `base_head` (never rewritten — it stays the first group's provenance baseline, Release groups above), compared byte for byte as `base_head` always was; two transitions are admitted beyond equality: (i) a base HEAD that is a descendant of the expected sha and an ancestor-or-equal of `origin/<base-branch>` while a `merged_stage_<N>` has no `ff_stage_<N>` — the interruption between the helper's base advance and its key, which the replayed helper call completes; (ii) on the FINAL routes, where the close still advances the base by hand (`/close-run` Flow 1 step 6, Flow 2, Flow 3), with every non-final group's `ff_stage` present and the journal `retained-green`, `merging`, or carrying `merged=` — or `active` on ONE route only: `/close-run`'s owner-dead admission under the OPERATOR's `--attest owner-dead`, supplied on the `/close-run --iso <iso-id>` re-entry that finishes the interrupted close, never this contract's own finding — a base HEAD that is, on a PR-backed close, the final pull request's `mergeCommit` or its descendant up to `origin/<base-branch>`; on an ancestry-only shipped-tip close, a descendant-or-equal of the run tip and an ancestor-or-equal of `origin/<base-branch>`; on the attended `--no-pr` local close, equal to the run tip before its push and as the ancestry-only case after it — each bound to the journal's recorded branch and tip. An `active` journal whose base moved is UNEXPLAINED movement for this contract: retain everything, stop, and surface — naming that attested re-entry as the one legal finisher when every phase is done and every non-final `ff_stage` is present; any other movement, or a dirty base, keeps the conservative route (retain everything, stop, touch nothing). **The group tail's first-incomplete-step contract (stated ONCE, here).** A resume inside a group close (Termination → Group end) reads its position from the journal's keys and the probe log's records, never from git state alone, and resumes at the FIRST incomplete step, repeating no irreversible act and skipping no required one: (1) the group record — `merged_stage_<N>` with its `cell=group-merge` record; a key without its record is replayed through the same helper call, its `--merge-commit` the sha the key stores (a matching sha and tag → `already-closed`, the record written; a disagreeing one → `group-identity-mismatch`, nothing written); (2) the fast-forward — `ff_stage_<N>`; absent with the group key present → the replayed helper call runs the fast-forward leg alone (the worktree's HEAD is never the test — the bookkeeping commit moves it; the base's HEAD is read against the expected sha above); on the grant-bearing route (the close's helper call carried `--grant <n> --away-check <config_hash>`, Mechanical close enforcement below) this step is complete only together with the matching `rebaselined` record in the stage probe log — `key=stage-<N>-set-refresh choice=rebaselined`, the same away pair, `to=` the sha `merged_stage_<N>` stores — the group's MERGE commit, never `ff_stage_<N>`'s fetched tip, which may lie past it (Mechanical close enforcement → The re-baseline; **Away mode** → Records → A re-baseline) — so a present `ff_stage_<N>` without that record resumes at the flagged helper call BEFORE Release work, whose already-closed branch appends the one missing record and nothing else (the idempotent repair; never a second record); a flag-less close keeps the v40.0 reading — the key alone — and nothing here is a requirement on an attended or historical close; (3) Release work items 4–6 — the probe log's release `start` / outcome records (an unresolved `start` is reconciled from the real state as **Away mode** → Ending the grant → Widening (1) settles it, never re-fired); (4) the 🟩 write and its bookkeeping commit — the worktree plan copy's group `[operator]` tasks 🟩 AND a clean worktree (dirty with only the plan copy changed → commit it; not yet 🟩 → write, then commit); (5) the spawn — the next stage's `ROLE: start` record. Before the group record: the group's pull request open → `/close-run` Step 3's open-PR path on the group route (`--group stage-<N>`); found CLOSED without merging → `/close-run` Step 3's disposition, never a silent re-open.
  - **Pre-creation failure** → NO partial artifacts; unchanged base.
  - **Any non-green close** → the worktree + branch are RETAINED, recoverable — never auto-cleaned.
- **Merge-back preconditions (`merge=auto`; composer-run; LOCAL only).** Merge the run branch into the base branch ONLY under the BASE-SCOPED CLOSE LOCK and ONLY against a CLEAN, UNMOVED base. The close lock — `.cursor/loops/close.lock` in the base checkout, taken by atomic create with write-then-atomic-rename content naming the holder's iso-ID + created-at — is acquired FIRST, and the clean/unmoved predicate is RE-READ under it: base status clean AND base HEAD still at the journal's recorded baseline, verified POST-acquisition (any pre-lock check is advisory — the predicate and the merge must be inseparable, or two green runs can both pass at the same HEAD and the second merges onto a moved base). The lock is held through the journal's `merging` write, the local merge, verification, the `merged` + authority persistence, and the cleanup decision, then released. A CONTENDED or ambiguously-stale close lock RETAINS the run's artifacts and STOPS without touching the base — stale-lock reconciliation is CONSERVATIVE, keyed on the named holder's journal/marker, never delete-by-guess (the marker rule). A post-lock predicate failure (moved or dirty base) likewise retains the run branch and STOPS — never an opportunistic merge onto the new HEAD. CLOSE-LOCK RECOVERY (a fresh session finding an extant `close.lock`; the disposition is TOTAL): validate the recorded holder FIRST via its named iso-ID's journal + ownership marker — (a) the holder is THIS resuming run (same iso-ID, live owner) → ADOPT the own lock and continue from the journal's state; (b) the holder is PROVABLY DEAD (its run-lifetime owner conclusively gone) → reconcile under an exclusive recovery acquisition against journal + base + run-branch state: a pre-merge journal state with the base unchanged → RELEASE the lock safely (a later close reacquires); journal `merging` with the merge NOT STARTED — base HEAD/status still byte-matching the recorded clean baseline AND no git merge metadata/index residue present → classify NOT-STARTED and either release safely (a later close reacquires and re-runs the post-lock predicate) or continue under the exclusive recovery ownership after re-running that predicate; journal `merging` with the merge PROVABLY COMPLETE (base HEAD is the run branch's merge result and verification passes) → persist `merged` + base authority, then release; journal `merged` with only the release pending → complete the release (idempotent convergence); anything ambiguous, dirty, or genuinely mid-merge → RETAIN + STOP without touching the base; (c) unknown liveness → the conservative rule: warn/refuse, never delete. Lock removal is always OWNERSHIP-CHECKED — only the recorded holder or the exclusive recovery owner removes it, never age-based. A failed or conflicted merge is ABORTED and the base restored byte/status-identical — the base is never left mid-merge — and the journal records the `merge-failed` outcome state (the orderly-stop enum value: never left at `merging`, never mislabeled `crashed/recovery-needed`), the run branch + worktree retained for a re-attempt or handoff. Worktree, branch, and journal are retained until merge VERIFICATION passes (retention-until-verified); cleanup is IDEMPOTENT (re-running a partial cleanup converges, never errors); and merge-back NEVER pushes — push stays the user's explicit call on every path. **The ONE carve-out (stated once, HERE):** the run itself never pushes — not the merge-back, not a phase commit, not the persist-before-close commit — and `/close-run`, run after the run has closed — or, from v40.0, inside a live run at a non-final group's close (its group route, Termination → Group end) — by the operator, by an agent acting on the operator's request, or by the composer under a bound grant with `merge` in scope, is the single workflow that pushes: the run branch for its ONE pull request (from v40.0 one per release group, each through this skill's group route — Termination → Group end), or the base on `--no-pr`, each under its own confirm table — except under a bound away grant — see **Away mode**: with `merge` in scope the composer runs `/close-run`'s pull-request path itself, the grant standing in for its confirm table (never `--no-pr`); every other "never a push" sentence in this skill, the STICKY card, and the orchestration doc points here.
