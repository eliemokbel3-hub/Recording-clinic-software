This is a shared Cursor/Codex/Claude Code Skill. Invoke it as `/retro` in Cursor or Claude Code, or `$retro` in Codex.

When this Skill references another shared workflow, use the current tool's sigil: `/workflow` in Cursor, `$workflow` in Codex, and `/workflow` in Claude Code.

`/retro` is a focused, propose-only diagnostics pass: after a loop run (`/execute-loop`, `/peer-loop`, `/review-loop`, or any run that left logs in `.cursor/loops/`), it reads the run's loop logs and the governing plan's review data and writes a structured run report answering "what happened, what did it cost, what failed and why". The report is the deliverable — `/retro` NEVER edits code or skills, never applies fixes, and never appends `Review Findings Log` rounds (findings rounds are `/review`-family artifacts with round-numbering semantics that `/fix` ingests; a retro report is synthesis, not findings). Its only writes are the report file and a single pointer line in the plan's `Current State / Handoff Note`.

This workflow is propose-only and agent-invocable: it carries `disable-model-invocation: false` (Cursor + Claude Code) and NO `agents/openai.yaml` (Codex), so an agent may invoke it automatically — for example right after a loop run converges — and you can still invoke it explicitly. Because its only writes are the gitignored report and the one pointer line, agent invocation cannot mutate code, skills, or docs.

Plan files are shared across all three tools. Handoff is through disk state, the plan file, and git, not conversation memory.

## Step 0 — Locate the run and the plan

Resolve these inputs before reading anything else. Explicit user-supplied overrides — a logs directory, a plan path, a run key, an ordered phase-log list (the fourth bullet below), or the Composer-seat cost proxies' CONTEXT-half overrides: an ordered auxiliary-context file list and an optional ordered endpoint pair (the fifth bullet below) — ALWAYS win over the defaults below; they are what make sandboxed/dogfood runs possible (point `/retro` at a snapshot directory and a plan copy, and every write confines itself there).

- **Logs directory:** default `.cursor/loops/` in the current repo.
- **Run key:** default = the `stage-<N>` log-file prefix present in the resolved logs directory (e.g. `stage-4` from `stage-4-executor.log`). If several prefixes exist, prefer the most recently modified; if none exist, fall back to the governing plan's feature name.
- **Governing plan:** find the plan in `.cursor/plans/` (excluding `completed/`) that the run built — on ambiguity prefer the most recent `Last plan sync`; if still ambiguous, ask the user which plan governs the run.
- **Ordered phase-log list (optional — the proxy-count corpus override, v32.5):** an explicit ordered list of probe-log files supplied at invocation, feeding ONLY the Composer-seat cost proxies' COUNT corpus on flat runs (Step 2's membership route (ii)). Scope guard: it never replaces the logs-directory / run-key / plan resolution above — those still drive every other input, including Step 1's per-role tee-log context scan — and it never alters ordinary single-run retro selection. Precedence: when supplied, the list IS the count-corpus membership (no discovery); when absent, Step 2's routes (i)/(iii) apply unchanged. Fail-closed validation at resolve time: every entry must be an authoritative-class filename (unsuffixed `stage-<N>-probe.log`) — a rotation-suffixed or out-of-class entry invalidates the list and the derivation falls to route (iii)'s PARTIAL with the gap named; two entries for one phase/`run=` key are the constructible duplicate-membership ambiguity — rule (iv)'s PARTIAL, never a sum. The report's disclosed count-source list preserves this list's order exactly, so corpus membership and order reconstruct from the report alone.
- **Group scope (optional — v40.0; defined ONCE here, applied at every input boundary below):** an explicit release-group selection — the stages of ONE release group, `stage-<a>..stage-<N>` with `<N>` the group's last stage (the run key the report is named by) — passed by the composer at a group close (`/execute-loop` → Termination → Group end; the journal's `groups=` key names each group's last stage). Under a group scope every input is bounded to the group: the authoritative probe corpus (Step 2's membership route (i) — the unsuffixed `stage-<N>-probe.log` class filtered to the scoped stages), the auxiliary tee-log context (Step 1's scan — the scoped stages' tee logs only), and the review rounds (Step 1 — a round belongs to the group whose phase it closed: the rounds the scoped stages' executors and peers ran, read from the round's position between the group's first `ROLE: start` and its last `ROLE: end`; plan peer-review rounds and run-wide records — a departure, a grant, a resume — are labelled SHARED context and listed among the disclosed sources, never counted as the group's work). The report is `retro-stage-<N>-<date>.md` (Step 3) and its `Run identity` names the selection, so a multi-group run's log root holds one report per group with no double counting. Absent, the whole run is read as today.
- **Ordered auxiliary-context file list + endpoint pair (both optional — the proxies' CONTEXT-corpus overrides, v32.5):** an explicit ORDERED list of per-role tee-log files for pool/usage CONTEXT only, plus an optional ordered endpoint PAIR (two checkpoint identifiers — file + in-file occurrence position or timestamp — start not after end). Scope guard: CONTEXT half only — these inputs never feed the proxy-count corpus, never replace the logs-directory / run-key / plan resolution above, and never alter Step 1's general tee scan. Precedence: on a FLAT run the supplied list IS the auxiliary membership (no discovery — Step 2's flat-run rule requires it; absent ⇒ every pool/usage context field is a named evidence gap); on an ISOLATED run the iso-root membership applies and a supplied list narrows it. Fail-closed validation, per entry: a path outside the resolved logs root / iso root, a duplicate entry, or an unreadable file turns THAT entry's dependent context fields into named gaps (never the counts, never the whole report); an endpoint pair that does not resolve to two parseable checkpoints in order gaps the delta fields alone. Traversal order (the TOTAL ordering Step 2's first/last rule uses): checkpoints are ordered by the supplied LIST order, then by position within each file — "first" = the first parseable checkpoint of the earliest listed file that has one, "last" = the last parseable checkpoint of the latest listed file that has one. The report's disclosed auxiliary-source list preserves the supplied order exactly and each delta names its endpoint pair, so every context value reconstructs from the report alone.

Degradations, flagged in the report rather than guessed around:
- **No loop logs** (the logs directory is missing, empty, or has no matching files) → produce a **plan-only report** from the plan's `Review History` / `Review Findings Log`, and flag prominently that no log evidence was available.
- **No plan** → produce a conversation-only summary in the chat and make **NO writes at all** (no report file, no pointer).

## Step 1 — Ingest the evidence

From the resolved logs directory:
- parse **`ROLE:` lines** (`start` / `end` pairs, per-round `round` lines, and `handoff` exit sentinels) — the key=value convention defined canonically in `/execute-loop`'s Visibility + run-state section: role, backend, model, timestamps, and any best-effort usage fields (`turns≈` / `tokens≈` / duration) — and, on a peer `ROLE: start`, the `via=launcher` mark the shipped codex peer launcher puts on every start it writes (v34.1: such a leg's end is the launcher's too and carries `duration=`, and the leg's verdict sits on its `CONSUME: … leg=<leg> result=` record, not on the end). **Who wrote a leg's end, and what its duration is (v48.0).** From v48.0 a wrapper-spawned leg's end is the spawn wrapper's too: it writes the `ROLE: end` when the role exits, before its `EXIT:` footer, with a mechanical `result=` — `exit <code>; handoff`, or `incomplete: exit <code>; handoff|no handoff` — and `duration=<whole seconds>`, the key the launcher's end carries. Such a leg's duration is that key (or the end's `ts=` minus the start's), and the composer's verdict for the leg is on its `CONSUME:` record, not on the end. An end for such a leg that is NOT in that form is the composer's clean close — written where the wrapper wrote none, and admitted by the helper only once the role read over or the operator attested it; its `result=` is the composer's text, naming `owner-dead` where the operator attested the role dead and otherwise saying why the wrapper's end is missing (the wrapper did not finish, or its end was refused). A clean close ends the leg and measures nothing: report that leg's duration as "not exposed" and name the leg. A run from before v48.0 — no wrapper-spawned leg's end is in that form, and its log folder holds no `<leg>.live` / `<leg>.exit` file — keeps composer-written ends on every wrapper-spawned leg: the end's `ts=` is when the composer wrote it — its consume time, unless the record also carries `logged_ts=` — so a start-to-end difference there includes the composer's delay, and the report says so beside any such duration. Timestamp trust follows that canonical definition: the `start`/`end` `ts=` values the composer writes — and those the helper stamps on a wrapper- or launcher-written start or end at the moment it is written — are the run's ordering truth; a role's self-written `ROLE: handoff` `ts=` is ADVISORY — headless sessions emit junk wall-clock (observed live: placeholder midnight timestamps) — so treat it as approximate, never as ordering evidence.
- parse **`DELEGATION:` lines** (`decision` / `outcome` / `roi` / `smoke-addendum` variants) — same key=value family: unit, spec one-liner, delegate backend/model, diff-vs-spec result, misses, smoke results, ROI observations.
- scan the **per-role tee logs** (`<runkey>-<role>*.log`) for hard evidence worth citing: verification failures, gate pauses, filesystem-escape checks, smoke results — under a group scope (Step 0) the scoped stages' tee logs only; a same-root tee log of another group is shared context, listed, never cited as the group's. (Flat-root caveat: phase runkeys recur across runs in a shared `.cursor/loops/` root, so a same-prefix tee log may belong to a PRIOR run — cite tee evidence with that caution; the Composer-seat cost proxies' auxiliary-context corpus in Step 2 uses its own deterministic membership rule, never this discovery scan.)

From the governing plan:
- parse **`Review History`** lines — under a group scope (Step 0) only the rounds that belong to the group (the rounds its stages' executors and peers ran); the rest are shared context, labelled so — the `X CRIT / X HIGH / X MED / X LOW` counts, `skew=`, and `action=` fields, using `/review`'s vocabulary verbatim (`skew` ∈ none / pre-existing / fix-induced / same-family / mixed; `action` ∈ none / escalate / strengthen-siblings / triage-and-ship). Do not invent a parallel taxonomy.
- parse **`Review Findings Log`** rounds — under a group scope (Step 0) the group's rounds alone are the group's work, plan peer-review rounds and run-wide records labelled SHARED and listed in the disclosed sources — `Source:` (which tool/family produced the round; a `Source:` ending in `plan peer-review` marks a PLAN peer-review round — label it plan-scoped in the round story, never as a code-review round), per-finding severities, `Triage:`, `/fix decision:`, and any scope-expansion or Deferral Confirmation Gate dispositions — and, on plan-peer rounds, the per-finding `Materiality:` labels and the round summary's verified counts (`Materiality: X build-affecting / Y record-only / Z invalid`; the enum is canonical in `/peer-review`'s plan-review mode). A compacted round appears as its digest (header, status, `Source:`, any `Materiality:` summary line, one line per finding) with a `Compacted … → findings-[feature].md` marker line — read the named sidecar for the full blocks; a missing or partial sidecar is an evidence gap to flag (fail closed), never "no findings".

**`ROLE:`-less logs are normal** — every log written before the convention existed has none. Infer role identity from `DELEGATION:` fields (`delegate=`, backend/model values), log filenames (`stage-<N>-<role>*.log`), and plan prose — and mark EVERY inferred identity as *(inferred)* in the report. Never present an inference as a logged fact.

## Step 2 — Synthesize

Build the run story from the evidence:

- **Rounds and findings by skew class** — how many review/peer rounds ran, finding counts per round, and the failure classes: fix-induced regressions vs same-family siblings vs pre-existing surfacing vs genuinely new. Where did the rounds go — which loop (review vs peer), and which model family caught what (same-family vs cross-family catches).
- **Per-role identity and usage** — a table of roles (composer / executor / architect / delegate / peer / advisor) with backend, model, activation count, and whatever usage evidence exists: `turns≈` / `tokens≈` / durations from `ROLE:` end lines or CLI output, timestamps otherwise (a leg's duration by Step 1's rule — who wrote the end decides what it measures, v48.0). Where a backend exposes nothing, state **"not exposed"** — never estimate or fabricate a number. The delegate row's Effort (v43.0) is the `Loop config:` `delegate=` group's `effort=` — `inherit` → `inherit (<architect effort>)` — labelled the LATEST configured value (the `Loop config:` rule below: the line holds only the latest values); when the run's records carry an `OWNERSHIP: config-change key=delegate.effort` the row shows the change history (`<old> → <new>` at the record's timestamp; an earlier value no record names → `unknown`), never the final value as the whole run's; a `delegate=` group with no `effort=` at all is a pre-v43.0 line — show `inherit (<architect effort>)` and say the key was unrecorded. Cost-attribution caveats — apply them explicitly whenever citing cost or usage numbers: per-invocation figures (`total_cost_usd`, token counts printed by a spawned CLI session) are per-session and CUMULATIVE across resumes — every `"type":"result"` line a resumed `claude -p` session prints carries the session's running total, so take the LAST result per session (or per-leg deltas between consecutive totals), never the sum over resumes (v42.0; `docs/lessons.md` → "A resumed `claude -p` session's `total_cost_usd` is cumulative"); distinct sessions sum as usual, and those last-per-session figures are the trustworthy per-run numbers; account-pool percentages (`/usage` headlines, usage-checkpoint lines in the logs) are ACCOUNT-GLOBAL — concurrent runs on other repos/devices share the pool — so cite them as context only, NEVER attributed to a single run; and `total_cost_usd` is API-equivalent pricing, not actual subscription draw — comparable between runs, not a bill.
- **Composer-seat cost proxies (v32.5 — the composer-cost measurement baseline)** — log-derivable counts of the composer seat's recurring work, derived under a MECHANICALLY-resolvable evidence boundary, never guessed from timestamps or feature prose; report-file-only (the closed journal family gains nothing, and `/retro` stays propose-only). **Corpus membership (canonical):** the authoritative filename class is the UNSUFFIXED `stage-<N>-probe.log` — exact class: rotation-suffixed siblings (e.g. `stage-0-probe.log.20260811-1340`) are EXCLUDED on both routes, and other `*probe*` names are outside the class (live log roots carry both shapes, so an unqualified "every probe log" rule double-counts a phase). Membership routes: (i) an ISOLATED run's corpus is every authoritative-class phase log under its iso-scoped root (`.cursor/loops/<iso-id>/`) — under a group scope (Step 0), those of the scoped stages only, the other groups' logs excluded from every counter (a multi-group root is per-group disjoint by stage, so the group roll-up is a sum over its own stages and never double-counts another group's); (ii) a FLAT run (`isolation=none`/`branch` — the shared `.cursor/loops/` root holds unsuffixed phase logs from MULTIPLE runs) requires the EXPLICIT ordered phase-log list defined in Step 0's override contract (the fourth Step 0 bullet — its fail-closed validation, scope guard, and disclosure-order rule bind here); (iii) absent both — flat directory, no explicit list — keep Step 0's default single-resolved-prefix behaviour and label the proxies block PARTIAL, naming the one phase covered, never whole-run totals; (iv) ANY ambiguity — a phase whose only probe log is rotation-suffixed, or duplicate candidate members for one phase (constructible only via an explicit list naming two files for the same phase/`run=` key; an excluded rotation sibling beside a present authoritative file is NOT ambiguity) — fails down to PARTIAL with the gap named, never a sum over an unresolved corpus. **Corpus split:** proxy COUNTS derive from the probe logs ONLY (structured records — per-role tee logs carry quoted-grammar echoes that false-positive line counts); pool/usage CONTEXT may additionally draw from an ENUMERATED per-role tee-log list, disclosed separately with per-claim provenance — under DETERMINISTIC membership (v32.5): on an ISOLATED run, the tee logs under the run's iso-scoped root; on a FLAT run, the ordered auxiliary-context file list defined in Step 0's override contract (the fifth Step 0 bullet — its scope guard, per-entry fail-closed validation, and disclosure rule bind here; same-prefix tee files from prior runs are indistinguishable by name in a shared root, so discovery is never used there) — absent that list, every pool/usage context field is a named evidence gap. Each per-pool DELTA binds to ONE deterministic ordered observation pair: the first and last parseable usage checkpoints under Step 0's TOTAL traversal order (supplied list order, then in-file position) for the covered phases, unless the Step 0 endpoint-pair override supplies them; unresolved membership or endpoints gap that context field ALONE. A context field whose source file is absent becomes that field's named evidence gap — counts unchanged in every case. **Metric dictionary (exact line-start predicates over the count corpus — the PREFIX-FAMILY counters are mutually disjoint, with TWO named exceptions, each a projection and never an additive category: *peer rounds* is a SUBSET projection of *role activations*, and (v33.4) *suppressed non-limit rate-limit wakes* is a VALUE-SUM projection over the `OWNERSHIP: exit-census` records already counted under *journal emissions*; canonical prefixes are not journal types):** *role activations* = `ROLE: start` line count (peer starts INCLUDED), with unmatched start/end pairs reported as an integrity note beside the count, never silently merged; *WATCH arms* = `WATCH: armed` lines; *monitor returns* = `MONITOR:` lines; *journal emissions* = the colon-terminated journal-family line-starts (CONSUME / CLASSIFY / ADOPT / KILL_DUP / OWNERSHIP / VERIFY_OK / VERIFY_FAIL / SENTINEL_ARMED / SENTINEL_FIRE / SPAWN / IDENTITY / NOTIFY), with the two wrapper-native tee shapes (`EXIT:<code>`, `SPAWN_WRAPPER_START`) reported as their own line, never folded in; *peer rounds* = `ROLE: start` lines with `role=peer` — a PROJECTION of the activation count: report it beside, never sum it with, *role activations* (the SOLE authority — log-derived; disagreement with the plan's `Review History` is noted as context, never reconciled by picking); *suppressed non-limit rate-limit wakes* (v33.4) = Σ of the integer `rl_suppressed=<n>` values over `OWNERSHIP: exit-census` lines — the spawn wrapper's per-leg count of the `allowed` / `allowed_warning` `rate_limit_event` lines it rewrote to `USAGE_TICK …` on the composer-facing mirror, each an event-shaped Layer-1 anchor match the mirror no longer carries — a VALUE-SUM, not a line count, and the SECOND named projection: the records it reads are already counted once under *journal emissions*, so report it beside, never sum it with, *journal emissions*; derived per phase and run-level like every other counter; a leg whose exit-census record lacks the key (a v33.3-or-older wrapper, a pump that did not exit clean, an unpublished count) — or that wrote no exit-census record at all — is reported as **"not measured"** with the leg named, NEVER summed as 0, and a total over a mix of measured and unmeasured legs is labeled with the measured-leg count it covers; malformed lines or lines missing required keys are counted as raw line-starts AND flagged as an evidence gap, never silently normalized. **Roll-up:** counts derive per phase (per `run=` key) and roll up into ONE run-level block with per-phase sub-lines and BOTH disclosed source lists (the count corpus; the auxiliary context files) — authoritative-class probe logs are per-phase disjoint append logs, so the roll-up is a sum with no cross-file dedup; any subset-of-run derivation is PARTIAL, labeled with the phases covered. **Pool deltas are CONTEXT ONLY** — cited per-pool, only where probe/checkpoint evidence exists in the run's own logs, under the account-global cost-attribution caveat above (the composer's own pool appears only when its account was probed and teed; absence is a NAMED evidence gap, never an estimate). **Evidence-gap statement (always present):** name what the logs cannot show — chat turn counts, STICKY re-read volume, and the phase-close `PROGRESS` lines (v33.0 D10: chat-only by design — no probe-log line, no NOTIFY record) are not log-derivable; and (v33.4) the *suppressed non-limit rate-limit wakes* row measures the wrapper's stdout mirror ONLY: Claude Code Layer-2 wakes — the monitor subagent's returns and a harness-native watch tool's events — read the role log or another surface and are not suppressed, so the row says nothing about them.
- **Per-peer-model block (v33.0 D14 — derived from the count corpus + the plan's review data, keyed by the peer `ROLE: start`'s `backend=`/`model=`; one sub-block per distinct peer model):** rounds (peer `ROLE: start` lines for that model), findings per round (the matching `### Round N` blocks' finding counts), LEG-1 upheld / downgraded / invalid (the verified tuples' verified-vs-original labels — `invalid` counted from the verified materiality), HIGH per round, zero-finding-round share, same-family share (`skew=same-family` on the round's `Review History` line), tokens per round MEDIAN (from the peer CLI's own printed per-session totals in the enumerated auxiliary tee logs ONLY — `not exposed` where a backend prints none; never an estimate — and from v47.0, for a codex round run through the peer launcher, from the `tokens=` line of that leg's identity file in the run's log folder (the file the launch named as `LOOP_IDENTITY_FILE`): `tokens=<digits>` is the total codex printed for that leg, read from the bytes that leg appended to the peer log; `tokens=unknown`, or no `tokens=` line at all — a leg from before v47.0, or an identity file the composer closed itself after the launcher died — is `not exposed`; it is a reading of what codex printed, not a measurement), wall minutes per round (start/end `ts=` deltas; on a launcher leg — a start carrying `via=launcher` — and, from v48.0, on a wrapper-spawned peer leg, the end's `duration=` when the end carries it, else the timestamp difference; Step 1's rule covers a clean close and a run from before v48.0), and quota/auth deaths (peer activations whose `ROLE: end result=` names a usage limit or auth failure; on a launcher leg the verdict — quota and auth deaths included — is read from the leg's `CONSUME: … leg=<leg> result=` record instead, because the launcher's end holds machine facts only; from v48.0 the same holds for a wrapper-spawned peer leg, whose end says only `exit <code>` and `handoff` or `no handoff` — read the `CONSUME:` record that follows that end, by its `leg=` where it carries one). A model whose rounds carry no verified tuples reports its LEG-1 cells as a named gap, never zeros.
- **Per-pass block (v33.0 D14 — derived from the D3 keys on the count corpus):** rounds per pass (peer `ROLE: start` lines grouped by `pass=`; the highest `peer_round=` per pass), raises per pass (`cap-raise=+1` auto-dispositions carrying that `pass=`), verdict counts (`cap-accept=close` with and without `residue=deferred`, `cap-raise=+1`, and surfaced caps — `must-pause` owners on cap keys — per pass), `attributed=` escape records per run (every `OWNERSHIP: escape-check … attributed=<iso>` with its `attributed_age=` — the D4 audit line: a named run that had no activation in that window is the finding this list exists to expose), and ONE audit line per `config-change key=caps` record that coincides with an open pass (a pass started before the change and not yet ended). Peer starts WITHOUT the three keys (a v32.5-started run, a standalone pass) are reported as `unkeyed` activations — a named gap, never folded into a pass. **Launcher coverage (v34.1)** — one line in this block: `launcher coverage: <k> of <n> keyed codex peer starts`. A keyed codex peer start is a `ROLE: start … role=peer backend=codex` carrying all three pass keys; it counts as launcher-written (`<k>`) when it carries `via=launcher`, and the others are listed by `leg=` as hand-written starts. The count ALWAYS comes from the run's records and is never suppressed: a later rewrite of the plan's `Loop config:` line cannot remove a recorded start from it (that line holds only the latest values). Unkeyed starts are not in `<n>` — the `unkeyed` line already reports them, and the standalone route that writes them is legitimate. Context note, added when it applies: if the `Loop config:` line, or ANY `OWNERSHIP: config-change` record of the run, shows `peer-seat=executor` or an `isolation=` other than `worktree`, the line ends `(hand route expected where peer-seat=executor or no run worktree applied)`. `/retro` does not assign each start to a configuration interval: the note says why some hand-written starts may be expected, and the list by `leg=` lets the reader judge. A run with no marked start at all reads `0 of <n> — the run did not use the launcher`, with no defect implied for a run on a workflow older than v34.1. It is a count in a report and refuses nothing; the mark is a free key anyone holding the `emit` grant can write, so the line shows use, not proof.
- **Delegation outcomes** — decisions taken (unit + delegate), diff-vs-spec results, misses and how they were handled, smoke results, and the logged ROI observations. Name the run's delegation posture (v43.0) from the `Loop config:` line's `delegation=` key — absent or malformed → `conservative`, the fail-closed reading every consumer shares — labelled the LATEST configured value (the `Loop config:` rule below); a `config-change key=delegation` record in the run's probe log is the history (`<old> → <new>` at the record's timestamp), so the report never presents one posture as every activation's; a pre-v43.0 line (no key) reads `conservative` and says the key was unrecorded.
- **Gate pauses** — every MUST-PAUSE surfaced to the user, every AUTO-DISPOSABLE candidate auto-applied and logged, and the dispositions taken.
- **Calibration readout** — map the round story onto the existing Round Classification guidance: mostly fix-induced findings → the executor model is the problem (escalate); mostly same-family siblings → reviews are missing pattern siblings (strengthen the next review); mostly pre-existing LOWs → the natural tail (triage and ship). Say which of these the run's evidence supports. On runs with plan-peer rounds, also trend the round summaries' materiality counts across rounds — gauging label inflation by the reclassification rate (the peer's preserved original label vs the owning session's verified label on each finding), not by the raw `record-only` / `invalid` share, which legitimately rises as a healthy loop converges.
- **Evidence gaps** — what the report could not determine and why (no `ROLE:` lines, usage not exposed, missing tee logs), so the reader knows the confidence level.

## Step 3 — Write the report

Write the report to **`<resolved logs dir>/retro-<runkey>-<YYYY-MM-DD>.md`** — default `.cursor/loops/` (gitignored, transient); an explicit logs-dir override redirects the report there, so a sandboxed run never dirties the invoking repo or the corpus source. Under a group scope (Step 0) `<runkey>` is the group's last stage, `stage-<N>`, so each group of a multi-group run writes its own file. A same-day rerun overwrites the file; a new date writes a new file.

Use these stable top-level headings, in this order — `/document`'s lessons distillation and other consumers grep them:

1. `Run identity` — run key, plan, date range, phases/tasks covered (under a group scope: the group's stages, named as the selection — the reuse test `/close-run` Step 4 reads), backends/models involved.
2. `Rounds and findings` — the per-round story with skew classes.
3. `Per-role usage` — the identity/usage table, inferences marked, cost last-per-session (v42.0 — a resumed session's `total_cost_usd` taken once, never summed over its resumes).
4. `Composer-seat cost proxies` — the proxy-count block per Step 2's corpus + metric-dictionary contract: one run-level roll-up with per-phase sub-lines, BOTH disclosed source lists, PARTIAL labeling wherever membership fails down, the (v33.4) `suppressed non-limit rate-limit wakes` row on its own line beside — never summed with — the journal-emissions line (Σ `rl_suppressed=` per phase and run-level, unmeasured legs named "not measured", never 0), pool deltas as context only, and the evidence-gap statement (chat turns, STICKY re-read volume, the chat-only `PROGRESS` lines, the Claude Code Layer-2 wakes the mirror filter does not cover) — followed by the two v33.0 D14 sub-blocks: `Per-peer-model` (one sub-block per peer model per Step 2) and `Per-pass` (rounds/raises/verdicts per `pass=`, the `attributed=` escape audit list, the `config-change key=caps` audit lines; unkeyed peer starts named as a gap).
5. `Delegation` — decisions, outcomes, misses, ROI (or "no delegation in this run").
6. `Gate pauses` — pauses and dispositions (or "none fired") — from v33.0 each surfaced gate's recorded `rec=` where present (the OPTIONAL executor/composer recommendation the ask led with; absent = `not recorded`) beside the operator's `choice=`, so follow-rate is readable per gate.
7. `Calibration` — the readout against Round Classification guidance.
8. `Evidence gaps` — what could not be determined and why.
