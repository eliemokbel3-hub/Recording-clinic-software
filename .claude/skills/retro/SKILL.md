This is a shared Cursor/Codex/Claude Code Skill. Invoke it as `/retro` in Cursor or Claude Code, or `$retro` in Codex.

When this Skill references another shared workflow, use the current tool's sigil: `/workflow` in Cursor, `$workflow` in Codex, and `/workflow` in Claude Code.

`/retro` is a focused, propose-only diagnostics pass: after a loop run (`/execute-loop`, `/peer-loop`, `/review-loop`, or any run that left logs in `.cursor/loops/`), it reads the run's loop logs and the governing plan's review data and writes a structured run report answering "what happened, what did it cost, what failed and why". The report is the deliverable — `/retro` NEVER edits code or skills, never applies fixes, and never appends `Review Findings Log` rounds (findings rounds are `/review`-family artifacts with round-numbering semantics that `/fix` ingests; a retro report is synthesis, not findings). Its only writes are the report file and a single pointer line in the plan's `Current State / Handoff Note`.

This workflow is propose-only and agent-invocable: it carries `disable-model-invocation: false` (Cursor + Claude Code) and NO `agents/openai.yaml` (Codex), so an agent may invoke it automatically — for example right after a loop run converges — and you can still invoke it explicitly. Because its only writes are the gitignored report and the one pointer line, agent invocation cannot mutate code, skills, or docs.

Plan files are shared across all three tools. Handoff is through disk state, the plan file, and git, not conversation memory.

## Step 0 — Locate the run and the plan

Resolve these inputs before reading anything else. Explicit user-supplied overrides — a logs directory, a plan path, a run key, an ordered phase-log list (the fourth bullet below), or the Composer-seat cost proxies' CONTEXT-half overrides: an ordered auxiliary-context file list and an optional ordered endpoint pair (the fifth bullet below) — ALWAYS win over the defaults below; they are what make sandboxed/dogfood runs possible (point `/retro` at a snapshot directory and a plan copy, and every write confines itself there).

- **Logs directory:** default `.cursor/loops/` in the current repo.
- **Run key:** default = the `stage-<N>` log-file prefix present in the resolved logs directory (e.g. `stage-4` from `stage-4-executor.log`). If several prefixes exist, prefer the most recently modified; if none exist, fall back to the governing plan's feature name.
- **Governing plan:** find the plan in `.cursor/plans/` (excluding `completed/`) that the run built — on ambiguity prefer the most recent `Last plan sync`; if still ambiguous, ask the user which plan governs the run.
- **Ordered phase-log list (optional — the proxy-count corpus override, v32.5):** an explicit ordered list of probe-log files supplied at invocation, feeding ONLY the Composer-seat cost proxies' COUNT corpus on flat runs (Step 2's membership route (ii)). Scope guard: it never replaces the logs-directory / run-key / plan resolution above — those still drive every other input, including Step 1's per-role tee-log context scan — and it never alters ordinary single-run retro selection. Precedence: when supplied, the list IS the count-corpus membership (no discovery); when absent, Step 2's routes (i)/(iii) apply unchanged. Fail-closed validation at resolve time: every entry must be an authoritative-class filename (unsuffixed `stage-<N>-probe.log`) — a rotation-suffixed or out-of-class entry invalidates the list and the derivation falls to route (iii)'s PARTIAL with the gap named; two entries for one phase/`run=` key are the constructible duplicate-membership ambiguity — rule (iv)'s PARTIAL, never a sum. The report's disclosed count-source list preserves this list's order exactly, so corpus membership and order reconstruct from the report alone.
- **Ordered auxiliary-context file list + endpoint pair (both optional — the proxies' CONTEXT-corpus overrides, v32.5):** an explicit ORDERED list of per-role tee-log files for pool/usage CONTEXT only, plus an optional ordered endpoint PAIR (two checkpoint identifiers — file + in-file occurrence position or timestamp — start not after end). Scope guard: CONTEXT half only — these inputs never feed the proxy-count corpus, never replace the logs-directory / run-key / plan resolution above, and never alter Step 1's general tee scan. Precedence: on a FLAT run the supplied list IS the auxiliary membership (no discovery — Step 2's flat-run rule requires it; absent ⇒ every pool/usage context field is a named evidence gap); on an ISOLATED run the iso-root membership applies and a supplied list narrows it. Fail-closed validation, per entry: a path outside the resolved logs root / iso root, a duplicate entry, or an unreadable file turns THAT entry's dependent context fields into named gaps (never the counts, never the whole report); an endpoint pair that does not resolve to two parseable checkpoints in order gaps the delta fields alone. Traversal order (the TOTAL ordering Step 2's first/last rule uses): checkpoints are ordered by the supplied LIST order, then by position within each file — "first" = the first parseable checkpoint of the earliest listed file that has one, "last" = the last parseable checkpoint of the latest listed file that has one. The report's disclosed auxiliary-source list preserves the supplied order exactly and each delta names its endpoint pair, so every context value reconstructs from the report alone.

Degradations, flagged in the report rather than guessed around:
- **No loop logs** (the logs directory is missing, empty, or has no matching files) → produce a **plan-only report** from the plan's `Review History` / `Review Findings Log`, and flag prominently that no log evidence was available.
- **No plan** → produce a conversation-only summary in the chat and make **NO writes at all** (no report file, no pointer).

## Step 1 — Ingest the evidence

From the resolved logs directory:
- parse **`ROLE:` lines** (`start` / `end` pairs, per-round `round` lines, and `handoff` exit sentinels) — the key=value convention defined canonically in `/execute-loop`'s Visibility + run-state section: role, backend, model, timestamps, and any best-effort usage fields (`turns≈` / `tokens≈` / duration). Timestamp trust follows that canonical definition: composer-written `start`/`end` `ts=` values are the run's ordering truth; a role's self-written `ROLE: handoff` `ts=` is ADVISORY — headless sessions emit junk wall-clock (observed live: placeholder midnight timestamps) — so treat it as approximate, never as ordering evidence.
- parse **`DELEGATION:` lines** (`decision` / `outcome` / `roi` / `smoke-addendum` variants) — same key=value family: unit, spec one-liner, delegate backend/model, diff-vs-spec result, misses, smoke results, ROI observations.
- scan the **per-role tee logs** (`<runkey>-<role>*.log`) for hard evidence worth citing: verification failures, gate pauses, filesystem-escape checks, smoke results. (Flat-root caveat: phase runkeys recur across runs in a shared `.cursor/loops/` root, so a same-prefix tee log may belong to a PRIOR run — cite tee evidence with that caution; the Composer-seat cost proxies' auxiliary-context corpus in Step 2 uses its own deterministic membership rule, never this discovery scan.)

From the governing plan:
- parse **`Review History`** lines — the `X CRIT / X HIGH / X MED / X LOW` counts, `skew=`, and `action=` fields, using `/review`'s vocabulary verbatim (`skew` ∈ none / pre-existing / fix-induced / same-family / mixed; `action` ∈ none / escalate / strengthen-siblings / triage-and-ship). Do not invent a parallel taxonomy.
- parse **`Review Findings Log`** rounds — `Source:` (which tool/family produced the round; a `Source:` ending in `plan peer-review` marks a PLAN peer-review round — label it plan-scoped in the round story, never as a code-review round), per-finding severities, `Triage:`, `/fix decision:`, and any scope-expansion or Deferral Confirmation Gate dispositions — and, on plan-peer rounds, the per-finding `Materiality:` labels and the round summary's verified counts (`Materiality: X build-affecting / Y record-only / Z invalid`; the enum is canonical in `/peer-review`'s plan-review mode). A compacted round appears as its digest (header, status, `Source:`, any `Materiality:` summary line, one line per finding) with a `Compacted … → findings-[feature].md` marker line — read the named sidecar for the full blocks; a missing or partial sidecar is an evidence gap to flag (fail closed), never "no findings".

**`ROLE:`-less logs are normal** — every log written before the convention existed has none. Infer role identity from `DELEGATION:` fields (`delegate=`, backend/model values), log filenames (`stage-<N>-<role>*.log`), and plan prose — and mark EVERY inferred identity as *(inferred)* in the report. Never present an inference as a logged fact.

## Step 2 — Synthesize

Build the run story from the evidence:

- **Rounds and findings by skew class** — how many review/peer rounds ran, finding counts per round, and the failure classes: fix-induced regressions vs same-family siblings vs pre-existing surfacing vs genuinely new. Where did the rounds go — which loop (review vs peer), and which model family caught what (same-family vs cross-family catches).
- **Per-role identity and usage** — a table of roles (composer / executor / architect / delegate / peer / advisor) with backend, model, activation count, and whatever usage evidence exists: `turns≈` / `tokens≈` / durations from `ROLE:` end lines or CLI output, timestamps otherwise. Where a backend exposes nothing, state **"not exposed"** — never estimate or fabricate a number. Cost-attribution caveats — apply them explicitly whenever citing cost or usage numbers: per-invocation figures (`total_cost_usd`, token counts printed by a spawned CLI session) are per-spawned-session and are the trustworthy per-run numbers; account-pool percentages (`/usage` headlines, usage-checkpoint lines in the logs) are ACCOUNT-GLOBAL — concurrent runs on other repos/devices share the pool — so cite them as context only, NEVER attributed to a single run; and `total_cost_usd` is API-equivalent pricing, not actual subscription draw — comparable between runs, not a bill.
- **Composer-seat cost proxies (v32.5 — the composer-cost measurement baseline)** — log-derivable counts of the composer seat's recurring work, derived under a MECHANICALLY-resolvable evidence boundary, never guessed from timestamps or feature prose; report-file-only (the closed journal family gains nothing, and `/retro` stays propose-only). **Corpus membership (canonical):** the authoritative filename class is the UNSUFFIXED `stage-<N>-probe.log` — exact class: rotation-suffixed siblings (e.g. `stage-0-probe.log.20260811-1340`) are EXCLUDED on both routes, and other `*probe*` names are outside the class (live log roots carry both shapes, so an unqualified "every probe log" rule double-counts a phase). Membership routes: (i) an ISOLATED run's corpus is every authoritative-class phase log under its iso-scoped root (`.cursor/loops/<iso-id>/`); (ii) a FLAT run (`isolation=none`/`branch` — the shared `.cursor/loops/` root holds unsuffixed phase logs from MULTIPLE runs) requires the EXPLICIT ordered phase-log list defined in Step 0's override contract (the fourth Step 0 bullet — its fail-closed validation, scope guard, and disclosure-order rule bind here); (iii) absent both — flat directory, no explicit list — keep Step 0's default single-resolved-prefix behaviour and label the proxies block PARTIAL, naming the one phase covered, never whole-run totals; (iv) ANY ambiguity — a phase whose only probe log is rotation-suffixed, or duplicate candidate members for one phase (constructible only via an explicit list naming two files for the same phase/`run=` key; an excluded rotation sibling beside a present authoritative file is NOT ambiguity) — fails down to PARTIAL with the gap named, never a sum over an unresolved corpus. **Corpus split:** proxy COUNTS derive from the probe logs ONLY (structured records — per-role tee logs carry quoted-grammar echoes that false-positive line counts); pool/usage CONTEXT may additionally draw from an ENUMERATED per-role tee-log list, disclosed separately with per-claim provenance — under DETERMINISTIC membership (v32.5): on an ISOLATED run, the tee logs under the run's iso-scoped root; on a FLAT run, the ordered auxiliary-context file list defined in Step 0's override contract (the fifth Step 0 bullet — its scope guard, per-entry fail-closed validation, and disclosure rule bind here; same-prefix tee files from prior runs are indistinguishable by name in a shared root, so discovery is never used there) — absent that list, every pool/usage context field is a named evidence gap. Each per-pool DELTA binds to ONE deterministic ordered observation pair: the first and last parseable usage checkpoints under Step 0's TOTAL traversal order (supplied list order, then in-file position) for the covered phases, unless the Step 0 endpoint-pair override supplies them; unresolved membership or endpoints gap that context field ALONE. A context field whose source file is absent becomes that field's named evidence gap — counts unchanged in every case. **Metric dictionary (exact line-start predicates over the count corpus — the PREFIX-FAMILY counters are mutually disjoint, with ONE named exception: *peer rounds* is a SUBSET projection of *role activations*, never an additive category; canonical prefixes are not journal types):** *role activations* = `ROLE: start` line count (peer starts INCLUDED), with unmatched start/end pairs reported as an integrity note beside the count, never silently merged; *WATCH arms* = `WATCH: armed` lines; *monitor returns* = `MONITOR:` lines; *journal emissions* = the colon-terminated journal-family line-starts (CONSUME / CLASSIFY / ADOPT / KILL_DUP / OWNERSHIP / VERIFY_OK / VERIFY_FAIL / SENTINEL_ARMED / SENTINEL_FIRE / SPAWN / IDENTITY / NOTIFY), with the two wrapper-native tee shapes (`EXIT:<code>`, `SPAWN_WRAPPER_START`) reported as their own line, never folded in; *peer rounds* = `ROLE: start` lines with `role=peer` — a PROJECTION of the activation count: report it beside, never sum it with, *role activations* (the SOLE authority — log-derived; disagreement with the plan's `Review History` is noted as context, never reconciled by picking); malformed lines or lines missing required keys are counted as raw line-starts AND flagged as an evidence gap, never silently normalized. **Roll-up:** counts derive per phase (per `run=` key) and roll up into ONE run-level block with per-phase sub-lines and BOTH disclosed source lists (the count corpus; the auxiliary context files) — authoritative-class probe logs are per-phase disjoint append logs, so the roll-up is a sum with no cross-file dedup; any subset-of-run derivation is PARTIAL, labeled with the phases covered. **Pool deltas are CONTEXT ONLY** — cited per-pool, only where probe/checkpoint evidence exists in the run's own logs, under the account-global cost-attribution caveat above (the composer's own pool appears only when its account was probed and teed; absence is a NAMED evidence gap, never an estimate). **Evidence-gap statement (always present):** name what the logs cannot show — chat turn counts and STICKY re-read volume are not log-derivable.
- **Delegation outcomes** — decisions taken (unit + delegate), diff-vs-spec results, misses and how they were handled, smoke results, and the logged ROI observations.
- **Gate pauses** — every MUST-PAUSE surfaced to the user, every AUTO-DISPOSABLE candidate auto-applied and logged, and the dispositions taken.
- **Calibration readout** — map the round story onto the existing Round Classification guidance: mostly fix-induced findings → the executor model is the problem (escalate); mostly same-family siblings → reviews are missing pattern siblings (strengthen the next review); mostly pre-existing LOWs → the natural tail (triage and ship). Say which of these the run's evidence supports. On runs with plan-peer rounds, also trend the round summaries' materiality counts across rounds — gauging label inflation by the reclassification rate (the peer's preserved original label vs the owning session's verified label on each finding), not by the raw `record-only` / `invalid` share, which legitimately rises as a healthy loop converges.
- **Evidence gaps** — what the report could not determine and why (no `ROLE:` lines, usage not exposed, missing tee logs), so the reader knows the confidence level.

## Step 3 — Write the report

Write the report to **`<resolved logs dir>/retro-<runkey>-<YYYY-MM-DD>.md`** — default `.cursor/loops/` (gitignored, transient); an explicit logs-dir override redirects the report there, so a sandboxed run never dirties the invoking repo or the corpus source. A same-day rerun overwrites the file; a new date writes a new file.

Use these stable top-level headings, in this order — `/document`'s lessons distillation and other consumers grep them:

1. `Run identity` — run key, plan, date range, phases/tasks covered, backends/models involved.
2. `Rounds and findings` — the per-round story with skew classes.
3. `Per-role usage` — the identity/usage table, inferences marked.
4. `Composer-seat cost proxies` — the proxy-count block per Step 2's corpus + metric-dictionary contract: one run-level roll-up with per-phase sub-lines, BOTH disclosed source lists, PARTIAL labeling wherever membership fails down, pool deltas as context only, and the evidence-gap statement (chat turns, STICKY re-read volume).
5. `Delegation` — decisions, outcomes, misses, ROI (or "no delegation in this run").
6. `Gate pauses` — pauses and dispositions (or "none fired").
7. `Calibration` — the readout against Round Classification guidance.
8. `Evidence gaps` — what could not be determined and why.

Then update the RESOLVED plan file's `Current State / Handoff Note` with the single pointer line:

```text
Retro report: <resolved logs dir>/retro-<runkey>-<YYYY-MM-DD>.md (YYYY-MM-DD)
```

Replace any existing `Retro report:` line rather than stacking a second one. If the governing plan's `Lifecycle State` is not Active (e.g. `Completed — Follow-ups Retained`), do not dirty it silently — skip the pointer and say so in the chat summary, or write it only on explicit user confirmation. Exception, named explicitly (v32): a `Paused` plan IS pointer-writable like Active — the pointer is run-record state, not a completion claim, and the report documents the paused run for its eventual resume; everything else about the Paused plan (its state, its `Paused …` fields) stays untouched. This pointer and the report file are the ONLY writes `/retro` makes.

Ephemeral hosts (v32): under `/execute-loop`'s `persist=on` close contract, the COMPOSER copies this report (plus a bounded probe-log tail) into tracked `docs/retros/retro-<runkey>-<YYYY-MM-DD>.md` and commits it on the run branch in the persist-before-close total order — that copy/commit is the loop's duty, not `/retro`'s: this workflow still writes only the gitignored report and the one pointer line.

## Step 4 — Report in chat

Give a short summary: headline counts (rounds, findings by severity, delegations, gate pauses), the calibration readout in one sentence, and the report path. Restate that `/retro` made no code or skill edits — applying anything the report suggests is separate, human-gated work (`/fix`, a plan amendment, or the next stage's planning).
